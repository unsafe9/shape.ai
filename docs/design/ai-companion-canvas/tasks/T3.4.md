# T3.4 Interaction Under Load

> Phase P3 (Good LOD And Infinite Object Performance), Wave F. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions lines 25-27/30-31/34, Explicit Non-Goals lines 81/85-86, P3 intro lines 473-477, T3.4 lines 542-560); upstream `docs/design/ai-companion-canvas/tasks/T3.2.md` (the cache/streaming structures + stats hooks that produce the *load*) and `docs/design/ai-companion-canvas/tasks/T3.3.md` (the heterogeneous fixture profiles `mixed-1k`/`mixed-5k`/`mixed-workspace` that *are* the load); real symbols in `src/client/renderer/{benchmark.ts,engine.ts,scene.ts,fixtures.ts}`, `src/renderer/core/src/{webgpu.rs,stats.rs,model.rs}`, `tests/{performance.test.ts,infinite-canvas-renderer.test.ts}`.
> Depends on: **T3.2** (cache/streaming: the `SpatialGrid`, residency tiers, density tiles, prefetch, eviction counters that determine how heavy a large scene actually is to interact with) and **T3.3** (the deterministic heterogeneous fixtures + `BenchmarkResult` metric set this task drives interaction *against*). T3.4 adds **no new renderer structure, no new fixture family, no LOD policy** — it specifies the test/evaluation harness and the latency contract that proves the T3.1/T3.2/T3.3 machinery stays interactive under load.

## Outcome

A concrete test/evaluation plan that drives every direct-manipulation flow — pan, zoom, select, drag, text-edit overlay, follow-agent, operation trace — through the existing input-batch/camera/overlay seams against the T3.3 heterogeneous fixtures at T3.2 streaming load, measuring per-input latency (not just frame time) so that interaction stays within an approved budget while LOD degrades gracefully, and follow/spectator camera animation never starves editor input.

## Deliverable

### 0. What exists today, and the exact gap

The Deliverable is one bullet — *a test/evaluation plan for pan, zoom, select, drag, text edit overlay, follow agent, and operation trace under large-scene load.* The harness that measures **frame time** already exists; what is missing is a harness that drives **discrete interactions** and measures **per-interaction latency**, plus fixtures wired to T3.2 streaming and a follow-vs-input contention test. Grounding each flow against the repo:

| Interaction flow | Seam in repo (real symbols) | Measurement state | Pointer |
| --- | --- | --- | --- |
| Pan / zoom | `engine.setCamera` / `wheelAtScreen` → `sendInputBatch([{kind:"set-camera"\|"wheel"}])`; scripted sweep `runScriptedPanZoom(engine, frames)` sweeps zoom `0.08→0.80` over `bounds` | **Frame time only** — `BenchmarkResult.p95FrameMs`/`maxFrameMs`/`averageVisibleCards`; no per-input latency | `benchmark.ts:51-117`; `engine.ts:148-161` |
| Select | pointer-down → `inputBatch` → core `apply_input_event` returns `CoreInputBatchResult.patches` containing a `select` patch + `CoreHitResult` | **Untimed** — `processInputResult` emits `selection`; `FrameStats.rustLastHit*` records the hit but nothing times the round trip | `engine.ts:617-654`; `webgpu.rs:1289-1359`; `stats.rs:51-63,116-122` |
| Drag (move card / group) | pointer-down→move→up; core `InputDragState::Group`/card produces `move-card`/`move-group` patches per move event | **Untimed**; correctness tested (`infinite-canvas-renderer.test.ts:985` "routes mouse drag fallback through the Rust input boundary") but not latency | `webgpu.rs:1359-1500` (`apply_input_event`, `InputDragState`) |
| Text-edit overlay | `beginTextEdit(hit)` → `requestOverlay` → `CoreOverlayRequest` → DOM `<textarea>` (`renderer-edit-overlay`); `updateOverlayPosition` re-projects each frame | **Untimed**; mount correctness tested (`infinite-canvas-renderer.test.ts:518-528`); no "overlay stays glued during pan under load" test | `engine.ts:204-209,440-477,664-676`; `scene.ts:42-75` |
| Follow agent | camera animation rides `focusBounds(bounds, {screen, zoom})` → `sendInputBatch([{kind:"focus-bounds"}])`; deferral guard `inputGestureActive`/`deferredScene`/`flushDeferredSceneSoon` already yields scene reloads to active gestures | **No follow loop yet** (P5/T5.3 owns the feature); `focus-bounds` seam + the gesture-deferral guard exist and are tested (`:747-756`, `:798` "defers full Rust scene reloads while a mouse drag is active") | `engine.ts:153-156,500-525` |
| Operation trace | trace events ride the same op stream T2.5 formalizes / P5/T5.4 renders; `FrameStats` already exposes `boundaryCalls`/`rustBoundaryCalls`/`inputBatchSize` per frame | **No trace render yet**; the cost lever (boundary calls / batch size) is already observable | `engine.ts:617-642`; `scene.ts:88-89` |

**The gap T3.4 closes:** the renderer measures *throughput* (`runScriptedPanZoom` → frame-time percentiles) but never *responsiveness of a discrete action*. T3.4 specifies (1) an **interaction-latency harness** that times input→commit→paint for each flow, (2) **load wiring** that runs those flows on T3.3 fixtures under T3.2 streaming/eviction, (3) an explicit **latency budget** keyed to the T3.1 tier the touched object resolves to, and (4) a **follow-vs-input contention** test that proves spectator animation never steals input responsiveness (the Stop-or-ask). Everything is additive over `runScriptedPanZoom`/`BenchmarkResult`/`FrameStats` and the existing input-batch boundary; no production renderer code or schema changes.

Per Locked Decision lines 30-31, all timed work is the **existing** Rust/core input-batch + camera + hit-test + overlay-projection path; the TS harness only scripts events and reads the stats the core already emits. The harness measures the boundary, it does not move logic across it.

### 1. Latency is the metric T3.4 adds (not a new renderer structure)

`BenchmarkResult` is a **steady-state frame-time** report. Interaction quality is a **discrete-event latency** question: when the user presses to select, drags a card, or starts typing, how long until the result is committed and painted. T3.4 defines an additive result type measured per scripted interaction, reusing the same `FrameStats` the engine already returns from every `sendInputBatch`/`renderFrame`:

```ts
// src/client/renderer/benchmark.ts — additive; runScriptedPanZoom + BenchmarkResult unchanged.

export type InteractionKind = "pan" | "zoom" | "select" | "drag" | "text-edit" | "follow";

export type InteractionLatencyResult = {
  kind: InteractionKind;
  samples: number;                 // discrete interactions scripted
  // input -> commit(core inputBatch returns) -> paint(renderFrame returns) round trip, ms
  p50LatencyMs: number;
  p95LatencyMs: number;
  maxLatencyMs: number;
  droppedFrames: number;           // frames whose FrameStats.frameMs exceeded the frame budget during the interaction
  // load context captured from the FrameStats the engine already returns
  totalCards: number;              // FrameStats.totalCards (scene scale under test)
  averageVisibleCards: number;     // FrameStats.visibleCards (post-cull working set)
  memoryBytes: number | null;      // FrameStats.memoryBytes
  // tier distribution at the camera the interaction ran at (T3.1 §6 per-tier counts on WebGpuFrameStats)
  tierCounts: { full: number; compact: number; shapeOnly: number; density: number; minimap: number };
};
```

- **Timing seam = the existing boundary, instrumented by the harness, not the engine.** A scripted interaction wraps the existing call: `performance.now()` before `engine.<flow>()` (which internally calls `sendInputBatch` → `webGpuRenderer.inputBatch` → `renderFrame`), `performance.now()` after the returned `FrameStats` is in hand. The engine path is unmodified; `sendInputBatch` already calls `renderFrame` and returns through `onEvent({type:"stats"})` (`engine.ts:633`), so the harness reads the same `FrameStats` it would in production.
- **Two clocks, one round trip.** *Commit latency* = input event → core `inputBatch` returns the `CoreInputBatchResult` (`stats.rs:116`) (camera/selection/patches/overlay resolved in Rust). *Paint latency* = that commit → `renderFrame` returns its `FrameStats.frameMs`. T3.4 reports the sum (input→paint) as the user-facing number and keeps `frameMs` separately so a slow *commit* (e.g. hit-test over a huge `SpatialGrid` cell) is distinguishable from a slow *paint*.
- **`droppedFrames`** counts frames during the interaction whose `FrameStats.frameMs` exceeded the frame budget (§3) — the "graceful degradation" signal: detail may drop (tier counts shift), but frames must not stall.
- **No new core stat is required for v1.** Everything above derives from `FrameStats` (`scene.ts:77-...`) + the T3.1 per-tier counts already planned on `WebGpuFrameStats`. An *optional* core-side `last_input_apply_us` micro-timer on `input_batch` (`webgpu.rs:1289`) is listed in Open Questions, not required — JS-side `performance.now()` around the boundary is the seed measurement.

### 2. Per-flow test/evaluation plan (the binding seven flows)

Each flow is a scripted sequence over a T3.3 fixture loaded under T3.2 streaming. All run through the **real** engine seams; none invent a new input path. Profiles named below are T3.3's (`mixed-1k`/`mixed-5k`/`mixed-workspace`).

| Flow | Scripted sequence (real seams) | What load stresses it | Pass signal |
| --- | --- | --- | --- |
| **Pan** | extend `runScriptedPanZoom` to drive `set-camera` steps at a fixed pixel velocity across the fixture bounds at several zoom bands; sample latency per step | `SpatialGrid.query` candidate-set size per frame (T3.2 §1); prefetch `merge_scene` churn on reveal (T3.2 §8) | `p95LatencyMs` ≤ pan budget (§3) at every band; `droppedFrames` ≈ 0 on reveal |
| **Zoom** | wheel sweep `0.08→0.80` (the existing sweep) plus discrete zoom steps that cross T3.1 tier thresholds (e.g. `Full→Compact→ShapeOnly→Density`) | per-frame tier re-resolution + cache-level transitions (T3.2 §3); density-tile build on `Cool` entry (T3.2 §7) | tier counts shift monotonically with zoom (degradation, not replacement); `maxLatencyMs` ≤ zoom budget on the tier-crossing frame |
| **Select** | scripted pointer-down at known card/edge/group/nested-group positions across the scene; assert the returned `select` patch + `CoreHitResult.id` match the expected object even at `Density`/`Minimap` tier | hit-test traversal under the `SpatialGrid` at far zoom; identity-stable selection of a tiny far object (T3.1 §4 invariant) | correct `rustLastHitId`/selection at every tier incl. `Minimap`; commit latency ≤ select budget |
| **Drag** | pointer-down→N×pointer-move→up scripted over a card and over a group (`InputDragState::Group`), each move a `move-card`/`move-group` patch + dirty-edge re-route | per-move dirty-range write + edge-route cache invalidation (T3.2 §6) at scale; gesture-deferral guard active | per-move `p95LatencyMs` ≤ drag budget; no full-scene reload mid-drag (`deferredScene` holds, `:798` invariant preserved under load) |
| **Text-edit overlay** | `beginTextEdit(hit)` to mount the `<textarea>`, then script a pan/zoom while editing; assert `updateOverlayPosition` keeps the overlay glued to the card's projected `screenRect` each frame | overlay re-projection cost while the underlying card streams/tiers; one DOM node only (Non-Goal line 81) | overlay screen-rect tracks the card within 1px/frame; mount→first-paint ≤ text-edit budget; exactly one `renderer-edit-overlay` element |
| **Follow agent** | drive `focusBounds(targetBounds, {screen, zoom})` on a timer to simulate a companion jumping between targets (P5/T5.3 seam), **while** scripting concurrent user pointer/drag input | camera-animation steps competing with user input on the same `sendInputBatch` boundary | user input latency under follow ≤ the same flow's budget without follow (the §4 contention contract); follow yields per `inputGestureActive` |
| **Operation trace** | replay a stream of MCP-style patches (`applyPatchBatch`) tagged as agent ops while panning, simulating trace markers updating; measure pan latency with trace load present | patch-apply + (future P5/T5.4) trace-marker render cost added to the frame; `boundaryCalls`/`inputBatchSize` rise | pan `p95LatencyMs` with trace load ≤ pan budget + a bounded trace margin (§3); trace cost is observable via `boundaryCalls` delta |

- **Follow and operation-trace are tested at the seam, not the full feature.** P5/T5.3 (follow) and P5/T5.4 (trace) own the product behavior; T3.4 only proves the **performance envelope** of the seams they will ride — `focus-bounds` camera animation and the patch/op stream — so that when those features land they have a measured headroom. This keeps T3.4 inside P3 (performance) and out of P5 (feature) scope.
- **Drag and text-edit reuse the exact correctness tests' setup.** The drag fallback test (`infinite-canvas-renderer.test.ts:985`) and overlay tests (`:518-528`) already construct the engine + a `inputBatch` spy; T3.4's interaction harness extends that setup with a large fixture and latency timing rather than a new test scaffold.

### 3. Latency budget (keyed to the approved benchmark target and the T3.1 tier)

The P3 Verify (line 477) requires "interaction latency within the approved benchmark target." There is no numeric target yet in the repo, so T3.4 defines **seed budgets** (tunable, like T3.1's thresholds and T3.2's memory budgets) anchored to a 60fps frame budget. Budgets are per-flow because a multi-move drag and a single select have different acceptable costs:

| Flow | Seed latency budget (input→paint p95) | Frame-drop tolerance during flow | Rationale |
| --- | --- | --- | --- |
| Pan | ≤ 16.7 ms/frame (one frame budget) | 0 sustained; ≤1 transient on reveal | pan must feel locked to the pointer; reveal may cost one prefetch frame |
| Zoom | ≤ 33 ms on a tier-crossing frame, ≤ 16.7 ms otherwise | ≤1 on the tier-crossing frame | crossing a tier rebuilds caches/density once; allowed a single heavier frame, not a stall |
| Select | ≤ 50 ms commit (hit-test + select patch) | n/a (single event) | a click feels instant under ~50 ms; covers `SpatialGrid` hit-test at far zoom |
| Drag | ≤ 16.7 ms per move | 0 sustained | drag is continuous pointer tracking; every move is a frame |
| Text-edit overlay | ≤ 50 ms mount→first-paint; ≤ 16.7 ms re-projection/frame while editing | 0 while editing | typing must not stutter; overlay glue is per-frame |
| Follow agent | user-input budgets above must hold **unchanged** while follow animates | as per concurrent flow | follow is the load, not the measured action (§4) |

- **Budgets are seeds, escalated by measurement.** Exactly like T3.1 thresholds and T3.2 memory caps, these constants are tuned against real runs on `mixed-5k`/`mixed-workspace`; the deliverable is the *contract shape* (per-flow p95 ≤ budget, bounded frame drops, degradation-not-stall), with the numbers as the first calibration point. They live in the harness/test, are ephemeral, and touch no schema (Locked Decision line 34).
- **"Graceful degradation" is the named pass condition** (Verify line 552): under load, the **tier distribution** (`tierCounts`) is allowed to shift toward `Density`/`Minimap` (detail drops), but `p95LatencyMs` must stay within budget and `droppedFrames` within tolerance. Degradation that preserves responsiveness passes; a stall that preserves detail fails. This is the operational reading of T3.1's "visual degradation, stable identity."

### 4. Follow-vs-input contention contract (the Stop-or-ask, designed out)

The Stop-or-ask is *"Follow/spectator animation competes with editor input responsiveness."* The repo already has the mechanism that prevents this; T3.4 makes it a **measured invariant** rather than an assumption:

- **Existing guard:** scene reloads already defer to active gestures — `loadScene` stashes into `deferredScene` while `inputGestureActive`, and `flushDeferredSceneSoon` only applies it after the gesture ends (`engine.ts:88-94,500-525`; tested `:798`). Follow animation rides `focus-bounds`/`set-camera` on the **same single-threaded** `sendInputBatch` boundary as user input, so the two are serialized, not racing — there is no second writer to the core.
- **The contention contract T3.4 proves:** with a follow loop animating `focusBounds` on a timer, scripted user pan/drag/select latency must equal (within tolerance) the same flow's latency **without** follow. Concretely the test asserts: (a) when `inputGestureActive` is true, follow camera steps **yield** (no `focus-bounds` applied mid-gesture, mirroring the `deferredScene` rule); (b) user-input `p95LatencyMs` under follow ≤ its no-follow budget (§3); (c) follow never mounts/steals the text-edit overlay while one is active.
- **Priority rule (design, no new mechanism):** user input > follow animation > operation-trace marker updates, all on the one boundary. Follow is a *consumer* of free frames between user inputs; it is throttled to the camera-animation cadence and skipped during gestures. This is the same "ephemeral state never blocks document interaction" split as Locked Decision line 34 (viewport/follow/companion animation are ephemeral; editing is document interaction).
- If a future follow implementation needed its **own** animation thread/RAF that wrote camera state outside `sendInputBatch`, that would re-introduce the race and **trigger** the Stop-or-ask — flagged as the boundary the implementer must not cross.

### 5. Load wiring: how T3.2 and T3.3 feed this harness

T3.4 is the consumer of the two upstream deliverables; the wiring is explicit so the load is real, not synthetic-in-isolation:

- **Scene source = T3.3 fixtures.** The harness loads `createHeterogeneousFixture({ profile })` (`mixed-1k`/`mixed-5k`/`mixed-workspace`, T3.3 §2.1) via `engine.loadScene(snapshot)`, plus the comment/actor-marker sidecars (T3.3 §4) for the operation-trace and follow flows (companion markers / comment overlays are the trace/follow targets). Determinism (fixed `(seed, profile)`) makes latency runs comparable across changes.
- **Streaming = T3.2 paging.** For `mixed-workspace` (10k+), the harness exercises the T3.2 viewport+zoom query path: pan triggers `merge_scene` of the next ring (T3.2 §2/§8), and the latency harness specifically samples the **reveal frame** (first frame after a prefetch ring loads) since that is where streaming stutter would appear. Eviction counters (T3.2 §9) are read alongside latency so a budget breach can be attributed to thrash vs. compute.
- **Stats already cover memory/object/cache.** P3 Verify (line 477) wants "frame time, memory, object count, text/cache stats, and interaction latency." The first four already flow through `BenchmarkResult`/`FrameStats` (`benchmark.ts:4-49`, `scene.ts:77-...`: `memoryBytes`, `totalCards`/`visibleCards`, the full `rustText*Cache*` set) and T3.2's added eviction/density counters; T3.4 supplies the **fifth** — interaction latency — and binds all five into one `InteractionLatencyResult` per flow. That closes the metric set the phase requires.
- **Where the harness lives:** additive in `src/client/renderer/benchmark.ts` (beside `runScriptedPanZoom`) with the interaction scripts as new tests beside `tests/performance.test.ts` / `tests/infinite-canvas-renderer.test.ts`. No new package, no renderer change. (Long-term, if fixtures/bench move to a shared core test-support location for the Metal adapter — T3.3 Open Question — this harness moves with them; out of scope here.)

### 6. What this task deliberately does **not** do

- **No new renderer/core structure.** The `SpatialGrid`, residency tiers, density tiles, edge cache, eviction (T3.2) and the LOD ladder (T3.1) are consumed, not added. T3.4 adds one TS result type + scripted tests.
- **No schema/contract change.** `Scene`/`ScenePatch`/`RenderScenePatch`/`SceneSnapshot`/`SceneQuery` untouched; `BenchmarkResult`/`FrameStats` untouched (the new `InteractionLatencyResult` is additive and reads existing fields).
- **No follow/trace feature build.** Follow (P5/T5.3) and operation-trace rendering (P5/T5.4) are tested only at their performance seam (`focus-bounds` camera animation, the op/patch stream); the product UI is out of P3 scope.
- **No real-input automation.** Interactions are scripted through the engine's input-batch boundary (the same path real pointer events take), not driven by a browser harness; this matches how `runScriptedPanZoom` already scripts camera moves.
- **No new numeric SLA invented as fact.** §3 budgets are seed constants tied to a 60fps frame budget, explicitly tunable against measurement — the contract is the *shape* (per-flow p95 ≤ budget, bounded drops, degrade-don't-stall), not the literal milliseconds.

### 7. End-to-end harness flow

```
T3.3 fixture (mixed-1k|5k|workspace, seeded)  + comment/actor-marker sidecars
   │  engine.loadScene(snapshot)   ;  T3.2 streaming for workspace scale
   ▼
for each InteractionKind:
   script events ─► engine.<flow>()  ──> sendInputBatch ──> core input_batch (commit)
   │   t0=now()                                            │  CoreInputBatchResult
   │                                                       ▼
   │                                          renderFrame ──> FrameStats (paint)
   │   t1=now()                                            (frameMs, tierCounts, memory, cache)
   ▼
InteractionLatencyResult{ p50/p95/maxLatencyMs, droppedFrames, tierCounts, memory } per flow
   │  assert p95 ≤ §3 budget  ;  droppedFrames ≤ tolerance  ;  identity stable at every tier
   ▼
follow contention case: follow loop animates focus-bounds WHILE user input scripted
   │  assert user-input p95 under follow == no-follow p95 (±tol)  ;  follow yields on inputGestureActive
   ▼
report (diagnostics drawer / CI perf gate)
```

The whole harness is additive over named existing symbols: `runScriptedPanZoom`, `BenchmarkResult`, `FrameStats`, `engine.{setCamera,wheelAtScreen,focusBounds,beginTextEdit,applyPatchBatch}`, `sendInputBatch`, core `input_batch`/`CoreInputBatchResult`/`CoreHitResult`, the `inputGestureActive`/`deferredScene` guard, and T3.1's per-tier counts. No parallel harness, no renderer change, no schema change.

| Stop-or-ask condition | Status | Why / decision needed if triggered |
| --- | --- | --- |
| **Follow/spectator animation competes with editor input responsiveness.** | **CLEAR (not triggered)** | §4: follow animation and user input share the **single** `sendInputBatch` boundary and are serialized, not raced — there is no second writer to the core. ## Open questions / risks

- **Per-flow budget numbers are seeds.** §3's millisecond budgets are anchored to a 60fps frame budget and marked tunable; the real approved target (P3 Verify line 477) must be calibrated on `mixed-5k`/`mixed-workspace` runs. The contract shape (per-flow p95 ≤ budget, bounded drops, degrade-don't-stall) is fixed; the constants are the calibration output, like T3.1 thresholds and T3.2 memory caps.
- **JS `performance.now()` granularity vs. an optional core micro-timer.** §1 measures input→paint with JS clocks around the boundary, which conflates commit and paint at sub-millisecond scale. If hit-test-under-huge-`SpatialGrid` latency needs finer attribution, an optional `last_input_apply_us` field on `input_batch`/`CoreInputBatchResult` (`webgpu.rs:1289`, `stats.rs:116`) would isolate the Rust commit cost — additive, deferred until measurement shows commit-vs-paint ambiguity matters.
- **Reveal-frame sampling depends on T3.2 `merge_scene` cadence.** The pan/streaming latency case (§5) samples the first frame after a prefetch ring loads; if T3.2's `merge_scene` vs `load_scene` stale-tile reclamation cadence (T3.2 Open Question) is not pinned, the reveal-frame budget is hard to assert deterministically. The two tunings must be calibrated together.
- **Scripted input vs. real pointer event timing.** Driving interactions through `sendInputBatch` matches the production code path but skips browser event-dispatch/coalescing latency (pointer event batching, `requestAnimationFrame` scheduling). The harness measures core+paint responsiveness, not end-to-end OS-to-pixel; a browser-level pass (deferred, possibly via the web automation harness) would close that last gap if the core-level numbers prove insufficient.
- **Operation-trace flow is a seam stand-in.** §2's trace flow replays patches as a proxy for the not-yet-built P5/T5.4 trace renderer; if the eventual trace render cost dominates (many simultaneous markers/ghost diffs), the trace margin in §3 must be re-measured against the real T5.4 implementation. Flagged so P3 evidence and P5 feature stay aligned.
