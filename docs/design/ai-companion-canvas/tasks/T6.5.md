### 1. Product scope

**In scope (the approved direction).** A local-first, Figma-*like* (not Figma-*equivalent*) infinite-canvas workspace where a user directly manipulates universal primitives — `shape`, `text`, `edge`, `frame`/group, `image_artifact`, `comment_marker`, plus a `Tag` registry — and where semantic surfaces (todo, wiki, ADR/design, server architecture, presentation, investigation map) are **templates that compose those primitives** (T0.1, T4.x). MCP clients read and write the same canvas over the existing tool surface, each gets a companion identity, and their reads/writes are observable as on-canvas activity (P5). The canvas is a *spatial working interface over* SQLite/files/Git/docs/artifacts — it does not replace the filesystem (Explicit Non-Goal).

**Out of scope (held firm by the Non-Goals, and confirmed not crept in by any phase).** Full Figma vector/path/boolean/auto-layout/component-system editing; Shape/project or structured-ADR as a privileged object model; always-full-detail rendering of all data; per-surface separate apps; a Svelte rewrite of canvas behavior; a React compatibility layer or dual shell; realtime remote collaboration (CRDT/Yjs, transport, remote auth, remote cursors, conflict UI); macOS/iOS apps now; moving the `src/` tree in this planning pass.

**Scope integrity check.** No upstream task expands beyond its bullets; each P2–P5 task explicitly states it adds "no new primitive / op / schema field / renderer object" beyond what it owns (T4.1 §8, T4.2–T4.5 relationship lines, T5.2 §3). The one place scope *grows* by necessity is D1's promotion of the **image/texture-quad primitive** — and that is a primitive promotion (universal, shared across templates), not a per-template special case, which is exactly what the Locked Decisions require when "a template needs a primitive that does not exist."

### 4. LOD evidence

**Good LOD = visual degradation with stable object identity** (Locked Decision), realized as a fixed core-owned ladder, not semantic replacement.

- **Policy (T3.1):** a single core function `apparent_px = max(bounds.width, bounds.height) * camera.zoom` selects a `LodTier` per object, per frame, inside the existing `build_draw_list` pass. The ladder `enum LodTier { Full, Compact, ShapeOnly, Density, Minimap }` (`model.rs` seed `SceneStateTokens.compact`) drops detail monotonically (Full ≥220px: full text+badges+handles → Minimap <8px: density tint), with **hysteresis dead-bands** to prevent tier flicker during continuous zoom.
- **Identity invariant (the load-bearing one):** every tier reads `bounds` but never mutates it; no tier substitutes a different rect or id. A card at `Minimap` tier is **still hoverable, selectable, and a valid edit/MCP target** — "far" means quieter, never a different object. LOD input is geometry-only; no business field (`status`/`node_type`/`confidence`) participates, keeping the core business-free (T3.1 §3, T1.1).
- **Streaming + load evidence (T3.2/T3.3/T3.4):** a core-owned spatial index drives a viewport+zoom query at the storage seam; tier-keyed caches (vertex slots, text layout, glyph atlas, edge geometry, density texture) sit behind explicit memory budgets with a prefetch ring — evolving the existing `SceneSnapshot`/`VertexRanges`/`TextLayoutCache`/`WebGpuFrameStats`, not a parallel renderer. T3.3 extends the fixture generator to a heterogeneous `mixed-1k`/`mixed-5k`/`mixed-workspace` mix; T3.4 specifies a per-input latency harness (not just frame time) over the existing input-batch/camera/overlay seams, asserting interaction stays in budget while LOD degrades and follow/spectator animation never starves editor input.

**D2 Approve-if bullet "good LOD keeps object identity stable while making large scenes performant" → satisfied as design + measurement plan** (implementation is P3/T3.x; the zoom→tier wiring lands core-side per T6.3 §2.4, never in Svelte). Note: T3.x is a *planned* implementation, so the evidence is design-and-harness, not yet measured numbers — see §10.

### 6. MCP activity tracker behavior

Observability, not decoration (Locked Decision). Built entirely on **ephemeral** presence/target data + the **document** `events` log, with zero new canonical schema and no remote-collaboration surface (P5).

- **Identity + dock (T5.1):** each connected MCP client gets a stable `McpClientIdentity` from the real transport (`Server.getClientVersion()`/`getClientCapabilities()`/`RequestHandlerExtra.sessionId`) and a dock entry whose state (idle/active/error/disconnected/muted) is ephemeral presence, surfaced over `/api/mcp/clients`. The dock projects the `actor_marker` ephemeral kind (T0.1), never a `Scene` object.
- **Tool→canvas target (T5.2):** every tool call resolves to a `CanvasTarget` (`group`/`node`/`edge`/`selection`/`viewport`/`artifact`/`canvas`) by reusing the T2.5 envelope `targetIds` (writes) or tool args (reads), placed via the existing core `selection_world_rect` → `CoreOverlayRequest` overlay path. Future template ops inherit targets automatically (op-kind-driven, not tool-name-driven). Defined fallbacks for non-spatial/whole-scene/failed calls — never jumps to origin, never flickers.
- **Follow + spectator (T5.3):** click-to-follow / pinned follow / pause / jump-to-target / recent trail / clean handoff, driven only through the existing imperative `focusBounds`/`setCamera` surface; **never writes document state, never touches core camera math, never steals control while the user is editing.**
- **Trace + write preview (T5.4):** a bounded trace derived from the `events` log (writes) + a small ephemeral read-event ring (the 3 read tools that bypass the log), shown as transient pulses + a per-client activity trail; risky writes render a non-committing **ghost preview** on T2.5's `sceneProposalSchema` staged-operation slot. No trace is persisted as document state; no permanent on-canvas decoration layer is added.

Every agent op is answerable — *what did this client read/write/comment/export/propose, and did anything fail* — from local data only. **D2 Approve-if "MCP companion tracker provides useful agent observability instead of decoration" → satisfied.**

### 7. Svelte shell migration

A clean cut, in place, wrapping the already-narrow canvas bridge (T6.2).

- **Verified scope fact:** exactly **10 `.tsx` files** import `react`/`lucide-react` (`main.tsx`, `App.tsx`, 5 `components/*.tsx`, 3 `components/node/*.tsx`); `src/client/renderer/*`, `lib/*`, `src/shared/*`, `src/server/*`, and all of `tests/*` import **zero** React. So this is a shell rewrite + dependency removal, not an engine rewrite.
- **What Svelte owns:** app chrome, panels, inspector, template picker (P4 slot), export drawer, MCP dock (P5 slot), spectator controls (P5 slot), active-text-overlay *host* node, diagnostics host, API/MCP orchestration. Shell state is partitioned into `lib/stores/` along the T6.1 document/ephemeral boundary; the debounced patch-save moves verbatim into a framework-neutral `lib/patchSaver.ts`.
- **What is removed:** `react`/`react-dom`/`@vitejs/plugin-react`/`lucide-react`/`@types/react*`, the 10 `.tsx`, `react()` in **both** `vite.config.ts` and `vitest.config.ts` (T6.4 §5 caught the second one), `"jsx": "react-jsx"`, the `index.html` entry. `lucide-react`→`lucide-svelte`; `svelte-check` added.
- **Bridge:** `RendererCanvasHost.tsx` logic extracts into a framework-neutral `lib/canvasHost.ts` exposing the existing `RendererCanvasHostHandle` commands + `EngineEvent` events verbatim (load scene / apply op batch / input batch / overlay requests / diagnostics snapshots / event callbacks). **No engine method, event variant, or batching path is added, removed, or rewritten.**
- **Tests:** zero React-rendering tests exist (suite is `environment: "node"`, React-free) → nothing to migrate; plan is additive (bridge contract tests + orchestration unit tests; optional per-file jsdom-pragma Svelte smoke tests).

Stop-or-asks (React compat layer / dual shell; Svelte rewriting the engine) are both **CLEAR** (T6.2). **D2 Approve-if "Svelte owns the web shell" → satisfied; Non-Goal "no React fallback / dual shell" → honored.**

### 8. Rust canvas boundary

Overwhelmingly a **ratification**, not a port (T6.3 §1): of 12 enumerated canvas responsibilities, **9 are already Rust/core-owned** (camera math, hit testing, selection geometry, group hull, membership visuals, LOD seed, culling, text layout — `screen_to_world`/`hit_scene_at_screen`/`selection_world_rect`/`build_draw_list`/`text.rs`/`SceneStateTokens.compact`), 2 sit correctly on the adapter seam (input batching, patch batching, diagnostics in `engine.ts`), and the residue is small and named:

- **Demote/delete the `scene.ts` JS parity layer** (`applyScenePatch` shadow-apply, `rectsIntersect`/`screenToWorld`/`worldToScreen` geometry dups, `validateScenePatch`, `truncateText`) → leaving only type re-exports; core becomes the single mutation authority (T6.3 §2.2).
- **Fix the camera two-way binding** — remove the `useEffect([camera])` write-back so camera is core-authoritative and the shell holds only a one-way display echo from the `stats` event (T6.3 §2.3, consistent with `5d3dc31`).
- **Relocate canvas clipboard/keyboard out of `App.tsx`** — canvas-scoped copy/paste/delete → adapter ops; business markdown (`formatNodeMarkdown`, keyed off the demoted fields) stays shell (T6.3 §2.5).
- **Promote the feature-gated core types** (`CanvasInputEvent` etc. out of `#[cfg(feature="wgpu-probe")]`) into the default `wasm-pack` build (T6.3 §2.1) — the one Rust change, a `#[cfg]` removal, no logic.

Enforced by **boundary contract tests** (framework-neutral, drive `ShapeCanvasEngine` directly): camera→`input_batch`, selection→`apply_patch_batch` without `load_scene`, a structural test that production `src/client` imports only *types* from `scene.ts`, overlay geometry core-sourced. LOD threshold logic is *forbidden* from Svelte and reserved core-side. **D2 Approve-if "Rust/core owns canvas performance-sensitive behavior" → satisfied; both T6.3 Stop-or-asks (Svelte as performance source of truth / business rules pulled into the renderer) → CLEAR.**

**Recommendation: approve broad implementation**, with two binding gates the reviewer should attach:

1. **Gate image-preview templates on D1 C1** (the image/texture-quad primitive). Authoring/structure for all six templates is unblocked today; presentation/wiki-evidence/architecture-image *previews* must either wait for the substrate or ship the documented captioned-box placeholder. 2. **Treat P3 LOD as the load-bearing performance proof to validate early.** §4 is a sound design + measurement harness, but the zoom→tier wiring and the latency numbers are not yet produced; run T3.4's harness against T3.3 fixtures before declaring large-scene performance, so "good LOD" is measured, not asserted.

If the reviewer prefers a **split**: pull the P6 migration (Svelte swap + Rust boundary, T6.2–T6.4) into a separately-gated track and let P2–P5 product implementation proceed in parallel — the dependency graph and gates for that split already exist (T6.4 §2/§3). No outcome requires a **redirect**.
