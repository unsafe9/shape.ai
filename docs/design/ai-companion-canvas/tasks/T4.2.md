> Real symbols grounded in: `src/shared/schema.ts` (`nodeTypeSchema` value `"task"`, `nodeStatusSchema` `"draft"|"complete"|…`, `sceneGroupSchema`, `sceneNodeSchema` default size `390×390`, `tagSchema`, `exportTypeSchema` `"ai_plan_md"`/`"mermaid"`), `src/shared/renderPatch.ts` (`RenderScenePatch` `create-group`/`create-card`/`create-edge`, `applyRenderPatchToShapeScene`, `commitAppPatch`), `src/shared/renderScene.ts` (`RenderCard.styleKey`, `defaultStyles`, `SceneStyleToken`), `src/server/local.ts` (`taskPlanSections` reads `node.type === "task"` at `local.ts:366`, `boundsForNodes`, `generateLocalExport`), `src/server/storage.ts` (`createGroup`, `nextGroupOffset`), `src/server/mcp.ts` (`patch_scene`, `create_group`, `export_group`, `add_comment`), `src/shared/template.ts` (the new T4.1 file this template is authored against).
> Relationship to upstream: **T4.1 owns the contract; T4.2 owns one concrete `TemplateContract` instance authored against it.** This task introduces no new primitive, op, schema field, renderer object, or persisted template record. It declares the todo/task board as recipe data and proves that the resulting objects are edited identically by a human (canvas tools) and an MCP agent (`patch_scene` / future template tool) through the one shared operation funnel.

## Outcome

Author the **todo/task board** as a single declared `TemplateContract` (T4.1) — frames as board columns, `shape` cards as tasks, status/owner/priority as `meta` + status-color `Tag` chips, dependency `edge`s, and `comment_marker`s — that lowers entirely to existing `create-group`/`create-card`/`create-edge`/`create-tag`/`set-object-tags`/`add-comment` ops, so a task board is created, edited, reordered, and exported by the same operation model whether the actor is a human or an MCP client, with no list database and no template-private renderer.

## Deliverable

The breakdown's T4.2 Deliverable is one bullet with six parts: a **template plan using (1) frames, (2) cards, (3) status labels, (4) dependency edges, (5) owner/priority badges, and (6) comments.** Each is a section below, expressed as a concrete `TemplateContract` (T4.1) over real symbols. §7 maps every editable field to a shared op (the Verify proof: "edited manually and by MCP using the shared operation model"). §8 covers the `ai_plan_md` export tie-in. §9 is the additive delta (none new at the contract layer). Nothing beyond the six parts is added.

### 0. This is a T4.1 instance, not new machinery

Per T4.1, a template is *recipe data* that lowers to the existing create ops and is consumed at apply time, leaving only ordinary `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` rows distinguishable solely by an ordinary `meta.templateKind` value. T4.2 fills in the todo board's recipe; it does not add a `TemplateContract` field, op kind, or renderer. The binding source is the T0.1 recipe row (`T0.1.md:106`):

> Todo / task board | `frame` per column → `shape` cards with status **labels** (tags) + owner/priority **labels**; dependency `edge`s; `comment_marker`s. `meta.templateKind="todo"`.

Everything below is that row turned into a declared `TemplateContract` and a field→op edit map.

### 1. Template metadata (the `TemplateMetadata`, T4.1 §1)

```ts
// Registered TemplateContract instance (authored against src/shared/template.ts; not implemented this pass)
const todoBoardTemplate: TemplateContract = {
  metadata: {
    id: "todo-board",                 // TemplateId; stable registry key
    title: "Todo / Task Board",       // picker label
    description: "Columns of task cards with status, owner, priority, and dependencies.",
    category: "planning",             // T4.1 §1 category enum
    icon: "board",                    // shell asset key (Svelte target); not a RenderObjectKind
    templateKind: "todo"              // the ONLY value landing on objects: meta.templateKind="todo"
  },
  // recipe/layout/exports/tags/promptHints below …
};
```

`templateKind:"todo"` is the only trace on canvas state (an ordinary `meta` string per T0.1 §3 / T2.1 §2); it gates nothing in the renderer or core.

### 2. Frames — board columns (the recipe `frames`, T4.1 §2 → `create-group`)

A board is a root frame containing one child frame per status column. Frames are `RecipeFrame`s lowering to `create-group` (`renderPatch.ts:7`); column nesting uses the T2.4 §10 `parentGroupId` passthrough (`SceneGroup.parentGroupId` already supports nesting). Default columns mirror the demoted `nodeStatusSchema` lifecycle the board is meant to track, but as **plain frame labels**, not the enum:

| `RecipeFrame.localId` | `title` | `meta` | Lowers to |
| --- | --- | --- | --- |
| `f-board` | "Task Board" | `{ templateKind: "todo", semanticType: "board" }` | `create-group` (root) |
| `f-todo` | "To Do" | `{ templateKind: "todo", semanticType: "column", column: "todo" }` | `create-group` (`parentLocalId: "f-board"`) |
| `f-doing` | "In Progress" | `{ … column: "doing" }` | `create-group` (child) |
| `f-done` | "Done" | `{ … column: "done" }` | `create-group` (child) |

Columns are ordinary nested frames: a user adds/renames/removes a column with the same `create-group`/`edit-text{target:"frame"}`/`delete-group` ops as any frame (T2.3/T2.4). Moving a card between columns is a membership change (`set-object-group`, T2.4) — there is no special "column" object. The default 3-column set is recipe data, not a fixed schema (Stop-or-ask: ordering/columns are canvas frames, not a list DB; §0).

### 3. Cards — tasks (the recipe `shapes`, T4.1 §2 → `create-card`)

Each task is a `RecipeShape` lowering to `create-card` (`renderPatch.ts:13`) → `renderCardToSceneNode` → `commitAppPatch`. A task card carries:

```ts
// one RecipeShape per task (T4.1 §2 shape)
{
  localId: "t-1",
  frameLocalId: "f-todo",              // membership = which column (SceneNode.groupId is required)
  title: "Wire up auth",               // SceneNode.title
  summary: "Add OAuth callback route", // SceneNode.summary
  detail: "",                          // SceneNode.detail (long-form, optional)
  styleKey: "task",                    // T4.1 §2 / D1 C3: chosen by template, NOT from a demoted nodeType
  tagLocalIds: ["tg-status-todo"],     // status-color Tag chip (§4) + optional owner/priority chips (§5)
  meta: {
    templateKind: "todo",
    semanticType: "task",              // demoted nodeType "task" → meta (T2.1 §2)
    status: "todo",                    // demoted nodeStatus → meta (T2.4) ; mirrors the column
    owner: "",                         // demoted owner → meta (§5)
    priority: "normal"                 // demoted priority → meta (§5)
  }
}
```

`styleKey:"task"` reuses the existing `defaultStyles` token whose id is the `nodeType` value `"task"` (`renderScene.ts` default tokens) — so today's visual identity for task cards is preserved with **no schema change** (`SceneStyleToken.id` / `RenderCard.styleKey` already accept any free string; T4.1 §2 binding rule). Default card size is the recipe's or the `sceneNodeSchema` `390×390` default (T4.1 §3). This is the same `type:"task"` card that `taskPlanSections` already exports (`local.ts:366`) — see §8.

### 4. Status labels (status as `meta.status` + a status-color `Tag` chip, T2.4)

Status is **not** an enum object property and **not** a semantic-replacement variant. Per T2.4 (`T2.4.md:184`: "`nodeStatus` → `meta.status` and/or a status-color `Tag`"), status appears two ways, both editable by normal ops:

| Status carrier | Real carrier | Set/changed by |
| --- | --- | --- |
| machine status value | `meta.status` on the card (`"todo"|"doing"|"done"|"blocked"`) | rides the `create-card` payload `meta`; later changed by an op carrying updated `meta` |
| visual status chip | a status-color `Tag` from the single registry (`tagSchema`: `name`,`color`) | `set-object-tags` / `create-tag` (T2.4 §7) |
| board position | the card's column frame membership (`SceneNode.groupId`) | `set-object-group` (T2.4) — drag card to another column |

The template seeds the status chips as suggested tags (§6) so dragging a card to "Done" and recoloring its status chip are both ordinary, actor-tracked operations. There is **no** status enum on the object; the LOD rule (T0.1 §6 / T2.4) keeps the chip a *visual* label that simplifies at distance, never a semantic replacement.

### 5. Owner / priority badges (also `meta` + label chips, T2.4)

Owner and priority are **labels**, exactly as the T0.1 row says ("owner/priority **labels**") and T2.4 demotes them — not new fields and not a person/priority object model:

| Badge | Machine value | Visual chip |
| --- | --- | --- |
| owner | `meta.owner` (free string / handle) | optional owner `Tag` chip (color-coded by person) via `set-object-tags` |
| priority | `meta.priority` (`"low"|"normal"|"high"`) | priority-color `Tag` chip via `set-object-tags` |

Both render through the existing T2.4 §6 tag-chip path (`RenderCard.tagIds` → a styled label run drawn by `text.rs`; no new engine, no new primitive). A user or agent changes an owner/priority by changing `meta` and/or swapping the chip tag — both are normal ops (§7). This keeps owner/priority inside the single `Tag` registry and the `meta` bag; no template-private taxonomy (honors T2.4's Stop-or-ask).

### 6. Dependency edges + comments (the recipe `edges` and comment_markers)

**Dependency edges** are `RecipeEdge`s lowering to `create-edge` (`renderPatch.ts:15`), with the demoted `edgeType` `"depends_on"` carried in `meta.semanticType` and `styleKey` chosen by the template (T4.1 §2, not the `edgeType` enum):

```ts
{ localId: "e-1", frameLocalId: "f-board", sourceLocalId: "t-2", targetLocalId: "t-1",
  label: "blocks", styleKey: "depends_on", meta: { semanticType: "depends_on" } }
```

`commitAppPatch` already validates that both endpoints exist before accepting a `create-edge`; deleting a task cascades incident-edge removal exactly as today (`applyRenderPatchToShapeScene` `delete-card` path computes `incidentEdgeIds`). So task dependencies are ordinary canvas edges, drawn/edited by `create-edge`/`delete-edge`/`edit-text{target:"edge"}`.

**Comments** are `comment_marker`s — `SceneComment` targeting the card/column/board (`SceneSelection` already covers `node`/`group`/`canvas`). The template recipe may seed none by default; at edit time a comment is added through the **promoted `add-comment` op** (T2.5 §6 turns `addShapeSceneComment` into `{ kind:"add-comment"; target; body; author? }`), which is the same path the `add_comment` MCP tool drives (`mcp.ts`). So a comment on a task is an actor-tracked operation like any other edit.

### 7. The Verify proof — same operation model for human and MCP edits

The breakdown's single Verify bullet is "Tasks can be edited manually and by MCP operations using the shared operation model." Every editable aspect of a task board maps to one shared op, and **both** the human (canvas gesture → core → op) and the MCP client (`patch_scene` / a future template tool → op) funnel through the same `applyRenderPatchToShapeScene` → `commitAppPatch`, wrapped once in a T2.5 `OperationEnvelope` (`actorType:"human"` for the shell, `"mcp"` for an agent, with `sourceToolCall` set by `mcp.ts`):

| Task-board edit | Shared op (real symbol) | Human path | MCP path |
| --- | --- | --- | --- |
| create task card | `create-card` | create-shape tool (T2.2) | `patch_scene` `{ nodes:[…] }` → op, or future template tool |
| rename / edit task text | `edit-text{target:"card",field}` (`edit-card-text` alias) | text overlay (T2.3) | `patch_scene` edit |
| move task / reorder in column | `move-card` (`move-card`) | drag (T2.2) | `patch_scene` `translate`/position |
| change column (status move) | `set-object-group` (T2.4) | drag card into column frame | `patch_scene` membership change |
| change `meta.status`/`owner`/`priority` | the create/edit op carrying updated `meta` (T2.1 §2) | inspector edit | `patch_scene` with `meta` |
| status/owner/priority chip | `set-object-tags` / `create-tag` (T2.4 §7) | tag UI | `update_group_tags`-style / `patch_scene` tag op |
| dependency edge add/remove | `create-edge` / `delete-edge` | edge tool (T2.2) | `patch_scene` `{ edges:[…] }` / `removeEdgeIds` |
| comment on a task | `add-comment` (T2.5 §6) | comment tool | `add_comment` MCP tool |
| delete task (cascade edges) | `delete-card` | delete (T2.2) | `patch_scene` `removeNodeIds` |
| apply the whole template | `batch` of the above in one `OperationEnvelope` (T4.1 §7) | picker | future template `create_group(templateId:"todo-board")` |

Because the recipe lowers to exactly these ops (T4.1 §7), the board the picker creates and the board an MCP agent builds with `patch_scene` are byte-identical `Scene` rows, and every later edit is one logged operation with `targetIds`. No edit reaches canonical state through an untracked blob overwrite (the T2.5 / breakdown anti-blob guarantee). **This is the Verify bullet, MET in full.**

### 8. `ai_plan_md` export tie-in (the `TemplateExports`, T4.1 §4)

The board advertises the export presets that already read task content — **no new export engine** (T4.1 §4):

```ts
exports: {
  allowed: ["ai_plan_md", "mermaid"],   // subset of exportTypeSchema
  default: "ai_plan_md"
}
```

`ai_plan_md` is generated by `taskPlanSections` (`local.ts:365`), which already filters `graph.nodes.filter((node) => node.type === "task")` and lists each as `${i}. ${task.title}: ${task.summary}`. Because §3 cards keep `type:"task"` (carried as `styleKey`/`meta.semanticType` after the T2.1 demotion; the export reads the same field), the existing exporter produces a task plan from a todo-board frame with no change. `mermaid` (`makeMermaid` via `sceneGraphForGroup`, `graph.ts`) renders the dependency edges as a graph. Both flow through the unchanged `generateLocalExport` / `export_group` (`mcp.ts`) path; `allowed` is a shell/`export_group` constraint surfaced by the export drawer (T4.1 §4).

> Compatibility note: `taskPlanSections` currently keys on `node.type === "task"`. After the T2.1/T6.1 demotion moves `nodeType` into `meta.semanticType`, the exporter reads `meta.semanticType === "task"` instead — owned by the T2.1/T6.1 migration, not T4.2; flagged in Open questions so the dependency is explicit.

### 9. Placement and additive delta (per T4.1 §8)

| Concern | Home |
| --- | --- |
| the `todoBoardTemplate` `TemplateContract` instance (data) | **shared contract** (`src/shared/template.ts` registry; authored against T4.1) — pure data; no GPU work |
| lowering the recipe to ops, running them | **T4.1's `lowerTemplateToOps` + the existing op funnel**; T4.2 adds none of it |
| geometry/hull/hit/selection of the produced cards/frames/edges | **Rust/core** (already owns it; templates emit ops, touch no core directly) |
| picker entry, export-drawer `allowed` filter, prompt-hint surfacing | **shell** (Svelte target) |
| MCP template application | **server/MCP** (`mcp.ts`), reusing `create_group`/`patch_scene` apply paths |

Net additive delta at the T4.2 level: **one registered `TemplateContract` value** (todo board) added to the registry T4.1 introduces. **No** `schema.ts` change (status/owner/priority ride the additive `meta` bag; `meta.templateKind="todo"` rides it too — no `ALTER TABLE`). **No** `renderPatch.ts` op added (every recipe element and every edit lowers to ops that already exist or are owned by T2.4/T2.5). **No** new exporter (`ai_plan_md`/`mermaid` already read task/edge content). **No** list database (Stop-or-ask cleared, §0). This mirrors the T4.1/T2.1 "evolve, don't replace" discipline exactly.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Todo ordering requires a separate list database instead of canvas operations. | **CLEAR (not triggered)** | Ordering is pure canvas state: a task's column is its frame membership (`SceneNode.groupId`), changed by `set-object-group` (T2.4); within-column order is `position`/`zIndex`, changed by `move-card`/`set-card-z-index` (existing ops). Columns are nested frames (`SceneGroup.parentGroupId`), added/removed by `create-group`/`delete-group`. Every ordering change is an op through `commitAppPatch` (§7), persisted in the existing `Scene` rows — no list table, no parallel order index, no sort database. If a future need (e.g. a saved "manual sort order" distinct from geometry, or cross-board task indexing) demanded an ordered list store outside canvas geometry, *that* would trip this condition and need a decision; the todo/task-board scope here does not — board order is the cards' spatial arrangement, which is canonical canvas document state already. |

## Open questions / risks

- **`ai_plan_md` reads `node.type === "task"` (export ↔ demotion coupling).** `taskPlanSections` (`local.ts:366`) filters on the literal `nodeType` value `"task"`. After the T2.1/T6.1 `nodeType→meta.semanticType` demotion lands, this filter must read `meta.semanticType === "task"` (or the template's `styleKey`). The fix is owned by the T2.1/T6.1 migration, not T4.2; flagged so the export-correctness dependency is explicit, not silently assumed. Until then, a todo-board card whose `meta` keeps a `"task"` semantic still exports correctly because the demotion preserves the value.
- **Per-template `meta` validation (D1 C4 / T4.1 Open question).** The todo board defines a `meta` namespace (`status ∈ {todo,doing,done,blocked}`, `priority ∈ {low,normal,high}`, `owner`, `column`). T4.1 recommends each `TemplateContract` may carry an optional Zod schema for its `meta`, validated at authoring/apply time only (never gating renderer/core). T4.2 should ship that small todo-`meta` Zod schema with the contract; it is named here as this template's concrete instance of the T4.1 recommendation.
- **Status chip vs column as dual source of truth.** §3/§4 carry status both as `meta.status` and as column membership (and a status-color chip). These can drift (card in "Done" column with `meta.status:"todo"`). Recommendation: treat column membership as the canonical status and derive/sync `meta.status` + chip on `set-object-group`, OR document `meta.status` as advisory metadata only. This is a small consistency rule to settle when the todo template's apply/edit code is authored (not a contract change); flagged so the single-source-of-truth choice is deliberate.
- **Owner/priority chip proliferation in the shared `Tag` registry.** Per-person owner chips and priority chips all live in the one `Tag` registry (T2.4). At scale this registry could accumulate many owner tags. This is consistent with the "single registry, no private taxonomy" decision and is not a T4.2 problem to solve; noted only so registry growth is an expected, accepted consequence, not a surprise.
