# T3.3 Benchmark Fixtures For Heterogeneous Work Objects

> Phase P3 (Good LOD And Infinite Object Performance), Wave E. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P3 intro, T3.3); upstream `docs/design/ai-companion-canvas/tasks/T2.1.md` (primitive vocabulary + the six persisted kinds and ephemeral `actor_marker`) and `docs/design/ai-companion-canvas/tasks/T3.1.md` (LOD tier ladder, per-tier `WebGpuFrameStats` counts); real symbols in `src/client/renderer/{fixtures.ts,benchmark.ts,scene.ts,adapter.ts}`, `src/shared/renderScene.ts`, `tests/{performance.test.ts,infinite-canvas-renderer.test.ts}`.
> Depends on: T2.1 (defines the primitive vocabulary the fixtures must cover) and T3.1 (defines the LOD tiers the heterogeneous mix must exercise). This task extends benchmark *coverage*; it does not change the renderer, the schema, or the LOD policy.

## Outcome

Extend the deterministic fixture generator from a single homogeneous decision-graph card/edge grid into a **composable heterogeneous-workspace generator** that emits the full T2.1 primitive mix (notes, shapes, edges, frames, todos, wiki cards, slide frames, architecture diagrams, comments, artifacts, active agent markers) at the existing 1k+ scale and beyond — so P3 performance evidence reflects real mixed workspaces, not one synthetic node grid.

## Deliverable

The breakdown's T3.3 Deliverable is one bullet: a *fixture plan* for the mixed object families. §1 grounds the exact gap; §2 is the binding fixture-mix plan (the named profiles + the per-family composition table); §3 sketches the additive generator API over real symbols; §4 covers the comment/artifact/actor-marker families that live outside `SceneSnapshot`; §5 ties the mix to the T3.1 LOD tiers and benchmark scale; §6 states the anti-synthetic guardrails the Stop-or-ask demands.

### 1. What exists today, and the exact gap

The benchmark harness is already built; only the fixture *content* is engineering-homogeneous.

| Capability | State in repo | Pointer |
| --- | --- | --- |
| Deterministic, seeded fixture generator | **Exists** — `createBenchmarkFixture(options)` with `lcg(seed)` PRNG; determinism asserted (`first.cards[42]` deep-equals `second.cards[42]`) | `src/client/renderer/fixtures.ts:12`; `tests/infinite-canvas-renderer.test.ts:27-35` |
| 1k+ card/edge scale | **Exists** — default `cards: 1_200`, `edges: cardCount`; test runs `cards: 1_050, edges: 1_080` | `fixtures.ts:15-16`; test `:28` |
| 10k canonical-`Scene` read fixture | **Exists** — server-side `Scene` (not snapshot) with 10,000 `SceneNode`s for renderer-side culling | `tests/performance.test.ts:13-57` |
| Scripted pan/zoom benchmark over a fixture | **Exists** — `runScriptedPanZoom(engine, frames)` sweeps zoom `0.08→0.80`, returns `BenchmarkResult` (frame time p95/max, visible cards, Rust text/cache/slot stats) | `src/client/renderer/benchmark.ts:51-117` |
| Small mixed-scale fixture | **Exists but homogeneous** — `createSmallFixture()` = same generator, 18 cards | `fixtures.ts:115-117` |
| Heterogeneous object mix | **MISSING** — every card is one of 5 decision-graph `type`s (`decision_point`/`option`/`evidence`/`task`/`tradeoff`); every edge is `supports`/`blocks`; no frames-as-slides, no todo cards, no wiki clusters, no architecture box diagrams, no comment/artifact/actor-marker density | `fixtures.ts:52,71,87` |

**The gap T3.3 closes:** `createBenchmarkFixture` produces a *uniform grid* — fixed `260×156` cards, one columns-per-group layout, decision-graph `type`/`status` only, every group the same size. That is exactly the "engineering node graph" the breakdown wants benchmark coverage to move *beyond*. T3.3 adds heterogeneity in **object family, geometry distribution, text profile, group/frame role, and out-of-snapshot density (comments/artifacts/markers)** while keeping the generator deterministic and at/above the 1k scale. It does **not** touch the renderer, the LOD policy (T3.1), or the schema (T2.1); fixtures are test inputs only.

### 2. Fixture mix plan (binding)

The plan has two parts: **named profiles** (what scale/shape a benchmark run loads) and a **per-family composition table** (how each heterogeneous family is generated from the existing render kinds).

#### 2.1 Named fixture profiles

Profiles are presets over the extended generator (§3). They are the units T3.4 (interaction under load) and T3.2 (cache/streaming) consume. The existing `createBenchmarkFixture()` default and `createSmallFixture()` are **retained unchanged** for back-compat with the 50+ existing test call sites; new profiles are additive.

| Profile | Scale (objects) | Composition intent | Replaces / adds |
| --- | --- | --- | --- |
| `homogeneous-1k` (existing default) | ~1,200 cards / ~1,200 edges, 6 groups | Today's uniform decision-graph grid — kept as the regression baseline | `createBenchmarkFixture()` unchanged |
| `mixed-1k` | ~1,000 objects total across all families | The headline heterogeneous mix at the existing 1k+ scale: notes, shapes, edges, frames, todo cards, wiki cards, slide frames, architecture boxes, plus comment/artifact/marker density | **new** |
| `mixed-5k` | ~5,000 objects | Same family distribution scaled up for far-zoom / `Density`-`Minimap` LOD pressure (T3.1 tiers) | **new** |
| `mixed-workspace` | ~10k+ objects, multi-frame "workspace" | Multiple top-level frames each holding a *different* template region (todo board, wiki cluster, slide deck, arch diagram) so culling and per-region LOD are exercised together; parallels the 10k `tests/performance.test.ts` canonical-`Scene` fixture at snapshot level | **new** |

Each profile is **deterministic per seed** (reuses the existing `lcg(seed)` — same determinism contract as `fixtures.ts:127-133`, asserted the same way as `:27-35`).

#### 2.2 Per-family composition table

Every heterogeneous family composes from the **existing three persisted render kinds** (`RenderGroup`, `RenderCard`, `RenderEdge` in `renderScene.ts:148-181`) plus existing `defaultStyles` keys — no new render type, exactly per T2.1 §6's universality table. The `type`/`styleKey`/`status` strings are *render-opaque* (consumed only for style + a11y text), so the fixture sets them freely to produce visual heterogeneity without any contract change.

| Fixture family | Built from | Geometry profile (vs. today's fixed 260×156) | Text profile | `styleKey` (from `defaultStyles`) |
| --- | --- | --- | --- | --- |
| Plain note | `RenderCard` (box-less look via flat style) | small, varied aspect (e.g. 180–320 wide, 90–260 tall) | short title only, or title + 1-line body; some empty summary | `default` |
| Shape (generic box) | `RenderCard` | square-ish and wide variants | label-only or no text | `default` / `option` |
| Edge / connector | `RenderEdge` | n/a (routes between cards) | mix of labeled and **label-less** edges (exercises the `compact` edge path, `webgpu.rs:2920`) | `default` / `risk` |
| Frame / group region | `RenderGroup` | mixed sizes: tight clusters and large wide frames (drives apparent-size LOD, T3.1 §1) | title + summary, some title-only | reuses group styling |
| Todo card | `RenderCard` | uniform small cards in board columns | title + short body; `status` ∈ `selected`/`viable`/`conditional`/`draft` (status as label) | `task` |
| Wiki card | `RenderCard` | tall cards (long `detail`), clustered, mixed CJK + Latin | **long multiline + Korean + mixed + no-space long tokens** (mirrors T2.3 text gates) | `evidence` |
| Slide frame | `RenderGroup` per slide + title/body `RenderCard`s + optional artifact-ref card | one large frame, sparse children (title `RenderCard`, body `RenderCard`) | large title text, body text | `default` |
| Architecture diagram | `RenderCard` boxes + dense `RenderEdge` connectors with labels | grid of boxes with high edge fan-out | short component names + edge labels (`depends on`/`produces`) | `decision`/`risk` for service-vs-risk tint |
| Image / artifact preview | `RenderCard` carrying an artifact-ref placement | medium fixed preview boxes | caption text | `artifact` |

Two families do **not** ride `SceneSnapshot` (see §4): comment markers and active agent (actor) markers. The fixture plan generates their density as a **sidecar payload** alongside the snapshot, because the production render snapshot deliberately excludes them (`renderScene.ts:242-254` `excludedBusinessFields`).

### 3. Additive generator API (real symbols, design-only)

The change is **purely additive** to `src/client/renderer/fixtures.ts`: keep `createBenchmarkFixture` / `createSmallFixture` exactly as-is, add a `createHeterogeneousFixture(profile)` builder and a small set of family emitters that each return arrays of the existing render types. No existing export changes signature.

```ts
// src/client/renderer/fixtures.ts — additive; existing exports unchanged.

export type FixtureProfile = "mixed-1k" | "mixed-5k" | "mixed-workspace";

export type HeterogeneousFixtureOptions = FixtureOptions & {
  profile?: FixtureProfile;
  // optional per-family weights so T3.2/T3.4 can skew a run toward, e.g., text-heavy wiki cards
  familyWeights?: Partial<Record<FixtureFamily, number>>;
};

export type FixtureFamily =
  | "note" | "shape" | "frame" | "todo" | "wiki"
  | "slide" | "architecture" | "artifactPreview";

// Returns the same SceneSnapshot shape the engine already loads (engine.loadScene),
// plus a sidecar for objects the render snapshot intentionally excludes (§4).
export type HeterogeneousFixture = {
  snapshot: SceneSnapshot;            // groups/cards/edges/styles/selection/metadata
  comments: FixtureCommentMarker[];   // anchored via SceneSelection target, NOT in snapshot
  actorMarkers: FixtureActorMarker[]; // ephemeral companion markers, NOT in snapshot
};

export function createHeterogeneousFixture(
  options: HeterogeneousFixtureOptions = {}
): HeterogeneousFixture;
```

Each family emitter is a pure function of `(random, frame, indexRange)` returning `RenderCard[]` / `RenderEdge[]` / `RenderGroup[]`, reusing the existing `lcg(seed)` PRNG and the existing `defaultStyles`. The composed `snapshot` is **a valid `SceneSnapshot`** (`metadata.source: "fixture"`), so it loads through `engine.loadScene(snapshot)` (`engine.ts:88`) and runs through `runScriptedPanZoom` (`benchmark.ts:51`) with zero harness changes — the existing `BenchmarkResult` fields already cover the heterogeneous mix (text glyph counts, cache hits/misses, slot churn).

Determinism contract (binding, mirrors the existing assertion at `infinite-canvas-renderer.test.ts:27-35`): for a fixed `(seed, profile)`, the emitted `snapshot.cards[i]` / `edges[i]` / `groups[i]` and the sidecar arrays are byte-stable across calls.

### 4. Comment, artifact, and actor-marker families (the out-of-snapshot mix)

The breakdown's mix explicitly lists **comments, artifacts, and active agent markers**, but the production render contract deliberately keeps those out of `SceneSnapshot` (per T2.1 §1 and `excludedBusinessFields()`):

- **Comments** are app-overlay objects anchored via `SceneSelection` (`canvas|group|node|edge`), excluded from the snapshot (`renderScene.ts:243` lists `Scene.comments`). The fixture emits a `FixtureCommentMarker[]` sidecar: `{ id, target: SceneSelection, body, author, resolved }`, with targets distributed across cards/edges/frames so comment-density benchmarks (overlay count under pan) are representable.
- **Artifacts** are referenced *from* a card via an artifact-ref placement (the `image_artifact` family, §2.2) — the previewable card rides the snapshot as a normal `RenderCard` with `styleKey: "artifact"`; the artifact payload itself (path/contentType/exportType) is app-owned and excluded from the snapshot. The fixture sets the preview card; no artifact blob enters the render layer.
- **Active agent (actor) markers** are the **ephemeral** `actor_marker` kind (T2.1 §1: never in persisted `Scene`/`SceneSnapshot`; P5/T5.x owns the model). The fixture emits a `FixtureActorMarker[]` sidecar: `{ clientId, actorType, target: SceneSelection | WorldRect, activityState }`, so T3.4/T5.3 can benchmark follow/spectator marker movement and trail density against a large scene **without** persisting markers as document state. This keeps the document/ephemeral split (Locked Decision) intact even in fixtures.

Modeling these three as a **sidecar** (not snapshot fields) is the correct shape: it (a) does not violate the render contract, (b) lets T3.4 load overlay density independently, and (c) avoids inventing snapshot fields the renderer would have to ignore.

### 5. Tie to LOD tiers and benchmark scale

The mix is designed to *exercise* the T3.1 ladder, not just to look varied:

- **Geometry spread** (§2.2) means a single camera zoom puts different families in different T3.1 tiers simultaneously: small notes hit `ShapeOnly`/`Density` while a large slide frame is still `Compact`/`Full` (T3.1 §1 keys on `apparent_px = max(w,h) * zoom`). A uniform grid cannot produce this distribution.
- **Text profiles** (short note vs. long CJK wiki card) stress the Rust text/glyph caches differently per tier, so the existing `BenchmarkResult` text-cache fields (`rustTextLayoutCacheHits/Misses`, `rustCjkGlyphs`, `rustTextAtlasOverflowGlyphs`) become meaningful across a heterogeneous load instead of one card shape.
- **Per-tier counts** (T3.1 §6 adds `full_tier_count`…`minimap_tier_count` to `WebGpuFrameStats`) become populated across a *real distribution* of object sizes — the heterogeneous fixture is what makes those tier counts non-degenerate.
- **Scale** is preserved and extended: `mixed-1k` matches the existing 1k+ baseline (so the Verify "1k+ card/edge scale plus heterogeneous mixes" holds in one run); `mixed-5k`/`mixed-workspace` push toward the 10k regime the `tests/performance.test.ts` canonical fixture already targets, now at snapshot/render level.

A representative regression test (design intent, mirroring the existing determinism + scale tests):

```ts
it("generates a deterministic heterogeneous 1k+ workspace mix", () => {
  const a = createHeterogeneousFixture({ seed: 21, profile: "mixed-1k" });
  const b = createHeterogeneousFixture({ seed: 21, profile: "mixed-1k" });
  const total = a.snapshot.cards.length + a.snapshot.edges.length + a.snapshot.groups.length;
  expect(total).toBeGreaterThanOrEqual(1_000);
  expect(a.snapshot.cards[100]).toEqual(b.snapshot.cards[100]);   // determinism
  expect(new Set(a.snapshot.cards.map((c) => c.styleKey)).size).toBeGreaterThan(3); // heterogeneity
  expect(a.comments.length).toBeGreaterThan(0);
  expect(a.actorMarkers.length).toBeGreaterThan(0);
});
```

### 6. Anti-synthetic guardrails (the Stop-or-ask, addressed in the design)

The Stop-or-ask is "benchmark data becomes too synthetic to reflect real workspaces." The plan builds in guardrails so the fixtures stay representative:

- **Family distribution mirrors the first template set** (todo board, wiki cluster, slide deck, architecture diagram — the same templates D1 must validate and P4 builds). The fixture is not arbitrary noise; each region is a recognizable workspace shape.
- **Geometry and text come from realistic ranges**, not single constants: mixed aspect ratios, mixed text lengths, CJK + Latin + no-space long tokens (the T2.3 text-quality cases), labeled and label-less edges, sparse and dense frames.
- **Clustering, not uniform grids**: families are placed as spatial clusters (a todo board column, a wiki cluster, a slide stack) so viewport culling and prefetch (T3.2) see realistic locality instead of an even lattice.
- **Comment/artifact/marker density is included** (§4), because real workspaces carry annotation and agent-activity overlays that a pure card grid omits — these are first-class to the mix, not decoration.
- **The homogeneous baseline is retained** so regressions are still comparable; heterogeneity is added *alongside*, never replacing the comparable baseline.

## Open questions / risks

- **Sidecar shape vs. P5 actor model.** The `FixtureActorMarker` sidecar (§4) is a deliberately minimal stand-in so T3.4/T5.3 can benchmark overlay density now; the canonical actor-marker model is owned by P5/T5.1. If T5.1's model diverges in fields, the fixture sidecar follows it — it is a test input, not a contract. Flagged so the two stay aligned.
- **Profile object-count budgets are seeds.** The `~1k / ~5k / ~10k+` targets and the per-family weights are tuning seeds, to be calibrated against T3.4 latency targets and T3.2 memory budgets once measured; like the T3.1 thresholds, they are policy constants, not magic numbers.
- **Determinism under family weighting.** Adding `familyWeights` must keep the per-seed determinism contract (§3). The risk is a weight-dependent branch consuming a different number of PRNG draws and shifting downstream objects; the emitters should consume a fixed PRNG budget per object regardless of family so `seed` alone fixes the output. Flag for the implementer.
- **Where the heterogeneous generator lives long-term.** It is added to `src/client/renderer/fixtures.ts` today (the web adapter), matching the existing fixture home. If a later task promotes fixtures into a shared/core test-support location (e.g. alongside the Rust core for Metal-adapter benchmarks), this generator should move with them — out of scope for T3.3.
