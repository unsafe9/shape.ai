# T0.2 Confirm Package And App Boundaries

> Phase P0 (Product And Package Contract), Wave A. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (T0.2, Repo Layout Planning, Locked Decisions, Done Criteria, P0 intro/review gate, Explicit Non-Goals); sibling fragments `docs/design/ai-companion-canvas/tasks/{T0.1,T1.1,T1.2,T1.3,T1.4}.md` (primitive/business seam, platform-neutral core, web adapter, Metal adapter, app-shell boundaries); real repo `src/{client,client/renderer,renderer/core,server,shared}`, `package.json`, `vite.config.ts`, `tsconfig.json`, `tsconfig.server.json`, `src/renderer/core/Cargo.toml`, `scripts/renderer-toolchain.sh`.

## Outcome

Confirm the future repo boundary by reading it out of the **current `src` structure** rather than from an aspirational layout, and lock the decision that the target layout is to **KEEP `src/` and reorganize ownership in place**. The five existing `src` areas already carry, one-to-one, the boundaries P1 specifies (platform-neutral core, web adapter, app shell, server/MCP, shared contracts); the native/Metal adapter and macOS shell are *contracts only* with no directory yet. Keep-in-place is the lowest-churn option, honors the Locked Decision that existing `src/` stays until a move is justified, and still supports a future iOS app via shared core plus a native adapter without putting product business logic in the renderer.

## Deliverable

Build wiring that already crosses these areas (evidence that the boundaries are load-bearing, not nominal):

- `package.json#renderer:wasm:build` runs `wasm-pack build src/renderer/core --out-dir ../../client/renderer/wasm` — core → web-adapter is an explicit, named pipeline already.
- `package.json#build` = `renderer:wasm:build && vite build && tsc -p tsconfig.server.json` — three boundaries (core, client, server) build through one chain.
- `vite.config.ts` `copyRendererWasm()` copies `src/client/renderer/wasm/*` into `dist/client/assets/wasm` — adapter owns the WASM artifact location.
- `tsconfig.server.json` compiles only `src/server` + `src/shared`; the root `tsconfig.json` (`jsx: react-jsx`) covers `src` + `tests`. Server and client already have distinct TS project scopes sharing `src/shared`.
- `scripts/renderer-toolchain.sh` pins a repo-local Rust toolchain (`.renderer-toolchains/`) for the core crate, independent of the Node toolchain.
- `tests/` (root, outside `src`) already targets these boundaries separately: `infinite-canvas-renderer.test.ts`/`performance.test.ts` exercise the renderer/adapter, `server.test.ts`/`storage.test.ts` the server, `graph.test.ts`/`export.test.ts`/`clipboard.test.ts` the shared/shell logic — so a layout move would also touch test import paths, reinforcing why churn must be justified.

Document-vs-ephemeral ownership across the areas (per the Locked Decision split, consistent with T0.1 §3 / T1.1 §4) confirms the boundaries are clean: **document state** (canonical, persisted, op-tracked) lives in `src/shared` (schema) and `src/server` (system of record); **ephemeral state** (camera/viewport, hover, active tool, follow mode, companion animation, render caches) lives in the core and adapter as transient state, never persisted. `src/client` (shell) holds product/app + ephemeral UI state and routes both through the narrow bridge. No area owns both a canonical write path and a render cache, which is what lets each map to one boundary.

### 2. Boundary note — breakdown boundaries mapped to current paths

The breakdown's P0/P1 boundary list maps onto current paths with no gaps for shipping concerns and two explicit *future* (contract-only) slots:

| Boundary (breakdown / P1) | Current path | Status |
| --- | --- | --- |
| Platform-neutral canvas core | `src/renderer/core/` (Rust crate `shape_canvas_core`) | Exists. Owns T1.1 contract surface. |
| Web canvas adapter | `src/client/renderer/` | Exists. Owns T1.2 contract surface. |
| Native / Metal adapter | **— (no directory yet)** | **Contract only (T1.3).** Future sibling of the web adapter over the same core; no dir is created until a native target is actually scaffolded (deferred per breakdown). |
| Web product shell | `src/client/` | Exists (React). Svelte is the production target (T1.4/T6.2); React is migration input. |
| Future macOS shell | **— (no directory yet)** | **Contract only (T1.4).** SwiftUI/native shell over the Metal adapter; no dir until macOS is scaffolded (deferred). |
| Server / API / MCP | `src/server/` | Exists. System of record + MCP. |
| Shared contracts | `src/shared/` | Exists. Canonical schema + render/op seams. |

Boundary integrity rules confirmed against the sibling fragments:

- The **core** (`src/renderer/core`) holds only the "Canvas scene" half of the 책임 경계 (T1.1 §1, §4): id/bounds/z-order/style/text/hit/selection/camera. Business meaning of `nodeType`/`status`/`confidence`, MCP/export/proposal stay out of the crate. The crate stays directory-agnostic in its own contract (T1.1 §3) — this task fixes that its *current home* is `src/renderer/core` and that home does not move.
- The **web adapter** (`src/client/renderer`) is the browser host and serialization boundary; it owns no product templates and no canonical persistence (T1.2 §8). The one boundary correction T1.2 names (canvas-scoped clipboard/keyboard leaking from `App.tsx`) is a shell-vs-adapter *ownership* fix, not a directory move, and is owned by T6.2/T6.3.
- The **shell** (`src/client`) never draws a frame and never owns scene geometry/LOD/hit/cache as a source of truth (T1.4 §3, invariants). Persistence stays in `src/server` + `src/client/lib/api.ts`.
- The **server** (`src/server`) is the system of record: `storage.ts#commitAppPatch` owns canonical writes, `sceneVersion`, and cascade rules; `mcp.ts` is the only agent write path. No adapter or core file calls HTTP or touches SQLite.
- The **shared contracts** (`src/shared`) are the one area every other boundary depends on and the only cross-cutting import target; `schema.ts` is the canonical document model and `renderScene.ts`/`renderPatch.ts` are the render/op seams the Rust core mirrors. It stays the single shared dependency root in every layout option.
- The **Metal adapter and macOS shell are sibling slots**, not new models: T1.3 §7 shows Metal as a sibling of the web adapter over a shared portable `SceneRenderer`; T1.4 §1 shows a macOS shell re-implementing the same shell rows against the Metal adapter and the same server/op contracts. Neither needs a directory at this stage.

Boundary invariants (binding for downstream layout tasks T0.3/T6.4):

1. **Each `src` area maps to exactly one boundary.** No area is split or merged in this pass; ownership is sharpened by contract, not by relocation.
2. **Additive, never relocating, for new platforms.** A second platform (macOS/iOS) adds a Metal-adapter directory and a native-shell directory; it never moves `src/renderer/core`, `src/client/renderer`, `src/client`, `src/server`, or `src/shared`.
3. **`src/shared` is the only shared dependency root.** New adapters/shells depend on it and on the core; they do not depend on the web shell or each other.
4. **Future paths stay out of build config until their migration task owns them.** No `vite.config.ts`/`tsconfig*`/`package.json`/toolchain reference points at a not-yet-created directory.

### 3. Target-layout options with tradeoffs

The breakdown's Repo Layout Planning lists candidate conclusions. Three are real options here; the rest (e.g. "move only the web shell at Svelte time") are special cases of (b)/(c) and deferred to their migration tasks (T6.x).

#### (a) KEEP `src/`, reorganize ownership in place — **CHOSEN**

Keep the five `src` areas where they are. Sharpen *ownership* (the document/ephemeral split, the demote/keep lists, the adapter-vs-shell clipboard line, the core-vs-shell performance line) via the P1 contracts, without moving any directory.

- **Pros.** Zero build/import/test churn now: `wasm-pack --out-dir`, the `vite build`/`tsc -p tsconfig.server.json` chain, `vite.config.ts` `copyRendererWasm`, `tsconfig.server.json` include globs, and `scripts/renderer-toolchain.sh` paths all keep working untouched. No path rewrites across `src/client`, `src/server`, `tests/*`. Honors the Locked Decision "현재 production code를 바로 새 top-level layout으로 이동하지 않는다" and "기존 `src/` production app을 이 planning pass에서 이동하지 않는다." The boundaries the breakdown wants already exist as real directories with a real build pipeline between them — the work is naming ownership, not relocating files.
- **Cons.** `src/renderer/core` (Rust) and `src/client/renderer` (web adapter) are not yet *visually* promoted to a canonical "engine + adapters" cluster — they read as client-subordinate. The core/web-adapter relationship is expressed only by the `wasm-pack --out-dir ../../client/renderer/wasm` build path, not by directory adjacency. This is a readability cost, not a correctness cost, and is exactly what T0.3 may revisit if portability pressure grows.
- **Why it wins now.** Build/import/test churn is not yet justified (breakdown: "어떤 결론이든 build/test/import path churn이 migration risk를 정당화해야 한다"). Nothing about a future iOS app requires moving today's files: iOS is served by the shared **core** (`src/renderer/core`) plus a **new** Metal adapter sibling and a native shell — additive directories, created when iOS is actually scaffolded — with zero business logic in the renderer (T1.3 §8). Keep-in-place therefore satisfies the portability Verify without paying relocation cost.

#### (b) Reorganize within `src` (e.g. `src/canvas/{core,web-adapter}`, `src/app/`, `src/server`, `src/shared`)

Promote `src/renderer/core` + `src/client/renderer` into a canonical engine/adapter cluster (e.g. `src/canvas/`) and pull the shell into `src/app/`, staying under `src`.

- **Pros.** Makes the engine/adapter boundary visible by directory; the Metal adapter would slot in as `src/canvas/metal-adapter` next to the web adapter, matching the P1 mental model.
- **Cons.** Immediate churn with no current payoff: rewrite the `wasm-pack --out-dir`, `copyRendererWasm` source path, every `src/client` import of `src/client/renderer/*`, `tsconfig.server.json` include globs, and many `tests/*` import paths — all before any second platform exists to benefit. Pure restructuring risk against a single-platform codebase.
- **Verdict.** Defer to a P6 migration task (T6.4 sequence) *if and when* a second adapter or the Svelte move makes adjacency worth the churn. Not now.

#### (c) Introduce top-level packages (`apps/`, `canvas/`, `packages/*` workspaces)

Split into a workspaces monorepo: `apps/web`, `apps/macos`, `canvas/core`, `canvas/web-adapter`, `canvas/metal-adapter`, `packages/shared`, `packages/server`.

- **Pros.** Cleanest long-term portability story; per-package build/publish; strongest enforcement of the boundaries.
- **Cons.** Heaviest churn by far: introduces a package manager workspace, multiple `package.json`/`tsconfig` project references, build-script rewrites, and bundler reconfiguration — explicitly the kind of "package manager, bundler, or TypeScript project-reference changes beyond the approved scope" that T0.3's and T6.4's stop-conditions guard against. The breakdown also forbids treating an empty scaffold as architecture ("빈 directory scaffold 자체는 성공 기준이 아니다").
- **Verdict.** Out of scope for P0. Revisit only when web + macOS + iOS shells genuinely coexist and per-package builds pay for themselves.

### 4. Explicit migration rule

**Current `src/` stays exactly where it is until a future, separately-approved move task.** This pass confirms the *keep-in-place* decision and the ownership mapping; it does not move, rename, or scaffold any directory. Specifically:

- No directory is created for the Metal adapter or the macOS shell in this pass. They are contracts (T1.3/T1.4); their physical location is decided when the native target is actually scaffolded (deferred per the breakdown's Deferred list).
- Any later relocation (option (b) or (c), or the Svelte-time shell move) is owned by a P6 migration task (T6.4 sequence) and gated by the P0 review gate (`human-decision`: approve the target layout before code moves) and the T6.4 stop-condition (no repo/package-manager change beyond approved scope).
- No build config (`vite.config.ts`, `tsconfig*.json`, `package.json` scripts, `scripts/renderer-toolchain.sh`) may import or reference a future path before the migration task that owns it (mirrors T0.3's "no build config imports a future path" rule).
- T0.3 (Plan Target Layout Placement) consumes this decision: with keep-in-place chosen, T0.3's migration map is mostly "stays where it is," and it only enumerates the additive future slots (Metal adapter, macOS shell) and any in-place ownership notes.

## Open questions / risks

- **Adjacency vs build-path coupling.** Keep-in-place leaves the core↔web-adapter relationship expressed only by the `wasm-pack --out-dir ../../client/renderer/wasm` path, not by directory adjacency. If a Metal adapter lands before any restructuring, it will sit far from the web adapter in the tree. Flag for T0.3/T6.4 to weigh adjacency (option (b)) against churn at that point — not a P0 decision.
- **Naming mismatch.** `src/renderer/core` is the *core*, while `src/client/renderer` is the *web adapter*; both contain "renderer," which can read as if the adapter is the renderer. This is a documentation/ownership-clarity risk that the P1 contracts already address by name; a rename is deliberately *not* done here (it would be churn). Recorded so a later task does not mistake the names for the boundaries.
- **Svelte-time shell move.** The breakdown lists "Svelte migration 시점에 web shell만 별도 위치로 이동" as a candidate. Whether `src/client` relocates at Svelte time or stays in place is owned by T6.2/T6.4, not decided here; keep-in-place is the default unless that migration justifies a move.
- **The clipboard/keyboard ownership correction (T1.2 §5) is ownership, not layout.** It does not move any directory and is not part of this layout decision; it is recorded so T0.3 does not treat it as a path move.
