# T3.2 Renderer Cache And Streaming Plan

> Phase P3 (Good LOD And Infinite Object Performance), Wave D. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions lines 25-27/31/34, Explicit Non-Goals lines 81/85-86, P3 intro, T3.2); upstream `docs/design/ai-companion-canvas/tasks/T3.1.md` (the LOD tier ladder this plan keys cache levels off); real symbols in `src/server/storage.ts`, `src/server/index.ts`, `src/server/mcp.ts`, `src/shared/{renderScene.ts,graph.ts,schema.ts}`, `src/renderer/core/src/{webgpu.rs,text.rs,stats.rs,model.rs}`, `src/client/components/RendererCanvasHost.tsx`, `src/client/lib/api.ts`.
> Depends on: **T3.1** — T3.1 defined the `LodTier` ladder (`Full`/`Compact`/`ShapeOnly`/`Density`/`Minimap`) selected per-object-per-frame by `apparent_px = max(bounds.w, bounds.h) * camera.zoom`. **T3.2 plans the cache/streaming that *feeds* that ladder**: which data enters the viewport, how it is indexed, cached, prefetched, and budgeted, so the tier a card resolves to is also the cache level it is loaded at. T3.3 builds the fixtures, T3.4 measures interaction under the resulting load.

## Outcome

Plan how an effectively unbounded scene enters the viewport without mounting every object as DOM or loading it at full detail: a core-owned spatial index drives a viewport+zoom-aware query at the storage seam, the renderer keeps tier-keyed caches (vertex slots, text layout, glyph atlas, edge geometry, density texture) behind explicit memory budgets, and a prefetch ring pulls the next-likely region — all evolving the existing `readScene`/`SceneSnapshot`/`VertexRanges`/`TextLayoutCache`/`WebGpuFrameStats` machinery rather than introducing a parallel renderer.

## Deliverable

### 0. What exists today, and the exact gap

The single Deliverable bullet enumerates nine concerns: *spatial index, viewport query, tile/cache levels, text cache, glyph atlas, edge cache, density texture, prefetch radius, memory budget.* Grounding each against the repo before planning:

| Concern | State in repo | Pointer |
| --- | --- | --- |

| Viewport query | **Absent** — `readScene(query)` reads the **full** scene (`readFullSceneInDb`) then filters only by `tagIds` in JS; `/api/scene/render-snapshot` accepts only `parseSceneQuery` (tagIds), no camera/zoom; renderer `load_scene(scene_json)` ingests one **whole** `SceneSnapshot` | `storage.ts:76-94`; `index.ts:120-124`; `webgpu.rs:744` |

**The gap T3.2 closes:** the renderer already *culls* a fully-resident scene and already *caches* text. It does not *stream* (everything is loaded), has no *spatial index* / *tile* structure, no *edge or density* cache, no *prefetch*, and no *eviction/budget*. T3.2 specifies all nine as additive structures layered on the existing seams: the storage→snapshot query, the core `build_draw_list` pass, and the existing caches. Every cache level keys off T3.1's `LodTier`, so detail demand and residency demand are the same axis.

All performance-sensitive structures (spatial index, tile/cache levels, edge cache, density raster, prefetch, eviction) live in **Rust/core**, per Locked Decision line 31. The Svelte/TS shell only issues a viewport+zoom-aware fetch and renders the returned snapshot deltas; it computes no index, tier, or budget (line 30).

### 1. Spatial index (core-owned)

A flat per-frame scan of every slot in `build_draw_list` is `O(total objects)` regardless of zoom; at 100k objects that dominates frame time even though most are culled. Add a **uniform-grid spatial index** over object `bounds` inside core — chosen over an R-tree because the scene is mutated by granular patches (`apply_patch_batch`) where a grid's O(1) cell insert/remove composes with the existing per-id `VertexRanges` slot churn far more cheaply than tree rebalancing, and the canvas is unbounded-but-sparse so cell hashing beats a balanced tree.

```rust
// shape_canvas_core — new core structure beside VertexRanges; pure geometry, no JsValue.
struct SpatialGrid {
    cell_size: f64,                          // world units; seed ~= 2 * default card edge (780)
    cells: HashMap<CellKey, Vec<ObjectRef>>, // CellKey = (i32, i32) from floor(x/cell), floor(y/cell)
}
struct ObjectRef { id: String, kind: RenderObjectKind, bounds: WorldRect } // kind from model.rs
impl SpatialGrid {
    fn insert(&mut self, r: ObjectRef);                 // bounds may span cells -> insert into each covered cell
    fn remove(&mut self, id: &str, bounds: &WorldRect);
    fn query(&self, viewport: &WorldRect) -> impl Iterator<Item = &ObjectRef>; // dedup refs spanning cells
}
```

- **Source of truth stays `SceneSnapshot`.** The grid is a derived acceleration structure, rebuilt on `load_scene` and incrementally maintained on `apply_patch_batch` for the same `dirty_card_ids`/`dirty_edge_ids`/`dirty_group_ids` already collected at `webgpu.rs:828-941`. A `move-card`/`move-group` op removes the old-bounds entry and inserts at new bounds; geometry math the core already owns.
- **`build_draw_list` queries the grid, not the full vector.** `webgpu.rs:1613` changes from iterating `scene.cards/edges/groups` in full to iterating `grid.query(padded_world_viewport)`; the existing `rects_intersect` becomes the fine cull on the grid's coarse candidate set. Slot lookup (`vertex_ranges.cards.get(&id)`) and draw-order sort by `slot.offset` are unchanged, so dirty-range and slot identity are untouched.
- **Index unit = `RenderGroup`/`RenderCard`/`RenderEdge` bounds**, which already exist (`model.rs` `WorldRect`). Edges index by `edge_visible_bounds(source, target)` so an edge whose endpoints are off-screen but whose curve crosses the viewport is still found.

### 2. Viewport + zoom-aware query (the storage/API/MCP seam)

Today the entire scene is shipped to the client and into `load_scene`. Stream instead: the client/MCP requests **a viewport rect + zoom**, the server returns only objects intersecting a padded viewport, at the **detail their tier permits**. This is the one part that must touch storage and is the Stop-or-ask probe.

**Query contract — extend the existing `SceneQuery`, do not replace it:**

```ts
// src/server/storage.ts — SceneQuery already has { tagIds?: string[] }
export type SceneQuery = {
  tagIds?: string[];
  viewport?: { x: number; y: number; width: number; height: number }; // WorldRect; omitted = whole scene (back-compat)
  zoom?: number;        // drives server-side detail trimming (see lod-aware projection below)
  prefetchPadding?: number; // world units added around viewport before the bounds query
};
```

- **SQL bounds filter via the existing index.** `idx_nodes_bounds ON nodes(x, y, width, height)` already exists. The node read changes from "select all" to a bounds-overlap predicate against the padded viewport:
  `WHERE x < :maxX AND x + width > :minX AND y < :maxY AND y + height > :minY`.
  Groups carry `bounds_json` (not decomposed columns); add `CREATE INDEX idx_groups_bounds` is impractical on a JSON column, so groups (typically few, large containers) are read whole and filtered with `boundsIntersect` (`graph.ts:131`) — cheap because group count ≪ node count. Edges select by `group_id` of in-viewport groups plus endpoint membership, reusing the existing `idx_edges_group` and the endpoint-validity filter already in `readScene` (`storage.ts:84`).
- **Tag filter composes.** The current `tagIds.every(...)` group filter (`storage.ts:80`) AND-composes with the bounds predicate; no semantics change when `viewport` is absent.
- **Zoom-aware projection = field trimming, not object swapping.** When `zoom` puts an object below `Compact` (T3.1: `apparent_px < 120`), the server omits the heavy text fields from the snapshot it sends — `shapeSceneToRenderSnapshot` already separates renderable from business (`excludedBusinessFields()`), so trimming `card.summary`/`card.detail` text payload for far objects is a payload optimization, **never** an identity change: `id`, `bounds`, `styleKey`, `groupId` are always present so the object stays the same selectable/hit-testable object (T3.1 §4 invariant). The Locked Decision line 25 (no semantic replacement) holds because trimming subtracts payload from *the same* object id.
- **MCP path:** `query_scene(tagIds?)` (`mcp.ts:59-66`) gains optional `viewport`/`zoom`, forwarding into the same `readScene`. Renderer-side culling still owns the *visual* viewport (the tool's existing description already says so); the new params let an MCP client page a huge scene spatially instead of pulling the whole blob — the read-cursor/target trace P5 needs is the same viewport the query carries.
- **Client/renderer wiring:** `fetchScene`/the `render-snapshot` route (`api.ts:17`, `index.ts:120`) pass the current camera-derived world viewport + `prefetchPadding`; `RendererCanvasHost` (`load_scene` at line 186) ingests the returned partial snapshot. **Partial-scene ingest is additive**: a second core entry `merge_scene(scene_json)` upserts the returned objects into the resident `SceneSnapshot` + `SpatialGrid` (reusing the `apply_patch_batch` upsert path) so panning streams new tiles without dropping resident slots, while `load_scene` keeps its full-replace semantics for back-compat.

### 3. Tile / cache levels (residency keyed to LOD tier)

A "tile" here is **a spatial-grid cell at a zoom band**, not a pre-rasterized image tile (we are vector-first per Locked Decision line 120 in the strategy doc / T3.1 §7). The cache levels are residency states a cell's objects occupy, indexed by the coarsest `LodTier` of the cell at the current camera:

| Cache level | Driven by tier (T3.1) | What is resident for objects in the cell | Backed by existing structure |
| --- | --- | --- | --- |
| `Hot` | `Full` / `Compact` | full vertex slots + text layout + glyphs + edge geometry | `VertexRanges` slots, `TextLayoutCache`, glyph atlas, new edge cache (§6) |
| `Warm` | `ShapeOnly` | vertex slots (fill+stroke only), **no** text layout / glyph residency | `VertexRanges` slots; text caches *not* populated |
| `Cool` | `Density` | aggregated into density texture; per-object slots **evictable** | density raster (§7); slots may be released under budget |
| `Cold` | `Minimap` / off-screen beyond prefetch | not resident; lives only in storage / density tint | storage, on next viewport query |

- **No DOM, ever.** Objects are GPU slots or density-texture contributions, never DOM nodes (Explicit Non-Goal line 81; Verify bullet). The Svelte shell mounts one `<canvas>` host (`RendererCanvasHost`), not per-object elements.
- **Level transitions are paint/residency only**, never identity: an object moving `Hot→Cool` keeps its `RenderCard.id` slot key; dropping its text-cache entry and per-object slot does not change `bounds`/selection/hit identity (T3.1 §4). Re-entry repopulates from the next viewport query.
- **Level is derived, not stored.** It is `LodTier`-of-cell per frame; it needs no schema field and stays ephemeral (Locked Decision line 34).

### 4. Text cache plan (evolve `TextLayoutCache` + raster cache with a budget)

The cache exists and works; it has **no eviction** — it grows unbounded over a long session. T3.2 adds bounded residency without changing the cache key or hit/miss accounting that `WebGpuFrameStats` already reports:

- **Layout cache (`TextLayoutCache`, `text.rs:66`)** keeps its `(value, max_width, font_size[, max_lines])` keys. Add **LRU eviction** with an entry cap derived from the text memory budget (§9). Tier gates *insertion*: `Warm`/`Cool`/`Cold` cells never request layout (their tiers suppress text per T3.1 §2), so the cache only ever holds text for `Full`/`Compact` objects near the viewport — the working set is bounded by visible+prefetch text, not by total scene text.
- **Raster cache (`TextEngine`, `text.rs:124`)** keeps `raster_cache_hits/misses` but gains LRU eviction tied to atlas residency (§5) so a glyph rasterized for an object that left the viewport can be reclaimed when the atlas pressures.
- **Stats already cover it:** `text_layout_cache_hits/misses`, `text_raster_cache_hits/misses` (`stats.rs:25-28`) make the cache's effectiveness measurable for T3.4; add `text_layout_cache_evictions` / `text_raster_cache_evictions` so budget pressure is observable.

### 5. Glyph atlas plan (bounded 2048×2048, eviction over overflow)

The atlas is fixed 2048×2048 (`text.rs:13-14`) and currently **overflows silently** — `text_atlas_overflow_glyph_count` counts glyphs that did not fit but nothing evicts (`webgpu.rs:1258`, `stats.rs:24`). For an unbounded multi-script scene the atlas must recycle:

- **Add LRU slot recycling to the atlas allocator.** Track last-used frame per atlas glyph; when a new glyph cannot fit, evict least-recently-used glyph slots instead of incrementing overflow. Overflow stays as the **saturation signal** (eviction thrash) for diagnostics, not the failure mode.
- **Tier-gated rasterization** (from §3/§4): only `Full`/`Compact` objects request glyphs, so the atlas working set is "visible + prefetch glyphs", which fits 2048² for realistic viewports; eviction only engages on extreme heterogeneous CJK + Latin mixes (exactly T3.3's fixtures).
- **Optional second atlas page** is deferred: spec says "glyph atlas" (singular budget), so T3.2 sizes the budget at one page and lets eviction handle pressure; a multi-page atlas is an Open Question, not in scope.
- **Stats:** reuse `text_atlas_glyph_count` (residency), keep `text_atlas_overflow_glyph_count` as the thrash signal; add `text_atlas_evicted_glyph_count`.

### 6. Edge cache (new, mirrors the slot+dirty model)

Edge cubic-route geometry and `edge_visible_bounds` are recomputed during build (`webgpu.rs:2905-3000`); for a dense graph this is wasted work when endpoints have not moved. Add a per-edge geometry cache keyed and invalidated exactly like the existing dirty-edge path:

```rust
// shape_canvas_core — cached edge geometry, invalidated by the SAME dirty_edge_ids set.
struct EdgeGeometryCache {
    routes: HashMap<String, CachedEdgeRoute>, // key = RenderEdge.id (the VertexRanges.edges slot key)
}
struct CachedEdgeRoute { route_vertices: Vec<f32>, visible_bounds: WorldRect, tier: LodTier }
```

- **Invalidation reuses `dirty_edge_ids`.** The move-card/move-group handlers at `webgpu.rs:920-941` already extend `dirty_edge_ids` for edges touching a moved card; an edge's cache entry is invalidated on exactly that set — no new dirtiness tracking.
- **Tier-aware route detail:** `Full`/`Compact` cache the cubic route + label-bounds; `ShapeOnly`/`Density` cache a straight thin-line route (T3.1 §2 edge row), so the cache stores the geometry actually drawn at that tier. A tier change re-derives the route once and re-caches.
- **`visible_bounds` feeds the spatial grid (§1)** so the index and the cache share one bounds computation.
- **Stats:** add `edge_route_cache_hits/misses` beside the existing edge slot counters (`stats.rs:38-41`).

### 7. Density texture (the `Density`/`Minimap` backing raster)

T3.1 defined `Density`/`Minimap` as group-hull tints aggregating far objects, but per-object draw still runs. T3.2 makes that aggregation a real cache so far regions cost a single textured quad, not N draws:

- **Per-group density tile.** For groups whose hull tier is `Density`/`Minimap`, render their members' `bounds` once into a low-res offscreen texture (one tile per owning `RenderGroup`, sized to hull bounds), tinted by member density and the group's `styleKey` color (T3.1 §5). The draw list emits one textured quad per density-tier group instead of per member.
- **Invalidation:** the texture is invalidated when any member's `bounds` changes (same `dirty_card_ids`/`dirty_group_ids` set) or when the group's hull tier changes; otherwise it persists across pan frames at the same zoom band. Membership is read from `RenderCard.groupId`/`SceneGroup.parentGroupId` — document fields LOD never mutates (T3.1 §5 invariant), so the aggregation never re-identifies objects.
- **Identity preserved:** members keep live slots in the spatial grid and hit-test (`CoreHitResult`, `stats.rs:53`) even while painted only as tint — a `Minimap` card is still selectable (T3.1 §4 corollary). The density texture is *paint*, not an object model; no clustering super-object is created (Locked Decision lines 25-26; Stop-or-ask aggregate-first guard inherited from T3.1).
- **Stats:** add `density_tile_count` / `density_tile_redraw_count` alongside T3.1's per-tier counts.

### 8. Prefetch radius

Streaming with a viewport-exact query stutters on pan because the just-revealed edge is fetched on demand. Prefetch a ring around the viewport so the next pan reveals already-resident objects:

- **Two distinct radii, both world-units:**
  - **Render cull padding** = existing `VIEWPORT_CULL_PADDING` (`webgpu.rs:1691`) — unchanged; controls what the renderer *draws* from resident data.
  - **Fetch prefetch radius** (new, `SceneQuery.prefetchPadding`, §2) — larger; controls what storage *returns* into residency. Seed: `prefetchPadding = (viewport longest edge) * 0.5`, i.e. fetch the next half-screen in every direction.
- **Velocity-biased (optional, deferred-tunable):** bias the prefetch ring toward the current pan direction so fast pans prefetch ahead, not symmetrically. Marked tunable for T3.4; the symmetric ring is the seed.
- **Prefetch is a `merge_scene` (§2), not a reload:** the prefetched ring upserts into the resident `SceneSnapshot`+`SpatialGrid` without disturbing the hot working set. Objects that leave `viewport + prefetch + cull` become eviction candidates (§3 `Cold`, §9).

### 9. Memory budget (explicit caps + eviction policy)

Today nothing evicts: `VertexRanges` only grows/compacts, the atlas overflows, the text caches grow unbounded. T3.2 sets named budgets per cache and an eviction order so a long session over an unbounded scene reaches a steady state:

| Cache | Budget (seed; tunable by T3.4) | Eviction policy | Existing hook |
| --- | --- | --- | --- |
| Vertex slots (`VertexRanges`) | cap on resident slot count ≈ (visible + prefetch) objects | release `Cold`/`Cool` per-object slots LRU; reuse `card_free_offsets`/compaction | `webgpu.rs:1089-1145`, `compact_*_slots` |
| Text layout (`TextLayoutCache`) | entry cap (e.g. 4k lines) | LRU | `text.rs:66` |
| Glyph atlas | one 2048² page | LRU glyph slots (§5) | `text.rs:124` |
| Edge route cache | entry cap ≈ resident edge count | LRU + dirty invalidation | new (§6) |
| Density tiles | cap on tile count + total texel budget | LRU by group, redraw on demand | new (§7) |

- **Eviction order under global pressure:** `Cold` per-object slots → `Cool` text/glyph residency → density tiles for off-screen groups. Hot (`Full`/`Compact` in-viewport) residency is never evicted while visible — that would cause the visible stutter T3.4 forbids.
- **Budget is core-owned and ephemeral** (Locked Decision line 31/34): no schema field, no document write; budgets are constants tunable against T3.4 latency targets, exactly like T3.1's threshold constants.
- **Observability:** the budget is verifiable through the eviction counters added in §4-§7 plus the existing slot/atlas/cache stats in `WebGpuFrameStats`; T3.4 reads memory + cache stats from this surface (P3 Verify line 477).

### 10. End-to-end flow (how the nine compose)

```
camera change (pan/zoom)  ──ephemeral, Svelte shell
   │  derive world viewport + zoom + prefetch ring
   ▼
SceneQuery{ viewport, zoom, prefetchPadding, tagIds? }  ──storage seam (§2)
   │  SQL bounds filter via idx_nodes_bounds + group boundsIntersect + zoom field-trim
   ▼
partial SceneSnapshot  ──HTTP /api/scene/render-snapshot  | MCP query_scene
   │  merge_scene -> resident SceneSnapshot + SpatialGrid (§1,§2)
   ▼  ── all below in Rust/core, per-frame
build_draw_list: grid.query(viewport) ─► per-object LodTier (T3.1) ─► cache level (§3)
   │            ├─ Hot: vertex slot + text cache (§4) + glyph atlas (§5) + edge route cache (§6)
   │            ├─ Warm: vertex slot only
   │            └─ Cool/Cold: density tile (§7)  ;  evict beyond budget (§9)
   ▼
FrameDrawList + WebGpuFrameStats (cache/tier/eviction counters, §4-§9)  ──diagnostics drawer / T3.4
```

The whole pipeline is additive over named existing symbols: `SceneQuery`, `idx_nodes_bounds`, `boundsIntersect`, `readScene`, `shapeSceneToRenderSnapshot`, `load_scene`/`apply_patch_batch`, `build_draw_list`, `VertexRanges`, `TextLayoutCache`, `TextEngine` atlas, `WebGpuFrameStats`, and T3.1's `LodTier`. No parallel renderer, no DOM mounting, no schema change.

### 11. What this task deliberately does **not** do

- **No schema/contract change.** `Scene`/`ScenePatch`/`RenderScenePatch`/`SceneSnapshot` are untouched; `SceneQuery` gains optional fields (back-compatible, omitted = today's behavior). Caches, index, budgets are ephemeral core state (Locked Decision line 34).
- **No rasterized image tiles / pyramid.** Cache "levels" are residency states of vector objects keyed to `LodTier`; the only raster is the `Density`/`Minimap` aggregation texture (§7). Vector-first stays (strategy §3 / T3.1 §7).
- **No new LOD policy.** Tiers/thresholds are T3.1's; T3.2 only consumes them as the cache-level axis.
- **No realtime/CRDT/transport.** Streaming is single-user local-first paging over the existing storage; no remote sync (Explicit Non-Goals lines 85-86).
- **No freeform hull shape math** (T2.4) and **no benchmark run / interaction test** (T3.3/T3.4) — T3.2 defines the cache/streaming structures and their stats hooks; the load is generated and measured downstream.

## Stop-or-ask

| Stop-or-ask condition | Status | Why / decision needed if triggered |
| --- | --- | --- |
| **SQLite/API query shape cannot support spatial paging and zoom-aware fetches.** | **CLEAR (not triggered)** | Spatial paging is already feasible: `nodes` stores decomposed `x,y,width,height` columns **with** `idx_nodes_bounds ON nodes(x, y, width, height)` (`storage.ts:441`), so the bounds-overlap predicate in §2 is index-backed; `graph.ts` already ships `boundsIntersect`/`pointInBounds`/`expandedBounds` for the in-JS group filter; `SceneQuery` and the `/api/scene/render-snapshot` + `query_scene` seams already take a query object, so adding optional `viewport`/`zoom`/`prefetchPadding` is additive and back-compatible. **Residual risks that would flip this to TRIGGERED:** (a) groups store `bounds_json` (JSON, not columns) so group bounds are not SQL-indexable — mitigated because group count ≪ node count and groups are read whole + filtered in JS; if group count grows large enough to matter, a decomposed-bounds column + index migration would be needed and is the decision to raise. (b) sql.js is in-process/synchronous; if zoom-band streaming demands sub-frame async paging, the loader/transport (not the query shape) becomes the constraint — that is a T3.4 measurement question, not a query-shape blocker today. |

## Open questions / risks

- **Grid cell size is provisional.** `cell_size ≈ 780` (2× default card edge) is a seed; heterogeneous fixtures (T3.3) with very large frames + tiny notes may want a two-level grid or per-kind cells. Tune against T3.4.
- **Prefetch radius vs. memory budget tension.** A larger `prefetchPadding` smooths pan but enlarges the resident working set; the §9 eviction order must be measured under T3.4's fast-pan case so prefetch does not thrash `Hot` residency.
- **Single atlas page assumption.** §5 sizes one 2048² atlas with LRU; extreme mixed-script scenes (CJK + Latin + symbol fonts) may thrash. A second atlas page is the deferred escalation if T3.3 fixtures saturate eviction.
- **`merge_scene` vs. `load_scene` lifecycle.** Introducing partial-snapshot merge alongside full-replace load needs a clear rule for when resident-but-now-out-of-query objects are dropped; §8/§9 give the eviction trigger, but the exact "stale tile" reclamation cadence is a T3.4 tuning input.
- **Density tile correctness under nested groups.** §7 renders one tile per density-tier group; deeply nested hulls (T3.1 §5 outside-in collapse) need a defined tile-ownership rule (innermost vs. outermost owns the texel) — flagged for the implementer, consistent with T3.1's outside-in hull degradation.
