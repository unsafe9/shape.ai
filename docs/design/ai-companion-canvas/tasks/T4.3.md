# T4.3 Wiki Note And Idea Board Templates

> Phase P4 (Template System On Primitives), Wave H. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P4 intro, T4.3); upstream `docs/design/ai-companion-canvas/tasks/T4.1.md` (the binding `TemplateContract` — metadata/recipe/layout/exports/tags/promptHints, the `localId`→sceneId lowering, the `meta.templateKind`/`styleKey`-from-template rules, the §7 application pipeline) and `docs/design/ai-companion-canvas/tasks/T2.3.md` (text-on-everything: `shape` title/summary/detail, `edge` label, `frame` title/summary, the generalized `edit-text` op, comment `body` via `addShapeSceneComment`).
> Real symbols grounded in: `src/shared/schema.ts` (`sceneGroupSchema`, `sceneNodeSchema`, `sceneEdgeSchema`, `graphNodeSchema.evidenceRefs`, `graphNodeSchema.childDecisionIds`, `sceneCommentSchema`, `artifactSchema`, `tagSchema`, `exportTypeSchema`, `sceneSelectionSchema`), `src/shared/renderScene.ts` (`SceneSnapshot`, `RenderCard.styleKey`, `defaultStyles`, `excludedBusinessFields`), `src/shared/renderPatch.ts` (`create-group`/`create-card`/`create-edge`/`edit-card-text`/`select` ops, `applyRenderPatchToShapeScene`, `commitAppPatch`, `addShapeSceneComment`), `src/server/local.ts` (`generateLocalExport`, `madrSections`, `confluence_html` branch, `boundsForNodes`, `node(...)`/`edge(...)` seed builders, `scopedId`), `src/server/mcp.ts` (`export_group`, `add_comment`, `create_tag`), `src/shared/graph.ts` (`sceneGraphForGroup`).
> Relationship to upstream: **T4.3 owns no new primitive, op, schema field, or renderer.** It authors *two concrete `TemplateContract` instances* (a wiki-note cluster template and an idea-board template) against the T4.1 contract, plus the source/evidence-card and reference-edge recipes those surfaces need. Everything lowers to the existing `create-group`/`create-card`/`create-edge`/`create-tag`/`set-object-tags` op funnel (T4.1 §2, §7); text edits use the T2.3 `edit-text` path; comments use `addShapeSceneComment`. The work is recipe authoring + the field-by-field mapping that makes "source/evidence cards" and "reference edges" land on existing primitives.

## Outcome

Author two `TemplateContract`s — **wiki note clusters** and **idea boards** — as primitive recipes (frames + shape cards + reference edges + source/evidence cards + suggested tags) that apply through the T4.1 lowering pipeline into ordinary `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` objects, so notes carry their text in `title`/`summary`/`detail`, sources in an `evidence`-styled card whose `evidenceRefs[]` holds the citation, and references as edges — all editable and spatially reorganizable with the same ops as any object.

## Deliverable

The breakdown's T4.3 Deliverable is one bullet with four parts: a template plan for **(1) wiki note clusters, (2) idea boards, (3) source/evidence cards, and (4) reference edges.** §1 fixes the shared primitive vocabulary these surfaces draw from (no new kinds). §2 is the wiki-note-cluster `TemplateContract`. §3 is the idea-board `TemplateContract`. §4 is the source/evidence-card recipe (shared by both). §5 is the reference-edge recipe (shared by both). §6 maps allowed exports. §7 proves the Verify property (spatial reorg preserves text/tags/comments/source refs) field-by-field. §8 states the additive delta. Nothing beyond the four parts is added — no long-form document editor (Stop-or-ask).

### 1. Shared primitive vocabulary (nothing new is introduced)

Both templates compose from the exact primitives T2.1/T4.1 already fixed. The mapping from "knowledge/ideation concept" to existing carrier:

| Template concept | Primitive (T4.1 recipe element) | Existing carrier symbol | Text/data slot |
| --- | --- | --- | --- |
| Wiki cluster / board container | `RecipeFrame` → `create-group` | `SceneGroup` (`sceneGroupSchema`) | `title`, `summary`; nested via `parentGroupId` (already nullable) |
| Note / idea card | `RecipeShape` → `create-card` | `SceneNode` (`sceneNodeSchema`) | `title` (heading), `summary` (lede), `detail` (body) |
| Section sub-frame inside a cluster | `RecipeFrame` (child) → `create-group` | `SceneGroup` with `parentGroupId` set | nested grouping (Locked Decision: nested grouping = arbitrary semantic hierarchy) |
| Source / evidence card | `RecipeShape` with `styleKey:"evidence"` + `meta` ref | `SceneNode`; citation in `evidenceRefs[]` | §4 |
| Reference / "see also" edge | `RecipeEdge` → `create-edge` | `SceneEdge` | `label` (T2.3-editable) | §5 |
| Note tags / topic labels | `SuggestedTag` + `tagLocalIds` | `Tag` registry (`tagSchema`) + `tagIds[]` | §2.4 |
| Annotation on a note | comment (not a recipe element) | `SceneComment` via `addShapeSceneComment` | created post-apply, not part of the recipe |

`styleKey` is chosen by the template, not by a demoted `nodeType` (T4.1 §2 / D1 C3). `RenderCard.styleKey` and `SceneStyleToken.id` accept any free string, and `defaultStyles` ships ids for the existing enum values — so a wiki note card declares `styleKey:"proposition"` (a calm prose-card token) and a source card declares `styleKey:"evidence"`, reusing existing tokens with **no schema or token change**. `meta.templateKind` is the only template trace persisted on objects (T4.1 §1).

### 2. Wiki note cluster template (`templateKind: "wiki-note"`)

A wiki cluster is a titled root frame containing prose note cards, optionally organized into nested section sub-frames, cross-linked by reference edges, and citing source cards. It is a `TemplateContract` (T4.1 §7 shape) whose recipe is declared data.

#### 2.1 Metadata (`TemplateMetadata`, T4.1 §1)

```ts
{ id: "wiki-note", title: "Wiki Note Cluster", description: "Linked prose notes with sources and references.",
  category: "knowledge", templateKind: "wiki-note" }
```

#### 2.2 Recipe (`TemplateRecipe`, T4.1 §2) — declared `localId`s, rewritten at apply

| Recipe element | Kind | Key fields (real slots) | Lowers to |
| --- | --- | --- | --- |
| `f-cluster` | `RecipeFrame` | `title:"Untitled Wiki"`, `summary:"…"`, `meta:{ templateKind:"wiki-note", semanticType:"wiki-cluster" }` | `create-group` |
| `f-section-a` | `RecipeFrame` | `parentLocalId:"f-cluster"`, `title:"Section"`, `meta:{ semanticType:"wiki-section" }` | `create-group` (nested) |
| `n-overview` | `RecipeShape` | `frameLocalId:"f-cluster"`, `styleKey:"proposition"`, `title`, `summary`, `detail`, `meta:{ semanticType:"note" }` | `create-card` |
| `n-note-1`, `n-note-2` | `RecipeShape` | `frameLocalId:"f-section-a"`, `styleKey:"proposition"`, prose in `title`/`summary`/`detail` | `create-card` |
| `n-source-1` | `RecipeShape` | source/evidence card — see §4 | `create-card` |
| `e-ref-1` | `RecipeEdge` | reference edge `n-note-1`→`n-note-2` — see §5 | `create-edge` |
| `e-cite-1` | `RecipeEdge` | citation edge `n-note-1`→`n-source-1` — see §5 | `create-edge` |

Body text lives entirely in the existing card text slots: heading in `title`, lede in `summary`, long-form body in `detail` (T2.3 wraps `detail` to ≤6 lines on-card, full text editable in the overlay). **This is the boundary against the Stop-or-ask:** "long-form" here means a multi-paragraph `detail` field edited through the same overlay every card uses — *not* a separate rich-text/document editor surface. The canvas stays the primary surface; `detail` is canvas-backed note text (§7, Stop-or-ask).

#### 2.3 Default layout (`RecipeLayout`, T4.1 §3)

Relative member positions in the recipe; frame `bounds` derived by `boundsForNodes(members)` (`local.ts:201`); whole template placed into free space by `nextGroupOffset` (T4.1 §3). Notes default to the existing `{390,390}` `sceneNodeSchema` size; source cards use a shorter `{390,220}` to read as citations. No auto-layout engine (Non-Goal) — a column-of-notes is just authored `position`s.

#### 2.4 Suggested tags (`TemplateTags`, T4.1 §5)

```ts
suggested: [ { localId:"t-topic", name:"topic", color:"#5B8DEF" },
             { localId:"t-source", name:"source", color:"#8E8E93" },
             { localId:"t-draft", name:"draft", color:"#E0A458" } ]
```
Applied via `create-tag` (only if no registry `Tag` of that `name` exists) + `tagLocalIds` on the relevant recipe elements → `tagIds[]`. Single `Tag` registry, no template-private taxonomy (T2.4 / T4.1 §5).

#### 2.5 Allowed exports / prompt hints — §6.

### 3. Idea board template (`templateKind: "idea-board"`)

An idea board is a freeform ideation surface: a root frame of loosely-placed idea cards, optionally clustered into theme sub-frames, with associative "relates-to" reference edges. Same contract shape, different recipe and styling intent (sparser, freer placement) — **not a different object model**.

#### 3.1 Metadata

```ts
{ id: "idea-board", title: "Idea Board", description: "Freeform ideation cards grouped into themes.",
  category: "knowledge", templateKind: "idea-board" }
```

#### 3.2 Recipe

| Recipe element | Kind | Key fields | Lowers to |
| --- | --- | --- | --- |
| `f-board` | `RecipeFrame` | `title:"Idea Board"`, `meta:{ semanticType:"idea-board" }` | `create-group` |
| `f-theme-1` | `RecipeFrame` | `parentLocalId:"f-board"`, `title:"Theme"`, `meta:{ semanticType:"idea-theme" }` | `create-group` |
| `n-idea-1..n` | `RecipeShape` | `frameLocalId:"f-board"` or a theme frame, `styleKey:"option"` (light "candidate" token), `title` = idea, `summary` = note, `meta:{ semanticType:"idea" }` | `create-card` |
| `n-source-1` | `RecipeShape` | optional source/evidence card (§4) | `create-card` |
| `e-rel-1` | `RecipeEdge` | associative reference edge (§5), `label:"relates to"` | `create-edge` |

Idea cards reuse the existing `option` style token (a "candidate/alternative" visual) so demoted objects keep visual identity without reviving enum coupling (T4.1 §2). Theme sub-frames use the **already-supported** nested grouping (`parentGroupId`) so a user can break apart / re-cluster ideas freely — exactly the "reorganize spatially" Verify (§7). Default layout/tags/exports follow the same mechanisms as §2.3–§2.5 with looser default `position`s and a `theme`/`spark`/`parked` tag set.

### 4. Source / evidence card recipe (shared by §2 and §3)

A source/evidence card is **not a new primitive** — it is a `RecipeShape` (→ `SceneNode`) with:

- `styleKey:"evidence"` (reuses the existing evidence token in `defaultStyles`; no new token).
- The citation/source reference stored in the canonical `evidenceRefs: string[]` field already on `graphNodeSchema` (`schema.ts:70`). A source card carries e.g. `evidenceRefs: ["https://…", "file:src/foo.ts:42", "confluence:PAGE-123"]`. This field is in the **business layer** — `excludedBusinessFields()` lists `Node.evidenceRefs` (`renderScene.ts:248`) as staying in the TS app, so it is *not* in `SceneSnapshot` and never reshaped by the renderer, but it *is* canonical document state persisted on the node. This is the existing, correct home for "source refs."
- `meta:{ semanticType:"source", citationKind:"url"|"file"|"page" }` for agent/export hints.
- Visible text: source title in `title`, citation summary in `summary`, quoted excerpt in `detail`.

Field-by-field, a source card on the wire is:

```ts
// produced SceneNode (after T4.1 lowering of a RecipeShape) — all existing fields
{ id, groupId, type: "evidence",            // demoted enum still accepted by sceneNodeSchema
  title: "RFC 9110 §10.2", summary: "HTTP semantics", detail: "…excerpt…",
  status: "draft", confidence: 0.5,
  evidenceRefs: ["https://www.rfc-editor.org/rfc/rfc9110"],  // ← the source ref, canonical
  childDecisionIds: [], position, size, zIndex,
  /* meta.templateKind / meta.semanticType ride the additive meta bag (T2.1 §4) */ }
```

A note that *cites* a source is connected to its source card by a citation edge (§5) **and/or** by adding the source-card id (or the ref string) to the note's own `evidenceRefs[]`. Recommendation: use the **reference edge** as the on-canvas, reorganizable link (it survives spatial moves, §7) and reserve `evidenceRefs[]` for the source card's own external citation strings. This avoids overloading `evidenceRefs` with intra-scene ids while keeping the existing external-citation semantics that `madrSections` already reads.

> Image-backed sources (a screenshot of a page) ride the `image_artifact` placement (T4.1 §2 / D1 C1): until the image substrate primitive lands in `webgpu.rs`, the source card is a captioned box whose `evidenceRefs`/`meta` hold the artifact ref — no contract change needed when pixels arrive.

### 5. Reference edge recipe (shared by §2 and §3)

A reference edge is a `RecipeEdge` (→ `SceneEdge`) with no new edge kind:

- `styleKey:"supports"` for a citation/"backs" link and a neutral token for an associative "relates to" link (both reuse existing `defaultStyles` ids; T4.1 §2 forbids keying style off `edgeType`).
- `meta:{ semanticType:"reference"|"citation"|"relates-to" }` carries the human-readable relation; the demoted `SceneEdge.type` enum value (e.g. `supports`) is accepted but not load-bearing for style.
- `label` holds editable edge text ("see also", "cited by") via the T2.3 `edit-text{target:"edge",field:"label"}` path — already render-shaped and now editable.
- `SceneEdge.groupId` is set to the cluster/board frame (membership), matching how `seedGroupScene` scopes edges.

Reference edges are ordinary edges: `commitAppPatch` validates both endpoints exist and cascades correctly on delete (T4.1 §2). Because they are scene objects keyed on stable source/target ids, a note keeps its references when moved (§7) — the edge re-routes geometrically in core, the link identity is unchanged.

### 6. Allowed exports (from `exportTypeSchema`, via `generateLocalExport`)

Both templates declare `TemplateExports` (T4.1 §4) over **existing presets that already read primitive text** — no export engine is added:

| Template | `exports.allowed` | `default` | Reads via |
| --- | --- | --- | --- |
| `wiki-note` | `design_doc_md`, `confluence_html`, `madr`, `mermaid` | `design_doc_md` | `generateLocalExport` → `madrSections` / `confluence_html` branch (`local.ts:184`) over `sceneGraphForGroup` |
| `idea-board` | `design_doc_md`, `mermaid`, `image_prompt` | `design_doc_md` | same; `mermaid` renders the relates-to graph, `image_prompt` summarizes the board |

These presets read `title`/`summary`/`detail` and node/edge structure; `madrSections` already treats `type:"evidence"` nodes as positive-consequence/evidence text (`local.ts:265,268`), so source cards flow into the export as citations **with no preset change**. `allowed` is a constraint the export drawer (shell) and `export_group` (`mcp.ts`) honor; the preset code is unchanged. (T4.3 matches T4.1 §4's wiki row, narrowing/extending only the declared set.)

Optional `promptHints` (T4.1 §6): `systemHint:"This is a wiki note cluster; cards are notes, evidence cards carry sources in evidenceRefs, edges are references."`; `fieldHints:{ note:"Heading in title, lede in summary, body in detail", source:"Put the citation in evidenceRefs" }`; `suggestedOperations:["create","connect","tag","comment"]`. Advisory only — templates are usable with hints absent.

### 7. Verify proof — spatial reorg preserves text, tags, comments, source refs

"Notes can be reorganized spatially without losing text, tags, comments, or source refs." Reorganizing = `move-card`, `move-group`, `group-objects`/regroup, `set-card-z-index` (existing geometry ops). Each touches **only geometry**; the data fields live elsewhere and are untouched:

| Asset | Where it lives | Mutated by a move? |
| --- | --- | --- |
| Note text | `SceneNode.title/summary/detail` | No — move ops set `position`/`groupId`/`zIndex` only (`commitAppPatch`), never text fields. |
| Tags | `SceneNode.tagIds[]`* / `SceneGroup.tagIds[]` → `Tag` registry | No — tag ids ride the object; move doesn't clear them. (*node tag carrier per T2.4 generalization.) |
| Comments | `SceneComment.target` (a `sceneSelectionSchema` `{kind:"node",id}`) | No — comments key on stable object **id**, not position; moving a node keeps `target.id` valid. |
| Source refs | `SceneNode.evidenceRefs[]` (business layer) + reference edges (`SceneEdge` keyed on src/target id) | No — `evidenceRefs` is untouched by geometry ops; edges re-route by id, link identity preserved. |

Because identity is stable across moves (Locked Decision: stable object identity, no semantic-replacement-on-zoom) and every data asset keys on object **id** rather than position, the Verify property holds by construction: a note dragged into another section frame keeps its body, tags, every comment, and every citation/reference. Regrouping changes only `groupId` (membership), which the schema already supports (every node requires a `groupId`, edges carry `groupId`); nested grouping is already in `sceneGroupSchema.parentGroupId`. This is the same guarantee `move-card`/`translateGroups` already provide for decision-graph nodes today.

### 8. Additive delta (no schema/op/renderer change)

| Concern | Home |
| --- | --- |
| `wiki-note` + `idea-board` `TemplateContract` instances (recipe data, exports, tags, hints) | **shared template registry** (`src/shared/template.ts`, the file T4.1 introduces) — pure declared data |
| lowering to ops, id rewrite, tag resolution | reuses T4.1 `lowerTemplateToOps` — no new code in T4.3 |
| running ops, geometry/hull/hit of produced objects, edge re-routing on move | **Rust/core** (already owns these) — templates emit ops, touch none of it |
| template picker, export-drawer `allowed` filtering, prompt-hint surfacing | **shell** (Svelte target) |
| source-card `evidenceRefs` persistence | already canonical in `sceneNodeSchema` / storage — unchanged |

Net: T4.3 adds **two `TemplateContract` records** and their recipes. **Zero** new primitive kinds, op kinds, schema fields, style tokens, or export presets. `evidenceRefs`/`childDecisionIds`/`meta` are reused as-is; `styleKey` is chosen from existing `defaultStyles` ids; comments use the existing `addShapeSceneComment`/`add_comment` path; reference edges are ordinary `SceneEdge`s. This mirrors the T4.1 / T2.x "evolve, don't replace" discipline.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Long-form document editing becomes the primary surface instead of canvas-backed note/detail editing. | **CLEAR (not triggered)** | The wiki/idea recipes keep the **canvas** as the primary surface. Note bodies are the existing `SceneNode.detail` field, edited through the **same** T2.3 text overlay every card uses — there is no separate rich-text/document editor, no page-mode, no document object (§2.2). `detail` is multi-paragraph canvas-backed text wrapped on-card (≤6 lines, full text in the overlay), not a long-form document surface. The Non-Goal "파일시스템 저장 계층을 대체하지 않는다 — spatial working interface over docs/artifacts" is honored: long documents remain *exports* (`design_doc_md`/`confluence_html`, §6) generated from primitive text, not an in-canvas word processor. **If** product later requires true long-form rich-text editing (headings, inline marks, embedded media) as the primary note surface, that would trip this condition and require a decision (a rich-text primitive vs. an external doc editor link), because it cannot be served by the `title/summary/detail` slots without a new editing model — flagged, not present in this recipe set. |

## Open questions / risks

- **Source-ref representation: edge vs `evidenceRefs[]`.** §4 recommends reference edges for on-canvas, reorganizable intra-scene citations and `evidenceRefs[]` for external citation strings. If product wants a single uniform source model, decide whether intra-scene citations also write the source-card id into the citing note's `evidenceRefs[]` (duplicating the edge) or rely on the edge alone. Current recommendation: edge for the link, `evidenceRefs` for external strings — avoids overloading and keeps `madrSections` export semantics.
- **`detail` wrap budget vs. note length.** Wiki notes can exceed the on-card `detail` ≤6-line budget (T2.3); long bodies render truncated-with-ellipsis on-card but are fully present in the data and the overlay. If users routinely write long notes, consider a LOD/expanded-card behavior (P3-owned) rather than a document editor — noted so the truncation is a deliberate canvas LOD choice, not data loss.
- **Per-template `meta` validation (D1 C4 / T4.1 Open questions).** A `wiki-note`/`idea-board` template may carry an optional Zod schema validating its `meta.semanticType ∈ {note, source, idea, …}` at authoring/apply time only (never gating the renderer). Recommended but the concrete schema is authored with the template, deferred per T4.1.
- **Image-source previews (D1 C1).** Screenshot/page-image sources depend on the image substrate primitive not yet in `webgpu.rs`; until then a source card is a captioned box holding the artifact ref (§4). No contract change when pixels land.
