> Phase P2 (Universal Primitive Editing Slice), Wave E. Design-only pass: no production code is written, moved, or scaffolded.

> Relationship to T2.1/T2.2/T2.3: T2.1 already maps `SceneGroup`→`frame` as **KEEP** and reserves `tagIds[]` for generalization onto objects. T2.2 owns *transient* multi-select that creates **no** `SceneGroup`. T2.3 already added `edit-text{target:"frame"}` for frame titles. T2.4 owns **persistent** grouping: group/ungroup ops, membership drag-in/out, nested moves, freeform hull *visualization*, group-vs-member selection rules, and the object/group/color/tag **label** model. Operation metadata (`operationId`/`actorId`/`baseRevision`/`targetIds`) is **T2.5** — every op here is shaped to carry that envelope unchanged.

## Outcome

Make grouping and labeling **generic canvas operations** by evolving the existing `frame` (`SceneGroup`) container and `Tag` registry: add `group`/`ungroup`/membership ops and group-level transforms on top of the already-working `MoveGroup`/`translateGroups`/`descendantGroupIds`/`removeGroupIds` machinery, add a render-only freeform **hull** projection to `RenderGroup` (visualization + hit-test only, no boolean/vector editing), define group-vs-member selection via an *ephemeral* active-group focus, and generalize `tagIds[]` from frames onto all objects so labels/color chips/tag suggestions are tag rendering — never a new object kind or a project/ADR hierarchy.

## Deliverable

The breakdown's T2.4 Deliverable has nine bullets. They map to sections: group/ungroup operation model (§1), interaction model for create/add/pull-out/move-between/ungroup-without-losing-identity (§2), group geometry — rect frames + freeform hulls (§3), hull update behavior (§4), selection & hit-testing rules (§5), drag/drop & creation affordances (§6), label/tag model (§7), label appearance across zoom without semantic-replacement LOD (§8), migration note for old project/Shape labels and ADR fields (§9). §10 is the core-vs-shell placement and op/input/schema delta summary. Every bullet is covered; nothing beyond them is added.

### 1. Group / ungroup operation model

The container already exists: `SceneGroup` (`frame`) with `parentGroupId` (nesting), `bounds`, `tagIds`, `collapsed`. Membership is the **required** `SceneNode.groupId` (every node belongs to exactly one group) and `SceneEdge.groupId`; `commitAppPatch` already drops any node/edge whose `groupId` is not in the live group set, so orphan prevention is built in. T2.4 adds the *operations that change membership and containment*, each translating to the **existing** `ScenePatch` upsert + `translateGroups`/`removeGroupIds` primitives.

| Group form (breakdown) | Mechanism | Op(s) — additive to `RenderScenePatch` | Already exists? |
| --- | --- | --- | --- |
| **temporary selection group** | the **ephemeral core selection set** from T2.2 §3 (option B). Produces **no** `SceneGroup`; batch-move mutates each member's own geometry. | (T2.2) `batch` over `move-card`/`move-group` | yes (T2.2) |
| **persistent frame / group** | `frame` = `SceneGroup`. Promote a transient selection into a real frame that becomes the members' `groupId`. | new `group-objects{ ids, frameId?, parentGroupId? }` | partial: `create-group` exists but cannot adopt members |
| **nested group** | `parentGroupId` + `descendantGroupIds` (already in `renderPatch.ts` and `graph.ts`); `delete-group` already cascades descendants. | reuse `create-group`/`group-objects` with `parentGroupId` set | yes (nesting infra) — but `renderGroupToSceneGroup` hardcodes `parentGroupId: null` (§10 fix) |
| **group membership update** | re-point `node.groupId`/`edge.groupId`; re-clamp/grow frame bounds. | new `set-object-group{ ids, frameId }` | no |
| **group-level transform** | translate frame + all members by one delta — **already implemented**: core `MoveGroup` translates `group.bounds` and every `card.group_id==id` (and re-dirties incident edges); app `translateGroups` does the same on `SceneNode.position`. | existing `move-group`; resize via T2.2 `resize-group` (members re-clamped — §4) | yes (move); resize re-clamp = §4 |

New ops (additive union members; each folds into `commitAppPatch` and is wrappable by a T2.5 envelope):

```ts
// src/shared/renderPatch.ts — RenderScenePatch additions (sketch, not implemented here)
| { kind: "group-objects"; ids: string[]; frameId: string; parentGroupId?: string | null; title?: string; bounds?: WorldRect }
| { kind: "ungroup"; id: string }                 // dissolve frame, re-parent members to frame.parentGroupId
| { kind: "set-object-group"; ids: string[]; frameId: string }  // move members between frames
```

Translations (all via existing `commitAppPatch` paths — no new persistence primitive):

- `group-objects` → compute hull bounds from the member set (§3), upsert a `SceneGroup` (`bounds` = padded union, `parentGroupId` = deepest common ancestor frame or the supplied value), and upsert each member `node`/`edge` with `groupId = frameId`. `selection` → `{kind:"group", id:frameId}`. One `sceneVersion` bump, one operation.
- `ungroup` → re-point every member with `groupId == id` to the frame's `parentGroupId` (the parent frame; or, at the top level, to the scene's root frame — see §10 root-frame note), upsert those members, then `removeGroupIds: [id]`. Crucially this **only** removes the container; member node/edge ids, geometry, text, tags, edges are untouched, so object identity is preserved (Verify). Nested child frames re-parent to `parentGroupId` too. Uses the existing `removeGroupIds` path but, unlike `delete-group`, **does not** add `removeNodeIds`/`removeEdgeIds`.
- `set-object-group` → upsert members with the new `groupId`; re-clamp both the source and destination frame bounds (§4). Validation: `frameId` must exist; moving a frame's *only* members elsewhere leaves an empty frame (allowed — empty frames are legal containers).

`delete-group` (existing) stays the **destructive** path (cascade-removes descendant frames + their nodes/edges, per `renderPatch.ts:40`). `ungroup` is the **non-destructive** counterpart this task adds. The two are distinct verbs in the T2.5 operation vocabulary (`group`, `ungroup`, `delete`).

### 2. Interaction model — create, add, pull out, move between, ungroup without losing identity

| Interaction (breakdown) | Gesture | Op | Notes |
| --- | --- | --- | --- |
| **intuitive group creation** | select N objects (transient set, T2.2 §3) → ⌘G / context "Group" | `group-objects{ ids: selectionSet, frameId: new }` | promotes the ephemeral set into a `frame`; hull bounds from members (§3). Reverse of ⌘⇧G |
| **add a new object into a group** | create tool fires while a frame is the **active group** (§5), or create inside a frame's bounds | new object's `groupId` = active/enclosing frame (T2.2 §2 already sets `groupId = active frame or root`) | no new op; create ops already carry `groupId` |
| **add an existing object into a group** | drag object so its center lands inside a frame whose bounds enclose it | `set-object-group{ ids:[obj], frameId }` on `PointerUp` when the gesture is unambiguous (§6) | re-clamp frame bounds (§4) |
| **pull an object out of a group** | drag object out of the frame bounds (clear exit gesture, §6) | `set-object-group{ ids:[obj], frameId: enclosing-ancestor-or-root }` | shrink source hull (§4) |
| **move object between nested groups** | drag from inner frame to a sibling/parent frame | `set-object-group{ ids:[obj], frameId: dropTarget }` | drop target = deepest frame whose bounds enclose the drop point (§5 deepest-hit rule) |
| **ungroup without losing object identity** | ⌘⇧G / context "Ungroup" on a selected frame | `ungroup{ id }` | §1: container removed, member ids/geometry/text/tags/edges preserved; members re-parent to `parentGroupId` |

The membership invariant is what makes all of this reversible and identity-preserving: a node's `groupId` is the *single source of truth* for membership, the frame `bounds` is a derived visual that re-clamps (§4), and `commitAppPatch` already keeps edges valid across membership changes. Undo/redo falls out of T2.5's operation log (every interaction above is exactly one operation with a `targetIds` list = the moved member ids).

### 3. Group geometry — rectangular frames and freeform hulls

`SceneGroup.bounds` is a `WorldRect` (rigid AABB) today; `RenderGroup.bounds` mirrors it (`renderScene.ts`, `model.rs`). T2.4 keeps `bounds` canonical and adds a **render-only hull** so frames can hug members more closely than a rigid box, **without** any boolean/vector geometry (the explicit Stop-or-ask).

Two geometry modes on a frame, selected by a `meta.hullMode` (T2.1 `meta` bag — no new canonical column):

| Mode | Canonical carrier | Renderable projection | Hit region |
| --- | --- | --- | --- |
| **rectangle** (default, = today) | `SceneGroup.bounds` (`WorldRect`) | `RenderGroup.bounds` unchanged | `point_in_rect(world, bounds)` — existing |
| **freeform hull** | `SceneGroup.bounds` stays the canonical AABB; `meta.hullMode = "hull"` | new optional `RenderGroup.hull?: WorldPoint[]` — a padded polygon hull of member AABBs, **computed in core** and emitted for fill/stroke | point-in-polygon over `hull` (falls back to `bounds` when absent) |

Design constraints that keep the hull a *visualization*, not vector editing (Stop-or-ask):

- The hull is a **convex (or padded-union/rounded) polygon derived from member bounds** — the union of member AABBs grown by a padding constant, then a hull/rounded outline. No user-editable vertices, no path tools, no boolean ops between hulls. This is the same class of geometry the breakdown calls "group visualization and hit testing."
- `bounds` (the AABB) remains the **canonical** persisted geometry and the resize/transform target; `hull` is a *derived* render field recomputed from members, never persisted as authored points. So a frame round-trips through `schema.ts` unchanged; only `RenderGroup` gains an optional projected polygon.
- Hull computation lives in **Rust core** (Locked Decision: "grouping hull geometry" belongs in core), beside the existing `build_group_vertices` group-vertex path. The TS `groupToFrame` projection adds `hull` only when `meta.hullMode === "hull"`, populated by the core path.

`RenderGroup` delta (render contract only — no `schema.ts` change):

```ts
// src/shared/renderScene.ts — RenderGroup gains an optional derived hull (render-only)
export type RenderGroup = {
  id: string; title: string; summary: string;
  bounds: WorldRect;           // canonical AABB — unchanged, still the transform/resize target
  hull?: WorldPoint[];         // NEW: derived padded polygon for freeform visualization + hit-test
  tagIds: string[]; zIndex: number; styleKey: string;
};
```

```rust
// src/renderer/core/src/model.rs — RenderGroup mirror (render-only, additive, #[serde(default)])
pub struct RenderGroup {
    pub id: String, pub title: String, pub summary: String,
    pub bounds: WorldRect,
    #[serde(default)] pub hull: Vec<WorldPoint>,   // empty => rectangle mode
    #[serde(default)] pub tag_ids: Vec<String>,
    pub z_index: f64,
    #[serde(default = "default_style_key")] pub style_key: String,
}
```

### 4. Hull update behavior — smooth shrink/expand on add/move/resize/remove

Membership and geometry already flow through one re-clamp point; T2.4 makes that re-clamp produce a *smoothly animated* hull/bounds. Triggers and the recompute:

| Trigger | Today | T2.4 |
| --- | --- | --- |
| member **added** (`set-object-group` / create-in-frame) | frame bounds unchanged (can clip new member) | recompute `bounds` = padded union of member AABBs; grow if needed |
| member **moved** (`move-card`, batch) | bounds unchanged | recompute hull/bounds from the moved member set |
| member **resized** (`resize-card`, T2.2) | bounds unchanged | recompute |
| member **removed** (`ungroup` of a child, `set-object-group` out) | bounds unchanged | recompute; frame may shrink (empty frame → minimum size) |
| frame **transformed** (`move-group` existing, `resize-group` T2.2) | members translate with the frame (`MoveGroup` already does this) | members re-clamped inside on resize; hull follows |

The recompute is a pure function of member geometry: `hull/bounds = pad(union(member_bounds))`, computed in **core** (`build_group_vertices` already has the member set and group bounds in scope). To avoid "jarring jumps" (Verify), the *visual* hull is **eased toward** the freshly computed target over a short animation in the renderer — this is an **ephemeral animation**, not a document mutation: the canonical `SceneGroup.bounds` snaps to the computed value (one op), while the GPU hull tweens to it across frames (companion-animation-class ephemeral state, per the document/ephemeral split). No intermediate bounds are persisted; only the settled value is the document state.

Performance note: recompute is incremental — only the frames whose member set or member geometry changed re-run, keyed off the existing `dirty_group_ids` tracking that `MoveGroup`/`write_dirty_group` already maintain.

### 5. Selection and hit-testing rules — group vs member, nested, edit without regroup

Today's hit order is **cards → edges → groups** (`hit_scene_at_screen`), so a member always wins over its containing frame, and there is no notion of "entering" a group. T2.4 adds an **ephemeral active-group focus** (Figma's double-click-to-enter), keeping selection-as-focus in the ephemeral state class per the Locked Decisions.

| Rule (breakdown) | Behavior | Mechanism |
| --- | --- | --- |
| **enter a group** | double-click a frame → it becomes the *active group*; subsequent clicks select members of that frame first | new **ephemeral** `active_group_id: Option<String>` in core input state (never in `Scene`); click-away or Escape clears it |
| **select the group vs a member** | with no active group: single-click a frame body selects the **frame**; click a member selects the **member** (members already win in hit order). With a frame active: clicks prefer members of that frame | hit order stays cards→edges→groups; the active-group focus only changes which *frame* a bare frame-body click resolves to and gates create/membership |
| **select nested groups** | click cycles outward: click selects deepest enclosing frame; click again (or Escape) selects its parent | "deepest enclosing frame" = the frame with the smallest area whose `bounds`/`hull` contains the point; parent via `parentGroupId` |
| **edit a member without accidental regrouping** | dragging/resizing/text-editing a member never changes its `groupId` unless the drag **exits** the frame with a clear gesture (§6) | membership only changes via `set-object-group` / drag-out threshold; in-frame edits emit `move-card`/`resize-card`/`edit-text` with `groupId` untouched |

Hit-test delta (core): the group branch of `hit_scene_at_screen` changes from "first frame whose `bounds` contains the point" to "**deepest** (smallest-area) frame whose `bounds`-or-`hull` contains the point", so nested selection resolves predictably. Point-in-hull replaces `point_in_rect` only when `hull` is non-empty (§3). This is the one behavioral change to the existing hit path; card/edge branches are unchanged.

### 6. Drag/drop and creation affordances

The rule: membership changes only on an **unambiguous** gesture, so editing-in-place never silently regroups (Verify: "predictable, can be undone").

| Affordance | Trigger | Resulting op | Disambiguation |
| --- | --- | --- | --- |
| **drop into a group attaches it** | drag an object so its center (and majority of its AABB) ends inside a frame's `bounds`/`hull` on `PointerUp` | `set-object-group{ ids, frameId }` | only fires when the object's center crosses into a frame it was not already in; hover highlight shows the target frame during drag |
| **create inside an active group includes it** | create-shape/text/edge fires while a frame is the active group (§5) or the click lands inside a frame | new object `groupId` = that frame (already T2.2 §2) | no new op; the create op's `groupId` is set from active/enclosing frame |
| **drag out detaches when the gesture is clear** | drag an object so its center leaves the frame `bounds`/`hull` past an exit threshold | `set-object-group{ ids, frameId: enclosing-ancestor-or-root }` | a small hysteresis margin around the boundary prevents flicker on edge-grazing drags |

Drag-target resolution (drop into / between nested frames) reuses the §5 **deepest enclosing frame** rule. The hover highlight, drag ghost, and threshold hysteresis are **ephemeral** (shell/core input state); only the settled `set-object-group` is a document op. Modifier override (e.g. hold a key to suppress attach) is a shell modifier flag forwarded into the core input batch (T2.2 §4 `PointerModifiers`), not a schema concern.

### 7. Label / tag model — object labels, group labels, tag chips, color labels, suggested labels

Labels are **already** modeled as the `Tag` registry (`tagSchema`: `id/name/color/description/timestamps`) + `tagIds[]`, today present only on `SceneGroup`. T2.4 generalizes `tagIds[]` from frames onto **all objects** and reads the existing `color` for color chips — no new taxonomy system, no label object kind (the Stop-or-ask).

| Label form (breakdown) | Carrier | Treatment |
| --- | --- | --- |
| **object labels** (on shapes, text, edges) | add `tagIds: z.array(z.string()).default([])` to `sceneNodeSchema`/`sceneEdgeSchema` (additive, defaults `[]`) | GENERALIZE the `tagIds[]` pattern that `sceneGroupSchema` already has onto nodes/edges |
| **group labels** | `SceneGroup.tagIds` (exists) + `SceneGroup.title`/`summary` (exists, editable via T2.3 `edit-text{target:"frame"}`) | KEEP |
| **tag chips** | render of `Tag.name` + `Tag.color` on/near an object | render-only: `RenderCard`/`RenderEdge`/`RenderGroup` already carry `tagIds`; the chip is a styled badge from the registry, drawn by core like a small label run (uses `text.rs`, no new engine) |
| **color labels** | `Tag.color` (exists) | a tag whose chip renders as a color swatch; same registry, no new field |
| **template-provided suggested labels** | template seeds `Tag` registry entries + suggests `tagIds` on created objects | template/preset metadata (T4.x); T2.4 only requires that any object can carry `tagIds`, so a template can pre-tag — no special path |

Tag-mutation ops (generalize the existing frame-only `update_group_tags` / `updateShapeSceneGroupTags`):

```ts
// src/shared/renderPatch.ts — generalize tag editing to any object (additive)
| { kind: "set-object-tags"; targetKind: "card" | "edge" | "frame"; id: string; tagIds: string[] }
| { kind: "create-tag"; tag: Tag }   // promote MCP create_tag into the op vocabulary so tag creation is actor-tracked
```

`set-object-tags` validates each `tagId` against the `scene.tags` registry exactly as `updateShapeSceneGroupTags` does today (`renderPatch.ts:135` "Unknown tag id" check), then upserts the object with the new `tagIds`. For `targetKind:"frame"` it is the existing `updateShapeSceneGroupTags` path; for `card`/`edge` it is the generalization. Every tag/label change is a normal operation event (Verify: "Label/tag changes produce normal operation events") — it flows through `commitAppPatch`, bumps `sceneVersion`, and carries a T2.5 envelope.

MCP surface (`src/server/mcp.ts`): `update_group_tags(groupId, tagIds)` is **kept** as a thin alias over `set-object-tags{targetKind:"frame"}`; `create_tag` maps to the `create-tag` op. No MCP contract is broken; the generalization is additive.

### 8. Label appearance across zoom levels — degradation, not semantic replacement

The Locked Decision: good LOD is *visual degradation with stable identity*, never semantic-replacement-on-zoom. Labels follow the **existing** `SceneStyleToken.states.compact` LOD seed (T2.1 §6, T3.1 owns the full policy) — the same object keeps the same id and position; only label *presentation* thins out as zoom decreases.

| Zoom band | Object label (tag chips / object text) | Group label (frame title / chips) | Identity |
| --- | --- | --- | --- |
| near (full) | full tag chips with name + color, all object text | frame title + summary + chips | stable id, stable position |
| mid (compact) | color swatch only (drop tag name text), title only | frame title only, color chips collapse to a count/swatch | unchanged id |
| far (minimal) | chips collapse to a single color band or hide; object reduces to its shape fill | frame shows a single title or just its hull outline + color | unchanged id |

This is purely a **render-time presentation choice** driven by the camera zoom and the `compact` style state — the canonical `tagIds`, `title`, and object identity are untouched at every band. No object is replaced by a different object at any zoom (the explicit non-goal). The thinning order (name → swatch → hidden) is a style/LOD rule the core applies; it adds **no** schema field and **no** new op. T3.1 owns the numeric thresholds; T2.4 only fixes that labels participate in the *same* visual-degradation LOD as the rest of the object, not a parallel regime.

### 9. Migration note — old project/Shape labels and ADR fields into generic labels/text/metadata

Per T2.1 §3 (Shape/project + ADR removal) and the Locked Decisions, the old structured identifiers become generic labels/text/`meta`, not a privileged hierarchy.

| Old concept | Lives today | Migrates to | Mechanism |
| --- | --- | --- | --- |
| Shape/project name/label | implicit "project = the `Scene`"; `migrateLegacyDesign` → `SceneGroup` | top-level `frame.title` + an optional project `Tag` | project becomes an ordinary frame (T2.1 §3); its name is the frame title, no privileged group type |
| ADR `nodeType` as structural label (`decision_point`/`option`/…) | `nodeTypeSchema` enum on `SceneNode` | a `meta.semanticType` (T2.1 §2) **plus** an optional status/role `Tag` chip | the visual "this is a decision" cue becomes a tag/color label, not an enum object type |
| ADR `nodeStatus` (`viable`/`infeasible`/…) | `nodeStatusSchema` enum | `meta.status` (T2.1) and/or a status-color `Tag` | status badge → tag chip with `Tag.color`; same registry |
| ADR edge semantics (`blocks`/`trades_off_with`/…) | `edgeTypeSchema` enum + `styleKey` rule (`renderScene.ts:298`) | `meta.semanticType` + edge `label` (T2.3) + optional edge `tagIds` (§7) | the `blocks→risk` styleKey rule moves to template style mapping (T2.1 §2) |
| ADR grouping by decision/task | none structural — was implied by node type | a freeform `frame` per decision, optionally tagged | nested `frame`s with arbitrary meaning (Stop-or-ask: no fixed hierarchy) |

No project/ADR-specific label *taxonomy* is created; everything lands in the one `Tag` registry, `frame.title`/text, or `meta`. This satisfies the breakdown's "Todo/wiki/ADR/server-diagram templates can use the same labeling model" — all four read `tagIds` + `Tag` + `title`, never a template-private label system.

### 10. Core-vs-shell placement and the additive delta summary

Per "grouping hull geometry, hit testing, selection geometry, render primitive generation, input batching" belong in **Rust core**:

| Concern | Home |
| --- | --- |
| hull computation (`pad(union(member_bounds))`), point-in-hull, deepest-enclosing-frame, hull tween, group re-clamp on member change | **Rust core** (`webgpu.rs` near `build_group_vertices`/`hit_scene_at_screen`/`MoveGroup`) |
| active-group focus, drag-into/out-of-frame threshold + hover highlight, modifier capture | **core ephemeral input state** + shell-forwarded DOM modifier flags (T2.2 §4) — never in `Scene` |
| `group-objects`/`ungroup`/`set-object-group`/`set-object-tags`/`create-tag` op apply | **shared contract** (`renderPatch.ts`) → `commitAppPatch` → server persistence |
| group/tag toolbar, context menu, label compose UI, tag registry picker | **shell** (Svelte target; React is migration input) |

Net additive delta (no wholesale replacement, no schema break):

- **`schema.ts`**: add optional `tagIds: z.array(z.string()).default([])` to `sceneNodeSchema` and `sceneEdgeSchema` (default `[]`, back-compat). Add optional `meta` consumers `meta.hullMode` (already in the T2.1 `meta` bag — no new column). **No** new table, **no** `ALTER TABLE` (tag arrays live inside `node_json`/`edge_json` like all other non-geometry fields, per T2.1 §5).
- **`renderScene.ts` / `model.rs`**: `RenderGroup` gains optional `hull` (render-only, `#[serde(default)]`); `RenderCard`/`RenderEdge` already carry no `tagIds` field → add render-only `tagIds: string[]` projection for chips (mirrors `RenderGroup.tagIds`). No selection/snapshot restructure.
- **`renderPatch.ts` / `model.rs` op union**: add `group-objects`, `ungroup`, `set-object-group`, `set-object-tags`, `create-tag` (5 additive ops). `renderGroupToSceneGroup` gains `parentGroupId` passthrough (today hardcoded `null` at `renderPatch.ts:274`) so nested-frame creation works.
- **Root-frame note**: because `SceneNode.groupId` is **required**, ungroup/drag-out at the top level must re-point members to *some* frame. The scene already guarantees a containing frame for every node; top-level ungroup re-points to the frame's `parentGroupId`, and a frame at depth 0 (whose `parentGroupId` is `null`) cannot be ungrouped into "no frame" — it can be deleted or its members moved, but a node never becomes group-less. This is a deliberate consequence of the required-`groupId` invariant and is called out so T2.5/T6.1 own any future "root canvas as implicit frame" relaxation. **Decision flagged, not silently chosen** (see Stop-or-ask).
- **`SceneSelection`**: unchanged. Frame selection = `{kind:"group"}`, member = `{kind:"node"|"edge"}`. Multi-select set stays ephemeral-core (T2.2 §3-B); no `Multi` variant added here.

## Open questions / risks

- **Required `groupId` vs "objects on the bare canvas."** Because `SceneNode.groupId` is required, there is no truly group-less object; top-level ungroup/drag-out re-points to the frame's `parentGroupId` and a depth-0 frame cannot dissolve into "no frame" (§10). If product wants objects floating directly on the root canvas, model the root canvas as an *implicit root frame* (every scene gets one) — a deliberate decision flagged for T2.5/T6.1, not silently made here. This is the one place the required-`groupId` invariant constrains the UX.
- **Membership = AABB-center vs hull containment.** §6 attaches on center-in-frame; with freeform hulls, "inside" can mean inside the `bounds` AABB or inside the tighter `hull` polygon. Recommend membership uses the canonical **`bounds` AABB** (stable, cheap) and the hull is purely visual, so attach/detect does not depend on the eased hull animation — confirm with T3.1's LOD/hit policy.
- **Tag-chip render budget.** Generalizing `tagIds[]` onto every card/edge means many small text/color runs at scale; chip rendering must respect the §8 LOD thinning (swatch-only at mid zoom, hidden at far) and the culling path so tag chips do not regress the large-scene pan/zoom budget (P3). Flagging as a P3 interaction, not a T2.4 schema concern.
- **`ungroup` vs `delete-group` discoverability.** Both verbs exist (non-destructive vs cascade-destructive). The UI must make the distinction obvious (Ungroup keeps objects, Delete removes them) so users do not lose work; a copy/affordance concern for the shell, not the contract.
- **Edge membership when endpoints span frames.** An `edge.groupId` may differ from its endpoints' frames after a member moves between frames. Current `commitAppPatch` keeps the edge valid as long as both endpoint nodes exist; the policy for which frame an inter-frame edge "belongs" to (source frame vs nearest common ancestor) is a one-line choice in `set-object-group` translation — defaulting to the source node's frame; flag for review.
