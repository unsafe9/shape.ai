# T0.3 Plan Target Layout Placement

> Phase P0 (Product And Package Contract), Wave A. Design-only pass: no production code is written, moved, or scaffolded. This fragment turns the boundary decision into a concrete placement plan; it does not run a migration.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (T0.3 Deliverable/Verify/Stop-or-ask, "Repo Layout Planning", "Locked Decisions", P0 review gate); boundary inventory in `docs/design/ai-companion-canvas/tasks/T0.1.md`; real build config `package.json` (scripts), `vite.config.ts`, `tsconfig.json`, `tsconfig.server.json`, `vitest.config.ts`, `scripts/renderer-toolchain.sh`, `index.html`, and the observed `src/` tree.

## Outcome

A reviewer-approvable placement plan that **keeps the current `src/` layout and evolves it in place**. The migration map is mostly no-op: existing paths stay where they are, the new P1–P6 responsibilities land in the directories that already own that boundary, and the few changes are internal-ownership cleanups rather than directory moves. Because nothing moves in this pass, the import/build/test churn that a top-level reorg would trigger is recorded as *avoided* (impact now = none), and the build couplings that a future move would have to re-point are documented so a later migration task can cost itself accurately.

## Decision (the layout that was chosen)

**Keep `src/` and evolve in place.** This selects option 1 from the breakdown's "Repo Layout Planning" list ("existing `src/` structure를 유지하고 내부 ownership만 정리한다") and is consistent with the T0.1 finding that the primitive/template seam already exists inside the current contracts — the boundaries P1 needs (`core`, `web adapter`, `app shell`, `shared contracts`, `server`) are *already* expressed as directories. The repo shape `src/renderer/core` (Rust core) + `src/client/renderer` (web adapter) + `src/client` (web shell) + `src/shared` (contracts) + `src/server` (API/MCP) is exactly the four-port boundary the Objective asks for, minus only the not-yet-existing native adapter. There is no portability or ownership problem that a reorg would solve, so per the breakdown ("build/test/import path churn이 migration risk를 정당화해야 한다") the churn is not justified. Top-level packages and a separate web-shell location are explicitly deferred (see §3, Deferred).

### 3. Import / build / test impact note

Because the layout is kept, **impact now = none**. No script, config, entry, or test path changes. The value of this section is the *coupling inventory*: the exact references a FUTURE move (top-level packages, or relocating the web shell at Svelte time) would have to re-point. Each is grounded in the real config.

| Coupling | Where it lives (real config) | What a future move would have to re-point | Impact this pass |
| --- | --- | --- | --- |
| WASM build out-dir | `package.json` → `renderer:wasm:build`: `wasm-pack build src/renderer/core --out-dir ../../client/renderer/wasm` (relative to the crate dir → `src/client/renderer/wasm`) | the `--out-dir` relative path if either the core crate **or** the web adapter moves | **none** (both stay) |
| WASM presence check + copy | `vite.config.ts` `copyRendererWasm()`: reads `src/client/renderer/wasm`, copies to `dist/client/assets/wasm` | both source and dest paths if the adapter or build outDir moves | **none** |
| Vite HTML/JS entry | `index.html` → `/src/client/main.tsx`; `vite.config.ts` `build.outDir: dist/client` | the entry path if `src/client` relocates | **none** |
| Server TS project includes | `tsconfig.server.json` → `include: ["src/server", "src/shared"]`, `outDir: dist-server` | both includes if server or shared move | **none** |
| Root TS project includes | `tsconfig.json` → `include: ["src", "tests", "vite.config.ts", "vitest.config.ts"]` | the `src` glob only if top-level packages replace `src` | **none** (whole-`src` glob already covers in-place growth) |
| Test discovery | `vitest.config.ts` → `include: ["tests/**/*.test.ts"]`; `package.json` `renderer:test` pins `tests/infinite-canvas-renderer.test.ts` | the `tests/**` glob and the pinned renderer-test path if tests relocate | **none** |
| Rust test/build manifest | `package.json` `renderer:rust:test` / `renderer:wasm:build` → `--manifest-path src/renderer/core/Cargo.toml` (and crate name `shape_canvas_core`) | the manifest path if the crate moves | **none** |
| Toolchain shim | `scripts/renderer-toolchain.sh` (resolves repo root relative to its own dir) | nothing unless `scripts/` itself moves | **none** |

Net: every changed line a migration would require traces to one of the eight couplings above. This pass changes zero of them, so `npm run build` (`renderer:wasm:build && vite build && tsc -p tsconfig.server.json`), `npm test`, and `npm run typecheck` keep working unchanged — satisfying the breakdown's "build/test commands remain available" expectation by construction.

### 4. Rule for placeholder directories

Binding rules for this plan and every P1–P6 task that follows it:

1. **No empty scaffold directories.** A directory is created only in the same change that lands a real file in it. An empty `src/native/`, `src/renderer/metal/`, `src/templates/`, or `packages/*` directory is forbidden as a way to "reserve" a boundary.
2. **A directory is never an architecture decision.** Naming a future home (e.g. the Metal adapter location) is documentation, not commitment. The boundary is committed by the approved *contract* (T1.x) and the file that implements it, never by a folder existing.
3. **No build config may import or reference a future path before the task that owns it.** No `tsconfig` include, no `vite` alias/entry, no `package.json` script, and no Rust manifest path may point at a directory that does not yet contain its owning task's real file. This is what keeps `renderer:wasm:build`'s `--out-dir`, the `vite` copy plugin, and the `tsconfig` includes honest: they reference only paths that exist and are owned now.
4. **Build outputs are not source placeholders.** `src/client/renderer/wasm` exists but is generated (`.gitignore = *`); it does not count as a hand-authored directory and is never used to stand in for an architecture decision.
5. **The P0 review gate approves the layout, not folders.** Per the P0 `human-decision` gate, the target layout and boundary names are approved as text here; no folder is created to represent that approval until P1+ lands code.

## Notes / forward pointers

- **When a move could become justified.** Two future triggers, both deferred and owned elsewhere: (a) the Svelte migration (T6.2) may relocate or rename `src/client` if it cleanly separates Svelte shell from React removal; (b) a real Metal adapter (T1.3) introduces the first native directory. Either move re-prices itself against the §3 coupling inventory; neither is committed here.
- **Build-output directory hygiene.** `src/client/renderer/wasm` is the one path that "exists but is not source." Keeping it ignored (`.gitignore = *`) and regenerated by `renderer:wasm:build` is what lets the keep-in-place plan claim zero source movement while the adapter still consumes the crate's output at a stable relative path.
- **Why not promote `src/renderer/core` + `src/client/renderer` to top-level packages now** (breakdown option 2/3): the boundary is already legible as directories and the contracts (T1.1/T1.2) carry the real ownership weight; promoting to packages would add a workspace manager, project references, and eight re-pointed couplings for no portability gain the contracts don't already provide. Revisit only if a native target or independent versioning makes the package boundary load-bearing.
