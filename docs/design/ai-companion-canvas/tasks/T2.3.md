# T2.3 Text On Everything

> Phase P2 (Universal Primitive Editing Slice), Wave D. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P2 intro, T2.3); `docs/rust-canvas-replacement-task.md` (P4 HarfBuzz-grade text, P5 input overlay — the binding text-quality gates); upstream `docs/design/ai-companion-canvas/tasks/T2.1.md` (primitive model, the "text on everything" cross-cutting capability in §1).
> Real symbols grounded in: `src/renderer/core/src/text.rs` (single shaping engine), `src/renderer/core/src/webgpu.rs` (`build_card_vertices`/`build_edge_vertices`/`build_group_vertices`, `card_text_layout`, `text_field_at_point`, `overlay_request_for_card`, `hit_scene_at_screen`, `overlay_max_lines`), `src/renderer/core/src/stats.rs` (`CoreHitResult`, `CoreOverlayRequest`, `CoreOverlayTarget`, `CoreOverlayStyle`), `src/shared/renderScene.ts` (`SceneTypographyToken`), `src/shared/renderPatch.ts` (`RenderScenePatch`, `edit-card-text`), `src/shared/schema.ts`.
> Relationship to T2.1: T2.1 §1 already declared "text on everything" a single cross-cutting capability over one engine, and reserved the shared text fields (`title`/`summary`/`detail` on `shape`, `label` on `edge`, `title`/`summary` on `frame`, `body` on `comment_marker`, free-standing `text`). T2.3 turns that reservation into the **attachment model + editing behavior**: it wires the already-rendered-but-not-editable text (edge labels, frame titles) into the same hit → overlay → op → shape path the card fields use today, with zero new text engine and no schema break.

## Outcome

Make label/text a shared capability across every primitive — `shape` (title/summary/detail), `edge` (label), `frame` (title/summary), `comment_marker` (body), and `image_artifact` (caption) — by generalizing the **one** existing card-only edit path (hit `field` → `CoreOverlayRequest` → `edit-card-text` op → shape mutation) to a target-kinded path, all flowing through the single `text.rs` shaping engine, so the renderer-replacement text-quality gates apply uniformly with no per-primitive text engine.

## Deliverable

The breakdown's T2.3 Deliverable has two bullets: a **text attachment model** for shapes/edges/frames/comments/artifact previews (§1), and **editing behavior** for direct text / edge labels / shape labels / frame titles (§2). §3 states the single-engine invariant that satisfies the Verify gates; §4 gives the field-by-field contract sketches (real symbols); §5 lists the exact code seams to evolve vs. add.

### 1. Text attachment model — one capability, five attachment sites, zero new engines

Text is **not** a primitive kind; it is a **named field slot on a primitive**, projected into renderable glyphs by the same engine. T2.1 §1 already established this; T2.3 fixes the canonical attachment table that every later task reads from.

| Primitive (T2.1 kind) | Real carrier symbol | Text field(s) | Renders today via | Single-line vs wrapped | Currently editable? |
| --- | --- | --- | --- | --- | --- |
| `shape` (incl. box-less `text`) | `SceneNode` → `RenderCard` | `title`, `summary`, `detail` | `build_card_vertices` → `add_text_line` (title) + `add_wrapped_text` (summary/detail) | title 1 line, summary ≤3, detail ≤6 (`card_text_layout`) | **Yes** (card-only path) |
| `edge` | `SceneEdge` → `RenderEdge` | `label` | `build_edge_vertices` → `add_text_line` in an `add_edge_label_capsule` | single line, ellipsized at `label_max_width = 180.0` | **No** — render-only |
| `frame` (group) | `SceneGroup` → `RenderGroup` | `title`, `summary` | `build_group_vertices` → `add_text_line` (title) + `add_text_line` (summary) | single line each | **No** — render-only |
| `comment_marker` | `SceneComment` | `body` | app/shell overlay (not a GPU primitive; T2.1 §1) | wrapped in overlay | Yes, but via `addShapeSceneComment` (app layer), not the canvas overlay path |
| `image_artifact` | `SceneArtifact` placed as a `shape` (T2.1 §1) | `title` (caption) | rides the `shape` `title` slot of its placement card | 1 line | Yes (as a `shape` card) — no new path |

Two structural facts make this an evolution, not a new model:

- **All five already shape through one engine.** `build_card_vertices`, `build_edge_vertices`, and `build_group_vertices` *already* call the same `add_text_line` / `add_wrapped_text` helpers, which call `TextLayoutCache::text_line` / `wrap_lines` on the single `TextEngine` (`text.rs`). There is exactly one shaping path (`rustybuzz::shape` + `fontdue` raster + grapheme font-fallback in `select_font_for_grapheme`). T2.3 adds **no** second engine — directly satisfying the T2.3 Stop-or-ask.
- **The gap is editing, not rendering.** Edge labels and frame titles are drawn but cannot be hit-as-text, cannot raise an overlay, and have no edit op. The entire "attachment" work is **plumbing those two sites into the existing card-text editing path**, generalized from card-keyed to target-kinded.

`image_artifact` caption needs no new work in T2.3: per T2.1 §1 it is a `shape` placement, so its caption is the `shape.title` slot already covered. We list it for completeness of the Deliverable's "artifact previews" bullet; it inherits the `shape` editing behavior verbatim.

### 2. Editing behavior — generalize the card-only path to a target-kinded path

Editing is already a 4-stage pipeline that exists **only for cards**. T2.3 widens each stage to carry a target kind. Stages and the exact real symbols:

```
double-click (CanvasInputEvent::DoubleClick)
  → hit_scene_at_screen  ─ produces CoreHitResult { kind, id, field }
  → overlay_request_for_*  ─ produces CoreOverlayRequest { target: CoreOverlayTarget{kind,id,field}, value, world_rect, screen_rect, style }
  → DOM input/textarea overlay (shell; P5 of renderer plan)
  → on commit: RenderScenePatch op  ─ apply_render_patch (core) + applyRenderPatchToShapeScene (shared) → SceneNode/SceneEdge/SceneGroup mutation
```

**Today** (card-only):
- `hit_scene_at_screen` sets `kind = "text"` and `field = Some(title|summary|detail)` **only** inside the card branch (`text_field_at_point`); the edge branch and group branch hard-code `field: None`.
- `DoubleClick` only raises an overlay `if hit.kind == "text"`, calling `overlay_request_for_card(hit.id, field)` whose `CoreOverlayTarget.kind` is the literal `"card-text"`.
- The only text op is `RenderScenePatch::EditCardText { id, field }` with `field ∈ {title, summary, detail}`, which mutates a `SceneNode`.

**T2.3 generalization** (additive, four edit targets):

1. **Hit testing — add field detection to edge and frame branches.** Introduce `edge_label_at_point(edge, world)` and `frame_title_at_point(group, world)` mirroring the existing `text_field_at_point(card,…)`. Set `field = Some("label")` on an edge hit when the world point is inside the label capsule rect (`add_edge_label_capsule` geometry), and `field = Some("title"|"summary")` on a frame hit inside the title/summary text rects (derived the same way `text_field_rect` derives card rects from `card_text_layout`). `CoreHitResult.field` already exists (`stats.rs:57`); only the assignment sites change. `CoreHitResult.kind` stays `"edge"`/`"group"` (identity preserved); the presence of `field` signals an editable text site — keeping selection-vs-edit disambiguation in `DoubleClick`.
2. **Overlay request — promote `overlay_request_for_card` to a target dispatcher.** Keep the existing function and add `overlay_request_for_edge` / `overlay_request_for_frame`. `DoubleClick` dispatches on `hit.kind`: `"text"|"card" → card`, `"edge" → edge` (when `field == Some("label")`), `"group" → frame` (when `field.is_some()`). `CoreOverlayTarget.kind` gains the values `"edge-text"` and `"frame-text"` alongside today's `"card-text"`. `CoreOverlayRequest`/`CoreOverlayStyle` structs are **unchanged** — they already carry `value`, `world_rect`, `screen_rect`, and full `style` tokens, so the shell overlay (P5) renders any target with one code path.
3. **`overlay_max_lines` — extend the field map.** Today `overlay_max_lines(field)` returns `title→1, summary→3, _→6`. Add `label→1` (single-line edge label) and reuse `title→1` / `summary→3` for frames. The value comes from the same per-field wrap budget the renderer uses (`card_text_layout.summary_max_lines`, edge single line, group single line), so overlay and rendered text agree.
4. **Edit op — generalize `edit-card-text` to one text op with a target.** Two equivalent shapes; recommend **(A)** to keep the op surface minimal:

   - **(A) Generalize the existing op** by widening `field` and adding an optional `target`:
     ```ts
     // src/shared/renderPatch.ts — RenderScenePatch union, evolve in place
     | { kind: "edit-card-text"; id: string; field: "title" | "summary" | "detail"; value: string }   // today
     // → generalize to:
     | { kind: "edit-text"; target: "card" | "edge" | "frame"; id: string;
         field: "title" | "summary" | "detail" | "label"; value: string }
     ```
     `card` accepts `title|summary|detail`; `edge` accepts `label`; `frame` accepts `title|summary`. Keep `edit-card-text` as a thin back-compat alias mapping to `edit-text{target:"card"}` so existing callers/tests do not break (mirrors T2.1's "evolve not break" discipline). Translation in `applyRenderPatchToShapeScene`:
       - `target:"card"` → today's `SceneNode` mutation (`nodes:[{...node,[field]:value}]`), unchanged.
       - `target:"edge"` → `SceneEdge` mutation `edges:[{...edge,label:value,updatedAt:now}]`, selection `{kind:"edge",id}`.
       - `target:"frame"` → `SceneGroup` mutation `groups:[{...group,[field]:value,updatedAt:now}]`, selection `{kind:"group",id}`.
     Validation in `validateRenderPatchForShapeScene` extends the existing membership checks: `target:"edge"` must hit `scene.edges`, `target:"frame"` must hit `scene.groups`.
   - **(B)** Add sibling ops `edit-edge-label` / `edit-frame-text` if a reviewer prefers narrow ops over a discriminated `target`. Same translations. (A) is preferred because T2.5 wraps **one** text op in actor/operation metadata rather than three.

   Core side: `apply_render_patch` already has the `EditCardText` arm (`webgpu.rs:957`) mutating `card.{title,summary,detail}`; add `target:"edge"` → mutate `edge.label` + mark `dirty_edge_ids`, `target:"frame"` → mutate `group.{title,summary}` + mark `dirty_group_ids`. The dirty-tracking and rebuild machinery (`write_dirty_edge`, `write_dirty_group`) already exists.

**Direct text (free-standing `text` primitive).** Per T2.1 §1/§4, a free-standing `text` is a box-less `shape` (style omits surface/stroke). Its editable field is `title` (single visible run) on the same `shape` path — no new behavior, just a `styleKey` (e.g. `"text-plain"`) and the existing card title overlay. Box-less hit/selection nuance is the only open item (Open questions), and is explicitly deferred by T2.1 unless proven needed.

### 3. Single-engine invariant (the Verify-gate guarantee)

The renderer-replacement plan's text-quality gates (P4 Verify: "Tests cover Korean, Latin, punctuation, mixed text, no-space long text, multiline summaries, edge labels") are satisfied **for every attachment site automatically**, because all five sites funnel into the same engine that those gates already exercise:

- `text.rs::wrap_text_lines` → grapheme-level break for no-space CJK (`append_wrapped_segment` falls back to `graphemes(true)` when a segment exceeds `max_width`) — covered by `wrapped_lines_break_no_space_korean_and_add_ellipsis`.
- `text.rs::shape_run_positions` → `rustybuzz::shape` per font-run, with per-grapheme font selection (`select_font_for_grapheme`) for mixed Latin/CJK — covered by `shaped_line_tracks_font_fallback_cjk_and_atlas_cache` and `shaped_line_handles_latin_punctuation_without_fallback`.
- Card/edge/group emit paths already assert shaped output: `multiline_card_summary_uses_shaped_text_path`, `edge_label_uses_shaped_text_path`, `detail_card_text_uses_shaped_text_path_and_hit_rect`, `wrapped_summary_uses_shaped_ellipsis`.

Because edge labels and frame titles **already** go through `add_text_line` → `text_line` → `shape_visible_line`, the *quality* gates hold today; T2.3 only adds the *editability* of those sites, and the new edge/frame overlay+op tests assert that edited values re-shape through the same path (extending the `*_uses_shaped_text_path` test family to the edge-label-edit and frame-title-edit cases). No new shaping code, no per-primitive engine.

## Verify

The breakdown's single Verify bullet: *"Korean, mixed text, multiline, no-space long text, and labels on edges/shapes pass the same text-quality gates as the renderer replacement plan."*

| Aspect of the Verify bullet | Status | How the design satisfies it |
| --- | --- | --- |
| Korean / mixed Latin+CJK / punctuation | **MET** | §3: every site funnels into `text.rs::shape_run_positions` (`rustybuzz::shape` + per-grapheme `select_font_for_grapheme`), the exact path covered by `shaped_line_tracks_font_fallback_cjk_and_atlas_cache` and `shaped_line_handles_latin_punctuation_without_fallback`. No site bypasses it. |
| Multiline (summaries) | **MET** | Card summary/detail use `add_wrapped_text` → `wrap_lines` (covered by `multiline_card_summary_uses_shaped_text_path`, `wrapped_summary_uses_shaped_ellipsis`). T2.3 adds no new wrap logic. |
| No-space long text | **MET** | `wrap_text_lines` grapheme-break fallback (`append_wrapped_segment`) is engine-level, covered by `wrapped_lines_break_no_space_korean_and_add_ellipsis`. Applies to any wrapped site. |
| Labels on **edges** | **MET (render) / extended (edit)** | Edge labels already shape through `add_text_line` (gate `edge_label_uses_shaped_text_path`). T2.3 adds the edit path (§2 stages 1–4); the new edge-label-edit test asserts the edited value re-shapes through the same path. |
| Labels on **shapes** (title/summary/detail, incl. frame titles) | **MET** | Shape fields already editable+shaped (`detail_card_text_uses_shaped_text_path_and_hit_rect`); frame titles already shaped, gain editing via the same generalized path. |
| "**same** text-quality gates" (one engine, no per-primitive engine) | **MET** | §1/§3/§5: single `TextEngine`; T2.3 adds no shaping code and no second engine, so the renderer-plan P4 gate set applies uniformly — this is also the explicit guarantee against the T2.3 Stop-or-ask. |

All gate facets are MET at the design level; the only net-new test surface is "edited edge-label / edited frame-title re-shapes through the engine," which extends the existing `*_uses_shaped_text_path` family rather than adding a parallel quality regime.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Label behavior requires a separate text engine per primitive type. | **CLEAR (not triggered)** | §1 and §3 show all five attachment sites already route through the single `text.rs` `TextEngine`/`TextLayoutCache` via shared `add_text_line`/`add_wrapped_text` emit helpers. T2.3 adds editing plumbing (hit `field`, overlay dispatch, one generalized `edit-text` op) and **zero** shaping/layout/font code. There is no per-primitive text engine, and the design's central invariant is that one never appears. If a future requirement (e.g. rich inline runs per primitive) forced a divergent engine, that would trip this condition and require a decision — none is present in the title/summary/detail/label/body scope here. |

## Open questions / risks

- **Box-less `text` hit/selection.** A free-standing `text` (box-less `shape`) overlaps card hit-testing assumptions (`point_in_rect` on `bounds`). T2.1 deferred promoting `text` to its own kind until T2.2/T2.3 prove distinct hit/selection/resize rules are needed. If a near-zero-surface `text` is hard to click/select reliably, raise a minimum-hit-padding rule (ephemeral) rather than a new primitive kind — confirm in T2.2/T2.4.
- **Edge label is single-line + ellipsized (`label_max_width = 180.0`).** Editing a long edge label shows full text in the overlay but renders ellipsized. This matches today's behavior and the `overlay_max_lines("label")→1` choice; flag whether product wants multi-line edge labels (would mean `add_wrapped_text` for edges + an overlay textarea), which is out of T2.3 scope unless required.
- **Comment `body` editing path divergence.** Comments edit via `addShapeSceneComment` (app layer), not the canvas `edit-text` op, because `comment_marker` is not a GPU primitive (T2.1 §1). This is intentional but means comment edits do not yet emit the same `RenderScenePatch` op; T2.5's operation model must decide whether comment edits get a unified op envelope — noting here so it is a deliberate T2.5 decision, not an oversight.
- **`edit-card-text` alias lifetime.** Keeping `edit-card-text` as an alias for `edit-text{target:"card"}` avoids breaking existing tests/MCP callers now; the eventual removal of the alias belongs to T2.5/T6.1 (op-model + compatibility), not here.
