## Outcome

Recommend **evolve the existing `Scene` schema in place** (additive `meta` + `proposals` + the existing `events` log), not a new canonical object model: the demote/generalize work the upstream tasks specify is a backward-compatible JSON-shape change with no `ALTER TABLE`, every MCP/API/export/comment flow keeps its contract, and the local-first SQLite store migrates through the codebase's own gated `migrateLegacy*` / `scene_layout_version` precedent with an idempotent recovery path.

## Deliverable

T6.1 has three Deliverable bullets: the **compatibility report verdict** (§1, with the three-option comparison the breakdown names), the **SQLite migration note for operation metadata / base revisions / actor records / document-vs-ephemeral boundaries** (§2), and the **removal/demotion migration note for old Shape/project + structured-ADR components** into generic primitives/labels/template metadata/export presets (§3). §4 gives the per-flow MCP/API/export/comment compatibility table (the binding Verify). §5 gives the SQLite recovery path (the Stop-or-ask). ### 1. Compatibility report: evolve in place vs. add a primitive layer vs. new canonical model

The breakdown asks for a verdict among three options. The decision is forced by one fact: **the decision-graph identity already lives only in two Zod enums and a handful of business fields inside JSON blob columns — never in the geometry, the tables, or the render/core contract** (`nodeToCard`/`edgeToRenderEdge` consume `type`/`status` as opaque `styleKey` inputs only; `excludedBusinessFields()` already lists `Node.confidence`/`evidenceRefs`/`childDecisionIds`/`Edge.confidence`/`rationale`). So "make the model universal" is a **demotion of fields into a `meta` bag**, not a structural rebuild.

| Option | What it means | Cost | Verdict |
| --- | --- | --- | --- |
| **A. Evolve `Scene` in place** (recommended) | Add optional `meta` to `graphNode`/`graphEdge`/`sceneGroup`; add optional `Scene.proposals`; relax the three enums to optional-with-back-compat; route every write through the T2.5 `OperationEnvelope` into the existing `events` table. | Additive Zod changes; one JSON-reshape migration (no `ALTER TABLE`); first-ever `INSERT INTO events`. | **CHOOSE.** Lowest churn, no schema break, reuses the existing `migrateLegacy*`/`scene_layout_version` machinery, keeps every MCP/API wire contract (§4). |
| **B. Add a parallel primitive layer** | New `primitiveKind` tables/types beside `nodes`/`edges`/`groups`, dual-write, adapter between old and new. | Two canonical models to keep in sync; dual persistence; every flow forks. | **REJECT.** Pure overhead — Option A already yields universal primitives because the existing `SceneNode`/`SceneEdge`/`SceneGroup` *are* the `shape`/`edge`/`frame` primitives once the enums demote (T2.1 §1). A parallel layer buys nothing the `meta` bag does not. |
| **C. New canonical object model** | Redesign `Scene` around `PrimitiveKind`, rewrite storage, MCP, export, render adapters. | Full rewrite of storage + MCP + export + render contract; breaks persisted data; breaks the wire surface. | **REJECT.** Trips the T2.1 and T6.1 Stop-or-ask ("schema must be broken instead of evolved" / "break existing local SQLite data without a recovery path"). The render/core contract (`SceneSnapshot`, `RenderObjectKind`, `model.rs`) is already universal — a new model would rewrite the only layer that needs no change. |

**Verdict: Option A — evolve in place.** This is the production commitment behind T0.1/T2.1's "evolve, not replace." Concretely, the net canonical delta (all upstream-owned, restated here as the production target):

```ts
// src/shared/schema.ts — the additive surface T6.1 commits to (each piece owned upstream)
export const objectMetaSchema = z.record(z.string(), z.unknown()).default({});         // T2.1
// graphNodeSchema  += meta; type/status/confidence/evidenceRefs/childDecisionIds -> demoted (parseable, not canonical)
// graphEdgeSchema  += meta; type/rationale/confidence -> demoted
// sceneGroupSchema += meta (frame template metadata)
// sceneSchema      += proposals: z.array(sceneProposalSchema).default([])             // T2.5 minimal slot
// nodeTypeSchema / edgeTypeSchema / nodeStatusSchema -> relaxed to optional (the relax T2.1 deferred to here)
```

The one piece of net-new work T6.1 *owns* (vs. merely ratifying upstream): the **enum-relax timing**. T2.1 §4 explicitly retained `nodeTypeSchema`/`edgeTypeSchema`/`nodeStatusSchema` as required-with-default through P2 and "the eventual relax-to-`.optional()` happening in T6.1's compatibility pass." T6.1 confirms: relax the three enums to `.optional()` here, gated behind the same migration that backfills `meta`, so legacy data keeps redundant enum + `meta` values and new objects may omit the enum entirely. Until the relax lands, P2–P5 work because new objects carry both.

### 2. SQLite migration note — operation metadata, base revisions, actor records, document-vs-ephemeral boundaries

The local-first store is `sql.js` in `src/server/storage.ts`. The compatibility-critical fact: **every demoted field already lives inside a JSON blob column, and every state-boundary slot already has a home** — so the migration is a JSON reshape plus first use of the `events` table, with zero column changes and zero index changes.

#### 2.1 Operation metadata + base revisions → the existing-but-unused `events` table

```text
events(id TEXT PRIMARY KEY, type TEXT NOT NULL, payload_json TEXT NOT NULL, created_at TEXT NOT NULL)
```

This table is created by `createSchema` (storage.ts:433) and is **genuinely unused today** — `grep` finds no `INSERT INTO events` / `FROM events` anywhere in `src/`. T2.5 §5 is the design that fills it; T6.1's migration note is the production wiring:

- **operation metadata** (`operationId`/`actorId`/`actorType`/`clientId`/`targetIds`/`timestamp`/`baseRevision`/`sourceToolCall`) is the T2.5 `OperationEnvelope`, serialized whole into `events.payload_json`; `events.id = operationId`, `events.type = patch.kind` (the verb), `events.created_at = timestamp`. **No `ALTER TABLE`** — the four existing columns hold the envelope.
- **base revisions** map to the existing `scene_version` metadata key (`getSceneVersion`/`bumpSceneVersion`, storage.ts:865–870). `baseRevision` = `getSceneVersion(db)` read *before* apply; the committed op then `bumpSceneVersion`s. Already the conflict-detection hook, present and recorded, unused for merge (the deferred realtime path).
- **write atomicity**: the `events` row is appended **inside the same `withWritableDb` block** that applies the patch and bumps `scene_version` (the `saveScenePatch`/`addComment`/`addArtifact` transactions at storage.ts:155–175, 244–262, 293–311), so an applied document op and its log row commit or roll back together.

Migration for existing stores: none needed for the log itself — the `events` table is empty, so history simply *starts* at the first post-migration op. No backfill of synthetic historical ops is required (and none should be invented).

#### 2.2 Actor records

There is no actor table today (`SceneComment.author` is a free string defaulting `"human"`, schema.ts:136; `addArtifact` records no actor). T6.1 confirms the T2.5 decision: **do not add an actor/users table** (that direction is the deferred realtime/remote-auth path, an Explicit Non-Goal). Actor identity is carried per-operation in the `events` envelope (`actorId`/`actorType`/`clientId`), not in a normalized table:

- shell writes: `actorType:"human"`, `actorId:"human"`, `clientId:"local-shell"`.
- MCP writes: `actorType:"mcp"`, `sourceToolCall:{tool}`, `clientId` from the session — **placeholder `"mcp-unknown"` until P5/T5.1** surfaces a stable `StdioServerTransport` client id (the T5.1 Stop-or-ask, not T6.1's). T6.1 only requires the fields exist in the row.
- migrations/repairs: `actorType:"system"`.

This keeps actor identity local-first and collaboration-ready (the envelope is the exact shape a future transport would stream) without building remote-user infrastructure.

#### 2.3 Document-vs-ephemeral boundary in SQLite

The boundary is already partly physical in the store; T6.1's note makes it the committed rule:

| State | Lives in (real carrier) | Migration action |
| --- | --- | --- |
| document: objects/text/geometry/style/`meta` | `nodes.node_json` / `edges.edge_json` / `groups.*` + denormalized `x,y,width,height,z_index` | JSON reshape only (§3 below); geometry columns and `idx_nodes_bounds` untouched. |
| document: comments / artifacts / proposals | `comments` / `artifacts` tables; `proposals` ride `Scene.proposals` (additive, default `[]`) | comments/artifacts unchanged; proposals are a new optional array, no table needed for the minimal slot (T2.5 §3). |
| document: revision | `scene_version` metadata key | unchanged. |
| document: history | `events` table | first use (§2.1). |
| **ephemeral: selection** | `selection_json` metadata key (storage.ts:171,462,579) **and** `Scene.selection` (dual today) | **correction**: designate `selection_json` (a metadata key, **not** a revision) authoritative-ephemeral; stop the `select`/`set_selection` path from `bumpSceneVersion` (T2.5 §4). `Scene.selection` retained for renderer/back-compat as a projection. No schema break (it stays in `sceneSchema`). |
| ephemeral: camera/hover/tool/follow/companion/read-cursor/trace | not in SQLite at all (`SceneSnapshot.camera` is render-time; the rest is core/shell) | none — already correctly outside the store. Resetting any of them touches no row. |

The single existing seam that crosses the boundary is selection (it currently both persists to `selection_json` *and* bumps `scene_version` through `commitAppPatch`). The migration's only behavioral correction is to stop the version bump on selection-only writes; this is what makes "ephemeral viewport/follow/hover/selection can be reset without changing persisted document state" true in production.

#### 2.4 The migration mechanism — reuse the codebase's own precedent

The store already has two gated, idempotent migration mechanisms; the `meta`/enum-relax reshape reuses them rather than inventing a new one:

- `prepareLegacyTables` + `renameTableIfPossible` (storage.ts:447–458) rename incompatible old tables aside on open.
- `migrateLegacyDesignsIfNeeded` → `migrateLegacyDesign` (storage.ts:465–565) one-shot-converts an old `designs` snapshot blob into `groups`/`nodes`/`edges`/`comments`/`artifacts` rows, gated on "no groups yet."
- `repairSceneLayoutIfNeeded` gated on `scene_layout_version === layoutRepairVersion` (`"11"`, storage.ts:885,927–931) — the exact precedent for a **versioned, run-once, idempotent reshape** keyed off a `metadata` version string.

T6.1's migration is modeled on `repairSceneLayoutIfNeeded`: a `scene_meta_version` (or bumped `scene_layout_version`) gate that, when stale, walks `nodes`/`edges` rows, parses `node_json`/`edge_json`, moves `type`/`status`/`confidence`/`evidenceRefs`/`childDecisionIds` (nodes) and `type`/`rationale`/`confidence` (edges) into a `meta` object, re-`toJson`s the blob, and stamps the version. Because `objectMetaSchema` defaults `{}` and the enums relax to optional, **a store that never runs the migration still parses** (old `node_json` with top-level `type`/`status` validates; new readers read `meta` first, falling back to the legacy top-level field during a transition window). This is what keeps the migration non-destructive and resumable.

### 5. SQLite recovery path (the Stop-or-ask)

The migration is non-destructive by construction, but T6.1 owns the explicit recovery guarantees so the Stop-or-ask ("Migration would break existing local SQLite data without a recovery path") stays cleared:

1. **No destructive DDL.** The reshape is `node_json`/`edge_json` rewrites + new optional fields + first `events` use. No `ALTER TABLE`, no `DROP`, no column removal, no index change (`idx_nodes_bounds` and the denormalized geometry columns are untouched — T2.1 §5). A pre-migration store opened by post-migration code still parses (additive defaults + relaxed enums).
2. **Gated + idempotent.** The reshape runs once, gated on a `metadata` version string (the `scene_layout_version`/`layoutRepairVersion` pattern, storage.ts:885,928–931). Re-running is a no-op; a partially-applied run re-completes because moving an already-moved field into `meta` is idempotent (read `meta` first, fall back to top-level).
3. **Backup before reshape.** The store is a single `sql.js` file persisted by `persistDb`; the migration writes a one-time copy (e.g. `database.pre-meta.bak`) before the first reshaping write, so a failed migration is recoverable by restoring the file — the same "single file = trivially backupable" property the local-first design already relies on.
4. **Legacy parse retained.** `prepareLegacyTables`/`migrateLegacyDesign` stay, so even an old pre-`groups` `designs`-snapshot store still upgrades through the existing path and then through the `meta` reshape, chaining cleanly.

Because the migration only *adds* (`meta`, `proposals`, `events` rows) and *moves fields within blobs*, the failure mode is "fields not yet relocated," not "data lost" — readers tolerate both shapes during the transition window. This is what makes the path recoverable rather than a one-way break.

## Open questions / risks

- **Transition-window dual-read.** §2.4/§5 tolerate "read `meta.semanticType` first, fall back to legacy top-level `type`." This dual-read should be time-boxed (one version) and removed once the gated reshape has run on all live stores, to avoid two permanent read paths. Recommend tying its removal to the same version gate that runs the reshape.
- **`actorId`/`clientId` for MCP is placeholder until T5.1.** Per §2.2, MCP ops log `clientId:"mcp-unknown"` until `StdioServerTransport` surfaces a stable session id (the T5.1 Stop-or-ask). T6.1 only requires the field; flag so the `events` rows authored before T5.1 are knowingly under-attributed, not silently wrong.
- **`events` retention/compaction.** The append-only log grows unbounded (also flagged in T2.5). Out of scope for the compatibility decision, but a compaction/snapshot-checkpoint policy should be settled before P3 large-scene history or long-lived local workspaces, since the log now becomes the primary edit unit.
- **`Scene.selection` dual-home is transitional.** §2.3 keeps `Scene.selection` for renderer/back-compat while making `selection_json` authoritative-ephemeral. A clean removal of `Scene.selection` is breaking and is deliberately deferred (it would change the snapshot the renderer reads); flag so the dual-home is a known transitional choice, not an oversight.
- **Enum-relax sequencing vs. in-flight P2–P5 work.** §1 relaxes the three enums to optional here. If T6.1's reshape ships before some P2–P5 task still assumes a required enum, those tasks keep working (new objects carry redundant enum + `meta`), but the relax should be announced so no downstream task hard-codes a required-enum assumption after this point.
