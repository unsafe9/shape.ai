# T2.5 Collaboration-Ready Operation Model

> Phase P2 (Universal Primitive Editing Slice), Wave F. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P2 intro, T2.5); upstream `docs/design/ai-companion-canvas/tasks/T2.1.md` (primitive model + `meta` demotion + `events` table note) and `T2.4.md` (group/ungroup/label ops shaped to carry "a T2.5 envelope").
> Real symbols grounded in: `src/shared/renderPatch.ts` (`RenderScenePatch` union, `applyRenderPatchToShapeScene`, `commitAppPatch`, `addShapeSceneComment`, `updateShapeSceneGroupTags`), `src/shared/schema.ts` (`scenePatchSchema`/`ScenePatch`, `sceneSchema.sceneVersion`, `sceneSelectionSchema`), `src/server/storage.ts` (`saveScenePatch`, `events(id,type,payload_json,created_at)` table, `bumpSceneVersion`/`getSceneVersion`/`scene_version` metadata key, `selection_json` metadata key), `src/server/mcp.ts` (`patch_scene`, `set_selection`, `add_comment`, `export_group`, `StdioServerTransport`), `src/shared/renderScene.ts` (`SceneSnapshot.camera`/`selection`/`metadata`, `excludedBusinessFields()`).

## Outcome

Wrap every canonical edit — human and MCP — in one **operation envelope** carrying `operationId`/`actorId`/`actorType`/`clientId`/`targetIds`/`timestamp`/`baseRevision`/`sourceToolCall`, persisted append-only into the **already-existing but unused** `events` table, so that the existing `RenderScenePatch` ops (T2.2/T2.3/T2.4) and the `patch_scene`/`add_comment`/`export_group` MCP path all flow through the same logged operation funnel, undo/redo and trace read from that log instead of raw snapshots, and viewport/hover/follow stay strictly ephemeral — all without adding CRDT, realtime transport, remote auth, or remote cursors.

## Deliverable

The breakdown's T2.5 Deliverable has five bullets, covered in: operation vocabulary (§1), required metadata envelope (§2), document-state boundary (§3), ephemeral-state boundary (§4), local operation log + undo/redo/trace/broadcast model (§5). §6 gives the additive contract/persistence delta and the core-vs-shell placement. Nothing beyond the bullets is added; CRDT/transport/auth/cursor are explicitly out (§7 Stop-or-ask).

### 1. Operation vocabulary

The breakdown lists 17 operation verbs. Every one is an **existing or T2.2–T2.4-planned `RenderScenePatch` member** — the vocabulary already exists; T2.5 does **not** invent a parallel op set, it *names the verb taxonomy* and *wraps each member in an envelope* (§2). The verb is derived from the patch `kind`, not stored as a second field.

| T2.5 verb | `RenderScenePatch` kind(s) (real symbol) | Origin | Status |
| --- | --- | --- | --- |
| `create` | `create-card`, `create-group`, `create-edge` | `renderPatch.ts` (exists) | existing op |
| `move` | `move-card`, `move-group` | `renderPatch.ts` (exists) | existing op |
| `resize` | `resize-card`, `resize-group` | T2.2 | planned op |
| `edit-text` | `edit-card-text{field}`, `edit-text{target:"frame"\|"edge"}` | `renderPatch.ts` + T2.3 | existing/planned |
| `connect` | `create-edge` | `renderPatch.ts` (exists) | existing op |
| `multi-select` | `select` (set form) | `renderPatch.ts` `select` + T2.2 batch | existing op |
| `group` | `group-objects` | T2.4 §1 | planned op |
| `ungroup` | `ungroup` | T2.4 §1 | planned op |
| `label` | `edit-text` on object label / `set-object-tags` | T2.3 / T2.4 §7 | planned op |
| `tag` | `set-object-tags`, `create-tag` | T2.4 §7 | planned op |
| `comment` | `addShapeSceneComment` → `add-comment` op | `renderPatch.ts` (fn exists) | promote fn → op (§6) |
| `export` | new `export` op wrapping `export_group`/`addArtifact` | `mcp.ts`/`storage.ts` | promote to op (§6) |
| `accept-proposal` | new `accept-proposal{ proposalId }` op | new (§3 proposal slot) | planned op |
| `reject-proposal` | new `reject-proposal{ proposalId }` op | new (§3 proposal slot) | planned op |
| `delete` | `delete-card`, `delete-group`, `delete-edge` | `renderPatch.ts` (exists) | existing op |

Two verbs need a **new op slot** because no patch kind covers them yet:

- `comment` — `addShapeSceneComment(scene, target, body)` already exists as a *function* in `renderPatch.ts` but is not a `RenderScenePatch` member, so it bypasses the op funnel today. T2.5 promotes it to `{ kind: "add-comment"; target: SceneSelection; body: string; author?: string }` so comments produce a logged operation like every other edit.
- `export` / `accept-proposal` / `reject-proposal` — exports are produced today by the `export_group` MCP tool + `addArtifact` (storage.ts) entirely outside `commitAppPatch`; proposals have **no data model at all** (the only "proposal" references are in `excludedBusinessFields()` and `local.ts` prose). T2.5 defines the minimal op slots and the document-state proposal record (§3) so these become logged operations. The proposal *UI/diff/ghost-write* behavior is **P5/T5.4**; T2.5 only owns the operation + document-state slot.

`select` / `multi-select` is the **one verb that is a no-op on document state**: the existing `select` op routes through `commitAppPatch` and bumps `sceneVersion` today (renderPatch.ts:110), but selection is *ephemeral* per the Locked Decisions (§4). T2.5's correction: `select`/`multi-select` is logged as an operation **only when it is the carrier of a user-visible action trace** (for MCP `set_selection`), but it must **stop bumping `sceneVersion`** — it writes the ephemeral `selection_json` metadata key (already how `saveScenePatch` persists selection, storage.ts:171), not a document revision. This is the only behavioral correction to an existing op (§4, §6).

### 2. Required metadata envelope

Every operation is wrapped once, at the `applyRenderPatchToShapeScene` boundary (the single funnel all ops already pass through). The envelope is **additive** — the inner `patch` is the unchanged `RenderScenePatch`; the envelope adds the seven required metadata fields plus the optional tool-call source.

```ts
// src/shared/operation.ts (new shared contract — sketch, not implemented this pass)
export type ActorType = "human" | "mcp" | "system";

export type OperationEnvelope = {
  operationId: string;        // ulid/uuid; primary key in `events`
  actorId: string;            // "human" today; MCP client identity (P5/T5.1) later
  actorType: ActorType;       // "human" | "mcp" | "system"
  clientId: string;           // session/connection id; "local-shell" for the web shell
  targetIds: string[];        // object ids the op reads/writes (drives MCP trace + undo scope)
  timestamp: string;          // ISO-8601, matches existing `now`/`updatedAt` strings
  baseRevision: number;       // scene.sceneVersion the op was authored against (conflict-readiness)
  sourceToolCall?: {          // present only for MCP-originated ops
    tool: string;             // e.g. "patch_scene", "add_comment", "export_group"
    callId?: string;          // MCP request id when available
  };
  patch: RenderScenePatch | { kind: "add-comment"; /*…*/ } | { kind: "export"; /*…*/ }
       | { kind: "accept-proposal"; proposalId: string } | { kind: "reject-proposal"; proposalId: string };
};
```

Field-by-field derivation from real symbols (no field is invented without a source):

| Envelope field | Today's nearest value | T2.5 source |
| --- | --- | --- |
| `operationId` | none | generated at the funnel (ulid); becomes the `events.id` primary key (storage.ts:434) |
| `actorId` | `SceneComment.author` defaults `"human"` (schema.ts:136); `addArtifact` has no actor | `"human"` for shell; MCP client identity surfaced by **P5/T5.1**; T2.5 only requires the field |
| `actorType` | implicit (comment author string) | `"human"` (shell) / `"mcp"` (any MCP tool) / `"system"` (migrations, repairs) |
| `clientId` | none — `StdioServerTransport` surfaces no client id (mcp.ts:281) | `"local-shell"` for the web shell now; stable MCP session id is a **P5/T5.1 dependency** (Stop-or-ask there, not here) |
| `targetIds` | implicit in each patch (e.g. `move-card.id`, `group-objects.ids`) | derived per `kind` (table below); the field the breakdown calls out as the anti-"raw blob" guarantee |
| `timestamp` | the `now`/`generatedAt` string already threaded through `applyRenderPatchToShapeScene` and `commitAppPatch` | reuse the existing `now` argument |
| `baseRevision` | `scene.sceneVersion` (schema.ts:155) / `getSceneVersion` (storage.ts:865) | the `sceneVersion` read **before** apply; the breakdown's "base revision" / collaboration-readiness hook |
| `sourceToolCall` | none | set by the MCP layer (mcp.ts) per tool; absent for shell ops |

`targetIds` derivation (the semantic-target guarantee that keeps this from being a raw blob patch — Stop-or-ask):

| Op kind | `targetIds` |
| --- | --- |
| `create-card`/`create-group`/`create-edge` | new object id (+ `groupId` for context) |
| `move-card`/`set-card-z-index`/`edit-card-text`/`delete-card`/`resize-card` | `[id]` |
| `move-group`/`delete-group`/`resize-group` | `[id]` + cascade ids (`descendantGroupIds`, already computed in `delete-group`) |
| `group-objects`/`ungroup`/`set-object-group` | `[frameId, ...memberIds]` (T2.4 already passes `ids`) |
| `set-object-tags`/`create-tag` | `[id]` / new tag id |
| `add-comment` | the comment `target` object id (or `[]` for canvas-level) |
| `export` | scope id(s) read by the export |
| `select`/`multi-select` | selected ids (ephemeral; not a document target) |

### 3. Document-state boundary

Canonical, persisted, revision-bearing state. Everything here mutates **only** through a logged operation (§2) committed by `commitAppPatch` → `saveScenePatch`, which is the single write that bumps `sceneVersion`/`scene_version` (renderPatch.ts:259, storage.ts:173). No untracked blob overwrite path is allowed to reach it (Verify).

| Document-state slice | Real carrier | Mutated by |
| --- | --- | --- |
| canonical objects (shape/text/edge/frame geometry, identity) | `Scene.{nodes,edges,groups}` (schema.ts) | create/move/resize/delete/group/ungroup ops |
| text | `SceneNode.{title,summary,detail}`, `SceneEdge.label`, `SceneGroup.{title,summary}` | `edit-text` ops (T2.3) |
| style | `styleKey` + `meta` (T2.1) | edit/template ops |
| comments | `Scene.comments` (`SceneComment`) | `add-comment` op (§1) |
| artifacts | `Scene.artifacts` (`SceneArtifact`) | `export` op (§1) |
| exports | `artifactSchema` rows + files | `export` op |
| **proposals** (new slot) | new `Scene.proposals: SceneProposal[]` (additive array; **minimal slot**, full model is P5/T5.4) | proposal-create (MCP write that is *staged*, not applied) / `accept-proposal` / `reject-proposal` |
| accepted operations (history) | the `events` table (storage.ts:433) | every committed op appends one `events` row |
| scene revision | `sceneVersion` (schema.ts:155) / `scene_version` metadata (storage.ts:866) | `bumpSceneVersion` on each document op |

Minimal proposal slot (only what `accept-proposal`/`reject-proposal` need — no diff/ghost UI, that is T5.4):

```ts
// src/shared/schema.ts — additive optional array, defaults [] (back-compat like T2.1 `meta`)
export const sceneProposalSchema = z.object({
  id: z.string().min(1),
  actorId: z.string().min(1),           // proposing agent
  status: z.enum(["pending", "accepted", "rejected"]).default("pending"),
  // the staged change is itself an operation envelope that has NOT been committed:
  operation: /* OperationEnvelope, stored as payload */ z.unknown(),
  createdAt: z.string().min(1)
});
// sceneSchema.proposals: z.array(sceneProposalSchema).default([])  // additive, optional
```

`accept-proposal` commits the staged envelope (re-runs it through `commitAppPatch`, then marks the proposal `accepted`); `reject-proposal` marks it `rejected` and discards the staged envelope. Both are themselves logged operations. This keeps "MCP write that needs human review" expressible **without** an apply-on-write side channel.

### 4. Ephemeral-state boundary

Never persisted to `Scene`, never logged as a document operation, resettable without changing document state (Verify: "Ephemeral viewport/follow/hover state can be reset without changing persisted document state").

| Ephemeral-state slice | Where it lives | Note |
| --- | --- | --- |
| viewport / camera | `SceneSnapshot.camera` (`CameraState`, renderScene.ts:186) — render-time only | already not in `Scene`; the adapter injects a default camera. Stays out of the op log |
| hover | core input state (T2.4 §6 hover highlight) | never in `Scene` |
| active tool | shell tool state | never in `Scene` |
| local selection focus | **ephemeral `selection_json` metadata key** (storage.ts:171) + core active-group focus (T2.4 §5) | see correction below |
| follow mode / spectator | shell + P5/T5.3 state | never in `Scene` |
| companion icon animation | adapter/shell (T2.4 §4 hull tween is the same class) | never persisted |
| transient read cursor | P5/T5.2 marker overlay; `actor_marker` is the ephemeral primitive (T2.1 §1) | never in persisted `Scene` |
| temporary trace effects | P5/T5.4 trace overlay | derived from the `events` log, not stored as document state |

**Selection correction (the one existing seam that crosses the boundary today).** Selection currently lives in two places: `Scene.selection` (schema.ts:162, bumps `sceneVersion` via `commitAppPatch`) *and* the `selection_json` metadata key (storage.ts:171). Per the Locked Decision ("local selection focus" is ephemeral), T2.5 designates `selection_json` (the metadata key, **not** a document revision) as the authoritative ephemeral home, and stops the `select` op from bumping `sceneVersion`. `Scene.selection` is retained for back-compat (it is in the snapshot the renderer reads) but is treated as a *projection of the ephemeral selection*, not document state — its mutation is not an `events`-logged document op. This is the minimal change that puts selection on the correct side of the boundary without a schema break (it stays in `sceneSchema`).

### 5. Local operation log + undo/redo/trace/broadcast

The append-only **operation log is the `events` table that already exists and is currently unused** (storage.ts:433, zero `INSERT INTO events` anywhere). T2.5's core deliverable is: *route every committed operation envelope (§2) into `events` as the primary edit unit, so raw snapshots stop being the unit of history.*

```text
events(id TEXT PRIMARY KEY, type TEXT NOT NULL, payload_json TEXT NOT NULL, created_at TEXT NOT NULL)
   id          = OperationEnvelope.operationId
   type        = patch.kind (the verb, e.g. "move-card", "group-objects", "add-comment")
   payload_json= JSON of the full OperationEnvelope (metadata + inner patch + targetIds)
   created_at  = OperationEnvelope.timestamp
```

The write becomes: `saveScenePatch` (and the comment/export/proposal funnels) appends one `events` row **inside the same `withWritableDb` transaction** that applies the patch and bumps `scene_version` (storage.ts:155–175) — so an applied document op and its log row are atomic. No `ALTER TABLE` (the table and all four columns already exist).

| Consumer (breakdown) | Driven from the log how |
| --- | --- |
| **undo/redo** | each op carries `targetIds` + `baseRevision`; undo = apply the inverse op (computed from the envelope + pre-image) and append a new op; redo replays forward. Because every op is granular and target-scoped, undo is explainable as "revert operation X on targetIds Y", not "restore snapshot N". Inverse-op derivation is per-`kind` (move↔move-back, create↔delete, group↔ungroup — the verb pairs in §1 are deliberately invertible). |
| **MCP trace** (P5/T5.2/T5.4) | query `events` filtered by `actorId`/`clientId`; `targetIds` + `type` give "what this agent read/wrote where". `sourceToolCall` links a canvas op back to the MCP call. |
| **audit display** | chronological `events` by `created_at`; `actorType` distinguishes human vs MCP vs system. |
| **future broadcast** (deferred) | the envelope is a self-contained, replayable, target-scoped, base-revisioned record — the exact shape a future transport would stream. T2.5 stops here: **no transport is built** (§7). `baseRevision` is the conflict-detection hook a future merge layer would use, present now, unused now. |

Why this is "not raw snapshots" (Verify): the unit written to `events` is the **operation envelope**, never a full `Scene` blob; `saveScenePatch` already applies *granular* upserts/removes (storage.ts:156–171), and T2.5 forbids any new code path that writes the whole scene as one untracked blob. The existing `saveScenePatch` partial-blob upsert is wrapped, not replaced — its inputs simply now arrive as a logged envelope.

### 6. Additive contract/persistence delta and core-vs-shell placement

Net additive delta (no wholesale replacement, no schema break, mirrors T2.1/T2.4 discipline):

- **`src/shared/operation.ts` (new file)**: `OperationEnvelope`, `ActorType`. Pure contract; no runtime behavior.
- **`renderPatch.ts`**: `applyRenderPatchToShapeScene` gains an envelope parameter and returns the envelope alongside `AppliedRenderPatch`; promote `addShapeSceneComment` → an `add-comment` `RenderScenePatch` member; add `export`, `accept-proposal`, `reject-proposal` members. `commitAppPatch` is unchanged internally; the envelope wraps it.
- **`schema.ts`**: add optional `proposals: z.array(sceneProposalSchema).default([])` to `sceneSchema` (additive, default `[]`, back-compat). **No** new metadata fields on `scenePatchSchema` — the metadata lives in the envelope/`events` row, not in the `ScenePatch` blob, so the existing `patch_scene` MCP wire contract is unchanged.
- **`storage.ts`**: inside `saveScenePatch`'s existing `withWritableDb` block, after applying the patch and before/with `bumpSceneVersion`, append one `events` row (`INSERT INTO events …` — first ever use of the table). The `select`-only path stops calling `bumpSceneVersion` (§4). No `ALTER TABLE`; geometry columns / indexes untouched (T2.1 §5 precedent).
- **`mcp.ts`**: each write tool (`patch_scene`, `add_comment`, `export_group`, tag tools) constructs an envelope with `actorType:"mcp"`, `sourceToolCall:{tool}`, `clientId` from the session (P5/T5.1 dependency — `"mcp-unknown"` placeholder until then). `set_selection` writes the ephemeral selection path, **not** a logged document op (§4).

Core-vs-shell placement (Locked Decision: performance-sensitive canvas work in Rust/core, op semantics in the shared contract, orchestration in the shell):

| Concern | Home |
| --- | --- |
| operation envelope construction, verb taxonomy, undo/redo inverse-op derivation, `events` append, document/ephemeral boundary enforcement | **shared contract + server** (`operation.ts`, `renderPatch.ts`, `storage.ts`) — this is op semantics/persistence, not GPU work |
| applying an op to geometry/hit/selection state for rendering, ephemeral camera/hover/active-group/hull-tween | **Rust/core** (already owns scene mutation application, hit testing, selection geometry per T2.4 §10) |
| selection-as-ephemeral, follow/spectator, companion animation, read cursor, trace overlay | **core ephemeral state + shell**; trace overlay is *derived from* the `events` log, never a document mutation |
| undo/redo UI, history/audit panel, proposal accept/reject affordance | **shell** (Svelte target; React is migration input) |

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Operations become a raw scene blob patch without semantic target information. | **CLEAR (not triggered)** | §2 makes `targetIds` a required envelope field with a per-`kind` derivation table; the inner unit is always a typed `RenderScenePatch` member (a verb with explicit ids), and §6 forbids any new whole-`Scene`-blob write path. The existing `saveScenePatch` partial-upsert is wrapped, not turned into a blob. Every logged `events` row carries verb + `targetIds`, so semantic target info is structurally guaranteed. |
| The implementation path requires adding CRDT, realtime transport, remote auth, or remote cursor UI now instead of keeping only collaboration-ready foundations. | **CLEAR (not triggered)** | §5 stops at the local append-only `events` log; `baseRevision` is recorded as the *future* conflict-detection hook but no merge/transport/auth/cursor is built. The proposal slot (§3) is a local document-state record with accept/reject ops — local single-user review, not co-editing. ## Open questions / risks

- **`clientId`/`actorId` for MCP depends on P5/T5.1.** `StdioServerTransport` (mcp.ts:281) surfaces no stable per-client/session identity today, so MCP ops would log a placeholder `clientId:"mcp-unknown"` / `actorId` until T5.1's client identity model lands. T2.5 only requires the *fields*; the stable-identity Stop-or-ask is owned by T5.1, flagged here so the dependency is explicit (this task `Depends on: T2.1, T2.4`, not P5 — the envelope is shaped now, populated later).
- **Inverse-op derivation needs a pre-image for non-self-inverse ops.** `move`/`group`/`ungroup` are cleanly invertible, but `edit-text`/`resize`/`delete` need the prior value to undo. Recommend the envelope (or the undo stack) capture a minimal pre-image for those `kind`s; storing it in `payload_json` keeps `events` self-sufficient. Settle the pre-image policy with the undo-stack implementation (still T2.5 scope, but an impl detail to confirm).
- **`Scene.selection` retained-but-demoted.** §4 keeps `Scene.selection` in `sceneSchema` for renderer/back-compat while making `selection_json` authoritative and ephemeral. A future clean removal of `Scene.selection` is breaking and deferred to T6.1; flagging so the dual-home is a deliberate transitional choice, not an oversight.
- **Proposal model is intentionally minimal.** §3 defines only the document-state slot + accept/reject ops needed to make MCP "staged writes" expressible and logged. The diff/ghost-write/preview UX is P5/T5.4; if T5.4 needs richer proposal fields, extend `sceneProposalSchema` additively then.
- **`events` table has no retention/compaction policy.** An append-only log grows unbounded. Out of scope for T2.5 (correctness first), but a compaction/snapshot-checkpoint policy should be decided before large-scene history (P3) or long-lived workspaces; flagging, not solving, here.
