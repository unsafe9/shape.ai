## Outcome

Author five engineering `TemplateContract`s — **ADR**, **decision map**, **server architecture diagram**, **dependency diagram**, **investigation map** — as pure primitive recipes (`frame` + `shape` + `edge` + `comment_marker` + tags) over the existing op funnel, plus an **export-preset plan** that reads primitive text/labels/edges/comments/artifacts through the *existing* `generateLocalExport`/`graph.ts` readers, so engineering semantics live only in template metadata, `meta.semanticType`, labels, comments, and export rules — with no structured-ADR core component, no template-private renderer, and a documented migration path for existing `seedGroupScene` ADR scenes.

## Deliverable

The breakdown's T4.4 Deliverable is two bullets: **(1)** template plan for ADR, decision map, server architecture diagram, dependency diagram, and investigation map as primitive recipes; **(2)** an export-preset plan for ADR formats that reads primitives instead of requiring structured ADR core components. §1 fixes how these five templates instantiate the T4.1 contract (no re-derivation of the contract shape). §2–§6 author each recipe. §7 is the export-preset plan. §8 is the migration path for existing structured-ADR scenes. §9 is the additive delta and core/shell placement. Nothing beyond the two bullets is added.

### 1. How these five templates instantiate the T4.1 `TemplateContract`

Each template below is one `TemplateContract` (T4.1 §7): `{ metadata, recipe, layout, exports, tags, promptHints? }`. The binding rules from T4.1/T2.1 that every recipe here obeys, stated once:

- **Recipe elements lower to existing ops only** (T4.1 §2): `RecipeFrame → create-group`, `RecipeShape → create-card`, `RecipeEdge → create-edge`, suggested labels → `create-tag`/`set-object-tags` (T2.4 §7). T4.4 introduces **zero** new ops or object kinds.
- **`styleKey` is chosen by the template, not by a demoted `nodeType`** (T4.1 §2, D1 C3). Each recipe element sets `styleKey` explicitly. Because `defaultStyles` ids today *are* the `nodeType` enum values (`renderScene.ts`) and `SceneStyleToken.id`/`RenderCard.styleKey` accept any free string, an ADR "decision" card uses `styleKey:"decision_point"` to keep the existing visual identity with no schema change.
- **Engineering semantics ride in `meta`** (T2.1 §2): `meta.templateKind` marks the template; `meta.semanticType` carries the demoted `nodeType`/`edgeType` value; `meta.status`/`meta.confidence`/`meta.evidenceRefs`/`meta.rationale` carry the demoted business fields. These never gate the renderer/core (already true — `RenderCard.type`/`status` are opaque strings).
- **Apply = one logged operation** (T4.1 §7, T2.5): the whole template lowers to one `batch` wrapped in an `OperationEnvelope` (`actorType:"human"` from the picker, `"mcp"` from an agent), whose `targetIds` are the created ids. After apply the scene holds only ordinary primitives.

So T4.4 owns *recipe data + export declarations*, not contract mechanics. The five recipes are deliberately the same five primitive kinds; they differ only in `meta.semanticType` vocabularies, default `styleKey`s, suggested tags, layout, and advertised exports.

`meta.semanticType` vocabularies these templates use (all are demoted `nodeTypeSchema`/`edgeTypeSchema` values — real enum members from `schema.ts`, reused as opaque `meta` strings, not revived enums):

| Template | Node `semanticType` values (from `nodeTypeSchema`) | Edge `semanticType` values (from `edgeTypeSchema`) |
| --- | --- | --- |
| ADR | `proposition`, `decision_point`, `option`, `evidence`, `tradeoff`, `blocker`, `subdecision`, `task`, `artifact` | `decomposes_to`, `chooses_between`, `supports`, `trades_off_with`, `blocks`, `depends_on`, `produces` |
| Decision map | `decision_point`, `option`, `subdecision` (lighter subset) | `chooses_between`, `decomposes_to`, `depends_on` |
| Server architecture | `artifact` (component), `option` (deployment tier) reused as opaque component/zone markers | `depends_on`, `produces` |
| Dependency diagram | `artifact`/`task` reused as opaque unit markers | `depends_on`, `blocks` |
| Investigation map | `proposition` (question), `evidence`, `option` (hypothesis), `decision_point` (finding), `task` (next step) | `supports`, `depends_on`, `chooses_between` |

These reuse existing enum *string values* purely so the existing export presets (§7) and the existing `defaultStyles`/`node_type_label()` keep working with no remapping. A future free-form `semanticType` namespace is a non-breaking superset; not needed for T4.4.

### 2. ADR template recipe

This is the de-facto template that already ships hard-coded as `seedGroupScene` (`local.ts:29`) — 10 nodes, 9 edges, fixed positions. T4.4 declares it as a `TemplateContract` so it is one of many, not the only, template (T4.1 §9). The recipe is a direct, mechanical transcription:

- `metadata`: `{ id:"adr", title:"ADR / Design Decision", category:"engineering", templateKind:"adr" }`.
- `recipe.frames`: one root `RecipeFrame` (the decision group) — the `SceneGroup` `seedGroupScene` builds today (`local.ts:142`).
- `recipe.shapes`: the 10 `node(...)` calls → 10 `RecipeShape`s, each with `meta.semanticType` = its `nodeType` argument and `styleKey` = the same string (so visual identity is preserved). Title/summary/detail carry the existing prose.

| `seedGroupScene` node | `RecipeShape.localId` | `meta.semanticType` | `styleKey` | `meta.status` |
| --- | --- | --- | --- | --- |
| `n-proposition` | `proposition` | `proposition` | `proposition` | `selected` |
| `n-decision-points` | `decision-points` | `decision_point` | `decision_point` | `draft` |
| `n-option-graph` | `option-graph` | `option` | `option` | `viable` |
| `n-option-freeform` | `option-freeform` | `option` | `option` | `conditional` |
| `n-evidence` | `evidence` | `evidence` | `evidence` | `draft` |
| `n-tradeoff` | `tradeoff` | `tradeoff` | `tradeoff` | `draft` |
| `n-blocker` | `blocker` | `blocker` | `blocker` | `infeasible` |
| `n-subdecision` | `subdecision` | `subdecision` | `subdecision` | `draft` |
| `n-task` | `task` | `task` | `task` | `draft` |
| `n-artifact` | `artifact` | `artifact` | `artifact` | `draft` |

- `recipe.edges`: the 9 `edge(...)` calls → 9 `RecipeEdge`s, each with `meta.semanticType` = its `edgeType` argument and `styleKey` chosen from the template (e.g. `blocks`/`trades_off_with` → `"risk"`, replicating today's `edgeToRenderEdge` rule but now sourced from the recipe, not hardcoded — T4.1 §2 / D1 C3).
- `layout`: relative positions from `defaultSeedNodePositions` (`local.ts:16`) become each `RecipeShape.position`; default shape size `{270,178}` (today's `nodeWidth`/`nodeHeight`). Frame `bounds` are derived by `boundsForNodes(members)` at apply, then placed by `nextGroupOffset` — exactly the existing `createGroup` path (T4.1 §3). No new geometry.
- `exports`: `{ allowed: ["madr","yadr","design_doc_md","confluence_html","mermaid"], default: "madr" }` (§7).
- `tags`: suggested status labels (`viable`/`conditional`/`infeasible`/`selected` as color chips) so status can also be read as a label, not only `meta.status` (T2.1 §2 "status-label tag").
- `promptHints`: the prose `seedGroupScene` bakes into summaries (e.g. *"The choice should be driven by feasibility, evidence strength, reversibility, and agent permissions"*, `local.ts:36`) pulled out as `systemHint`; per-`semanticType` guidance as `fieldHints` (T4.1 §6).

### 3. Decision map template recipe

A lighter decision-graph surface: just the decision/options/subdecision spine, without the full ADR evidence/tradeoff/blocker scaffold. Same primitives, narrower `meta.semanticType` set (§1 table).

- `metadata`: `{ id:"decision-map", title:"Decision Map", category:"engineering", templateKind:"decision-map" }`.
- `recipe`: one root `frame`; `shape`s for a central `decision_point` plus N `option` cards; optional `subdecision` cards; `edge`s `chooses_between` (decision→option) and `decomposes_to` (option→subdecision). `styleKey`s `decision_point`/`option`/`subdecision`.
- `layout`: a small radial/column default (relative positions in the recipe; `boundsForNodes` + `nextGroupOffset` place it).
- `exports`: `{ allowed: ["mermaid","madr","design_doc_md"], default:"mermaid" }` — `makeMermaid` reads the spine directly.
- `tags`: `viable`/`conditional` chips on options.
- `promptHints.systemHint`: *"A decision map: one decision point, competing options, optional sub-decisions. Edges show choice and decomposition."*

This is the ADR recipe minus the evidence/tradeoff/blocker rows; it proves templates differ by recipe data, not by code.

### 4. Server architecture diagram template recipe

Box-and-arrow component diagram with deployment zones. From D1's table this is "Buildable" via `shape` boxes + `edge` connectors + `frame` zones/tiers + editable edge labels (single `text.rs` engine).

- `metadata`: `{ id:"server-architecture", title:"Server Architecture", category:"engineering", templateKind:"server-architecture" }`.
- `recipe.frames`: a root frame plus nested `RecipeFrame`s for tiers/zones (e.g. "Edge", "Service", "Data") — nested frames use the T2.4 §10 `parentGroupId` passthrough; `meta.semanticType:"zone"`.
- `recipe.shapes`: component boxes as `shape`s with `meta.semanticType:"component"` (reusing the opaque `artifact` `styleKey` string for box styling, or a template `styleKey:"component"`; both are free strings). Title = component name, summary = role.
- `recipe.edges`: connectors with `meta.semanticType:"depends_on"`/`"produces"`, `label` = protocol/relationship text (the shared edge-text capability, T2.3). `styleKey` from the template.
- `layout`: zone frames stacked; components placed relative within their zone frame. `boundsForNodes` derives each zone frame's bounds from its members.
- `exports`: `{ allowed: ["mermaid","architecture_image","image_prompt"], default:"mermaid" }`. `makeMermaid` emits `flowchart LR` from the boxes/edges; `architecture_image`/`image_prompt` emit the text `imagePrompt` (`local.ts:175`) — see §7 and the image caveat (Open questions).
- `tags`: zone/tier color chips (`Edge`/`Service`/`Data`).
- `promptHints.systemHint`: *"A server architecture diagram: boxes are components, frames are deployment zones/tiers, edges are dependencies labeled with the protocol or call."*

The architecture-image **embed** (a real bitmap of the rendered diagram on canvas) inherits the `image_artifact` substrate gap (D1 C1); the *export* side is unaffected because it only emits a text prompt today. Until the image substrate lands, an `image_artifact` recipe element degrades to a documented captioned-box placeholder (T4.1 §2, D1 C1).

### 5. Dependency diagram template recipe

A focused subset of the server-architecture recipe: units + dependency edges, no zone frames required. Surfaces `depends_on`/`blocks` relationships among modules/packages/services.

- `metadata`: `{ id:"dependency-diagram", title:"Dependency Diagram", category:"engineering", templateKind:"dependency-diagram" }`.
- `recipe`: one root `frame`; `shape` unit boxes (`meta.semanticType:"unit"`, reusing `artifact`/`task` `styleKey`); `edge`s `depends_on` (+ optional `blocks` for cycles/conflicts, styled `"risk"`).
- `layout`: left-to-right columns by dependency depth (relative recipe positions; no auto-layout engine — Explicit Non-Goal).
- `exports`: `{ allowed:["mermaid","architecture_image"], default:"mermaid" }`. `makeMermaid` is a literal dependency-graph renderer.
- `tags`: optional `blocking`/`external` chips.
- `promptHints.systemHint`: *"A dependency diagram: boxes are units (modules/services/packages), edges are 'depends on'; mark blocking dependencies with a blocks edge."*

### 6. Investigation map template recipe (D1 C2 — the previously-undemonstrated sixth template)

D1 flagged the investigation map as a binding Approve-if template with **no demonstrated recipe** (D1 condition C2). T4.4 owns that recipe. It composes from the *same* primitives as ADR — no new primitive (D1 finding: "plausibly reuses existing `frame`/`shape`/`edge`/`comment_marker`/`tags`"; this confirms it).

- `metadata`: `{ id:"investigation-map", title:"Investigation Map", category:"engineering", templateKind:"investigation-map" }`.
- `recipe.frames`: a root frame; optional sub-frames per investigation thread.
- `recipe.shapes`: a central question `shape` (`meta.semanticType:"proposition"`, `styleKey:"proposition"`); `evidence` cards (`semanticType:"evidence"`); hypothesis cards (`semanticType:"option"`); finding cards (`semanticType:"decision_point"`); next-step cards (`semanticType:"task"`).
- `recipe.edges`: `supports` (evidence→hypothesis), `chooses_between` (question→hypothesis), `depends_on` (finding→next-step). `styleKey`s from the template.
- `comment_marker`s: investigation notes anchor to evidence/finding cards via `SceneSelection` (`sceneCommentSchema.target`) — the same anchoring ADR uses; survives regrouping (T2.4).
- `layout`: question at center/top, evidence fanning to hypotheses, findings below. Relative recipe positions + `boundsForNodes` + `nextGroupOffset`.
- `exports`: `{ allowed:["design_doc_md","mermaid","ai_plan_md"], default:"design_doc_md" }`. `taskPlanSections` (`ai_plan_md`) reads the `task` next-step cards (`local.ts:365`); `makeMermaid` reads the evidence/hypothesis/finding graph; `design_doc_md` (→ MADR shape) reads the rest.
- `tags`: `confirmed`/`refuted`/`open` chips on hypotheses/findings.
- `promptHints.systemHint`: *"An investigation map: a question, evidence cards, competing hypotheses, findings, and next steps. Edges show which evidence supports which hypothesis and which findings drive next steps."*

This discharges D1 C2: the sixth binding template now has an explicit primitive composition, reusing only existing primitives and ops, with zero new core/renderer work.

### 7. Export-preset plan — ADR formats read primitives, not structured ADR core components

The breakdown's second Deliverable bullet: *export presets for ADR formats that read primitive text/labels/comments/edges/artifacts instead of requiring structured ADR core components.* This already largely holds in the codebase and needs **no new export engine** — the existing presets read a `DecisionGraph` that is *derived from the scene's primitive objects*, not from a privileged ADR component.

The existing pipeline (all real symbols):

1. `export_group(groupId, type|types, scope?)` (`mcp.ts:177`) / the export drawer call `exportGroupContent` (`mcp.ts`).
2. `exportGroupContent` builds `graph = sceneGraphForGroup(scene, groupId)` (`graph.ts:121`) — which **reads primitive `SceneNode`/`SceneEdge` rows** filtered by `descendantGroupIds`, strips geometry via `stripSceneNode`/`stripSceneEdge`, and returns a `DecisionGraph`. This is already "read the primitives," not "read an ADR component."
3. `generateLocalExport(graph, request, groupTitle)` (`local.ts:164`) dispatches by `exportType` to `makeMermaid` / `madrSections` / `yadrSections` / `taskPlanSections` / `imagePrompt` / `confluence_html`.

The single required adjustment is the **read source for semantics**, which T2.1's demotion changes from typed `node.type`/`node.status` fields to `meta.semanticType`/`meta.status`. The export readers today key off `node.type`/`node.status`/`node.summary`:

| Preset reader (real symbol) | Reads today | After demotion reads | Change |
| --- | --- | --- | --- |
| `madrSections` (`local.ts:258`) | `node.type === "option"/"blocker"/"tradeoff"/"evidence"/"decision_point"/"subdecision"`, `node.status === "selected"/"viable"` | the same values from `meta.semanticType`/`meta.status` (a back-compat reader falls back to `node.type`/`node.status` when `meta` absent) | read-source shim only; same MADR output |
| `yadrSections` (`local.ts:310`) | same `node.type`/`node.status` partitions | same via `meta.*` with fallback | read-source shim only |
| `taskPlanSections` (`local.ts:365`) | `node.type === "task"` | `meta.semanticType === "task"` (fallback `node.type`) | read-source shim only |
| `makeMermaid` (`graph.ts:109`) | `nodeTypeLabels[node.type]`, `edgeTypeLabels[edge.type]`, `edge.label` | label from `meta.semanticType` via the same label maps; `edge.label` already primitive text | read-source shim only |
| `graphTextDigest` (`graph.ts:76`) | `node.type`/`status`/`confidence`, `edge.type`/`label` | from `meta.*` with fallback | read-source shim only |
| `imagePrompt` (`local.ts:385`) | static prose + `graphTextDigest` | unchanged (rides the digest) | none |
| `confluence_html` (`local.ts:184`) | wraps `madrSections` output | unchanged | none |

So the export-preset plan is: **keep every preset; add a single `semanticType`/`status` read shim** (read `meta.semanticType` ?? `node.type`, `meta.status` ?? `node.status`) so presets read demoted primitive metadata. This is the same back-compat discipline T2.1 §4 mandates (old data without `meta` still parses and exports correctly). No structured-ADR core component is required or revived — `sceneGraphForGroup` already proves the export reads primitives.

Per-template advertised exports (the `TemplateExports.allowed` from each recipe, mapped to `exportTypeSchema`):

| Template | `exports.allowed` (`exportTypeSchema`) | Read path |
| --- | --- | --- |
| ADR | `madr`, `yadr`, `design_doc_md`, `confluence_html`, `mermaid` | `madrSections`/`yadrSections`/`makeMermaid` over `sceneGraphForGroup` |
| Decision map | `mermaid`, `madr`, `design_doc_md` | same |
| Server architecture | `mermaid`, `architecture_image`, `image_prompt` | `makeMermaid` + `imagePrompt` (text prompt; image embed deferred, D1 C1) |
| Dependency diagram | `mermaid`, `architecture_image` | `makeMermaid` + `imagePrompt` |
| Investigation map | `design_doc_md`, `mermaid`, `ai_plan_md` | `madrSections` + `makeMermaid` + `taskPlanSections` |

Notes on existing aliasing the plan reuses unchanged: `design_doc_md` is already routed to the MADR section path (`generateLocalExport`'s default-MADR branch, `local.ts:196`; `exportTypeLabels.design_doc_md = "MADR Markdown"`); `architecture_image` already returns the text `imagePrompt` (`local.ts:175`); the MCP `markdown` alias maps to `madr` via `normalizeExportType` (`mcp.ts:210`). `allowed` is a constraint surfaced by the export drawer (shell) and the `export_group` tool; the preset code is unchanged.

### 8. Migration path for existing structured-ADR content (the binding Verify)

Existing scenes are exactly the `seedGroupScene` output: a `SceneGroup` + 10 `SceneNode`s with typed `nodeType`/`status`/`confidence` + 9 typed `SceneEdge`s (and any human/MCP edits since). The migration to "primitive objects plus ADR export metadata" is the T2.1 demotion reshape applied to these rows, owned in code by T6.1, specified here for the ADR shape:

| Existing field (real) | Migrates to | Mechanism |
| --- | --- | --- |
| `SceneNode.type` (`nodeTypeSchema` value) | `meta.semanticType` (same string) **and** `styleKey` (same string) | JSON reshape of `node_json` (no `ALTER TABLE`, T2.1 §5); keep the redundant `node.type` populated through P2 so `node_type_label()` badges and `defaultStyles` keep working (D1 C3/C5) |
| `SceneNode.status` (`nodeStatusSchema`) | `meta.status` + optional status-label `tagId` | JSON reshape; status chip via the suggested-tags registry (§2) |
| `SceneNode.confidence`/`evidenceRefs`/`childDecisionIds` | `meta.*` | already in `excludedBusinessFields()`; JSON reshape |
| `SceneEdge.type` (`edgeTypeSchema`) | `meta.semanticType` + `styleKey` | JSON reshape of `edge_json` |
| `SceneEdge.rationale`/`confidence` | `meta.*` | JSON reshape |
| `SceneGroup` (the ADR group) | ordinary `frame` + `meta.templateKind:"adr"` | the group is already an ordinary `SceneGroup` with no privileged type; only `meta.templateKind` is added |
| MADR/YADR/mermaid/design_doc exports | **export presets** that read the demoted primitives (§7) | `makeMermaid`/`madrSections`/`yadrSections` retained as primitive readers with the `meta` read shim |

The result: an existing ADR scene becomes ordinary `frame`/`shape`/`edge` primitives carrying `meta.templateKind:"adr"` + `meta.semanticType`, fully editable by the standard ops, still exporting correct MADR/YADR/mermaid. No structured-ADR core component survives. The round-trip must be gated by a real migration fixture (D1 C6), not asserted — flagged for T6.1, which owns the migration code.

### 9. Additive delta and core/shell placement

Per the Locked Decisions (op semantics in the shared contract; performance-sensitive canvas work in Rust/core; UI orchestration in the Svelte shell):

| Concern | Home |
| --- | --- |
| The five `TemplateContract` definitions (recipe data, `meta.semanticType`/`styleKey` choices, advertised exports, suggested tags, prompt hints) | **shared contract / template registry** (`src/shared/template.ts`, the file T4.1 introduces) — pure data; no runtime |
| Lowering each recipe to `create-group`/`create-card`/`create-edge`/`create-tag`/`set-object-tags` ops and running them through `applyRenderPatchToShapeScene` | **shared contract** (T4.1's `lowerTemplateToOps`) → `commitAppPatch` |
| Geometry/hull/hit/selection of the produced objects | **Rust/core** (templates emit ops; touch none of this directly) |
| The `meta.semanticType`/`status` **read shim** in the export presets (§7) | **server** (`local.ts`/`graph.ts`) — a read-source change, additive, with `node.type`/`node.status` fallback |
| Template picker, export-drawer `allowed` filtering, prompt-hint surfacing | **shell** (Svelte target) |
| Template-aware MCP application (future template tool) | **server/MCP** (`mcp.ts`), reusing `create_group`'s `withWritableDb` apply path (T4.1 §8) |

Net additive delta (no wholesale replacement, no schema break — mirrors T4.1/T2.1 discipline):

- **Five `TemplateContract` records** authored against T4.1's contract in the template registry. Data only; no new type, op, kind, or table.
- **One export read shim** (`meta.semanticType ?? node.type`, `meta.status ?? node.status`) in the existing presets (`madrSections`/`yadrSections`/`taskPlanSections`/`makeMermaid`/`graphTextDigest`). No new preset, no new `exportType`, no `ALTER TABLE`.
- **The hard-coded `seedGroupScene` ADR graph** becomes the ADR `TemplateContract` (T4.1 §9); `createGroup`/`create_group` default `templateId` to it for back-compat, so today's `create_group(prompt)` callers are unchanged.
- **No new primitive** (D1 C2 investigation-map recipe reuses existing primitives); **no image substrate work here** (architecture/image embed deferred to D1 C1's owner; export emits text prompt today).

## Open questions / risks

- **Per-template `meta` validation (D1 C4).** T4.1 recommended each `TemplateContract` carry an optional Zod schema for its `meta` namespace (e.g. ADR validating `meta.semanticType ∈ {decision_point, option, …}`), validated at authoring/apply only, never gating the renderer. T4.4 authors the concrete per-template schemas for these five (the `semanticType` vocabularies in §1 are the schema content). Recommendation: define them alongside the recipes so the demoted-enum integrity ADR/decision-map rely on is restored; flagged because it lands with these contracts, not before.
- **Core badge text vs demoted `semanticType` (D1 C5).** §2/§8 keep `node.type`/`styleKey` redundantly populated so `node_type_label()` (`webgpu.rs`) badges and `defaultStyles` keep rendering correct ADR identity. Once the C5 core badge-migration task replaces `node_type_label()` with `meta`-driven badge text, these templates' `meta.semanticType` becomes the badge source directly and the redundancy can drop. Until then a template card whose `semanticType` has no badge mapping shows the graceful `"Node"` fallback. Dependency flagged, not silently assumed.
- **Architecture-image and dependency-diagram on-canvas previews (D1 C1).** The `architecture_image` *export* emits a text `imagePrompt` today and is unaffected. A real bitmap *embed* of the rendered diagram on canvas depends on the image/texture-quad substrate D1 C1 owns; until it ships, an `image_artifact` recipe element degrades to a captioned-box placeholder (T4.1 §2). The recipes are shaped to carry the artifact ref now and render pixels once the substrate lands — no recipe change needed then.
- **Export read-shim ordering vs T2.1 demotion.** §7's `meta.semanticType ?? node.type` shim must land in the same wave as (or after) the T2.1 demotion reshape; if presets read `meta` before any object carries it, the fallback keeps them correct, but the shim and the reshape should be sequenced together in T6.1's compatibility pass. Flagged so the read-source change is owned, not assumed instantaneous.
- **`design_doc_md` vs `madr` overlap.** `exportTypeSchema` has both `madr` and `design_doc_md`, and `exportTypeLabels` maps both to "MADR Markdown" with `generateLocalExport` routing `design_doc_md` through the default-MADR branch. The recipes advertise whichever reads naturally, but the two are near-aliases today; a future consolidation is cosmetic and out of T4.4 scope (defining templates), flagged for whenever export types are rationalized.
