## Outcome

Let a user pick one MCP companion and watch its canvas activity — click-to-follow, pinned follow, pause/resume, jump-to-current-target, a recent trail, and a clean handoff back to manual control — built entirely from the **existing** imperative camera surface (`focusBounds`/`setCamera`) and the **ephemeral** presence/target data T5.1/T5.2 already produce, so follow never writes document state, never touches the canvas core's camera math, and **never steals control while the user is editing**.

## Deliverable

The breakdown gives T5.3 one Deliverable bullet — the interaction plan covering six behaviors: click-to-follow, pinned follow, pause/resume, jump-to-current-target, recent trail, and handoff back to manual viewport control. §0 fixes where follow lives and the one shared ephemeral type; §1 is the follow state machine that ties the six behaviors together; §2–§7 specify each behavior against real symbols; §8 is the "never steal control" guard that the Verify bullet turns on; §9 fixes core-vs-shell placement.

### 0. Where follow lives — one ephemeral controller, zero new document state

Follow is the textbook **ephemeral activity state** the Locked Decisions name explicitly ("viewport, hover, active tool, **follow mode**, companion animation, transient read cursor는 ephemeral state다"). It therefore lives next to the other ephemeral presence state already classified in T5.1/T5.2 — in the Svelte shell, reading the T5.1 `/api/mcp/clients` stream and commanding the canvas through the T5.1/T5.2 imperative handle — and adds **nothing** to `Scene`, `SceneSnapshot`, the `EngineEvent` document stream, or the canvas core.

One new shell-only type captures the whole feature. It is a single-followee model (Outcome: "observe **one** agent"), matching the P5 verify ("click an icon to inspect or follow **the** agent's current work"):

```ts
// NEW — ephemeral shell-only state (proposed home: src/client/lib/followController.ts,
// surfaced to App/shell as a small store; T1.4 "shell reads MCP state, commands the canvas via the handle").
// NOT persisted; reset on reload is correct (matches the T2.5/T0.1 ephemeral boundary).

type FollowMode =
  | "off"        // no followee; camera is fully user-owned
  | "pinned"     // actively following: each new target re-frames the camera (animated)
  | "paused";    // a followee is selected and its trail still records, but the camera is frozen (user owns it)

type FollowState = {
  mode: FollowMode;
  followeeClientId: string | null;   // T5.1 McpClientIdentity.clientId; the one agent being watched
  userControlled: boolean;           // true while/just-after the user drives the viewport (see §8)
  lastFollowedTarget: CanvasTarget | null; // T5.2 CanvasTarget; what the camera last framed (for jump-to-current)
  trail: TrailEntry[];               // bounded recent activity, newest last (§6)
};

// One recent-activity entry for the trail (§6). Derived from the existing presence/trace stream,
// not stored in Scene. Mirrors what T5.4's richer trace will emit; T5.3 needs only location + time + verb.
type TrailEntry = {
  target: CanvasTarget;              // resolved by T5.2
  verb: "read" | "write" | "comment" | "export" | "error"; // coarse activity class (T5.4 owns the full trace model)
  at: number;                        // epoch ms (McpClientIdentity.lastActivityAt at the time)
};
```

The followee's live target is **not** duplicated here — it is read from the T5.1 registry record (`McpClientIdentity` for `followeeClientId`, whose `lastTarget: CanvasTarget` T5.2 keeps current). `FollowState.lastFollowedTarget` records only what the **camera** has framed, so jump-to-current (§5) can detect "the agent moved since we last framed it."

The camera is moved **only** through the two methods T5.1 §5 / T5.2 §5 already established — no new bridge method:

```ts
// EXISTING — src/client/components/RendererCanvasHost.tsx
RendererCanvasHostHandle.focusBounds(bounds: WorldRect, options?: FocusBoundsOptions) // frame a rect (groups/objects/artifacts)
RendererCanvasHostHandle.setCamera(camera: CameraState)                                // set an explicit camera (viewport targets)
```

The shell resolves the followee's `CanvasTarget` → `WorldRect` via the core geometry T5.2 already reuses (`selection_world_rect`, multi-union, tag-hull, scene-fit — surfaced through `getSnapshot()` + the existing core path), then calls `focusBounds` for spatial targets and `setCamera` for a `{kind:"viewport"}` target. **Follow invents no framing or camera math** — it composes the existing input vocabulary.

### 1. Follow state machine

All transitions are ephemeral. "user grab" = the editor signals the user took the viewport (§8). "new target" = the followee's `McpClientIdentity.lastTarget` changed (T5.2 wrote it). "agent gone" = the followee's `dockState` became `disconnected` or it was `muted` (T5.1).

```text
                click chip / "Follow"                 new target arrives
   off ───────────────────────────────▶ pinned ──────────────────────────┐
    ▲                                    │  ▲   │                          │ (re-frame camera, animated §3)
    │ unfollow / followee gone           │  │   │ user grab (§8)           │
    │                                    │  │   ▼                          ▼
    │                            "Pause" │  │ paused ◀── pinned, trail still records, camera frozen
    │                                    │  │   │
    │  "Resume" ─────────────────────────┘  └───┘ "Resume" / re-pin
    │                                            (snaps to followee's current target, §4)
    └──────────────────── unfollow (Esc / click followed chip / click empty) ──────────────────────────┘
```

| From | Event | To | Camera effect |
| --- | --- | --- | --- |
| `off` | click a companion chip, or "Follow" in its inspector | `pinned` | One framing jump to the followee's current `lastTarget` (animated, §3). |
| `pinned` | followee's `lastTarget` changes (T5.2) | `pinned` | Re-frame to the new target (animated, §3), append to trail (§6). |
| `pinned` | **user grab** (§8: pointer-down / wheel / manual `setCamera`) | `paused` | Camera **immediately** yields to the user. No animation, no fight. |
| `pinned` / `paused` | "Pause" / "Resume" toggle | `paused` / `pinned` | Pause freezes camera; Resume snaps to followee's current target (§4). |
| `paused` | "Jump to current" (no resume) | `paused` | One-shot frame of the live target; stays paused (§5). |
| any | unfollow (Esc, click followed chip again, "Stop following") | `off` | Camera stays where it is; user fully owns it again (§7). |
| `pinned` / `paused` | followee `disconnected` or `muted` (T5.1) | `off` | Camera stays put; dock surfaces "agent left"; no surprise jump (§8). |

### 2. Click-to-follow

Entry point, reusing T5.1's clickable dock chip (T5.1 §5: "the chip to be clickable and to carry the `clientId`").

- Clicking a companion chip whose `dockState ∈ {idle, active, error}` sets `followeeClientId = chip.clientId`, `mode = "pinned"`, and performs **one** framing jump to that client's current `lastTarget` via `focusBounds`/`setCamera` (§3). This is exactly the path `App.tsx` already uses for `focusGroup`/`focusNode` (`rendererRef.current?.focusBounds(group.bounds, {...})`), now driven by a companion's resolved target instead of a user selection.
- Clicking a `muted` or `disconnected` chip does **not** start follow (no target motion for a silenced/absent agent — consistent with T5.1's mute semantics).
- Click-to-follow is a **one-time camera move** on entry; continuous re-framing only happens because `mode` is now `pinned` and §3 handles subsequent targets. There is no auto-follow without this explicit click — the camera never moves toward an agent the user did not pick (P5 Locked Decision: observability, not hijacking).

### 3. Pinned follow

While `mode === "pinned"`, the controller re-frames the camera every time the followee's resolved target changes:

- The followee's `lastTarget` is kept current by T5.2 (it writes `CanvasTarget` into the T5.1 registry as each tool call resolves). The shell observes target changes through the T5.1 `/api/mcp/clients` live stream (poll/SSE, T5.1 §4) — **not** through `EngineEvent`, keeping presence off the canvas document stream.
- On each change: resolve `CanvasTarget → WorldRect` (T5.2's core path), then `focusBounds(rect, opts)` for `group|node|edge|selection|artifact`, or `setCamera` for `{kind:"viewport"}`. Set `lastFollowedTarget = newTarget` and append a `TrailEntry` (§6).
- **Framing options are bounded, reusing the existing `FocusBoundsOptions`** (`engine.ts:38`): pass `padding`, `minZoom`, `maxZoom` so a single tiny card does not over-zoom and a scattered multi-target write (T5.2's union rect risk) does not yank the camera to a useless altitude. Concretely, reuse the `App.tsx` `focusGroup` defaults as the baseline (`minZoom`/`maxZoom`, centered `screen`), with `maxZoom` capped so reads on a wide hull "fit" rather than slam in.

#### 3.1 Animation: where the smoothing lives

Ground-truth finding: **core applies `FocusBounds`/`SetCamera` instantly** — `apply_input_event` sets `self.camera = focus_camera_to_bounds(...)` / `clamp_camera(camera)` in a single input batch (`webgpu.rs:1546`/`:1565`); there is no tween/easing/RAF loop in core. So a raw pinned re-frame would teleport the camera, which is disorienting in spectator mode.

The smoothing is a **shell-side camera tween that emits a short sequence of `setCamera` batches** toward the target camera, not a new core animation system:

- Compute the destination `CameraState` for the target (for `focusBounds` this is the camera core *would* land on; the shell can read it back via `getCamera()` after a dry `focusBounds`, or interpolate from the current `getCamera()` toward the target rect's framed camera). Interpolate `{x,y,zoom}` over a short, fixed duration (a few hundred ms) with an ease-out curve and drive it on the shell's RAF, issuing one `setCamera` per frame through the existing handle.
- This keeps the Locked-Decision boundary intact: **the tween is orchestration (shell), the camera math/clamping is core** (`clamp_camera`, `focus_camera_to_bounds`). The shell never recomputes projection or hit math; it only chooses intermediate `{x,y,zoom}` values and hands each to core's `SetCamera`.
- **Interruptible by design (this is the safety property).** A user grab (§8) cancels the tween mid-flight on the very next frame — the shell simply stops issuing `setCamera` and lets the user's own pointer/wheel batches own the camera. Because every tween step is just another `setCamera` input batch interleaved with user input batches, the user always wins the race: their `PointerDown`/`Wheel` is processed by the same `apply_input_event` loop and the tween yields.
- Respects `prefers-reduced-motion`: reduced-motion → single `setCamera`/`focusBounds` jump (no tween), still interruptible.

### 4. Pause / resume

- **Pause** (`pinned → paused`): stop issuing camera commands. The followee's `lastTarget` and the trail keep updating (presence stream is independent of camera), so the user can study the current view while the agent moves on. The dock companion stays `active`; only the camera is frozen. Pause does **not** unfollow — `followeeClientId` is retained.
- **Resume** (`paused → pinned`): re-pin and snap to the followee's *current* `lastTarget` (which may have advanced while paused) via one animated frame (§3), then resume per-target re-framing. Resume is the explicit "catch me back up" action.
- Pause is also the **automatic** landing state when the user grabs control during pinned follow (§8): rather than dropping follow entirely, a user grab demotes `pinned → paused`, so the followee is remembered and one tap of "Resume" returns to live following. This is the key "never steal control, but stay easy to re-engage" behavior.

### 5. Jump-to-current-target

- A one-shot "Jump to current" action (button on the followed companion / inspector, or a keyboard shortcut) frames the followee's **live** `lastTarget` once, without changing `mode`. From `paused` it stays `paused`; from `off` with a selected followee it does a single frame without pinning.
- Implementation is one `focusBounds`/`setCamera` call to the resolved live target — identical to the §2 entry jump, minus the state transition. It exists precisely so a user who paused (because they were editing) can take a single deliberate peek at where the agent is *now* without surrendering the camera to continuous follow.
- "Current" is read from the registry (`McpClientIdentity.lastTarget`), not from `lastFollowedTarget`, so it always jumps to the freshest location even if pinned follow last framed something older.

### 6. Recent trail

A bounded, ephemeral record of where the followee has recently been — the "operation trace" P5 calls for, scoped to T5.3's *navigation* need (the full per-verb trace model and ghost-diff preview are T5.4; T5.3 needs only enough to retrace recent locations).

- `FollowState.trail: TrailEntry[]` is a fixed-capacity ring (e.g. last N entries, N small) appended on each followee target change in `pinned` and `paused` (trail records even when the camera is frozen). Each entry is `{ target, verb, at }`, derived from the presence/activity stream — `verb` is the coarse class from the activity hooks T5.1 §3 already emits (`active` write vs read, error), and the exact mapping to read/write/comment/export is T5.4's responsibility; T5.3 consumes whatever verb T5.4 surfaces and falls back to `read`/`write`.
- **Rendering:** the trail is presented two ways, both shell-owned and ephemeral:
  1. A small list in the followed-companion inspector/dock popover ("recent: group A · wrote, card 12 · read, …"), each row clickable → jump-to that entry's `target` (a `focusBounds` one-shot, like §5 but to a historical target). This gives "retrace the agent's recent steps."
  2. An optional faint on-canvas breadcrumb: prior target rects drawn as low-emphasis ephemeral overlays via the **same `CoreOverlayRequest` overlay path the `actor_marker` already uses** (T5.2 §5) — no new canvas surface, no `Scene` object, decaying with age. This is opt-in and respects `muted`/reduced-motion (static, no animation).
- The trail is **not** persisted (resettable, ephemeral) and is **per-session, per-followee** — switching followee resets the trail to that client's recent activity (which T5.4's richer trace can backfill if available; otherwise it starts empty and grows).

### 7. Handoff back to manual viewport control

Two clean ways out, both leaving the camera exactly where it is (no snap-back, no surprise):

- **Soft handoff (stay subscribed):** any user grab demotes `pinned → paused` (§8). The user now owns the camera; the companion is still selected; "Resume"/"Jump to current" re-engage. This is the common case — the user nudged the view to read something and can hop back.
- **Hard handoff (stop following):** Esc, clicking the followed chip again, "Stop following" in the inspector, or clicking empty canvas → `mode = "off"`, `followeeClientId = null`. The camera does not move. The dock chip returns to its normal (non-followed) appearance.
- In **all** exits the controller issues **no** camera command on the way out — handoff is the *absence* of follow commands, so the last frame the user is looking at is the frame they keep. This is what makes the feature feel like "let go," not "yank back."

### 8. The "never steal control" guard (the Verify-critical piece)

Follow must never move the camera while — or just after — the user is interacting. The guard is built on signals the engine **already emits**, so it needs no new core/engine surface:

| User-grab signal | Real source | Why it's authoritative |
| --- | --- | --- |
| Pointer drag / pan / select start | core `CanvasInputEvent::PointerDown` → engine `beginInputGesture()` → `EngineEvent { type:"gesture", active:true }` (`engine.ts:501`, surfaced to App via `onGestureChange`) | `PointerDown` is the same event that commits a `Select` and starts `input_drag` (Pan/Card/Group/Edge) in core (`webgpu.rs:1367`) — i.e. the literal moment the user takes the canvas. |
| Wheel zoom / scroll | core `CanvasInputEvent::Wheel` (`webgpu.rs:1526`) → engine `wheelAtScreen`/`onWheel` | Direct manual camera change; must beat follow. |
| Any user-originated camera change | `onCameraChange` firing with a camera the controller did **not** command | Distinguishes user pan/zoom from the controller's own `setCamera` (the controller marks its own commands so they don't self-trigger the guard). |

Guard rules:

1. **`gesture.active === true` ⇒ follow is suspended.** While an input gesture is live, the controller issues **zero** camera commands and cancels any in-flight tween (§3.1). This is hard-interlocked: the controller cannot win a frame against an active gesture because it simply does not emit.
2. **On user grab during `pinned`, transition to `paused`** (§4/§7 soft handoff), not back to live follow. A short cooldown after `gesture.active` goes false keeps the camera with the user (no immediate re-pin the instant they lift the pointer); re-engagement is explicit (Resume / Jump-to-current).
3. **The controller tags its own camera commands** so `onCameraChange` from its own `setCamera` is not misread as a user grab. Only an *unexpected* camera delta (or a gesture/wheel event) counts as a grab.
4. **Agent-initiated changes never grab on the user's behalf.** A new followee target re-frames only in `pinned` with no active gesture; in `paused`/`off` it updates `lastTarget`/trail but moves no camera. There is no code path where an agent's tool call moves the user's camera while the user is editing.

This directly closes the P5 "follow must not steal control" Verify and the Stop-or-ask ("spectator conflicts with direct manipulation"): direct manipulation always preempts follow because both flow through the **same** core `apply_input_event` batch loop and the user's input is never withheld for the controller.

### 9. Core-vs-shell placement

| Concern | Home | Why |
| --- | --- | --- |
| `FollowState` + follow state machine (§1) | **shell** (`src/client/lib/followController.ts` + a small store) | pure ephemeral UI orchestration; Locked Decision puts follow in ephemeral state, and T1.4 puts orchestration in the shell. |
| Reading followee target / presence | **shell** (T5.1 `/api/mcp/clients` stream) | presence is server→shell; follow is a reader, never a writer. |
| `CanvasTarget → WorldRect` resolution | **Rust/core** (`selection_world_rect`, union, hull, scene-fit — reuse, T5.2 §0) | selection/hull geometry is a Locked-Decision core responsibility; not re-implemented in the shell. |
| Camera framing math + clamping (`focus_camera_to_bounds`, `clamp_camera`) | **Rust/core** (existing `FocusBounds`/`SetCamera`) | camera math lives in core; the shell only supplies rects/cameras. |
| Follow camera tween (interpolating `{x,y,zoom}`) | **shell** RAF emitting `setCamera` batches (§3.1) | a tween is orchestration over the existing input vocabulary, not new projection math; keeps animation out of the core frame budget and trivially interruptible. |
| User-grab detection (gesture/wheel/camera-delta) | **shell**, off the **existing** `EngineEvent`/`onGestureChange`/`onCameraChange` | no new engine event; reuses `gesture{active}` that input batching already emits. |
| Trail breadcrumb render | **core overlay** (`CoreOverlayRequest`, shared with `actor_marker`) + **shell** list | reuses the ephemeral overlay path; no new canvas surface, no `Scene` object. |

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Spectator mode conflicts with local direct manipulation. | **CLEAR (not triggered).** | The design is built so the two cannot conflict: follow is purely ephemeral and drives the camera only through the existing `setCamera`/`focusBounds` input batches, which are processed by the **same** core `apply_input_event` loop as the user's `PointerDown`/`Wheel`. §8 hard-interlocks follow to the already-emitted `gesture{active}` signal — while the user is editing, the controller emits nothing and any tween is cancelled — and a user grab demotes pinned follow to `paused` (remembered, one-tap resume) instead of contesting the camera. No document state is touched, so there is no edit/observe data conflict either. The one design dependency that makes this true (core processes user input in the same batch loop and never withholds it for the controller) is satisfied by the current engine, so the gate stays clear. |

## Open questions / risks

- **Tween destination camera for `focusBounds`.** §3.1 needs the *destination* `CameraState` that core would compute for a `focusBounds` rect, so the shell can interpolate toward it. Cleanest is a tiny read-back (apply `focusBounds`, read `getCamera()`, then animate from the prior camera) or exposing a pure "camera for these bounds" core helper later; either is a small mechanic, flagged so the tween doesn't reimplement `focus_camera_to_bounds` in the shell.
- **Presence stream latency vs follow smoothness.** Pinned follow re-frames when the `/api/mcp/clients` stream reports a new `lastTarget`. If that stream is poll-based (T5.1 §4 left poll/SSE open), follow may lag the agent by the poll interval. Acceptable for observability, but SSE/live push gives noticeably better follow feel; flagged as a T5.1 read-path choice that materially affects T5.3.
- **Trail vs T5.4 trace overlap.** §6 deliberately keeps a minimal `TrailEntry` (location + time + coarse verb) for navigation and defers the full per-verb trace + ghost-diff preview to T5.4. If T5.4 lands first, T5.3 should consume T5.4's trace entries directly rather than maintain a parallel ring; noted so the two don't build duplicate activity buffers.
- **Multi-followee is intentionally out of scope.** Outcome says "observe **one** agent"; `FollowState` is single-followee. If a later requirement wants split-screen or multi-agent watch, that is a new design (and a harder "whose camera wins" problem), not a T5.3 extension.
- **`prefers-reduced-motion` users lose the tween.** §3.1 degrades to instant jumps for reduced-motion. Instant re-frames on a fast agent could feel jumpy; mitigated by the same `minZoom`/`maxZoom` bounding, but flagged as a known UX edge for reduced-motion spectators.
