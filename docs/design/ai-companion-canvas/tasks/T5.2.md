# T5.2 Tool Call To Canvas Target Mapping

> Phase P5 (MCP Companion Activity Tracker), Wave G. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P5 intro, T5.2); upstream `docs/design/ai-companion-canvas/tasks/T2.5.md` (the `OperationEnvelope` with `targetIds`/`sourceToolCall`, the `events` log, the document/ephemeral split, the `select`→ephemeral correction) and `T5.1.md` (the `McpClientIdentity` registry, the reserved `lastTarget` field, the `actor_marker` dock projection, `focusBounds`/`setCamera` as the only canvas command surface).
> Real symbols grounded in: `src/server/mcp.ts` (all 10 registered tools + `jsonResponse`), `src/shared/renderScene.ts` (`SceneSnapshot`, `CameraState`, `WorldRect`, `RenderGroup/Card/Edge`), `src/shared/schema.ts` (`sceneSelectionSchema` = `canvas|group|node|edge`, `exportScopeSchema`, `scenePatchSchema`), `src/shared/renderPatch.ts` (`RenderScenePatch` union, `validateSceneSelection`), `src/client/components/RendererCanvasHost.tsx` (`RendererCanvasHostHandle.focusBounds(bounds, FocusBoundsOptions)`/`setCamera`), `src/client/renderer/engine.ts` (`FocusBoundsOptions`, `focus-bounds` input batch), `src/renderer/core/src/webgpu.rs` (`selection_world_rect(scene, selection) -> Option<WorldRect>`, `world_rect_to_screen_rect`), `src/renderer/core/src/model.rs`/`stats.rs` (`SceneSelection`, `WorldRect`, `CoreOverlayRequest{world_rect,screen_rect}`, `WebGpuDebugSnapshot.selection_world_rect/_screen_rect`).

## Outcome

Resolve every MCP tool call to a concrete **canvas target** — a `SceneSelection` (group/node/edge), a viewport rect, the canvas root, or an artifact preview — so the companion `actor_marker` (T0.1 ephemeral kind, owned by T5.1's `McpClientIdentity.lastTarget`) can move to where the agent is actually reading or writing, reusing the **already-extracted** `targetIds` from the T2.5 `OperationEnvelope` and the **already-existing** Rust `selection_world_rect` geometry, with an explicit fallback for calls that carry no concrete target. No new canvas-core method, no `Scene`/snapshot schema change, no document mutation.

## Deliverable

The breakdown's T5.2 has two Deliverable bullets: (§1–§3) the per-tool mapping for `query_scene` viewport, `get_group`, `patch_scene`, `set_selection`, `add_comment`, `export_group`, tag updates, and future template ops; and (§4) the fallback when a call has no concrete target. §5 wires the resolved target to the canvas through the existing `focusBounds`/`setCamera` surface; §6 fixes core-vs-shell placement. Nothing beyond the bullets is added.

### 0. What a "canvas target" is — one ephemeral type, four resolvers

The marker needs a *location*, not a business object. Everything in P5 already speaks `SceneSelection` (`canvas|group|node|edge`, `schema.ts:125`) and `WorldRect` (`renderScene.ts:10`), and T5.1 already reserved the slot:

```ts
// T5.1 already declared this field on the ephemeral registry record:
// lastTarget: SceneSelection | { kind: "viewport" } | null
```

T5.2 only needs to *name the resolved target* and fill that field. It is an **ephemeral, app-layer** value — never in `Scene`, `SceneSnapshot`, or the `events` log payload (the log already carries `targetIds`; T5.2 does not duplicate it into document state):

```ts
// NEW — ephemeral app-layer type (proposed home: src/server/mcpClients.ts, next to McpClientIdentity).
// Written by the T5.4 tracking middleware after a tool resolves; read by the dock + the follow controller (T5.3).
// NOT persisted; resettable with zero document-state change (T2.5 §4 ephemeral boundary).
type CanvasTarget =
  | { kind: "canvas" }                                   // whole-scene / no concrete object  → fallback (§4)
  | { kind: "group"; id: string }                        // SceneSelection group
  | { kind: "node"; id: string }                         // SceneSelection node
  | { kind: "edge"; id: string }                         // SceneSelection edge
  | { kind: "selection"; ids: SceneSelection[] }          // multi-target write (patch_scene touched many)
  | { kind: "viewport"; rect: WorldRect }                // query_scene / pan-to-region intent
  | { kind: "artifact"; artifactId: string; groupId: string }; // export_group → artifact preview anchor
```

The first four variants are exactly `SceneSelection`; `selection`/`viewport`/`artifact` are the three super-selection cases T5.1's `lastTarget` type (`SceneSelection | {kind:"viewport"} | null`) anticipated. **Recommendation:** widen T5.1's `lastTarget` to `CanvasTarget | null` so the dock, the follow controller (T5.3), and the trace (T5.4) share one resolved-target shape.

The marker is positioned by resolving a `CanvasTarget` to a `WorldRect`. **This geometry already exists in core** and is reused, not rebuilt:

```rust
// src/renderer/core/src/webgpu.rs:4845 — ALREADY resolves any SceneSelection → world rect
fn selection_world_rect(scene: &SceneSnapshot, selection: &SceneSelection) -> Option<WorldRect>
// :4735 — ALREADY maps world → screen for overlay placement
fn world_rect_to_screen_rect(rect: &WorldRect, camera: &CameraState) -> WorldRect
```

So the four `SceneSelection`-shaped targets need **no new geometry**: a `group|node|edge` target is fed straight into the existing `selection_world_rect`; `selection`-multi unions the per-id rects (the same `accumulate_selection`/`push_unique` pattern at `webgpu.rs:3209`); `viewport.rect` is already a `WorldRect`; `canvas` falls back to the scene-fit rect (`fitScene`). The `actor_marker` overlay is then placed exactly like the existing text-edit overlay (`CoreOverlayRequest{ world_rect, screen_rect }`, `stats.rs:105`), keeping marker placement on the Rust/core geometry boundary (Locked Decision: hit testing, selection geometry, hull geometry, culling live in core).

### 1. Where the target comes from — `targetIds` already extracted by T2.5

The single biggest simplification: **T5.2 does not parse tool payloads from scratch.** T2.5 already wraps every write at the `applyRenderPatchToShapeScene` funnel in an `OperationEnvelope` with a per-`kind` `targetIds` derivation (T2.5 §2) and `sourceToolCall:{ tool, callId }`. T5.2 *consumes that envelope*: `targetIds + sourceToolCall.tool` → `CanvasTarget`. The mapping is therefore a thin, deterministic projection, evaluated by the T5.4 tracking middleware at the same MCP choke point T5.1 §3 identified (`jsonResponse`).

For the **read-only** tools that never reach the write funnel (`query_scene`, `list_groups`, `get_group`), T5.2 reads the target directly from the tool's *input arguments* (group id, tag filter) — there is no envelope, but the argument is the target.

### 2. Per-tool mapping (every breakdown-named tool)

Read across: tool → target source (real arg/op symbol) → resolved `CanvasTarget` → marker behavior. Write tools (`*`) get their `targetIds` from the T2.5 envelope; read tools resolve from input args.

| MCP tool (`mcp.ts`) | Op kind / source | `targetIds` source | Resolved `CanvasTarget` | Marker behavior |
| --- | --- | --- | --- | --- |
| `query_scene(tagIds?)` | read; renderer-side culling owns viewport (tool description) | none | `{kind:"viewport", rect}` where `rect` = hull of groups matching `tagIds` (or scene-fit rect if no filter) | Pan-to-region read pulse over the matched area; **does not move selection** |
| `list_groups` | read; whole-scene survey | none | `{kind:"viewport", rect: scene-fit}` | Brief whole-canvas read sweep |
| `get_group(groupId)` | read | `groupId` arg | `{kind:"group", id: groupId}` | Marker hops to the group's `selection_world_rect`, read-style (no write ring) |
| `create_group(prompt,…)` | `create-group` (write) | new group id (T2.5 §2) | `{kind:"group", id: newGroupId}` | Marker lands on the **new** group bounds after commit; write-style |
| `patch_scene(ScenePatch)`\* | `create/move/edit-text/delete/...` (the inner `RenderScenePatch` kind) | envelope `targetIds` (1..N) | 1 id → `{kind:group\|node\|edge}`; N ids → `{kind:"selection", ids:[…]}` | Single → hop to object; multi → marker centers on the union rect, write-style |
| `set_selection(selection)`\* | `select` (ephemeral; T2.5 §1 — no `sceneVersion` bump) | the `selection` arg ids | the `selection` itself, mapped 1:1 (`canvas\|group\|node\|edge`) | Marker mirrors the agent's intended selection; **ephemeral**, drives T5.3 follow without writing a document op |
| `add_comment(target,body)`\* | `add-comment` (T2.5 promoted op) | the comment `target` selection (`[]` for canvas-level, T2.5 §2) | `target` mapped 1:1; canvas-level → `{kind:"canvas"}` | Marker drops on the commented object with a comment glyph cue (trace detail is T5.4) |
| `export_group(groupId,type/types,scope?)`\* | `export` (T2.5 promoted op) | `scope` id(s) read (T2.5 §2) | `{kind:"artifact", artifactId, groupId}` (post-commit, from `addArtifact` result) | Marker anchors on the produced **artifact preview** for that group; read-then-produce |
| `update_group_tags(groupId,tagIds)`\* | `set-object-tags`/tag op (T2.5 verb `tag`) | `[groupId]` (T2.5 §2 `set-object-tags`) | `{kind:"group", id: groupId}` | Marker on the group; tag-edit cue |
| `create_tag(name,color)`\* | `create-tag` (T2.5 verb `tag`) | new tag id (registry, not spatial) | `{kind:"canvas"}` (registry write — no canvas location) → **fallback §4** | No marker hop; dock-only "registry edit" activity (see §4) |

Notes that keep this faithful to the codebase:

- **`query_scene` is explicitly viewport, not selection.** Its own description says "Renderer-side culling owns viewport and zoom behavior" (`mcp.ts:61`); the tag-filtered hull is the only honest "where did it read" answer. The hull is computed in core (same `RenderGroup.bounds` union the cull already walks), not in the shell.
- **`set_selection` is the cleanest case** and the one T2.5 already corrected to be ephemeral: it carries an explicit `SceneSelection` and maps 1:1. It is the canonical "agent points at X" signal and is what T5.3 follow keys on.
- **`export_group` resolves to an artifact, not a node.** The breakdown lists "artifact preview" as a marker destination; the export reads `scope` (group/node/edge/selection, `exportScopeSchema` at `schema.ts:189`) and produces an `artifactSchema` row (`addArtifact`, `mcp.ts:231`) whose `target` is a `SceneSelection`. The marker's *during-read* target is the scope; its *result* target is the artifact preview anchored on `groupId`.

### 3. Future template operations

Locked Decision: templates compose from primitives with no private renderers/object models, and T2.5 §1 already routes future template verbs (`group`, `ungroup`, `label`, `tag`, `resize`, proposal verbs) through the **same** `RenderScenePatch` funnel and the **same** `targetIds` derivation. Therefore **no per-template mapping code is added**: any future template tool that writes through `patch_scene`/the funnel inherits its `CanvasTarget` automatically from `targetIds`. The mapping is *op-kind driven*, not *tool-name driven*, so a "create_todo_card" or "insert_adr_template" tool that emits `create-card`/`group-objects` ops needs zero T5.2 changes — its targets fall out of the envelope. Only a genuinely new *spatial* concept (one with no `RenderScenePatch` representation) would require extending the table, and that would first require a new op in T2.x, not a T5.2 special-case. This is the explicit "templates don't get private behavior" guarantee.

### 4. Fallback when a call has no concrete target

Three distinct no-target cases, each with a defined, non-disruptive behavior (Locked Decision: companion is observability, must not steal focus / clutter):

| No-target case | Examples | Resolution | Marker behavior |
| --- | --- | --- | --- |
| **Registry / non-spatial write** | `create_tag`, a tag rename | `{kind:"canvas"}` | No canvas hop. Dock chip shows `active` (T5.1 §2) with a "registry edit" tooltip; marker stays at its last resting target or hides. |
| **Whole-scene read** | `list_groups`, `query_scene` with no `tagIds` | `{kind:"viewport", rect: scene-fit}` | A brief, low-amplitude read sweep over the scene-fit rect; no selection change. |
| **Empty / failed resolution** | `patch_scene` with empty `targetIds`; a tool that threw before producing an envelope; an id that no longer exists | `null` → keep prior `lastTarget` | No movement. Dock reflects `active`/`error` (T5.1 owns dock state); the marker does **not** jump to `{0,0}` or the origin. |

Resolution order (first match wins): (1) envelope `targetIds` present and ids resolve in the current scene → spatial `CanvasTarget`; (2) read tool with a group/tag arg → group/viewport; (3) whole-scene read → scene-fit viewport; (4) registry/non-spatial or unresolvable → `canvas`/`null` per the table. The "keep prior target on `null`" rule is what prevents target flicker between an agent's successive calls and satisfies the "must not steal focus" constraint inherited by T5.3.

### 5. How a resolved target reaches the canvas (no new canvas surface)

T5.2 adds **no** method to the canvas bridge — it reuses exactly what T5.1 §5 established:

- **Marker placement (always):** the resolved `CanvasTarget` → `WorldRect` via the existing core `selection_world_rect`/union; the `actor_marker` overlay is emitted as an **ephemeral render overlay** (the `CoreOverlayRequest{world_rect,screen_rect}` mechanism, `stats.rs:105`), not as a `Scene` object and not on the `EngineEvent` document stream. The marker rides the ephemeral overlay path the text-edit overlay already uses, so it inherits camera-correct screen placement for free.
- **Camera follow (only when the user opts in — T5.3):** clicking a companion chip or pinning follow calls the **already-existing** `RendererCanvasHostHandle.focusBounds(rect, FocusBoundsOptions)` (`RendererCanvasHost.tsx:21`, → engine `focus-bounds` input batch, `engine.ts:153`) for object/group/artifact targets, or `setCamera` for a viewport. T5.2 supplies the rect; T5.1 supplies the click; T5.3 owns the follow policy and the "never steal control" guard. **T5.2 never auto-pans on its own** — resolving a target only moves the *marker overlay*, not the *camera*, unless follow is active.
- **`FocusBoundsOptions` reuse:** `padding`/`zoom`/`minZoom`/`maxZoom` (`engine.ts:38`) already exist to frame a target without over-zooming a single tiny card — the follow controller passes them; T5.2 does not invent framing math.

This keeps the T5.1 boundary intact: presence/target flows server→shell over the `/api/mcp/clients` read path (T5.1 §4), and the shell drives the canvas only through the imperative handle. The marker overlay is the one on-canvas surface, and it is ephemeral.

### 6. Core-vs-shell placement

| Concern | Home | Why |
| --- | --- | --- |
| `targetIds` extraction per op kind | **shared/server** (T2.5 envelope, already built) | T5.2 consumes it; no re-parse |
| `CanvasTarget` type + tool→target projection (§2 table) + fallback (§4) | **server** (`src/server/mcpClients.ts`, next to T5.1 registry) | pure metadata mapping, not GPU work |
| `CanvasTarget` → `WorldRect` (selection rect, multi-union, tag hull, scene-fit) | **Rust/core** (`selection_world_rect`, hull union — reuse) | selection/hull geometry is a Locked-Decision core responsibility |
| `actor_marker` overlay emission + screen placement | **Rust/core** (`world_rect_to_screen_rect`, overlay request) | culling/overlay/camera math lives in core |
| marker render (icon/color/animation to the rect) | **core overlay + shell** | dock chip cue is shell (T5.1 §2.1); on-canvas marker geometry is core |
| follow camera command (`focusBounds`/`setCamera`) | **shell** (T5.3 controller via existing handle) | orchestration, not geometry |

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Tool payloads lack enough target information to visualize intent. | **CLEAR (not triggered).** | Every write tool already carries semantic targets: T2.5 §2 makes `targetIds` a *required* envelope field with a per-`kind` derivation, and T2.5's Stop-or-ask ("operations become a raw blob without semantic target info") is itself **cleared** there — so T5.2 inherits structurally-guaranteed target ids. The read tools (`query_scene`, `list_groups`, `get_group`) carry their target in their input args (`tagIds`/`groupId`) or resolve to a scene-fit viewport. The only payload-poor case (`query_scene` with no filter, `list_groups`, `create_tag`) is **not** ambiguous intent — it is genuinely whole-scene or non-spatial, and §4 defines the correct, non-disruptive behavior for exactly those. ## Open questions / risks

- **`query_scene` hull precision.** Mapping a tag-filtered read to "the hull of matching groups" is an approximation of what the agent looked at (renderer-side culling, not the tool, decides the real viewport). It is honest and non-disruptive (read sweep, no selection change), but it is a heuristic; if a later requirement wants the *exact* culled rect, that would need the renderer to report its last-served viewport — deferred, flagged.
- **Multi-target write framing.** `patch_scene` touching many objects resolves to the union rect; for a write scattered across the whole canvas the union can be large and the "hop" becomes a "fit". Acceptable (it honestly shows scope), but T5.3's follow policy should cap auto-zoom-out via the existing `FocusBoundsOptions.maxZoom`/`minZoom` so a wide write does not yank the camera to a useless altitude.
- **`lastTarget` type widening is a T5.1 touch.** §0 recommends widening T5.1's `lastTarget` from `SceneSelection | {kind:"viewport"} | null` to `CanvasTarget | null`. This is additive and within the ephemeral registry, but it is a cross-task contract edit; flag it so T5.1 and T5.2 agree on the one shared shape rather than each defining a parallel target type.
- **Marker overlay vs text-edit overlay sharing.** §5 reuses the `CoreOverlayRequest` overlay path for the `actor_marker`. If a future requirement needs a human text-edit overlay and an agent marker on the same object simultaneously, the core overlay slot may need to hold more than one overlay; single-overlay is fine for the current single-user local model, noted so it is a deliberate scope choice, not an oversight.
