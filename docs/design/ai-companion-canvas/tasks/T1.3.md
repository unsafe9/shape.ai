# T1.3 Define Metal Adapter Contract

> Phase P1 (Portable Canvas Core Boundary), Wave B. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P1 intro, T1.3); upstream `docs/design/ai-companion-canvas/tasks/T0.1.md` (primitive/business seam, document/ephemeral split); `docs/rust-canvas-replacement-task.md` P2/P3; ground truth in `src/renderer/core/src/{lib.rs,model.rs,stats.rs,webgpu.rs,Cargo.toml}` and `src/client/components/RendererCanvasHost.tsx`.

## Outcome

Specify what a native **Metal adapter** (macOS/iOS) owns and what it borrows from the shared canvas core, by factoring the existing web-coupled `ShapeWebGpuRenderer` into a platform-neutral render/scene engine plus a thin per-platform surface/input/text-overlay adapter — so the *same* `SceneSnapshot`, `RenderScenePatch`, `CanvasInputEvent`, and hit/overlay/stats payloads drive Metal rendering with no fork of the semantic scene model.

## Deliverable

### 0. Where the web/Metal seam actually is today

`ShapeWebGpuRenderer` (`src/renderer/core/src/webgpu.rs:462`) is **one struct that mixes two responsibilities**. The Metal adapter contract is precisely the line that splits them:

| Field group in `ShapeWebGpuRenderer` | Class | Web-coupled today? | Metal disposition |
| --- | --- | --- | --- |
| `scene`, `camera`, `width`, `height`, `device_pixel_ratio`, `vertex_ranges`, `text_engine`, `text_layout_cache`, `input_drag`, `last_hit`, all `*_count` stats | **Portable core** | No (plain Rust/serde) | **Shared** — reused verbatim |
| `surface`, `device`, `queue`, `config`, `pipeline`, `bind_group`, `uniform_buffer`, `vertex_buffer`, `_text_texture/_text_view/_text_sampler` | **GPU pipeline** | Created via `wgpu`, so *backend-portable*; only `surface` creation is platform-specific | **Shared via wgpu**, with platform surface injection |
| `canvas: HtmlCanvasElement` | **Platform surface** | Yes (`web_sys`) | **Replaced** by `CAMetalLayer` / `MTKView` handle |

The web coupling is narrow and locatable:
- `wgpu::Backends::BROWSER_WEBGPU` (`webgpu.rs:524`)
- `wgpu::SurfaceTarget::Canvas(canvas)` (`webgpu.rs:528`)
- `canvas.set_width()/set_height()` on resize (`webgpu.rs:520,737`)
- `web_sys`/`wasm-bindgen` JSON-string method signatures and the `Cargo.toml` `wgpu-probe` feature wiring `web-sys`, `wasm-bindgen-futures`, and `wgpu` features `["webgpu"]`.

Everything else — `load_scene`, `apply_patch_batch`, `input_batch`, `build_draw_list`, `render_frame`'s encoder/pass/draw loop, `overlay_request`, `debug_snapshot`, hit testing, the WGSL shader, the text atlas — is platform-neutral. **The Metal adapter contract is: keep the portable core, swap the platform surface + I/O bridge, retarget wgpu's backend to Metal.**

### 1. Native surface lifecycle

The Metal adapter owns surface acquisition and hands a configured `wgpu::Surface<'static>` to the shared core, mirroring `ShapeWebGpuRenderer::create` (`webgpu.rs:511`) field-for-field with native equivalents.

| Web today (`webgpu.rs`) | Metal adapter contract |
| --- | --- |
| `HtmlCanvasElement` arg | `CAMetalLayer` / `MTKView` (via `raw-window-handle` `RawWindowHandle::AppKit`/`UiKit`, or a wgpu-rs `SurfaceTargetUnsafe::from_metal_layer`) |
| `wgpu::Backends::BROWSER_WEBGPU` | `wgpu::Backends::METAL` |
| `instance.create_surface(SurfaceTarget::Canvas(...))` | `instance.create_surface(<metal layer target>)` |
| `surface.get_default_config(&adapter, w, h)` | identical call; format negotiated from the Metal layer (`MTLPixelFormat`) |
| `canvas.set_width/height` + `surface.configure` on `resize` | `MTKView.drawableSize` / layer `drawableSize` set by host; adapter calls the same `resize(width, height, display_scale)` core method then `surface.configure` |
| `surface.get_current_texture()` → `present()` (`render_frame`, `webgpu.rs:1177,1227`) | identical wgpu calls against the Metal drawable; native run-loop (`CADisplayLink`/`MTKViewDelegate.draw`) replaces the browser `requestAnimationFrame` driver |

Lifecycle states the adapter must handle (web has analogues but the native host raises them explicitly): `create` (async adapter/device request — `request_adapter` + `request_device`, `webgpu.rs:532,542`), `resize`/scale-change, surface-lost / device-lost (reconfigure), occlude/background (iOS app suspension → stop the display link, drop the drawable, keep the core scene), and `destroy`. None of these touch `SceneSnapshot` — they only re-acquire the GPU surface.

### 2. GPU pipeline

No new pipeline contract. `wgpu` already abstracts Metal; the WGSL shader (`SHAPE_WEBGPU_SHADER`), `ViewUniform`, vertex layout, `RenderPipeline`, `BindGroup`, and the `build_draw_list` → `pass.draw(range)` loop (`webgpu.rs:1217-1224`) are reused unchanged. The adapter contributes only what is platform-bound:

- Backend selector = `Backends::METAL` and the negotiated swapchain `TextureFormat`/`present_mode` (web hard-codes via `get_default_config`; Metal does the same but typically `Bgra8Unorm` + `Fifo`/`Mailbox`).
- The clear color, render pass descriptor, encoder, and submit/present sequence are copied verbatim from `render_frame` (`webgpu.rs:1194-1227`).
- The text glyph atlas upload (`create_text_atlas`, `flush_text_atlas`) is wgpu-texture based and portable; only its allocation site moves under the Metal `device`/`queue`.

Open dependency note: the crate's `wgpu` feature set is currently `["std","webgpu","wgsl"]` (`Cargo.toml:26`). A Metal build adds the `metal` wgpu feature behind a `metal-adapter` cargo feature, parallel to today's `wgpu-probe`. This is a feature-flag addition, not a code rewrite — flagged in §7 / Open questions.

### 3. Native text input bridge (the overlay contract)

The web adapter never reimplements IME/clipboard; it overlays a DOM `<textarea>` positioned by `CoreOverlayRequest` from `overlay_request` (`stats.rs:105`, `webgpu.rs:1319`; consumed by `RendererCanvasHost.tsx` `overlayRef`). The Metal adapter keeps this exact division — the **core stays the single source of overlay geometry and typography**; the adapter only mounts the native control.

| Web overlay (Locked Decision: native input) | Metal adapter contract |
| --- | --- |
| Core returns `CoreOverlayRequest { target, value, world_rect, screen_rect, style: CoreOverlayStyle }` | **Identical struct, unchanged.** Core math is platform-neutral. |
| Host mounts DOM `<textarea>` in `overlayRef`, styled from `CoreOverlayStyle` (`font_family`, `font_size`, `padding_*`, `caret_color`, `selection_background_color`, `max_lines`, `state`, …) | macOS: `NSTextView`/`NSTextField`; iOS: `UITextView` positioned at `screen_rect`, styled from the **same** `CoreOverlayStyle` fields |
| Browser owns IME, selection, clipboard, focus/blur, commit/cancel | Native AppKit/UIKit text system owns IME (incl. Korean 2-set), selection, clipboard, focus/blur, commit/cancel — same "do not reimplement text input in Rust" rule |
| On commit, host emits `edit-card-text` patch via `apply_patch_batch` | Same: native commit → `EditCardText { id, field, value }` (`model.rs:374`) into `apply_patch_batch` |

`CoreOverlayStyle` already carries everything a native control needs (`stats.rs:77-100`); the only adapter-specific work is mapping CSS-ish string fields (e.g. `box_shadow`, hex `text_color`) onto AppKit/UIKit attributes.

### 4. Pointer / touch / keyboard bridge

The core consumes a serde `CanvasInputEvent` stream (`model.rs:407`) and returns `CoreInputBatchResult { camera, hit, selection, patches, overlay }` (`stats.rs:116`) from `input_batch` (`webgpu.rs:1289`). The Metal adapter's only job is to translate native events into that **already-existing** vocabulary — no new event types, because the core's input semantics are platform-neutral.

| `CanvasInputEvent` variant | Web source | Metal/native source |
| --- | --- | --- |
| `PointerDown/Move/Up/Cancel { pointer_id, screen }` | DOM Pointer Events | macOS `NSEvent` mouse; iOS `UITouch` (multi-touch → multiple `pointer_id`s, already a field) |
| `Wheel { screen, delta_y }` | `wheel` event | macOS `scrollWheel`; iOS pinch/pan gesture recognizers mapped to wheel/zoom deltas |
| `DoubleClick { screen }` | `dblclick` | `NSClickGestureRecognizer` / double-tap |
| `FitScene`, `FocusBounds`, `SetCamera` | shell buttons (`RendererCanvasHostHandle`) | native toolbar/shortcut → same camera commands |

`screen` is in CSS-px-equivalent logical points; the core multiplies by `device_pixel_ratio` internally (`webgpu.rs:518,690`). The adapter passes **logical points** and lets the core scale — see §5. Hit testing (`hit_at_screen`, returning `CoreHitResult`, `stats.rs:53`), drag interpretation (`input_drag`), selection geometry, and patch generation all stay in core (Locked Decision: performance-sensitive canvas work lives in Rust/core). Keyboard shortcuts that are pure shell actions (delete selection, copy/paste of objects, undo/redo) are routed by the **native shell**, not the renderer — matching how the web shell, not the renderer, owns those today.

### 5. Display scale

Web's `device_pixel_ratio` (`window.devicePixelRatio`) generalizes directly to native backing scale. The core already treats it as an opaque multiplier; the contract is to feed the native value through the unchanged `resize(width, height, display_scale)` path.

| Web | Metal adapter |
| --- | --- |
| `window.devicePixelRatio` | macOS `NSScreen.backingScaleFactor` / `NSView.window.backingScaleFactor`; iOS `UIScreen.nativeScale` / `UITraitCollection.displayScale` |
| `engine.resize(rect.width, rect.height, dpr)` (`RendererCanvasHost.tsx:163`) | `resize(logicalW, logicalH, backingScale)` → core sets `config.width = round(w * scale)` (`webgpu.rs:735`) |
| ResizeObserver drives resize | `viewDidChangeBackingProperties` / `traitCollectionDidChange` / layout pass drives resize |

Logical-point vs physical-pixel separation is **already correct in the core**; the adapter just supplies native scale and native logical bounds. No core change.

### 6. Platform diagnostics

The web adapter surfaces `WebGpuFrameStats` (`stats.rs:8`, returned by `render_frame`) and `WebGpuDebugSnapshot` (`debug_snapshot`, `webgpu.rs:1324`) into the diagnostics drawer (`RendererDiagnosticsDrawer`). These payloads are pure serde structs — **fully reusable on Metal**. The contract:

- Render/text/cache counters in `WebGpuFrameStats` (visible counts, vertex/draw ranges, glyph + fallback + atlas + layout/raster cache stats, patch/dirty-range/rebuild counts, slot capacity/compaction) are platform-neutral and emitted identically.
- The `backend` string flips from `"rust-wgpu-visible"` to a Metal marker (e.g. `"rust-wgpu-metal"`), and the WebGPU-probe report (`WebGpuProbeReport`, `stats.rs:141`) is replaced by a Metal capability probe with the same field shape (`supported`, `adapter_found`, `device_created`, `surface_configured`, `format`, `present_mode`, `backend`, `enabled_backends`).
- Native-only telemetry the adapter *may* add without touching core: GPU family / Metal feature set, ProMotion refresh rate, thermal state, memoryless-attachment usage. These are adapter-layer additions, never new core fields.

### 7. Concrete factoring sketch (design intent, not to be implemented now)

The contract implies one refactor of `webgpu.rs`: extract the portable state into a `SceneRenderer` (no `web_sys`, no `canvas`) and let each platform adapter own surface + I/O.

```rust
// PORTABLE (no web_sys, no HtmlCanvasElement): the shared core engine.
pub struct SceneRenderer {
    scene: Option<SceneSnapshot>,     // model.rs — unchanged
    camera: CameraState,              // model.rs — unchanged
    width: f64, height: f64, display_scale: f64,
    vertex_ranges: VertexRanges,
    text_engine: TextEngine,          // text.rs — unchanged
    text_layout_cache: TextLayoutCache,
    input_drag: Option<InputDragState>,
    last_hit: Option<CoreHitResult>,  // stats.rs — unchanged
    // + all *_count diagnostics fields
    // GPU handles injected by the adapter (wgpu, backend-agnostic):
    device: wgpu::Device, queue: wgpu::Queue,
    surface: wgpu::Surface<'static>, config: wgpu::SurfaceConfiguration,
    pipeline: wgpu::RenderPipeline, /* bind group, buffers, atlas … */
}

impl SceneRenderer {
    // Pure data-in/data-out — identical bodies to today's methods:
    pub fn load_scene(&mut self, snapshot: SceneSnapshot);                 // was loadScene
    pub fn apply_patch_batch(&mut self, patches: Vec<RenderScenePatch>);   // was applyPatchBatch
    pub fn input_batch(&mut self, events: Vec<CanvasInputEvent>) -> CoreInputBatchResult;
    pub fn render_frame(&mut self) -> WebGpuFrameStats;                    // encoder/pass/present
    pub fn overlay_request(&self, id: &str, field: &str) -> Option<CoreOverlayRequest>;
    pub fn debug_snapshot(&self) -> WebGpuDebugSnapshot;
    pub fn resize(&mut self, w: f64, h: f64, display_scale: f64);
}

// WEB ADAPTER (today's ShapeWebGpuRenderer, thinned): wasm-bindgen JSON wrappers
//   + HtmlCanvasElement surface + SurfaceTarget::Canvas + Backends::BROWSER_WEBGPU.

// METAL ADAPTER (new, behind a `metal-adapter` cargo feature):
//   CAMetalLayer/MTKView surface + Backends::METAL + native text overlay host
//   + NSEvent/UITouch → CanvasInputEvent translation. Drives the SAME SceneRenderer.
```

The Metal adapter is therefore a *sibling* of the web adapter over a shared `SceneRenderer`, not a second renderer. This is the structural assertion the contract makes; the actual extraction is owned by a later migration task (P6 / T6.3 Rust boundary), not this design pass.

### 8. Ownership boundary (what Metal does NOT own)

Per P1 Verify ("Product shell retains API/MCP/business state") and the T1.3 stop-condition:

- **No scene model fork.** Metal consumes `SceneSnapshot`/`RenderScenePatch` and emits `CoreInputBatchResult`; it never defines object types, `nodeType`/`edgeType` semantics, templates, or persistence.
- **No business/MCP/export logic.** Comments, artifacts, tags registry, proposals, MCP companion state, and exports stay in the shell/server (the `excludedBusinessFields()` set from T0.1) — the macOS/iOS shell owns them, exactly as the web shell does.
- **No canonical persistence rules.** Document state lives in the shared canonical store (SQLite/API); the Metal adapter is render + native I/O only. Ephemeral state (viewport, hover, active tool, follow, companion animation) stays adapter/shell-local, matching the T0.1 document/ephemeral split.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| A native feature would require forking the semantic scene model. | **CLEAR (not triggered)** | Every native need maps onto an existing core payload: native surface → injected `wgpu::Surface`; native input → existing `CanvasInputEvent`; native text → existing `CoreOverlayRequest`/`CoreOverlayStyle`; display scale → existing `device_pixel_ratio` path; diagnostics → existing `WebGpuFrameStats`/probe shape. Metal-only telemetry (GPU family, ProMotion, thermal) is additive adapter-layer data, not a scene-model field. No macOS/iOS requirement forces a second object model, a per-platform `SceneSnapshot`, or template/business logic into the renderer. |

## Open questions / risks

- **Upstream T0.2/T0.3 not yet produced.** Only `T0.1.md` exists under `docs/design/ai-companion-canvas/tasks/`; the breakdown's T0.2 (package boundaries) and T0.3 (target layout) are unwritten. This contract is therefore directory-agnostic by design — it specifies *responsibility* boundaries, not file paths — and explicitly defers "where does the Metal adapter live" to T0.2/T0.3 (matching this task's "independent of its final directory" outcome). If T0.2 later chooses a layout that splits core from adapter, this contract is already aligned.
- **Core is not yet physically DOM-free** (the PARTIAL above). The `web_sys`/`HtmlCanvasElement` link in the `wgpu-probe` feature must be extracted into a web-only adapter before a Metal build can compile. Recommend a `metal-adapter` cargo feature parallel to `wgpu-probe`, with the portable `SceneRenderer` compiled under both — sequencing owned by P6/T6.3, not this pass.
- **wgpu Metal surface ergonomics.** `wgpu::SurfaceTarget::Canvas` has a clean web path; the Metal path needs `raw-window-handle` or `SurfaceTargetUnsafe::from_metal_layer`, which is `unsafe` and host-lifecycle-sensitive (drawable validity across background/foreground on iOS). This is an adapter implementation risk, not a contract gap.
- **Async device acquisition on native run-loops.** `create` is `async` (`request_adapter`/`request_device`); the native shell must bridge this to AppKit/UIKit lifecycle (the browser handles it via `wasm-bindgen-futures`). A native executor (e.g. `pollster` at init, or integration with the app's async runtime) is an adapter concern to settle when iOS is actually scaffolded (currently deferred per the breakdown's Deferred list).
