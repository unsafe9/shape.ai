## Outcome

Sequence the production cutover as **three independently-runnable, gate-bounded steps on a feature branch — (S1) land the T6.1 SQLite/op-envelope migration, (S2) land the T6.3 Rust performance boundary, (S3) swap the React shell to Svelte and delete React — with `npm run build`/`test`/`typecheck` green at every commit**, while the directory tree (`src/client`, `src/client/renderer`, `src/renderer/core`, `src/server`, `src/shared`) stays in place because the Rust core is *already* at its production location (`src/renderer/core`, crate `shape_canvas_core`) and there is no `poc/` to promote.

## Deliverable

T6.4 has two Deliverable bullets: the **migration sequence** for promoting validated engine code into the chosen renderer/core layout, moving the shell toward the Svelte location, and deleting React after acceptance gates pass (§1–§4); and the **coordination plan** for package dependencies, build scripts, entrypoints, CSS/assets, tests, and local dev commands (§5). T6.4 owns *ordering, gates, and rollback* — it does not re-decide the migration *contents*, which T6.1 (schema/SQLite), T6.2 (Svelte shell), and T6.3 (Rust boundary) already own. §1 records the two facts that collapse the sequence; §2 is the ordered step list with its dependency rationale; §3 defines the two mandatory gates; §4 the rollback posture; §5 the per-surface coordination.

### 1. Two ground-truth facts that shape (and shrink) the sequence

The breakdown's Deliverable phrasing ("promoting validated POC/engine code into the chosen renderer/core layout, moving app shell toward the chosen Svelte shell location") anticipates two moves that the repo evidence shows are **already done or out of scope**, so T6.4 must not re-litigate them:

1. **There is no POC/engine promotion left and no directory move.** The Rust core already lives at `src/renderer/core` (crate `shape_canvas_core`, `crate-type = ["cdylib","rlib"]`, `wgpu-probe` feature) and the web adapter at `src/client/renderer` (`engine.ts`/`scene.ts`/`adapter.ts`/`wasmLoader.ts`). `renderer:wasm:build` already emits `wasm-pack` output into `src/client/renderer/wasm` (gitignored), which `vite.config.ts copyRendererWasm()` already copies to `dist/client/assets/wasm`. Recent history (`870e158` "promote Rust WebGPU canvas renderer", `5d3dc31` "decouple canvas drag from React sync") confirms the engine is already the production renderer. There is no top-level `apps/` or `canvas/` and no `poc/`. **The "chosen renderer/core layout" is the current `src/` layout** — consistent with the Locked Decision "현재 production code를 바로 새 top-level layout으로 이동하지 않는다" and with T6.2 §1 / T6.3 keeping everything in place. T6.4 therefore commits: **no directory move in this sequence**; the Svelte shell replaces the React shell *in place* at `src/client/`. (A later dedicated web-shell relocation, if ever wanted, is a separate task gated on its own churn justification — the breakdown's Repo Layout Planning rule "build/test/import path churn이 migration risk를 정당화해야 한다.")

2. **The three migration contents are nearly independent and can be ordered by blast radius.** T6.1 touches only `src/server` (`storage.ts`/`mcp.ts`/`index.ts`) + `src/shared/schema.ts` and `src/renderer/core/src/model.rs` enum-relax — no `.tsx`. T6.3 touches `src/renderer/core` (one `#[cfg]` removal) + `src/client/renderer/scene.ts` (demote JS parity) + `src/client/components/RendererCanvasHost.tsx` (camera write-back) + relocates `App.tsx` canvas clipboard. T6.2 touches the 10 `.tsx` files + `package.json`/`vite.config.ts`/`vitest.config.ts`/`tsconfig.json`/`index.html`. The only file both T6.3 and T6.2 touch is `RendererCanvasHost.tsx` (T6.3 fixes the camera write-back; T6.2 extracts the whole file into `lib/canvasHost.ts` + `ShapeCanvasHost.svelte`). **Ordering T6.3 before T6.2 means the camera fix lands in the React file once and is carried into the extraction, not redone in Svelte** — this is the load-bearing ordering constraint and matches the breakdown's `Depends on: T6.2, T6.3` (both must be designed before the sequence, but their *landing* order is T6.4's call).

**Why not parallelize S1/S2/S3.** They are *content*-independent but share `App.tsx` and `RendererCanvasHost.tsx` (S2 and S3 both edit them) and the same test-runner config. S1 *could* run in its own worktree concurrently with S2 (disjoint files: server/shared/core-enum vs. client-canvas), but the gate sequence (R before X) and the single-branch acceptance model make a linear S1→S2→S3 the lower-risk default; only split S1 into a parallel worktree if schedule pressure demands it, then merge it first.

### 4. Rollback / build-availability posture

The build-availability invariant ("Build/test commands remain available throughout the migration") is satisfied structurally, not by hope:

- **Each step is independently revertible.** S1, S2, S3 are commit groups with green CI; reverting a step restores the prior green state because no step removes a capability another already-merged step depends on *in the wrong order* (S3's React deletion is last; S1/S2 never depend on Svelte; S2's `scene.ts` demotion is depended on only by S3's bridge extraction, which is in the same later step).
- **Replacement-before-deletion in S3.** The `.svelte` files and `main.ts` are added and made to compile/render *before* the `.tsx` files and React deps are removed, so there is no commit where the app cannot build. This is the same "Svelte files replace `.tsx` before removal" property T6.2 §5(5) established; T6.4 makes it the sequencing rule.
- **SQLite recoverability (S1).** The T6.1 reshape is gated/idempotent and writes a one-time `*.pre-meta.bak` of the single `sql.js` file before its first reshaping write (T6.1 §5), so an S1 failure is recoverable by restoring the file; no destructive DDL is run.
- **The branch is the macro-rollback unit.** If S4 acceptance fails, the whole branch is abandoned/reset to the S0 baseline without touching `main`. Per the AGENTS guardrail, no substantial work starts on `main`.

## Open questions / risks

- **`vitest.config.ts` `react()` plugin is an extra removal point T6.2 under-counted.** Verified: `vitest.config.ts` loads `@vitejs/plugin-react` independently of `vite.config.ts`. GATE-X §3 already lists it, but flag it explicitly so the React-removal grep covers *both* config files, not just `vite.config.ts` — otherwise `@vitejs/plugin-react` cannot be fully uninstalled.
- **S1↔S2 worktree-parallelism is optional, not free.** §2 notes S1 (server/shared/core-enum) and S2 (client-canvas) touch disjoint files and *could* run in parallel worktrees. The cost is that GATE-R then needs both merged before evaluation, and S1's `model.rs` enum-relax and S2's `model.rs` `#[cfg]` removal both edit `model.rs` — a Rust merge point. Default to serial S1→S2; only split under schedule pressure, and merge S1 first.
- **GATE-R's boundary tests must outlive S3 unchanged.** The risk in any framework swap is that someone "ports" the boundary tests to a Svelte harness and weakens them. §2/§3 require they stay framework-neutral (drive `ShapeCanvasEngine` directly); flag so S3 does not rewrite them — they are the proof that the swap didn't move canvas state into Svelte.
- **Directory-move temptation at S4.** Once Svelte lands, a reviewer may want to relocate the shell to a dedicated web-shell folder "while we're here." §1 defers that to a separate, churn-justified task; flag so S4 acceptance does not silently scope-creep into a tree move that the Locked Decision and this Stop-or-ask forbid in this pass.
- **T6.5 consumes this branch, not `main`.** The final direction review (T6.5) reviews the merged result; if S4 is abandoned, T6.5 reviews the design intent instead. Flag so the review gate knows whether it is auditing shipped code or a plan.
