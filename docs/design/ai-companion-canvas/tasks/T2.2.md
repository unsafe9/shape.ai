# T2.2 Minimal Figma-Like Editing Tools

> Phase P2 (Universal Primitive Editing Slice), Wave D. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P2 intro, T2.2); upstream `docs/design/ai-companion-canvas/tasks/T2.1.md` (primitive vocabulary + demote/keep lists); real symbols in `src/shared/{renderPatch.ts,renderScene.ts,schema.ts}`, `src/renderer/core/src/{model.rs,webgpu.rs,stats.rs}`, `src/client/renderer/{engine.ts,scene.ts}`, `src/client/App.tsx`, `src/client/lib/nodeClipboard.ts`.
> Relationship to T2.1 / T2.4 / T2.5: T2.1 fixed the *primitive model* (`shape`/`text`/`edge`/`frame`/`image_artifact`/`comment_marker`). T2.2 specifies the **direct-manipulation tool set and multi-select model** that drives those primitives, by *extending the existing input vocabulary and op vocabulary*, not inventing a parallel one. Persistent group/ungroup, freeform hulls, membership drag-in/out, and the full label model are **T2.4** — T2.2 only needs *transient* multi-select that creates no permanent group. Operation metadata (`operationId`/`actorId`/`baseRevision`/`targetIds`) is **T2.5** — T2.2 keeps the new ops batchable and id-stable so that envelope drops on cleanly later.

## Outcome

A minimum direct-manipulation tool set — select / pan / zoom / create-shape / create-text / create-edge / frame / resize / align-distribute / z-order / duplicate / copy-paste / comment / delete — plus a transient multi-select model (marquee, modifier-click, select-all-in-frame, batch move/z-order/delete), specified as **additive extensions to the existing `CanvasInputEvent` input vocabulary and `RenderScenePatch` op vocabulary** so that a slide, todo board, wiki-note cluster, and architecture box diagram can be assembled by hand, and multiple objects can move together without becoming a permanent group.

## Deliverable

The breakdown's T2.2 Deliverable has two bullets: a **tool plan** (§1–§2) and a **multi-select plan** (§3). §4 is the input-vocabulary delta these need, §5 is the op-vocabulary delta, §6 maps each tool to its core-vs-shell home per the Locked Decisions, and §7 holds the line against design-tool drift (the Stop-or-ask). Every named tool and multi-select capability from the breakdown is covered; nothing beyond them is added.

### 1. What already exists vs what T2.2 adds

The renderer core (`webgpu.rs`) already drives a working subset of these tools through `InputDragState` and `RenderScenePatch`. Building on the existing seam means most tools are **wiring an already-present op to a gesture/affordance**, and only three families (object resize, batch transforms, align/distribute) are genuinely new core work.

| Tool (breakdown) | Today | Existing gesture / op | T2.2 work |
| --- | --- | --- | --- |
| select | exists | `PointerDown`→`selection_from_hit`→`Select`; `InputDragState` single-pick | extend to multi-id selection (§3) |
| pan | exists | `InputDragState::Pan` on empty hit | none (keep) |
| zoom | exists | `CanvasInputEvent::Wheel`→`zoom_camera_at_screen`; `FitScene`/`FocusBounds` | none (keep) |
| create shape | partial | `RenderScenePatch::CreateCard{card}` exists; today reached only via App.tsx `addNode`/MCP | add an active **create tool** + click/drag-to-place gesture in core (§2, §4) |
| create text | new slot | T2.1 models `text` as box-less `shape` (`styleKey:"text-plain"`); reuses `CreateCard` | same `CreateCard` op + `text` style preset; double-click-empty → text (§2) |
| create edge | exists | `InputDragState::Edge` port-drag → `CreateEdge` on `PointerUp` over a `target` port | none (keep); also reachable from create-edge tool |
| frame / group | partial | `CreateGroup{group}` exists (App.tsx/MCP); `MoveGroup` drag exists | add a **frame tool** drag-to-draw rectangle → `CreateGroup` (§2). Persistent membership/hulls = **T2.4** |
| resize | **missing** | none — `InputDragState::Card` emits `MoveCard` only; no handles | **new**: resize handles + `ResizeCard`/`ResizeGroup` ops (§2, §5) |
| rotate | **omitted** | none | **not built** — breakdown says "only if required"; no primitive needs it (§7) |
| align / distribute | **missing** | none | **new**: `AlignCards`/`DistributeCards` batch op over a selection (§2, §5) |
| z-order | exists | `SetCardZIndex{id,zIndex}` exists | add bring-front/send-back/forward/back affordances computing zIndex (§2) |
| duplicate | app-only | `cloneNodeForPaste` (`nodeClipboard.ts`) → `addNode` path; no core op | promote to a `DuplicateObjects` batch op so it is actor-trackable (§5) |
| copy / paste | app-only | `copyNode`/`pasteCopiedNode` in App.tsx; ephemeral JS clipboard | keep clipboard ephemeral (shell); paste emits `CreateCard`(s) (§2, §6) |
| comment | exists | `addShapeSceneComment` / MCP `add_comment` → `SceneComment` | none (keep); comment is anchored to any `SceneSelection` target |
| delete | exists | `DeleteCard`/`DeleteGroup`/`DeleteEdge` (with cascade in `commitAppPatch`) | extend to batch delete over multi-select (§3, §5) |

### 2. Tool plan — per-tool gesture, op, and home

Tools are modeled as an **ephemeral active-tool** state (one of `select | shape | text | edge | frame`), which is exactly the "active tool" item the Locked Decisions list as *ephemeral activity state* — it never persists in `Scene`. `select` is default; the others are momentary creation modes that revert to `select` after one placement (Figma's behavior). The active tool lives in the shell/core input layer, **not** in `Scene` document state.

| Tool | Gesture | Emits (op or input) | Notes |
| --- | --- | --- | --- |
| **select** | click → pick; drag on object → move; drag on empty → marquee (§3) | `Select` / `MoveCard` / `MoveGroup` (existing) | default tool; modifier-click extends selection (§3) |
| **pan** | space-drag or middle-drag or empty-drag w/o marquee modifier | camera mutation in core (`InputDragState::Pan`) | existing; ephemeral, no op |
| **zoom** | wheel / pinch; `FitScene`, `FocusBounds` | camera mutation in core | existing; ephemeral, no op |
| **create shape** | click (default `390×390`) or drag-to-size rectangle | `CreateCard{ card: RenderCard }` | `RenderCard.styleKey` from a shape preset, `meta.semanticType` unset (T2.1). New card gets a fresh stable id and `groupId` = active frame or scene root frame |
| **create text** | click → empty text box; double-click empty canvas → text + immediate edit | `CreateCard` with `styleKey:"text-plain"` then `EditCardText` | box-less `shape` per T2.1 §1; reuses `RenderObjectKind "text"` hit kind + `text.rs` shaping; no new render type |
| **create edge** | drag from a source `port` to a target `port` | `CreateEdge{ groupId, source, target, edgeId, label? }` | existing port-drag path in `webgpu.rs` (`InputDragState::Edge`); the tool just pre-arms port hit-testing. Edge `groupId` inherited from source card |
| **frame** | drag-to-draw rectangle | `CreateGroup{ group: RenderGroup }` | T2.2 creates an empty frame by geometry; **membership attach/detach, nested moves, freeform hulls = T2.4**. `parentGroupId` defaults null (top-level) or active frame |
| **resize** | drag a corner/edge handle on a selected `shape`/`frame` | **new** `ResizeCard{ id, bounds }` / `ResizeGroup{ id, bounds }` (§5) | handles + hull math in core; `size`/`bounds` write canonical geometry. Aspect-lock on shift is a shell modifier flag (§4) |
| **align / distribute** | toolbar action over ≥2 (align) / ≥3 (distribute) selected | **new** `AlignCards{ ids, axis, mode }` / `DistributeCards{ ids, axis }` (§5) | one batch op = one operation event (T2.5-ready). Geometry computed in core from selection bounds |
| **z-order** | bring-to-front / send-to-back / forward / backward | `SetCardZIndex{ id, zIndex }` (existing), batched for multi (§3) | new zIndex computed in core from min/max of siblings in the same frame; no new op for single |
| **duplicate** | ⌘D / drag-with-alt | **new** `DuplicateObjects{ ids, delta }` (§5) | replaces the app-only `cloneNodeForPaste`→`addNode` path with a core op so it is one actor-tracked event; offsets clones, remaps ids, rewires intra-selection edges |
| **copy / paste** | ⌘C / ⌘V | ephemeral JS clipboard (shell) → paste emits `CreateCard`(s) / `CreateEdge`(s) | clipboard buffer is ephemeral and stays in the shell (`nodeClipboard.ts` precedent); only the paste *result* is a document op |
| **comment** | comment tool → click a target → body | `addShapeSceneComment(scene, target, body)` / MCP `add_comment` | existing; `target` is any `SceneSelection` (`canvas`/`group`/`node`/`edge`) |
| **delete** | Delete/Backspace; context menu | `DeleteCard` / `DeleteGroup` / `DeleteEdge`, batched for multi (§3) | existing cascade (incident-edge removal, descendant-group removal) in `commitAppPatch` / `delete_card` Rust path is preserved |

**Rotate is deliberately not built.** The breakdown lists it "only if required," and none of the four target surfaces (slide, todo board, wiki cluster, box diagram) or the T2.1 primitive set needs rotation. `RenderCard`/`RenderGroup`/`model.rs` carry no angle field today (verified: no `rotate`/`angle`/`rotation` symbol anywhere in the render contract or core). Adding rotation would require an angle field on geometry + rotated hit-testing + rotated text layout — that is design-tool parity, so it is excluded per §7.

### 3. Multi-select plan — transient selection that creates no permanent group

This is the second Deliverable bullet and the second P2 Verify line ("multiple objects can be selected and moved together without creating a permanent group"). The constraint: multi-select must be **ephemeral** and produce **no `SceneGroup`**. Persistent grouping is T2.4.

Today `SceneSelection` (both `schema.ts` `sceneSelectionSchema` and `model.rs::SceneSelection`) is single-target: `Canvas | Group{id} | Node{id} | Edge{id}`. Two viable shapes for multi-select:

- **(A) Extend `SceneSelection` with a `Multi{ targets: SceneSelection[] }` variant** — persists the multi-set in document `selection`.
- **(B) Keep `SceneSelection` single-target in the document; hold the multi-set as an *ephemeral core selection set*** that is not serialized into `Scene.selection`.

**Recommended: (B), with a small additive document touch only if a single canonical `selection` must echo a multi-set.** Rationale: the Locked Decisions classify selection-as-active-set as *ephemeral activity state*, and the document `selection` field exists mainly so MCP/API/persistence can restore a focus. Keeping the live multi-set in core (where hit-testing, marquee geometry, and selection-bounds already live per the Locked Decisions) avoids a breaking change to `sceneSelectionSchema` and to the MCP `set_selection`/`get_group` contracts. The canonical `selection` continues to carry the *primary/anchor* target (or `canvas`), exactly as today. If product later needs the full multi-set echoed canonically, add an **additive** `Multi` variant in T2.4/T2.5 alongside grouping — not now.

| Multi-select capability (breakdown) | Mechanism | Lives in |
| --- | --- | --- |
| **marquee selection** | drag on empty canvas with select tool → rubber-band rect; on `PointerUp`, core hit-tests all object AABBs intersecting the rect | **core** (`webgpu.rs`): new `InputDragState::Marquee{ pointer_id, start }`; selection-set is core ephemeral state. Marquee rect render is a transient overlay primitive |
| **modifier-click selection** | shift/⌘-click toggles a target in/out of the set | **core** selection set; needs modifier flags on `PointerDown` (§4) |
| **select all in frame/group** | ⌘A or context action selects all members of the active frame | **core**: enumerate cards/edges where `groupId == frameId` (already indexed) → selection set |
| **selection bounds** | union AABB of the selection set, used by resize/align/move | **core** (`selection_world_rect` already computes a single-target rect; generalize to the set) |
| **batch move** | drag any selected object → translate the whole set by the same delta | **core**: emit one `MoveObjects{ ids, delta }` (or N `MoveCard`/`MoveGroup`) per pointer-move; see §5 batching note |
| **batch resize where safe** | drag a handle on the selection bounds → scale members proportionally | **core**: `ResizeObjects` over the set; "where safe" = uniform scale of the union bounds, no per-object skew (no boolean/vector math — §7) |
| **batch z-order** | bring-front/back applied to all selected, preserving relative order | **core** computes per-id zIndex; emits batched `SetCardZIndex` |
| **batch delete** | Delete over the set | batched `DeleteCard`/`DeleteEdge`/`DeleteGroup` with existing cascade |

The key invariant: **selecting and batch-moving N objects mutates each object's own `position`/`bounds`; it never creates a `SceneGroup`.** The set evaporates on click-away. This is what separates T2.2 transient multi-select from T2.4 persistent frames.

### 4. Input-vocabulary delta (`CanvasInputEvent` / `model.rs`) — additive

Today's `CanvasInputEvent` (verified in `model.rs:407`) has no modifier flags and no marquee. Three additive changes; none breaks existing payloads (new fields are optional / new variants).

```rust
// src/renderer/core/src/model.rs — CanvasInputEvent additions (sketch, not to implement here)
PointerDown { pointer_id: i32, screen: WorldPoint, modifiers: Option<PointerModifiers> },  // +modifiers
// new:
struct PointerModifiers { shift: bool, meta: bool, alt: bool }   // marquee-add, multi-toggle, duplicate-drag/aspect-lock
// no new top-level input event is required for marquee — it is a drag mode entered from PointerDown on empty
// when the active tool == select; the rubber-band is core ephemeral state, surfaced as a transient overlay.
```

On the web adapter side (`engine.ts` `onPointerDown`/`onPointerMove`), the `PointerEvent` already exposes `shiftKey`/`metaKey`/`ctrlKey`/`altKey`; today they are dropped (only a `⌘/Ctrl+Enter` overlay shortcut reads them, `engine.ts:420`). T2.2 forwards them into the `pointer-down` batch payload as `modifiers`. `sendInputBatch` and the `RustCanvasInputEvent` type in `scene.ts` gain the optional `modifiers` field. The active **tool** is shell→core state set via a new lightweight input event (e.g. `SetActiveTool{ tool }`) or a core setter; it is ephemeral and never serialized.

`InputDragState` (`webgpu.rs:428`) gains:

```rust
enum InputDragState {
    Pan { .. }, Group { .. }, Card { .. }, Edge { .. },   // existing
    Marquee { pointer_id: i32, start: WorldPoint },        // new — rubber-band select
    Resize { pointer_id: i32, target: ResizeTarget, handle: HandleId, start: WorldPoint, start_bounds: WorldRect }, // new — object resize
}
```

### 5. Op-vocabulary delta (`RenderScenePatch`) — additive, batchable, T2.5-ready

The existing union (`renderPatch.ts:6`, mirrored `model.rs:355`) already covers create/delete/move/z-order/edit/connect/select. T2.2 adds the smallest set the new tools need, each shaped so a T2.5 operation envelope (`operationId`, `actorId`, `actorType`, `clientId`, `targetIds`, `timestamp`, `baseRevision`) can wrap it without changing the op body. Each maps to the existing `applyRenderPatchToShapeScene` → `commitAppPatch` translation (increment `sceneVersion`, cascade, keep edges valid).

| New op (TS `RenderScenePatch` + `model.rs`) | Translates to app `ScenePatch` | For tool(s) |
| --- | --- | --- |
| `{ kind: "resize-card"; id; bounds: WorldRect }` | `nodes: [{ ...node, position:{x,y}, size:{width,height}, updatedAt }]` | resize |
| `{ kind: "resize-group"; id; bounds: WorldRect }` | `groups: [{ ...group, bounds, updatedAt }]` (members optionally re-clamped — T2.4 owns hull) | resize |
| `{ kind: "align-cards"; ids: string[]; axis: "x"\|"y"; mode: "start"\|"center"\|"end" }` | one `nodes:[…]` upsert recomputing each `position` from selection bounds | align |
| `{ kind: "distribute-cards"; ids: string[]; axis: "x"\|"y" }` | one `nodes:[…]` upsert spacing centers evenly | distribute |
| `{ kind: "duplicate-objects"; ids: string[]; delta: WorldPoint }` | `nodes:[…]`/`edges:[…]` upserts with new ids, offset by `delta`, intra-set edges rewired; `selection` → the clones | duplicate, paste |
| `{ kind: "batch"; ops: RenderScenePatch[] }` | folds child ops into a single `ScenePatch` (one `sceneVersion` bump, one event) | batch move / resize / z-order / delete |

Notes:
- **`batch` is the multi-select workhorse.** Rather than inventing `MoveObjects`/`DeleteObjects`/`ResizeObjects` for every verb, a `batch` wrapper lets transient multi-select reuse the *existing* single-object ops (`move-card`, `move-group`, `set-card-z-index`, `delete-card`/`delete-edge`/`delete-group`) and the *new* `resize-card`/`align-cards`/etc., applied atomically. This keeps the op vocabulary small (Stop-or-ask §7) and gives T2.5 exactly one envelope per user gesture with a `targetIds` list = the batched ids. `commitAppPatch` already merges multi-entry `nodes`/`edges`/`removeNodeIds` arrays in one pass, so `batch` mostly concatenates child app-patches.
- **`duplicate-objects` replaces an app-only path.** Today duplicate/paste run through `cloneNodeForPaste` (`nodeClipboard.ts`) + `addNode`, which is *not* an actor-tracked core op. Promoting it makes "primitive operations are actor-tracked and serializable" (P2 Verify) true for duplicate/paste too.
- **No new geometry columns.** `resize-*` writes `size`/`bounds` which already denormalize to `nodes(x,y,width,height)` / group bounds in `storage.ts`; no `ALTER TABLE`.
- **`select` stays single-anchor in the document.** Multi-select set is core-ephemeral (§3-B); if echoed, an additive `Multi` selection variant is a T2.4/T2.5 decision.

### 6. Core-vs-shell placement (honors the Locked Decisions)

Per "Canvas-related performance work belongs in Rust/core by default" and the explicit list (hit testing, selection geometry, grouping hull geometry, camera math, input batching), the split is:

| Concern | Home | Why |
| --- | --- | --- |
| hit testing, marquee intersection, selection-bounds union | **Rust core** (`webgpu.rs` hit path, `stats.rs::CoreHitResult`) | listed performance-sensitive work; already there for single-pick |
| drag-state machine (pan/move/resize/marquee/edge), camera math, zoom | **Rust core** (`InputDragState`, `zoom_camera_at_screen`) | input batching + camera math are core per Locked Decisions |
| align/distribute/duplicate geometry, z-order recompute | **Rust core** | selection geometry + render primitive generation |
| op emission (`RenderScenePatch`) and canonical apply | **shared contract** (`renderPatch.ts`) → server persistence | already the canonical write seam |
| active tool, ephemeral JS copy/paste buffer, toolbar/menus, modifier capture from DOM | **shell** (Svelte target; React today is migration input) | ephemeral UI orchestration; not perf-sensitive. `nodeClipboard.ts` clipboard stays shell-side |
| comment compose UI; comment op | shell UI → `addShapeSceneComment` / MCP | existing |

No marquee math, hull math, or selection geometry is placed in shell component state. The shell only forwards DOM modifier flags and active-tool changes into the core input batch.

### 7. Scope guard — minimum working canvas composition, not design-tool parity

The Stop-or-ask is "the tool list drifts into full design-tool parity." Explicit exclusions held in this design (each also a breakdown Explicit Non-Goal where noted):

- **No path/vector editing, no boolean geometry, no auto-layout, no component system** (Explicit Non-Goal). Resize is uniform AABB scale; "batch resize where safe" = scale union bounds, never per-object skew or vector reshaping. Freeform hull *visualization* is T2.4 and is hit-test/visual only — not boolean editing.
- **No rotate** (breakdown "only if required" → not required; §2).
- **No alignment guides / smart-snap engine, no measurement overlays, no constraints.** Align/distribute are one-shot batch transforms over an explicit selection, not a live constraint system. (Snap is part of the broader Done Criteria but is not a T2.2 Deliverable bullet; not added here.)
- **No styling/property panel work** beyond what `styleKey` selection already gives; T2.3 owns text, T2.4 owns labels/tags.
- The op vocabulary grows by **six additive entries** (`resize-card`, `resize-group`, `align-cards`, `distribute-cards`, `duplicate-objects`, `batch`), and the input vocabulary by **modifier flags + two drag states (`Marquee`, `Resize`) + active-tool**. That is the floor for the listed tools, not a superset.

## Open questions / risks

- **Multi-select selection echo (option A vs B).** Recommending the ephemeral core selection set (B) to avoid a breaking `sceneSelectionSchema`/MCP change in P2. If product needs the multi-set restored across reloads or visible to MCP `get_group`, the additive `Multi` variant (A) should be decided alongside T2.4 grouping / T2.5 op model — flagging so it is a deliberate choice, not a silent default.
- **`batch` vs per-verb plural ops.** `batch` keeps the vocabulary small and gives T2.5 one envelope per gesture, but an op-log reader must descend into `ops[]` to see `targetIds`. If T2.5 prefers flat per-verb ops (`move-objects`, `delete-objects`) for a cleaner event stream, that is a T2.5 call; T2.2 only requires *some* atomic batching primitive. Both are additive.
- **Resize handle hit-testing precision under LOD.** Resize handles are small screen-space targets; at low zoom (compact LOD, T3.1) handles may shrink below a hittable size. Handle hit-testing should use a screen-space tolerance independent of object world size — a core hit-test detail to confirm with T3.1's LOD policy, not a schema concern.
- **Duplicate edge-rewiring scope.** `duplicate-objects` rewires edges *internal* to the duplicated set and drops edges crossing the boundary (Figma behavior). Confirming this matches product expectation; alternative (keep boundary-crossing edges pointing at originals) is a one-line policy flip in the op's app-patch translation.
