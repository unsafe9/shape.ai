# T6.3 Rust-Owned Canvas Performance Boundary

> Phase P6 (Product Integration, Svelte Migration, And Rust Boundary Plan), Wave J. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P6 intro, T6.3); upstream `docs/design/ai-companion-canvas/tasks/T1.1.md` (platform-neutral `CanvasCore` contract — owner of camera math, hit, selection geometry, cull, LOD, text, op application), `T1.2.md` (web adapter contract — `ShapeCanvasEngine`/`RendererCanvasHostHandle`/`EngineEvent`; flags `scene.ts` JS geometry + `App.tsx` clipboard as "owned by T6.3"), `T6.1.md` (schema evolves in place; op metadata rides the T2.5 envelope into `events`, never the core/op kinds).
> Real symbols grounded in: `src/renderer/core/src/webgpu.rs` (`ShapeWebGpuRenderer`: `load_scene`, `apply_patch_batch`, `input_batch`, `render_frame`, `overlay_request`, `debug_snapshot`; `screen_to_world`/`world_to_screen`/`zoom_camera_at_screen`/`fit_camera_to_scene`/`focus_camera_to_bounds`/`clamp_camera`; `hit_scene_at_screen`; `build_draw_list`/`padded_world_viewport`; `selection_world_rect`; `overlay_request_for_card`), `model.rs` (`CanvasInputEvent` (feature-gated), `RenderScenePatch`, `SceneStateTokens.compact`), `stats.rs` (`CoreHitResult`, `WebGpuFrameStats`, `WebGpuDebugSnapshot`), `src/client/renderer/engine.ts` (`ShapeCanvasEngine`, `sendInputBatch`, `applyPatchBatchInRust`, `mirrorAcceptedPatches`, `EngineEvent`), `scene.ts` (`applyScenePatch`, `validateScenePatch`, `screenToWorld`/`worldToScreen`/`worldRectToScreen`, `rectsIntersect`/`pointInRect`/`sceneWorldBounds`, `truncateText`), `adapter.ts`, `src/client/components/RendererCanvasHost.tsx` (`RendererCanvasHostHandle`, `cameraFromStats`, `cameraAlmostEqual`, the `[camera]` write-back effect), `src/client/App.tsx` (global `keydown`, `copyNode`/`pasteCopiedNode`, `formatNodeMarkdown`/`cloneNodeForPaste`), `src/client/renderer/benchmark.ts` (`sceneWorldBounds`).

## Outcome

Audit every canvas-adjacent responsibility, prove that the **performance-critical set already lives in Rust/core** (`ShapeWebGpuRenderer`), and name the small residue still computed in TypeScript — the `scene.ts` JS-geometry/op-mirror layer and `App.tsx` canvas clipboard/keyboard — so it is demoted to core/adapter *before* the Svelte shell (T6.2) can inherit it as component state. The boundary is enforced by contract tests that prove the shell calls narrow adapter APIs (`inputBatch`/`applyPatchBatch`/`overlayRequest`) instead of deriving canvas state through reactivity.

## Deliverable

T6.3 has three Deliverable bullets: the **responsibility audit** (§1), the **migration plan** moving residue into Rust/core or the adapter while TS/Svelte keeps only product semantics + API + DOM-overlay mounting + shell event routing (§2), and the **boundary/contract tests** proving the shell calls narrow canvas APIs rather than deriving canvas state through reactivity (§3). §4 walks the named flows (pan/zoom/select/drag/group/label/follow/trace) as shell-event → core/adapter routes (binding Verify). Nothing beyond the bullets is added. The throughline: this is overwhelmingly a **ratification + small-demotion** task, not a port — T1.1 already specified the core as the owner and the shipping `ShapeWebGpuRenderer` already *is* that owner.

### 1. Responsibility audit — every canvas-adjacent behavior, where it lives today

The breakdown enumerates twelve responsibilities. For each, the audit records the **real current owner** and the verdict. The dominant finding: 9 of 12 are **already Rust/core-owned** and need only contract ratification; 2 are a **JS parity/mirror residue** (`scene.ts`) to demote/delete; 1 (clipboard/keyboard) is an **App.tsx leak** to relocate to the adapter (the T1.2 §5 correction, whose code-move T1.2 explicitly assigns here).

| # | Responsibility | Current owner (real symbol) | Verdict |
| --- | --- | --- | --- |

| 3 | **Selection geometry** | core: `selection_world_rect` → `WebGpuDebugSnapshot.selection_world_rect`/`selection_screen_rect` | **Rust/core (ratify).** Group/multi-select hull is the T2.4 widening of this method (T1.1 open question), not a JS responsibility. |

T6.3 owns this code-move conceptually (§2.5). |

Conclusion: the **performance-critical set (1–8) is Rust/core-owned today or core-reserved**; items 9–11 already sit on the correct adapter/shell seam; the only *behavioral* moves T6.3 commits are (a) demote/delete the `scene.ts` JS parity layer (items 5,7,8,10), (b) fix the camera write-back (item 1), and (c) relocate canvas clipboard/keyboard out of `App.tsx` (item 12). No performance-critical behavior is in TypeScript that a Svelte port could "inherit" — the risk is that the *parity residue* gets re-wired as Svelte reactive state during T6.2, which §2 forecloses.

### 2. Migration plan — what moves, what is demoted, what TS/Svelte retains

**TS/Svelte retains exactly four roles** (Locked Decision restated): product semantics (business fields in `meta`, templates, export presets, comments/proposals/MCP workflow), API/MCP calls, DOM-overlay *mounting* (not its geometry — core computes the rect/style via `overlay_request`), and shell event routing (`EngineEvent` in, imperative API out). Everything else is Rust/core or the platform adapter.

#### 2.1 Promote feature-gated core types into the default build (prerequisite)

`CanvasInputEvent` (and per T1.1's open question `RenderScenePatch`/`CoreInputBatchResult`/`CoreOverlayRequest`) are `#[cfg(feature = "wgpu-probe")]`-gated in `model.rs`. For the boundary to be the *production* canvas API (not a probe-only path), these must be available in the default `wasm-pack build` the web adapter consumes (`renderer:wasm:build`). This is the one Rust change the boundary requires and it is purely a `#[cfg]` removal — no logic. (T1.1 explicitly deferred this gate-removal to "T6.3 / the migration that owns the core module.")

#### 2.2 Demote/delete the `scene.ts` JS parity layer (items 5,7,8,10)

`src/client/renderer/scene.ts` carries a JS reimplementation of core behavior. Audit of real consumers (grep):

| `scene.ts` export | Real production consumer | Action |
| --- | --- | --- |
| `applyScenePatch` | `engine.ts` `mirrorAcceptedPatches` only (+ tests) | **Demote.** It exists to keep `engine.snapshot` so `getSnapshot()` returns a JS object. Replace with a thin getter over the core (`debug_snapshot`/a core `snapshot()` export) so the JS shadow stops being a second mutation path. Core is the single mutation authority; the adapter holds at most a *cache* of the last loaded snapshot, never a divergent fork. |
| `validateScenePatch` | none in production (tests only) | **Delete** from the production path. Validation already happens in core (`apply_patch_batch` rolls back on error and returns it). |
| `rectsIntersect` / `pointInRect` / `worldRectToScreen` / `screenToWorld` / `worldToScreen` | none in production (`scene.ts`/tests only; grep finds no `src/client` or `src/shared` consumer outside `scene.ts`) | **Delete.** Pure duplicates of `rects_intersect`/`screen_to_world`/`world_rect_to_screen_rect` in core; production never calls the JS copies. |
| `sceneWorldBounds` | `benchmark.ts` only | **Keep as a test/benchmark helper**, clearly out of the production render path (core does cull via `build_draw_list`); or fold into the benchmark harness. Not adapter ownership. |
| `truncateText` | none in production (tests only) | **Delete.** Text truncation/ellipsis is core's (`text.rs`). |

Net: `scene.ts` collapses to the **type re-exports** it shares with the core wire contract (`SceneSnapshot`/`RenderScenePatch`/`HitResult`/`DomOverlayRequest`/`FrameStats`) plus the test/benchmark `sceneWorldBounds`. No JS geometry, no JS op-apply, no JS validation survives in production. This is the structural guarantee that "Svelte state does not become source of truth for object geometry, visible object sets, hit regions, LOD, text layout, or render caches."

#### 2.3 Fix the camera two-way binding (item 1)

Today `RendererCanvasHost` reads camera back from Rust (`cameraFromStats(stats)` over `WebGpuFrameStats`/`debug_snapshot`) **and** has a `useEffect(..., [camera])` that writes the React `camera` state *into* `engine.setCamera`, guarded only by `cameraAlmostEqual`. That makes a React/Svelte value a *writer* of camera — the exact "component state becomes performance-critical source of truth" anti-pattern.

- **Rule:** camera is **core-authoritative, ephemeral**. The shell holds camera only as a *display echo* (for the minimap/zoom-badge), updated one-way from the `stats` event (`cameraFromStats`). The `[camera]`→`setCamera` write-back is removed; programmatic camera moves go through explicit imperative calls (`fitScene`/`focusBounds`/`setCamera`/`wheelAtScreen`) that route into `input_batch`, exactly as the toolbar buttons already do (`App.tsx` `fitScene`/`focusBounds`). The Svelte shell binds `camera` read-only.
- This keeps the existing `gesture` event behavior (commit `5d3dc31`, suppress resync mid-drag) — the shell never re-derives camera reactively.

#### 2.4 LOD thresholding lands core-side (item 6)

LOD is **not yet implemented**; the `SceneStateTokens.compact` token is the seed in `model.rs`. T6.3's binding constraint (not its implementation, which is P3/T3.x): the zoom→state-variant decision must be computed in core inside the `render_frame`/`build_draw_list` path keyed off `self.camera.zoom`, selecting `states.compact` vs `states.default` per object while keeping the **same object id, bounds, and slot** (visual degradation, no semantic replacement — Locked Decision). The Svelte shell must never receive a zoom value and decide visibility/detail. The adapter passes `SceneSnapshot` + camera events only; it gains no LOD logic.

#### 2.5 Relocate canvas clipboard/keyboard from `App.tsx` to the adapter (item 12)

Split rule (T1.2 §5): *acts on a canvas primitive via an op → adapter; acts on business semantics or shell chrome → shell.*

| Behavior (today in `App.tsx`) | New owner | Routed as |
| --- | --- | --- |
| Copy/paste/duplicate of selected primitive (`copyNode`/`pasteCopiedNode`, `cloneNodeForPaste`) | **Adapter** | clipboard payload = render primitive; paste emits `create-card`/`create-edge` ops with new ids via `applyPatchBatch` (the existing `create-card` duplicate/paste parity, tests at `infinite-canvas-renderer.test.ts:394`) |
| Delete selected primitive | **Adapter** | `delete-card`/`delete-edge`/`delete-group` op |
| `e`-to-edit / `Escape` / `Cmd+Enter` commit | **Adapter** | opens/commits the overlay → `edit-card-text` op (already half-owned by `engine.ts` overlay `keydown`) |
| `formatNodeMarkdown` (business markdown of a node, keyed off `nodeType`/`confidence`/`evidenceRefs`) | **Shell/template** | business export string; *not* a canvas op (these are exactly the `meta`-demoted fields from T6.1) |
| Toggle diagnostics / panels / export drawer shortcuts | **Shell** | shell UI state |

The adapter exposes canvas clipboard/keyboard as part of surface 5 (T1.2). Because the canvas-scoped half speaks only render primitives + ops, the Svelte shell never re-implements clipboard against the business `SceneNode` shape — which would re-couple the shell to the decision-graph model T6.1 is demoting. (T1.2 §5/open-questions assign the *code move* to T6.3; this is that assignment, design-level.)

#### 2.6 What does NOT move

- Persistence/revisioning (`storage.ts` `commitAppPatch`, `sceneVersion`, the T6.1 `events` log/`OperationEnvelope`) stays server/shell. The adapter relays ops; the server is the system of record. T2.5 op metadata rides *inside* the JSON envelope — the core/adapter never reads it (T1.1, T6.1).
- Templates/export presets/comments/proposals/MCP workflow stay shell/server.
- `actor_marker`/companion trace (P5) arrives as ordinary ephemeral render primitives via `load_scene`; it is **not** core logic and **not** Svelte canvas-state — it is a shell-supplied overlay layer in the snapshot (T1.1 §4).

### 3. Boundary / contract tests — prove the shell calls narrow APIs, not reactivity

The breakdown requires tests proving "Svelte calls narrow canvas APIs instead of deriving canvas state through component reactivity." The pattern **already exists** in `tests/infinite-canvas-renderer.test.ts` — spy on the `RustWebGpuRenderer` methods and assert the engine routes through them. T6.3 extends that pattern to lock the boundary. These are framework-neutral (they drive `ShapeCanvasEngine` directly, no React/Svelte test utils — satisfying T6.2's "no React test utilities" too).

| Boundary test | Asserts | Seed / pattern |
| --- | --- | --- |
| **Camera goes through `input_batch`** | `focusBounds`/`fitScene`/`setCamera`/`wheelAtScreen` each produce exactly one `input_batch` call with the right event; the shell never computes camera | EXISTS: "routes focus bounds through the Rust input boundary" (spies `renderer.inputBatch`) — extend to the other three |
| **Selection sync goes through `applyPatchBatch`, never reloads the scene** | `syncSelection` calls `apply_patch_batch` once with a `select` op and does **not** call `load_scene`, and emits no app `patch` event | EXISTS: "syncs external selection without reloading the Rust scene or emitting app patches" (spies `loadScene`/`applyPatchBatch`) |
| **No JS geometry/op-apply in production path** | grep/structural test (or import-graph assertion) that production `src/client` does not import `applyScenePatch`/`screenToWorld`/`rectsIntersect`/`validateScenePatch`/`worldToScreen` from `scene.ts` — only types | NEW: codifies §2.2 deletions; a lint/boundary test, not a runtime one |
| **Hit/overlay geometry is core-sourced** | `beginTextEdit` mounts the textarea from `overlay_request` output (rect/style from core), not from JS-computed coords; geometry refreshes via `overlay_request` after camera/card move | EXISTS: "mounts a focused native textarea with Rust-provided overlay style" + "refreshes active overlay geometry and style after Rust camera and card movement" |
| **Patch application is core-authoritative** | after `applyPatchBatch`, the engine's reported snapshot matches the core (`debug_snapshot`), proving no divergent JS shadow; an invalid op is rejected by core and surfaced, not silently JS-applied | EXISTS (adapt): "rejects invalid engine patches at the app boundary"; tighten to assert core is the rejecter |
| **Diagnostics is a one-way snapshot** | the drawer/consumer receives `FrameStats` via the `stats` event and issues no callback that mutates canvas state | EXISTS implicitly (T1.2 §6); assert the `EngineEvent` stream carries diagnostics as data only |

The acceptance bar: every pan/zoom/select/drag/group/label/follow/trace flow in §4 has at least one test that spies the corresponding narrow `RustWebGpuRenderer` method and asserts the shell forwarded the gesture rather than deriving the result.

### 4. Named flows as shell-event → core/adapter routes (binding Verify)

Each flow is "DOM/shell event → adapter normalize → core compute → result event → shell reaction (persist/echo)." No flow computes canvas state in the shell.

| Flow | Shell/DOM event | Adapter (`engine.ts`) | Core (`ShapeWebGpuRenderer`) | Shell reaction |
| --- | --- | --- | --- | --- |
| **Pan** | pointer/mouse drag on empty canvas | normalize → `RustCanvasInputEvent` | `input_batch` → `apply_input_event` updates `self.camera` | `stats` event echoes camera (read-only) |
| **Zoom** | wheel / `wheelAtScreen` / pinch | `wheel` event | `zoom_camera_at_screen` (cursor-stable) | camera echo only |
| **Select** | pointer-down on object / `syncSelection` | `input_batch` / `apply_patch_batch({select})` | `hit_scene_at_screen` → `select` op; `selection_world_rect` | `selection` event → shell sets product selection, calls `set_selection` MCP/API |
| **Drag (move)** | pointer drag on object | `pointer-move` events | core moves slot, emits `move-card`/`move-group` patch | `patch` event → shell persists via `patch_scene`/`commitAppPatch` |
| **Group** | create/delete/move-group op | `apply_patch_batch` | `create-group`/`delete-group`/`move-group` (members translated in core) | `patch` event → persist; cascade owned by server |
| **Label/tag** | tag pick in panel | — (business) | core renders `tagIds` opaquely on the snapshot (label visual only) | shell calls `update_group_tags`; re-`load_scene` with new snapshot |
| **Follow** (P5) | click companion icon → `focusBounds` | `focus-bounds` event | `focus_camera_to_bounds` | camera echo; follow target is ephemeral shell state, not canvas-state |
| **Trace** (P5) | MCP op writes / read cursor | — | `actor_marker` arrives as ephemeral render primitives in `load_scene` snapshot | shell supplies the marker layer; no core MCP awareness |

Label, follow, and trace are the three flows with a *product* half: that half (tag registry, companion identity, MCP trace) stays in the shell/server (it is business/ephemeral, not performance-critical geometry), while their *canvas* half (rendering tags/markers, camera focus) is core/adapter. This is the line the Stop-or-ask guards (§ Stop-or-ask).

## Open questions / risks

- **`getSnapshot()` after the JS shadow is removed.** §2.2 replaces the `applyScenePatch` mirror with a core-sourced snapshot. The core must expose a cheap "current snapshot" read (today only `debug_snapshot` + the last loaded JSON exist); if a full `snapshot()` export is too costly per call, the adapter may keep a *passive* cache of the last `load_scene` payload patched by accepted ops — but that cache must be asserted equal to core (the §3 "patch application is core-authoritative" test) so it never silently diverges. Decision belongs to the implementer; flag so the cache is not mistaken for a re-introduced JS source of truth.
- **Feature-gate removal scope (§2.1).** Promoting `CanvasInputEvent`/`RenderScenePatch` out of `#[cfg(feature = "wgpu-probe")]` touches the default `wasm-pack` build; confirm it does not enlarge the non-WebGPU build surface unexpectedly. Pure `#[cfg]` change, but it is the one Rust edit the boundary needs and should land before/with T6.2.
- **LOD ownership is asserted, not built.** §2.4 fixes the *owner* (core) and the *constraint* (stable identity, no Svelte threshold logic), but the actual zoom→`compact` selection is P3/T3.x. Flag so T6.2 does not, in the interim, sneak a zoom-based detail toggle into the Svelte shell.
- **Camera echo precision.** §2.3 makes the shell camera a one-way echo from `stats`. The `cameraAlmostEqual` epsilon currently exists to damp the two-way loop; once the write-back is gone, confirm the echo still updates the minimap/zoom-badge smoothly without the guard masking real moves.
