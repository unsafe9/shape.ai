# T4.1 Template Contract

> Phase P4 (Template System On Primitives), Wave G. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P4 intro, T4.1); upstream `docs/design/ai-companion-canvas/tasks/T0.1.md` (primitive/template separation, `meta`/`templateKind` convention, the binding template recipe table), `T2.1.md` (additive `meta` bag, demoted enums, export-preset demotion), `T2.2.md`/`T2.3.md` (`create-card`/`create-edge`/`create-group`/`edit-text`/`batch` ops), `T2.4.md` (`group-objects`/`set-object-tags`/`create-tag` ops + tag registry generalization), `T2.5.md` (`OperationEnvelope`, the logged-op funnel), and `D1-primitive-sufficiency-review.md` (conditions C1 image substrate, C3 `nodeType→styleKey` decoupling, C4 per-template `meta` validation).
> Real symbols grounded in: `src/shared/schema.ts` (`sceneGroupSchema`, `sceneNodeSchema`, `sceneEdgeSchema`, `tagSchema`, `exportTypeSchema`, `GroupSeedOutput`, `createGroupRequestSchema`), `src/shared/renderPatch.ts` (`RenderScenePatch` union, `applyRenderPatchToShapeScene`, `commitAppPatch`), `src/shared/renderScene.ts` (`SceneSnapshot`, `RenderCard`/`RenderEdge`/`RenderGroup`, `defaultStyles`, `SceneStyleToken`, `styleKey`), `src/server/local.ts` (`seedGroupScene` → `GroupSeedOutput`, `defaultSeedNodePositions`, `generateLocalExport`, `boundsForNodes`), `src/server/storage.ts` (`createGroup`, `nextGroupOffset`, `withWritableDb`), `src/server/mcp.ts` (`create_group`, `export_group`), `src/shared/graph.ts` (`makeMermaid`, `graphTextDigest`, `sceneGraphForGroup`).
> Relationship to upstream: T0.1/T2.1 fixed the primitive vocabulary and the `meta` demotion; T2.2–T2.5 fixed the op vocabulary and the logged-op funnel. **T4.1 owns nothing new in the primitive or op layer** — a template is a *recipe over the existing primitives and ops*. This task formalizes the de-facto template that already ships hard-coded inside `seedGroupScene`/`createGroup` into a declared `TemplateContract`, so applying a template is "construct ops, run them through the existing funnel," and the result is indistinguishable from hand-drawn objects. T4.2–T4.5 are concrete templates *authored against this contract*; this task defines only the contract.

## Outcome

Define a `TemplateContract` — template metadata + a primitive **recipe** (objects/edges/groups/tags expressed as the existing create ops), a default layout, an allowed-export set, suggested tags, and optional AI prompt hints — that **lowers entirely to existing `RenderScenePatch` create/group/tag ops** run through the existing `applyRenderPatchToShapeScene`/`commitAppPatch` funnel, so applying any template produces ordinary `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` objects with no template-private renderer, object family, persisted template field, or editing mode.

## Deliverable

The breakdown's T4.1 Deliverable is a single bullet with six parts: **contract for (1) template metadata, (2) primitive recipe, (3) default layout, (4) allowed exports, (5) suggested tags, and (6) optional AI prompt hints.** Each part is a section below. §7 gives the application pipeline (the "results in normal canvas objects" proof), §8 the placement and additive delta, §9 the relationship to the existing `seedGroupScene` template that this contract replaces. Nothing beyond the six parts is added.

### 0. Where templates live today (the thing this contract generalizes)

There is already exactly one template in the codebase — it is just hard-coded and unnamed. `seedGroupScene(prompt, …)` in `src/server/local.ts` builds a fixed 10-node / 9-edge ADR decision-graph (`node("n-proposition", "proposition", …)` … `edge("e1", "decomposes_to", …)`), positions them via `defaultSeedNodePositions`, wraps them in a `SceneGroup`, and returns a `GroupSeedOutput { title, explanation, group, nodes, edges }` (`schema.ts:268`). `createGroup` (`storage.ts:120`) calls it, offsets the group with `nextGroupOffset`, parses every object through `sceneNodeSchema`/`sceneGroupSchema`, and upserts. The `create_group` MCP tool (`mcp.ts:114`) is the wire surface.

So the seam already exists: **a template is a function that emits a group + nodes + edges, applied by upserting them.** T4.1's job is to (a) make the recipe *declared data* instead of one hard-coded ADR function, (b) route application through the **op funnel** (`applyRenderPatchToShapeScene`, so each created object is a logged operation per T2.5) rather than the raw `upsert*InDb` calls, and (c) carry the five extra recipe parts (metadata, layout, exports, tags, prompt hints) the breakdown lists. `GroupSeedOutput` is the ancestor of `TemplateContract`'s recipe output (§9).

### 1. Template metadata

Stable identity and presentation for the template picker/registry. **Metadata is registry data, never persisted onto the produced objects** — the only trace a template leaves on canvas state is `meta.templateKind` on the created objects (T0.1 §3 / T2.1 §2 convention), which is an *ordinary `meta` value*, not a privileged field.

```ts
// src/shared/template.ts (new shared contract — sketch, not implemented this pass)
export type TemplateId = string;            // e.g. "todo-board", "adr", "presentation"

export type TemplateMetadata = {
  id: TemplateId;
  title: string;                            // picker label, e.g. "Todo / Task Board"
  description: string;                      // one-line picker help
  category: "planning" | "knowledge" | "engineering" | "presentation" | "general";
  icon?: string;                            // picker glyph key (shell asset, not a render primitive)
  templateKind: string;                     // value written to created objects' meta.templateKind
};
```

| Field | Source / precedent | Note |
| --- | --- | --- |
| `id` / `title` / `description` | `seedGroupScene` `explanation` + `titleFromPrompt`; `createGroupRequestSchema.title` | Today these are ad-hoc strings inside the seed fn; the contract names them. |
| `category` | new (picker grouping only) | Picker UX, never reaches `Scene`. |
| `icon` | shell asset key | Shell concern (Svelte target); not a `RenderObjectKind`. |
| `templateKind` | `meta.templateKind` convention (T0.1 §3, T2.1 §2 example `meta.templateKind="adr"`) | The **only** value that lands on canvas objects, and it is a plain `meta` string. |

### 2. Primitive recipe

The recipe is the declared list of primitive objects the template creates, expressed **as the existing create ops** (T2.2/T2.3/T2.4), so "apply" is "emit these ops." It introduces **no new object kind and no new op** — every recipe element is one of `create-group`, `create-card`, `create-edge`, plus `set-object-tags`/`create-tag` for suggested labels (T2.4 §7). Recipe element ids are *template-local placeholder ids* that get rewritten to scene-unique ids at apply time (§7), exactly as `seedGroupScene` already rewrites `n-proposition` → `scopedId(groupId, "n-proposition")` (`local.ts:124`).

```ts
// src/shared/template.ts — recipe is a declarative op list over template-local ids
export type RecipeFrame = {                 // -> create-group
  localId: string;
  title: string; summary?: string;
  parentLocalId?: string;                   // nested frame; null/absent = root template frame
  tagLocalIds?: string[];
  meta?: Record<string, unknown>;           // e.g. { templateKind, semanticType }
};
export type RecipeShape = {                 // -> create-card (incl. box-less `text`, image_artifact ref)
  localId: string;
  frameLocalId: string;                     // membership (SceneNode.groupId is required)
  title?: string; summary?: string; detail?: string;
  styleKey?: string;                        // chosen from template, NOT from a demoted nodeType (D1 C3)
  tagLocalIds?: string[];
  meta?: Record<string, unknown>;           // semanticType/status/templateKind, etc.
  // image_artifact ride: meta references an existing SceneArtifact id; image *pixels* depend on
  // the image substrate primitive (D1 C1) — until it lands, an image recipe element is a
  // captioned-box placeholder, see §4 / Open questions.
};
export type RecipeEdge = {                   // -> create-edge
  localId: string;
  frameLocalId: string;
  sourceLocalId: string; targetLocalId: string;
  label?: string;
  styleKey?: string;                         // from template (D1 C3), not edgeType
  meta?: Record<string, unknown>;            // e.g. { semanticType: "depends_on" }
};
export type TemplateRecipe = {
  frames: RecipeFrame[];
  shapes: RecipeShape[];
  edges: RecipeEdge[];
};
```

Recipe-element → existing op mapping (the binding lowering table):

| Recipe element | Existing op (real symbol) | Existing apply path |
| --- | --- | --- |
| `RecipeFrame` | `create-group` (`renderPatch.ts:7`) | `renderGroupToSceneGroup` → `commitAppPatch` (with the T2.4 §10 `parentGroupId` passthrough fix) |
| `RecipeShape` (incl. box-less `text`) | `create-card` (`renderPatch.ts:13`) | `renderCardToSceneNode` → `commitAppPatch`. `text` = degenerate `shape` with a text `styleKey` (T2.1 §1) |
| `RecipeEdge` | `create-edge` (`renderPatch.ts:15`) | `commitAppPatch` validates endpoints exist |
| suggested tag (registry) | `create-tag` (T2.4 §7) | seeds the `Tag` registry if absent |
| suggested label on object | `set-object-tags` (T2.4 §7) | attaches `tagIds` to created objects |
| `meta.semanticType` / `meta.status` | carried on the `create-card`/`create-edge` payload `meta` | demoted-enum convention (T2.1 §2) |

**`styleKey` is chosen by the template, not by a `nodeType` (D1 C3).** Today `nodeToCard` sets `styleKey = node.type` and `edgeToRenderEdge` hardcodes `blocks||trades_off_with → "risk"` (`renderScene.ts:284`,`:298`); `defaultStyles` ids *are* the `nodeType` enum (`renderScene.ts:206-219`). A template recipe sets `styleKey` explicitly per element (e.g. an ADR "decision" card uses `styleKey:"decision_point"`, a todo card uses `styleKey:"task"`). This is the binding rule that lets demoted objects keep visual identity without reviving the enum coupling — it needs **no schema change** because `SceneStyleToken.id` / `RenderCard.styleKey` already accept any free string. (The core badge text decoupling — `node_type_label()` — is the separately-owned migration task from D1 C5, not T4.1.)

### 3. Default layout

The recipe carries relative geometry; apply places it into open canvas space. This generalizes the two layout mechanisms `seedGroupScene`/`createGroup` already use, with **no new geometry engine** (Explicit Non-Goal: no auto-layout system).

- **Relative positions, fixed offsets.** Each `RecipeShape` carries a template-local `position {x,y}` and `size {width,height}` (default the existing `{390,390}` from `sceneNodeSchema`, or the recipe's own — `seedGroupScene` uses `270×178`). These are *relative to the template's origin*, exactly like `defaultSeedNodePositions` (`local.ts:16`).
- **Frame bounds are derived, not authored.** Frame `bounds` are computed by `boundsForNodes(members)` (`local.ts:201`) — the same padded-union function `createGroup` already calls (`storage.ts:142`). The freeform-hull projection is T2.4 §3 (render-only); the template authors only member positions.
- **Placement into free space.** The whole template translates by the existing `nextGroupOffset(db, bounds)` (`storage.ts:132`) so a newly applied template does not overlap existing groups — this is exactly today's `createGroup` offset behavior, reused unchanged.

```ts
export type RecipeLayout = {
  origin?: WorldPoint;                       // default {0,0}; the offset pass relocates it
  defaultShapeSize?: { width: number; height: number };  // default {390,390} (sceneNodeSchema)
};
```

So "default layout" = relative member positions + `boundsForNodes` for frames + `nextGroupOffset` for placement. All three already exist; the contract only declares the relative positions as recipe data instead of the hard-coded `defaultSeedNodePositions` map.

### 4. Allowed exports

The set of `exportType` presets the template advertises. **Exports are already presets keyed off `exportType`** (`generateLocalExport`, `local.ts:164`) that *read primitives* via `sceneGraphForGroup` → `makeMermaid`/`graphTextDigest`/MADR/YADR (`graph.ts`, T2.1 §3). The template does not add an export engine; it declares which existing presets are meaningful for its content.

```ts
export type TemplateExports = {
  allowed: ExportType[];                     // subset of exportTypeSchema (schema.ts:36)
  default?: ExportType;                      // pre-selected in the export drawer
};
```

| Template (T4.x) | Sensible `allowed` (from `exportTypeSchema`) | Reads via |
| --- | --- | --- |
| ADR / design (T4.4) | `madr`, `yadr`, `design_doc_md`, `confluence_html`, `mermaid` | `generateLocalExport` over `sceneGraphForGroup` |
| Server architecture (T4.4) | `mermaid`, `architecture_image`, `image_prompt` | same; `architecture_image` returns an `imagePrompt` today (`local.ts:175`) |
| Todo / task board (T4.2) | `ai_plan_md`, `mermaid` | `taskPlanSections` already reads `type:"task"` nodes (`local.ts:365`) |
| Wiki / idea board (T4.3) | `design_doc_md`, `confluence_html` | MADR/HTML presets |
| Presentation (T4.5) | `image_prompt`, `design_doc_md` | image prompt + outline |

`allowed` is a constraint surfaced by the export drawer (shell) and `export_group` (`mcp.ts:177`); the preset code is unchanged. D1 C1 caveat: `architecture_image`/presentation image *previews* (real pixels) depend on the image substrate primitive; the export side already only emits a text `imagePrompt`, so allowed-export declaration is unaffected — the gap is in on-canvas preview, handled in §2/Open questions.

### 5. Suggested tags

Templates seed and suggest labels through the **single existing `Tag` registry** (`tagSchema`) and the generalized `tagIds[]` (T2.4 §7) — no template-private taxonomy (T2.4's Stop-or-ask; this contract honors it).

```ts
export type SuggestedTag = {
  localId: string;                           // referenced by tagLocalIds in the recipe
  name: string; color: string;               // tagSchema fields
  description?: string;
};
export type TemplateTags = {
  suggested: SuggestedTag[];                 // created via create-tag if not already present
};
```

Apply (§7): for each `SuggestedTag`, if no registry `Tag` with the same `name` exists, emit a `create-tag` op (T2.4 §7) to register it; map `localId` → the resulting `Tag.id`; then any recipe element's `tagLocalIds` become real `tagIds` via the create op's payload (or a `set-object-tags` follow-up). Color labels use the existing `Tag.color`. This is the same registry `update_group_tags`/`create_tag` (`mcp.ts:132`,`:141`) already drive — additive, not a new system.

### 6. Optional AI prompt hints

Optional, **non-canonical** hints an MCP client can read to author or extend an instance of this template. They are registry metadata that never persist onto objects and never gate rendering.

```ts
export type TemplatePromptHints = {
  systemHint?: string;                       // e.g. "This is a todo board; cards are tasks, edges are deps."
  fieldHints?: Record<string, string>;       // per-semanticType guidance, e.g. { decision_point: "..." }
  suggestedOperations?: string[];            // verb hints from the T2.5 vocabulary, e.g. ["create","connect","tag"]
};
```

| Field | Precedent | Note |
| --- | --- | --- |
| `systemHint` | the prose `seedGroupScene` bakes into node summaries (`local.ts:36`, "The choice should be driven by feasibility…") | Pulled out as advisory text, not node content. |
| `fieldHints` | the per-`nodeType` semantics MADR export assumes (`madrSections`, `local.ts:258`) | Lets an agent fill `meta.semanticType` slots correctly. |
| `suggestedOperations` | the T2.5 verb vocabulary | A hint list, never enforced. |

These are surfaced to MCP clients (a future template-aware `create_group`/template tool, P5/T5.2 "future template operations") but are advisory: a template is fully usable with `promptHints` absent (it is `optional`), satisfying "optional AI prompt hints."

### 7. Application pipeline — the "results in normal canvas objects" proof

The full contract:

```ts
export type TemplateContract = {
  metadata: TemplateMetadata;     // §1
  recipe: TemplateRecipe;         // §2
  layout: RecipeLayout;           // §3
  exports: TemplateExports;       // §4
  tags: TemplateTags;             // §5
  promptHints?: TemplatePromptHints;  // §6 (optional)
};
```

Applying a template is a pure lowering to ops — there is no template runtime, mode, or object:

1. **Allocate a frame id** (`group-${uuid}` like `createGroup`, `storage.ts:124`) and rewrite every recipe `localId` → a scene-unique id (the `scopedId` pattern, `local.ts:249`).
2. **Resolve suggested tags** (§5): emit `create-tag` for new registry entries; build `localId → Tag.id`.
3. **Build the op list** in dependency order: `create-group` (frames, parents before children) → `create-card` (shapes/text/image refs) → `create-edge` (endpoints now exist) → `set-object-tags` for suggested labels. `meta.templateKind` and `meta.semanticType` ride on each create payload; `styleKey` is set from the recipe (§2, D1 C3).
4. **Place into free space**: translate by `nextGroupOffset` (§3); frame bounds via `boundsForNodes`.
5. **Run each op through `applyRenderPatchToShapeScene`** (`renderPatch.ts:31`) wrapped in a **single T2.5 `batch` + `OperationEnvelope`** (`actorType:"human"` for picker, `"mcp"` for an agent), so the whole template application is one logged operation whose `targetIds` are the created ids.

After step 5 the scene contains only `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` rows — byte-shaped identically to hand-drawn ones, distinguishable *only* by their ordinary `meta.templateKind` value. They are selected, moved, resized, regrouped, ungrouped, labeled, deleted, commented, and exported by the **same** ops as any object, because they **are** the same objects. This is the Verify guarantee: a template is consumed at apply time and leaves nothing behind but normal primitives — exactly what `createGroup`/`seedGroupScene` already produce (a real `SceneGroup` + parsed `SceneNode[]`/`SceneEdge[]`), now generalized and logged.

### 8. Core-vs-shell placement and the additive delta

Per the Locked Decisions (performance-sensitive canvas work in Rust/core; op semantics in the shared contract; UI orchestration in the Svelte shell):

| Concern | Home |
| --- | --- |
| `TemplateContract` type, recipe-lowering to `RenderScenePatch` ops, `localId`→sceneId rewrite, tag resolution | **shared contract** (`src/shared/template.ts`) — pure data + a lowering function over the existing op funnel; no GPU work |
| running the lowered ops, geometry/hull/hit/selection of the produced objects | **Rust/core** (already owns scene-mutation application, hit testing, hull — T2.4 §10) — templates touch none of this directly; they emit ops |
| template registry, picker UI, export-drawer `allowed` filtering, prompt-hint surfacing | **shell** (Svelte target; React is migration input) |
| template-aware MCP application (future template tool) | **server/MCP** (`mcp.ts`), reusing `create_group`'s `withWritableDb` apply path |

Net additive delta (no wholesale replacement, no schema break — mirrors T2.1/T2.4/T2.5 discipline):

- **`src/shared/template.ts` (new file)**: `TemplateContract` and its parts (§1–§6) + a `lowerTemplateToOps(contract, ids): RenderScenePatch[]` (or a single `batch`) helper. Pure contract + lowering; no runtime, no persistence, no renderer.
- **No `schema.ts` change**: templates persist nothing of their own; `meta.templateKind` rides the already-additive `meta` bag (T2.1 §4). No new table, no `ALTER TABLE`.
- **No `renderPatch.ts` op added**: the recipe lowers to ops that already exist (`create-group`/`create-card`/`create-edge`) or are owned by T2.4 (`create-tag`/`set-object-tags`). T4.1 adds *zero* op kinds.
- **`local.ts`/`storage.ts`/`mcp.ts`** (later tasks, not this pass): the hard-coded `seedGroupScene` ADR recipe becomes *one registered `TemplateContract`* (the ADR template, T4.4); `createGroup`/`create_group` gains an optional `templateId` selecting a registered contract, defaulting to the ADR template for back-compat (§9). No existing call signature breaks.

### 9. Replacing the de-facto `seedGroupScene` template (back-compat)

`seedGroupScene` (`local.ts:29`) is the current template, expressed as code. Under this contract it becomes the **ADR `TemplateContract`** (authored in T4.4): its 10 `node(...)` calls → `RecipeShape[]`, its 9 `edge(...)` calls → `RecipeEdge[]`, `defaultSeedNodePositions` → recipe `position`s, its prose → `promptHints`, MADR/YADR/mermaid → `exports.allowed`. `GroupSeedOutput` (`schema.ts:268`) is the output shape the lowering already targets — the contract just makes it *one of many declared templates* instead of the only, hard-coded one.

Back-compat rule: `createGroup`/`create_group` keep working unchanged by defaulting `templateId` to the ADR template, so today's `create_group(prompt)` callers get identical behavior. This keeps the change additive and avoids breaking the existing MCP/API surface (the same discipline T2.1–T2.5 apply).

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| A template requires a private editing mode to be useful. | **CLEAR (not triggered)** | The contract is consumed entirely at *apply* time (§7) and lowers to the standard create ops; after application the objects are edited by the *same* select/move/resize/group/label/text/delete ops as any primitive (T2.2–T2.4). No template carries an editor, a mode flag, or behavior — only declarative recipe + advisory `promptHints` (§6, `optional`). The single trace on canvas is `meta.templateKind`, which gates nothing. If any planned template (T4.2–T4.5) is found to need a private editing mode to be usable, *that* would trip this condition; none in the todo/wiki/ADR/server-arch/presentation set does — each composes from primitives per the T0.1 §6 / D1 recipe tables. The de-facto `seedGroupScene` template already proves a template needs no private mode: its output is ordinary, fully-editable `SceneGroup`/`SceneNode`/`SceneEdge`. |

## Open questions / risks

- **Per-template `meta` validation (D1 C4, deferred to here).** T0.1/T2.1 deferred "namespaced, optionally-validated `meta` shapes" to T4.1. Recommendation: each `TemplateContract` may carry an optional Zod schema for its `meta` namespace (e.g. an ADR-template schema validating `meta.semanticType ∈ {decision_point, option, …}`), validated at *authoring/apply* time only — it never gates the renderer/core (which keep treating `meta`/`type` as opaque). This restores the enum validation the `meta` demotion dropped without re-coupling the render layer. Flagged as a recommendation; the concrete per-template schemas are authored in T4.2–T4.5, not here.
- **Image substrate dependency (D1 C1).** Recipe elements that want a real image preview (`image_artifact` with pixels — presentation slides, wiki evidence, architecture-image embed) depend on the image/texture-quad primitive D1 promotes, which does not yet exist in `webgpu.rs`. Until it lands, an image recipe element must apply as a documented captioned-box placeholder (§2). The contract is shaped to carry the artifact ref now and render pixels once the substrate ships — no contract change needed then.
- **`styleKey` source rule vs the core badge (D1 C3/C5).** This contract fixes that `styleKey` comes from the template recipe, not a demoted `nodeType` (§2). But the Rust core `node_type_label()` badge text is still keyed on the decision-graph enum (D1 C5) and is owned by a separate migration task. A template card with `meta.semanticType` but no matching badge mapping will show the graceful `"Node"` fallback until that task lands; flagged so the visual-identity dependency is explicit, not silently assumed.
- **Investigation-map recipe (D1 C2).** D1 requires the investigation-map template's recipe be demonstrated before P4 template work. It composes from `frame`/`shape`/`edge`/`comment_marker`/`tags` like ADR (no new primitive), but the explicit `TemplateContract` for it is authored in the T4.x wave; this contract supports it with zero changes. Noting the dependency so it is owned, not assumed.
- **Template `id` collision / versioning.** A registry of `TemplateContract`s needs stable `id`s and a versioning story if a template's recipe changes after instances exist on canvas (instances are plain objects, so they are unaffected — but a re-apply or "update from template" feature would need it). Out of scope for T4.1 (define the contract); flag for whenever a template-update feature is requested.
