# T5.1 MCP Client Identity And Dock

> Phase P5 (MCP Companion Activity Tracker), Wave C. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P5 intro, T5.1); upstream `docs/design/ai-companion-canvas/tasks/T0.1.md` (the `actor_marker` ephemeral kind + document/ephemeral split) and `T1.4.md` (the companion dock as a Svelte-shell responsibility reading MCP state and commanding `focusBounds`/`setCamera`). Ground truth read in `src/server/mcp.ts` (tool registry + stdio `main`), `src/server/index.ts` (`/mcp` Streamable HTTP transport, `sessionIdGenerator: undefined`), `@modelcontextprotocol/sdk` (`Server.getClientVersion()`, `getClientCapabilities()`, `oninitialized`, `RequestHandlerExtra.sessionId`, `StreamableHTTPServerTransport`), `src/shared/schema.ts` (`SceneSelection`), `src/client/renderer/engine.ts` (`EngineEvent`), `src/client/components/RendererCanvasHost.tsx` (`RendererCanvasHostHandle`).

## Outcome

Give every connected MCP client a stable companion identity and a dock entry whose visual state (idle / active / error / disconnected / muted) and active-motion cue are driven by **ephemeral** presence data, not by document state — building directly on T0.1's reserved `actor_marker` kind and T1.4's "dock is a Svelte-shell reader of MCP state" boundary, without touching the canonical `Scene` schema or the canvas core.

## Deliverable

### 0. Where identity comes from: the real transport surface

P5 turns headless tool calls into visible companions, so the first job is to anchor "who is this client" in something the MCP SDK actually exposes. Two transports run today and both must be covered:

| Transport | Where it lives | Server lifetime | What the SDK gives us for identity |
| --- | --- | --- | --- |
| stdio | `src/server/mcp.ts#main()` → `StdioServerTransport` | one process = one client = one server instance | `server.getClientVersion(): Implementation` after `initialize`; `oninitialized` fires once |
| Streamable HTTP | `src/server/index.ts` `app.all("/mcp")` → `StreamableHTTPServerTransport({ sessionIdGenerator: undefined })` | **stateless: a fresh `createSceneMcpServer()` + transport per HTTP request**, closed on `reply.raw.on("close")` | `server.getClientVersion()` per request; `RequestHandlerExtra.sessionId` is **`undefined`** in stateless mode |

The MCP `Implementation` (the client's `clientInfo` from `initialize`) is a rich identity payload — confirmed real fields from `ImplementationSchema` (`@modelcontextprotocol/sdk/.../types.d.ts`):

```ts
// EXISTING SDK type — clientInfo reported by every MCP client at initialize
type Implementation = {
  name: string;            // e.g. "claude-code", "cursor"  → label seed
  title?: string;          // human-readable display name    → dock label
  version: string;         // e.g. "1.29.0"
  websiteUrl?: string;
  description?: string;
  icons?: { src: string; mimeType?: string; sizes?: string[]; theme?: "light"|"dark" }[]; // → dock icon seed
};
```

Critical finding for the Stop-or-ask gate (§Stop-or-ask): **`name`/`title`/`icons` are stable per client build, but they are not unique per connection.** The HTTP path is stateless, so `RequestHandlerExtra.sessionId === undefined` and `getClientVersion()` returns the same `Implementation` for two concurrent Cursor windows. The identity model below therefore derives a **server-minted `clientId`** rather than trusting a transport-provided session id, and §4 documents the small server change needed to make that id stable across the stateless HTTP request stream.

### 1. Client identity model (`McpClientIdentity`)

This is the **ephemeral, app-layer** record the Svelte shell renders in the dock. It is *not* added to `Scene`, `SceneSnapshot`, or core; it lives next to the other ephemeral state T0.1/T1.4 already classify (camera, hover, follow). It reuses T0.1's `actor_marker` fields verbatim (`clientId`, `actorType`, target, activity state) and extends them only with display + dock-state fields.

```ts
// NEW — ephemeral app-layer type (proposed home: src/server/mcpClients.ts registry
// + a /api/mcp/clients read path; mirrored into the Svelte shell's ephemeral store).
// NOT persisted in Scene/SQLite; reset is harmless (matches T2.5 ephemeral-state boundary).

type McpClientDockState =
  | "idle"          // connected, no in-flight tool call
  | "active"        // a tool call is in flight (jumping/motion cue)
  | "error"         // last tool call threw, or initialize/transport error
  | "disconnected"  // transport closed (stdio EOF / HTTP stream "close")
  | "muted";        // user suppressed this companion's motion + trace (local UI toggle)

type McpClientIdentity = {
  clientId: string;            // server-minted stable id (see §4); the actor_marker.clientId
  actorType: "mcp";            // T2.5 actorType; distinguishes from "human" edits
  // display identity, seeded from Implementation, deterministic + overridable:
  label: string;               // Implementation.title ?? Implementation.name
  name: string;                // Implementation.name (raw, for disambiguation)
  version: string;             // Implementation.version
  color: string;               // deterministic hash(clientId) → stable palette slot
  iconRef: string | null;      // Implementation.icons[0]?.src ?? null (fallback: initial glyph)
  transport: "stdio" | "http";
  // dock state (ephemeral):
  dockState: McpClientDockState;
  lastTarget: SceneSelection | { kind: "viewport" } | null; // T5.2 fills this; null at connect
  connectedAt: number;         // epoch ms
  lastActivityAt: number;      // epoch ms; drives idle decay + dock ordering
  muted: boolean;              // mirrors dockState === "muted"; user-controlled
};
```

Field-by-field seed mapping from the SDK `Implementation` to the dock identity:

| `McpClientIdentity` field | Source | Rule |
| --- | --- | --- |
| `clientId` | server-minted (§4), not transport | Stable for the lifetime of one logical connection; the value used as `actor_marker.clientId` and as T2.5 `actorId`/`clientId`. |
| `label` | `Implementation.title ?? Implementation.name` | Human display. If two live clients collide on label, append ` (2)`, ` (3)` by connect order. |
| `name` / `version` | `Implementation.name` / `.version` | Verbatim; shown in the dock tooltip / inspector. |
| `color` | `hash(clientId)` → fixed palette | Deterministic so the same client keeps its color within a session; not derived from `name` (two windows of the same tool must differ). |
| `iconRef` | `Implementation.icons[0]?.src` | If absent, render an initial-glyph chip in `color`. No network fetch required to assign identity. |
| `transport` | which transport accepted the connection | Drives the disconnect detector (stdio EOF vs HTTP stream close). |
| `actorType` | constant `"mcp"` | Matches T2.5's `actorType`; lets the shell separate agent vs human in the dock and the trace. |

### 2. Dock behavior and state machine

The dock is the companion strip described in T1.4 §1 ("Companion dock — per-client companion icons, dock states, active motion … the dock only *reads* MCP state + commands `focusBounds`/`setCamera`"). It owns no document state.

State transitions (all ephemeral, server-observed where noted, user-driven where noted):

```text
            initialize ok                tool call starts
 (none) ───────────────────▶ idle ───────────────────────▶ active
                              ▲ │                              │
        tool call returns ok  │ │ user mute                    │ tool call returns ok
        (after active) ───────┘ ▼                              ▼
                              muted ◀── user unmute ──┐    idle (lastActivityAt bumped)
                                                      │        │
   transport close (EOF /     ┌──────────────────────┘        │ tool call throws
   HTTP stream "close") ──────▼                               ▼
                          disconnected ◀────────────────── error ── next call ok ──▶ active/idle
```

| Dock state | Entered when | Visual | Behavior |
| --- | --- | --- | --- |
| `idle` | `initialize` completed; no in-flight call; or a call just resolved | Static chip, full opacity, `color` + `iconRef` | Clickable (→ T5.3 follow). Sorted by `lastActivityAt`. |
| `active` | a registered tool call is in flight (§3 hook) | Subtle motion cue (see §2.1) + accent ring in `color` | While active, T5.2 sets `lastTarget`; T5.3 can follow. Motion stops the instant the call resolves. |
| `error` | last tool handler threw, or `initialize`/transport error | Warning badge over the chip, no motion | Tooltip surfaces the error message. Clears to `idle`/`active` on the next successful call. |
| `disconnected` | stdio process EOF, or HTTP `reply.raw.on("close")` with no live request stream for that `clientId` | Dimmed chip, slated for removal | Held briefly (grace window, e.g. a few seconds) so a reconnect re-attaches the same `clientId`; then dropped from the dock. |
| `muted` | user toggles mute on the chip | Greyed chip, no motion, trace suppressed | The companion still tracks internally (state still updates) but produces **no** active motion and is excluded from auto-follow; user can unmute. Mute is local UI state, never persisted. |

Ordering rule: dock lists clients by `dockState` priority (`active` > `error` > `idle` > `muted` > `disconnected`) then by `lastActivityAt` descending, so the agent currently doing something is always findable.

#### 2.1 Active "jumping"/motion rule (non-distracting)

Locked Decision context: MCP companion tracker is observability, not decoration; and follow/animation must never steal editor focus (P5 intro; T5.3 stop-condition). The motion rule therefore:

- **Bounded, looping, low-amplitude.** A small vertical bob / pulse on the dock chip only (a few px, ~1 Hz), not a full-canvas animation. The on-canvas `actor_marker` movement to the real target is owned by T5.2; T5.1 only governs the **dock chip** cue and the *presence* of an on-dock active indicator.
- **Driven by ephemeral state, rendered by the shell, not the core render loop.** The bob is a Svelte/CSS animation on the dock DOM, so it never enters the WebGPU frame budget or competes with editor input (T1.4 invariant 1: shell never draws a canvas frame; T3.4 stop-condition: follow/spectator animation must not compete with editor responsiveness).
- **Respects `prefers-reduced-motion`** and the per-client `muted` toggle: muted or reduced-motion → swap the bob for a static accent dot.
- **Self-terminating.** Motion is tied 1:1 to an in-flight tool call. If `active` persists past a watchdog (e.g. a long-running export), the cue degrades to a steady pulse rather than continuous jumping, so a slow agent does not produce indefinite distraction.

### 3. Activity hooks: how dock state actually changes

Identity is set at connect; dock state changes are driven by tool-call lifecycle. The MCP `McpServer.registerTool` handlers in `src/server/mcp.ts` are the single choke point — every tool (`query_scene`, `list_groups`, `get_group`, `create_group`, `patch_scene`, `create_tag`, `update_group_tags`, `set_selection`, `add_comment`, `export_group`) already funnels through `jsonResponse(...)`. The design wraps that lifecycle (the concrete tracking middleware is implemented in T5.2/T5.4; T5.1 only needs the **state signals** it emits):

| Signal | Server source | Dock effect |
| --- | --- | --- |
| connect + `initialize` | `server.oninitialized` / first request; `getClientVersion()` available | create `McpClientIdentity`, `dockState = idle` |
| tool call start | tool handler entry (per `clientId`) | `dockState = active`, bump `lastActivityAt` |
| tool call success | tool handler returns `jsonResponse` | `dockState = idle` (unless another call in flight) |
| tool call throw | tool handler throws (e.g. `Group not found`) | `dockState = error` + message |
| transport close | stdio EOF / `reply.raw.on("close")` | `dockState = disconnected` (grace window → drop) |
| user mute/unmute | shell UI toggle | `dockState = muted` / restore |

`lastTarget` (which group/object/viewport the active call touches) is **out of T5.1 scope** — it is T5.2's mapping deliverable. T5.1 reserves the field and the `active` state that T5.2 will decorate with a target.

### 4. The one required server change: a stable `clientId` over a stateless transport

Because `/mcp` runs stateless (`sessionIdGenerator: undefined`), nothing in the SDK gives a per-connection id today. T5.1's identity model needs one. The minimal, surgical change (design only here; implementation belongs to P5 build):

- **stdio:** trivial — one process is one client. Mint `clientId = "stdio:" + uuid` once in `main()` after `oninitialized`.
- **HTTP:** the dock needs presence to survive across the per-request server instances. Two viable options, with the recommendation:
  1. **(Recommended) Turn `/mcp` stateful** by passing `sessionIdGenerator: () => randomUUID()` to `StreamableHTTPServerTransport` and keeping a `Map<sessionId, McpClientIdentity>` registry alongside the existing per-request `createSceneMcpServer()`. Then `RequestHandlerExtra.sessionId` is populated and equals the dock `clientId`. This is the SDK-sanctioned path (`streamableHttp.d.ts` stateful mode) and the smallest correct fix; the only cost is honoring the MCP session header, which compliant clients already do.
  2. **(Fallback) Keep stateless** and derive a soft `clientId` from `Implementation` + connection metadata (`name`+`version`+a per-stream nonce). This is weaker — two identical concurrent clients are indistinguishable — and is the case the Stop-or-ask gate flags.

The registry is **ephemeral app/server state** (in-memory `Map`, lost on server restart), exposed to the Svelte shell via a small read path (e.g. `GET /api/mcp/clients` returning `McpClientIdentity[]`, or an SSE/poll stream for live dock updates). It never touches `Scene`/SQLite. This keeps T1.4's boundary intact: the dock **reads** MCP state and **commands** the canvas via the adapter handle; it never persists presence.

### 5. How the dock connects to the canvas (no new canvas-core surface)

T5.1 adds **no** new method to the canvas bridge. The dock is pure shell UI plus the existing imperative handle:

- **Dock → canvas:** clicking a chip (T5.3 follow) calls the already-existing `RendererCanvasHostHandle.focusBounds(bounds)` / `setCamera(camera)` (see `RendererCanvasHost.tsx`). T5.1 only needs the chip to be clickable and to carry the `clientId`; the camera command path already exists.
- **canvas → dock:** none required for identity/dock state. The on-canvas `actor_marker` rendering (a companion icon that *moves on the canvas* to the read/write target) is T5.2's job and will be expressed through the render snapshot as an ephemeral overlay, not through `Scene`. T5.1's dock state is fed entirely by the server-side activity hooks in §3, surfaced to the shell over the §4 read path — it does **not** ride the `EngineEvent` stream (`stats|selection|patch|overlay|gesture|status`), keeping presence cleanly separate from canvas events.

This satisfies the T0.1 classification: `actor_marker` is the only new ephemeral kind, its dock projection is `McpClientIdentity`, and neither enters document state.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| MCP transport cannot provide stable client/session identity. | **PARTIALLY TRIGGERED — decision needed.** | stdio is fine (one process = one client). The **HTTP path is the problem**: `src/server/index.ts` runs `StreamableHTTPServerTransport({ sessionIdGenerator: undefined })` (stateless), so `RequestHandlerExtra.sessionId` is `undefined` and `getClientVersion()` alone cannot disambiguate two concurrent identical clients. The design resolves this with §4 option 1 (make `/mcp` stateful via `sessionIdGenerator: () => randomUUID()` + a `Map<sessionId, McpClientIdentity>`), which is the SDK-sanctioned fix and keeps identity fully stable. **Decision required:** approve turning the HTTP MCP transport stateful (recommended), or accept the weaker stateless fallback (§4 option 2) where two identical concurrent HTTP clients share one dock entry. Everything else in T5.1 is unblocked either way. |

## Open questions / risks

- **Stateful HTTP cost.** Option 1 changes `/mcp` from per-request-disposable to session-keyed; the current `reply.hijack()` + per-request `createSceneMcpServer()` shape (index.ts) must keep one server per session instead of per request. Mechanics belong to P5 build, but the boundary (registry is in-memory ephemeral, server still owns persistence) is fixed here.
- **Disconnect grace window.** Streamable HTTP closes the stream between calls; a naive "stream close = disconnected" would flap every client to `disconnected` between tool calls. The `disconnected` state must key off session expiry/heartbeat, not individual request-stream close. Flagged for the §3 transport-close signal in P5 build.
- **Dock vs on-canvas marker split.** T5.1 owns the dock chip; T5.2 owns the on-canvas `actor_marker` that moves to the target. The shared field is `lastTarget`/`clientId`; keep the dock state machine (§2) authoritative for `dockState` and let T5.2 only write `lastTarget`, so the two tasks don't both mutate companion state.
- **Identity persistence across restarts.** The registry is intentionally non-persistent (ephemeral). If a future requirement wants "same agent, same color across sessions," that color seed would have to derive from `Implementation.name` rather than `clientId` — a deliberate tradeoff against the "two windows must differ" rule. Not needed now; noted so it isn't reintroduced by accident.
