# T6.2 React To Svelte Web Shell Migration

> Phase P6 (Product Integration, Svelte Migration, And Rust Boundary Plan), Wave J. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P6 intro, T6.2); upstream `docs/design/ai-companion-canvas/tasks/T1.4.md` (app-shell boundary table, the `ShapeCanvasHost` bridge sketch, the Rust/core line, the file-by-file React→target map, boundary invariants), `T6.1.md` (evolve-in-place schema verdict, `events`-log op envelope, document/ephemeral split — T6.2 inherits its write/ephemeral contract, does not re-decide it).
> Real symbols grounded in: `src/client/main.tsx` (`createRoot`/`StrictMode`), `index.html` (`/src/client/main.tsx` entry, `#root`), `src/client/App.tsx` (~1000-line React shell: `useState`/`useEffect`/`useRef`/`useCallback`, `rendererRef`, the debounced `rendererPatchSave*` flow, the inline node menu), `src/client/components/{RendererCanvasHost,Sidebar,ExportDrawer,SelectedNodeInspector,RendererDiagnosticsDrawer}.tsx` + `components/node/{NodeEditForm,NodeReadNote,NodeComments}.tsx`, `src/client/components/RendererCanvasHost.tsx` (`RendererCanvasHostHandle`, `RendererHealth`, `RendererStats`, `cameraFromStats`, `hitToSceneSelection`), `src/client/renderer/engine.ts` (`ShapeCanvasEngine`, `EngineEvent`, `ShapeCanvasEngineOptions`, `FocusBoundsOptions`, `DomOverlayRequest`, `sendInputBatch`/`applyPatchBatch`/`beginTextEdit`/`commitTextEdit`/`syncSelection`/`mountOverlay`), `src/client/renderer/{adapter,scene,wasmLoader}.ts` (`shapeSceneToFilteredRenderSnapshot`, `SceneSnapshot`/`FrameStats`/`HitResult`/`WorldRect`, `loadRustCore`), `src/client/lib/{api,flow,nodeClipboard}.ts`, `src/shared/{renderScene,renderPatch}.ts` (`CameraState`, `RenderScenePatch`), `package.json`, `vite.config.ts` (`@vitejs/plugin-react`, `copyRendererWasm`), `tsconfig.json` (`"jsx": "react-jsx"`), `vitest.config.ts` (`environment: "node"`), `tests/*.test.ts`.

## Outcome

Replace the React web shell with a **Svelte web shell that wraps the already-narrow `RendererCanvasHostHandle` + `EngineEvent` bridge unchanged**, deleting `react`/`react-dom`/`@vitejs/plugin-react`/`lucide-react`/`@types/react*`, the 10 `.tsx` files, and the JSX build assumptions, while the canvas adapter (`src/client/renderer/*`), `lib/*`, `src/shared/*`, server, and the entire (already framework-neutral, node-environment) `tests/` suite carry over without touching canvas behavior.

## Deliverable

T6.2 has four Deliverable bullets: the **Svelte-shell migration plan** for every named UI surface + API/MCP orchestration (§1–§2), the **React removal plan** (§3), the **Svelte↔adapter bridge contract** (§4), and the **shell-level test migration plan without React test utilities** (§5). §6 restates the binding boundary invariants T6.2 inherits from T1.4. T6.2 owns the *migration mechanics*; T1.4 owns the *target boundary* (this task does not re-derive it) and T6.1 owns the *write/ephemeral contract* (this task routes the shell into it, does not re-decide it).

The single fact that shapes the whole plan, verified against the tree: **React already touches only the shell.** Exactly 10 files import `react` or `lucide-react` — `main.tsx`, `App.tsx`, the 5 `components/*.tsx`, the 3 `components/node/*.tsx`. `src/client/renderer/*`, `src/client/lib/*`, `src/shared/*`, `src/server/*`, and `tests/*` import zero React. So the migration is a **shell rewrite + dependency removal**, not an engine rewrite — which is exactly what the Stop-or-ask forbids violating.

### 1. Svelte web shell location and structure

**Location.** The web shell stays at `src/client/` (T1.4 invariant 4 + the breakdown's "현재 production app을 이 planning pass에서 이동하지 않는다" — the directory move is T6.4's concern, gated; T6.2 only swaps the framework *in place*). Svelte components replace the `.tsx` files 1:1 by responsibility. New entry: `src/client/main.ts` mounting a root `App.svelte`; `index.html`'s `<script type="module" src="/src/client/main.tsx">` retargets to `/src/client/main.ts` (the `#root` div is unchanged).

**Shell state model.** Today App.tsx holds ~20 `useState` cells (`scene`, `selection`, `activeTagIds`, `currentGroupId`, `prompt`, `tagName`, `commentValue`, `status`, `busy`, `groupPanelOpen`, `editingNodeId`, `nodeMenu`, `copiedNode`, `exportPreview`, `exportPreviewCopied`, `camera`, `rendererStats`, `rendererHealth`, `diagnosticsOpen`, `rendererStatus`) plus refs (`rendererRef`, `sceneRef`, `selectionRef`, `rendererPatchSaveRef`, `pendingRendererPatchSaveRef`, `rendererPatchSaveTimerRef`, `rendererGestureActiveRef`). These map to **Svelte stores in `src/client/lib/stores/`**, partitioned by the T6.1 document/ephemeral boundary (so the shell physically separates the two classes, not just conceptually):

| Class (T6.1 boundary) | State | Today (App.tsx) | Target (Svelte) |
| --- | --- | --- | --- |
| document projection (read of server scene) | `scene` | `useState<Scene>` | `writable<Scene \| null>` set only from `api.ts` responses |
| ephemeral selection | `selection` | `useState<SceneSelection>` + `selectionRef` | `writable<SceneSelection>`; T6.1 makes selection ephemeral (no `bumpSceneVersion`), so the store is the local truth, server `set_selection` is fire-and-forget |
| ephemeral viewport | `camera` | `useState<Camera>` + `cameraRef` | `writable<CameraState>` mirrored from `EngineEvent.stats` via `cameraFromStats` — **core stays authoritative** (T1.4 §3) |
| ephemeral UI/chrome | `groupPanelOpen`, `editingNodeId`, `nodeMenu`, `diagnosticsOpen`, `busy`, `status`, `prompt`, `tagName`, `commentValue`, `exportPreview*` | `useState` | plain Svelte component state / small `writable`s |
| ephemeral renderer readout | `rendererStats`, `rendererHealth`, `rendererStatus` | `useState` | `writable`, set only from bridge events (§4) |
| app filter | `activeTagIds`, `currentGroupId` | `useState` | `writable`; drives `fetchScene({tagIds})` and `shapeSceneToFilteredRenderSnapshot` |

The debounced renderer-patch save (`rendererPatchSaveRef`/`pendingRendererPatchSaveRef`/`rendererPatchSaveTimerRef`/`rendererGestureActiveRef` — the "commit on gesture-end, debounce otherwise" logic at App.tsx) moves verbatim into a framework-neutral `src/client/lib/patchSaver.ts` module (plain closures + `setTimeout`, no React); the Svelte shell calls it and it calls `saveScenePatch`. Pulling it out of the component is required because Svelte has no `useRef`/effect-cleanup idiom — but it is **pure orchestration, no canvas math** (T1.4 §3 stays satisfied).

### 4. Bridge contract: Svelte shell ↔ web canvas adapter

The bridge is **already narrow and React-agnostic in shape** (T1.4 §2). T6.2's mechanics: extract `RendererCanvasHost.tsx`'s logic into a framework-neutral `src/client/lib/canvasHost.ts` class that owns the `ShapeCanvasEngine` lifecycle (the work currently in the three `useEffect`s: `loadRustCore`, WebGPU-renderer creation, engine construct/resize/start/stop), and a thin `ShapeCanvasHost.svelte` that owns only the three DOM nodes (`webgpu` canvas, input canvas, `overlayRoot` div) and forwards them in. The command/event surface is **the existing `RendererCanvasHostHandle` + `EngineEvent`, verbatim** — drop only React's `forwardRef`/`useImperativeHandle`/`useRef`/`useState`/`useEffect`.

```ts
// Target: src/client/lib/canvasHost.ts — framework-neutral, no React.
// Commands == existing RendererCanvasHostHandle (RendererCanvasHost.tsx). Events == existing EngineEvent (engine.ts).
class ShapeCanvasHost {
  // lifecycle (replaces the 3 useEffects)
  async mount(input: HTMLCanvasElement, webgpu: HTMLCanvasElement, overlayRoot: HTMLElement): Promise<void>;
  resize(width: number, height: number, dpr?: number): void;   // ResizeObserver lives in the Svelte node
  destroy(): void;

  // load scene — shell maps Scene -> snapshot via the EXISTING adapter fn
  loadScene(snapshot: SceneSnapshot): void;
  // snapshot built by shapeSceneToFilteredRenderSnapshot(sceneForRenderer, activeTagIds, {camera, sceneId}) — UNCHANGED

  // apply operation batch (already batched: engine.applyPatchBatch)
  applyPatch(patch: RenderScenePatch): string[];               // -> engine.applyPatch / applyPatchBatch
  syncSelection(selection: SceneSelection): string[];          // -> engine.syncSelection

  // input batch + camera (already batched: engine.sendInputBatch)
  setCamera(camera: CameraState): void;
  focusBounds(bounds: WorldRect, options?: FocusBoundsOptions): void;
  fitScene(): void;
  wheelAtScreen(screen: { x: number; y: number }, deltaY: number): void;

  // overlay requests + diagnostics snapshots + event callbacks
  getSnapshot(): SceneSnapshot | null;
  onEvent(cb: (e: EngineEvent) => void): void;  // stats|selection|patch|overlay|gesture|status
  onHealthChange(cb: (h: RendererHealth) => void): void;  // derived from rust status + stats, as today
}
```

Mapping each Deliverable bridge concern to an existing real symbol (nothing new invented):

| Bridge concern (Deliverable) | Existing carrier | Svelte usage |
| --- | --- | --- |
| load scene | `shapeSceneToFilteredRenderSnapshot` → `engine.loadScene(SceneSnapshot)` | store subscription on `scene`/`activeTagIds`/`camera` calls `host.loadScene`; **same snapshot args as App.tsx** |
| apply operation batch | `engine.applyPatch`/`applyPatchBatch` (`RenderScenePatch`) → `EngineEvent{type:"patch"}` | shell calls `host.applyPatch`; patch event routes to `patchSaver` → `saveScenePatch` |
| input batch | `engine.sendInputBatch` behind `setCamera`/`focusBounds`/`fitScene`/`wheelAtScreen` + pointer/wheel listeners the engine attaches to its own canvas | Svelte never per-event-calls; it commands the batched methods. **Batching stays in the engine** (T1.4 §3). |
| overlay requests | `EngineEvent{type:"overlay"; request: DomOverlayRequest \| null}`; engine `mountOverlay` builds the `<textarea>` | Svelte provides `overlayRoot`; engine owns the node + IME/clipboard. Shell does not compute overlay coordinates. |
| diagnostics snapshots | `EngineEvent{type:"stats"; stats: FrameStats}` (= `RendererStats`) + `RendererHealth` | `RendererDiagnosticsDrawer.svelte` reads the stores fed by `onEvent`/`onHealthChange` |
| event callbacks | the full `EngineEvent` union (`stats\|selection\|patch\|overlay\|gesture\|status`) | one `host.onEvent` subscription; `selection`→`hitToSceneSelection` store, `stats`→`cameraFromStats` mirror, `gesture`→debounce gate, `status`→status store. Helpers `hitToSceneSelection`/`cameraFromStats`/`cameraAlmostEqual` are pure functions → move to `lib/canvasHost.ts`. |

The bridge surface is byte-for-byte the T1.4 `ShapeCanvasHost` sketch realized from `RendererCanvasHost.tsx` + `engine.ts`. **No engine method, event variant, or batching path is added, removed, or rewritten** — satisfying the "wrap the adapter, don't rewrite the engine" Stop-or-ask.

### 5. Shell-level test migration plan (no React test utilities)

The current suite needs **no migration** (§3: zero React-rendering tests). The plan is therefore *additive* — provide shell-level coverage that does not depend on React/Svelte component-render harnesses, keeping `vitest --environment node` as the default:

1. **Bridge contract tests (the load-bearing shell test).** Test `lib/canvasHost.ts` against a stub `ShapeCanvasEngine` (the engine is already injectable via `ShapeCanvasEngineOptions.onEvent`): assert that each `ShapeCanvasHost` command issues exactly one batched engine call and that each `EngineEvent` routes to the right store update (e.g. `stats`→`cameraFromStats` mirror only when `cameraAlmostEqual` is false; `patch`-with-errors→status, not save). These run in `environment: "node"` — no DOM, no Svelte render. This is also the T6.3 "Svelte calls narrow canvas APIs, not component reactivity" contract seed.
2. **Orchestration unit tests.** `lib/patchSaver.ts` (debounce + gesture-gated commit) and `lib/api.ts` request shaping are plain functions → vitest `node` with mocked `fetch`/timers (`vi.useFakeTimers`), as `tests/server.test.ts`/`performance.test.ts` already mock at the node level. No component render.
3. **Pure-helper tests carry over unchanged.** `tests/clipboard.test.ts`, `graph.test.ts`, `export.test.ts`, `infinite-canvas-renderer.test.ts`, `storage.test.ts`, `server.test.ts`, `performance.test.ts` import framework-neutral modules and are untouched by the swap.
4. **Optional Svelte component smoke tests** (only if a component holds non-trivial branching, e.g. inspector edit/read toggle): use **`vitest-browser-svelte` or `@testing-library/svelte` under a per-file `// @vitest-environment jsdom` pragma**, scoped to that file so the default suite stays node-environment. This is the Svelte-native analogue of React Testing Library and is **not a React test utility**. Default to (1)+(2) and add (4) only where component logic warrants it — avoiding a blanket DOM test harness.
5. **Build/test availability during migration.** `npm test` (`vitest run`), `npm run typecheck` (`tsc --noEmit` over `.ts`), and `npm run build` stay runnable at every step because the React files are removed *after* their Svelte replacements compile, and the test suite never depended on them. A `svelte-check` script is added for `.svelte` type coverage. No window exists where `npm test`/`npm run build` is unavailable.

### 6. Inherited boundary invariants (binding, from T1.4 §5 — restated, not re-derived)

1. Shell never draws a frame: Svelte holds no object geometry, visible-object set, hit region, LOD decision, text layout, or render cache as source of truth — it reads `EngineEvent`/`FrameStats` and commands via `ShapeCanvasHost`.
2. Canvas never calls product I/O: `canvasHost.ts`/`engine.ts`/adapter never call HTTP or know MCP/export/proposal semantics; persistence stays server + `lib/api.ts`.
3. One bridge, two directions: all shell→canvas via `ShapeCanvasHost` methods (= `RendererCanvasHostHandle`); all canvas→shell via `EngineEvent`. No back-channel through Svelte reactivity.
4. Per-platform shell, shared core: this swap changes only `src/client/` shell files + `package.json` deps + `vite.config.ts`/`tsconfig.json`/`index.html` build glue; the scene model, op vocabulary, adapter (`renderer/*`), and Rust core are untouched.

## Open questions / risks

- **`canvasHost.ts` extraction fidelity.** `RendererCanvasHost.tsx` encodes ordering across three effects (load Rust core → create WebGPU renderer → construct/resize/start engine, with `engineReadyKey` re-runs on scene/selection). The framework-neutral class must preserve that ordering and re-load on renderer recreation; a mechanical port risk, not a boundary risk. Flag for the implementer to mirror the effect dependency graph as explicit lifecycle calls.
- **Svelte reactivity vs. batching.** Naive `$:` reactive statements could re-call `host.loadScene`/`applyPatch` per keystroke. The shell must route document writes through `lib/patchSaver.ts` (debounced, gesture-gated) and command the *batched* host methods, never re-derive canvas inputs reactively. Contract enforcement is T6.3's boundary tests; flagged here so the store wiring is built batch-aware from the start.
- **`lucide-svelte` parity.** Assumes 1:1 icon-name coverage with `lucide-react`; if any icon used by the shell is missing, fall back to an inline SVG, not a React shim. Low risk (Lucide ships matched ports), but verify the 24 icon names enumerated in §2 resolve.
- **Directory move deferred to T6.4.** T6.2 swaps the framework in place at `src/client/`; whether the Svelte shell later moves to a dedicated web-shell location is T6.4's gated sequence decision. This task does not move the tree (honoring the breakdown's no-move-this-pass rule).
- **`svelte-check` in CI.** Type coverage for `.svelte` files needs `svelte-check` since `tsc` no longer sees JSX; ensure it is wired into the same gate as `typecheck` so Svelte type regressions are caught (mechanics for T6.4's build coordination).
