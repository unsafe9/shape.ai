# T1.4 Define App Shell Boundaries

> Phase P1 (Portable Canvas Core Boundary), Wave B. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P1 intro, T1.4); `docs/infinite-canvas-engine-strategy.md` 책임 경계 + "JavaScript API 형태" (the `ShapeCanvas` wrapper sketch); upstream `docs/design/ai-companion-canvas/tasks/T0.1.md` (primitive/business seam, document vs ephemeral split); current shell in `src/client/{App.tsx,main.tsx}`, `src/client/components/*`, `src/client/lib/api.ts`, the bridge in `src/client/components/RendererCanvasHost.tsx` + `src/client/renderer/engine.ts`, and `src/server/index.ts`.
> Note: prompt referenced T0.2/T0.3 as upstream; only `T0.1.md` exists in-repo. This task builds on T0.1 and the breakdown's P0 boundary verifies, and does not contradict them.

## Outcome

Separate **product shell responsibility** (UI composition + event routing + API/MCP/persistence orchestration) from **canvas engine responsibility** (scene behavior + performance-sensitive geometry/text/render work), and fix the web shell target as a **Svelte shell** that talks to the canvas only through the already-existing narrow bridge (the `RendererCanvasHostHandle` imperative API + the `EngineEvent` callback stream), so the shell can be swapped per platform while Rust/core stays stable.

## Deliverable

### 1. App shell contract (web shell + future macOS shell)

The "app shell" is everything outside the canvas surface: it owns nothing the renderer needs to draw a frame. It owns product semantics, server I/O, and the chrome around the canvas. The same contract describes the current React shell (`App.tsx`), the target Svelte web shell, and a future macOS/SwiftUI shell — only the implementation language and the platform adapter change.

| Shell responsibility | Owns (state + behavior) | Current home (React) | Target home | Boundary rule |
| --- | --- | --- | --- | --- |
| Account / session | Local-first single-user; no auth today. Slot reserved for future per-shell identity, never required by core. | none | Svelte shell (web) / native shell (macOS) | Never enters `SceneSnapshot` or core. Ephemeral/app-only. |
| MCP connection state | Connected MCP clients, per-client status (`idle\|active\|error\|disconnected\|muted`), companion identity. **Net-new (P5).** | none | Svelte shell + server (`src/server/mcp.ts`) | Document part (who/what was written) goes through the op model (T2.5); presence/animation is ephemeral. |
| Persistence / API | All HTTP calls and scene fetch/patch round-trips. | `src/client/lib/api.ts` (`fetchScene`, `saveScenePatch`, `createGroup`, `createTag`, `updateGroupTags`, `exportGroup`, `createComment`, `updateComment`) | Svelte shell, unchanged API client | Canonical persistence rule stays server + `lib/api.ts`; adapter/core never call HTTP. |
| Panels / chrome | Sidebar, group panel, toolbar, status strip, node menu. | `components/Sidebar.tsx`, `App.tsx` chrome | Svelte components | Pure presentation + event routing. No camera/hit/LOD math. |
| Inspector | Selected-object detail + edit forms. | `components/SelectedNodeInspector.tsx`, `components/node/*` (`NodeEditForm`, `NodeReadNote`, `NodeComments`) | Svelte components | Reads document state; writes via op/patch path, not by mutating snapshots. |
| Template picker | Apply a template → emit primitive-creating operations. **Net-new (P4/T4.1).** | none | Svelte shell | Produces ops (T2.5 vocabulary), never private renderers/object models. |
| Export drawer | Export trigger + preview rendering. | `components/ExportDrawer.tsx`, `App.tsx` export flow → `lib/api.ts#exportGroup` | Svelte component | Export semantics stay app/server (`src/server/local.ts`, `exportType` enum). |
| Companion dock | Per-client companion icons, dock states, active motion. **Net-new (P5/T5.1).** | none | Svelte shell | Presence is ephemeral; the dock only *reads* MCP state + commands `focusBounds`/`setCamera` on the adapter. |
| Spectator / follow controls | Click-to-follow, pin, pause/resume, jump-to-target, handoff to manual. **Net-new (P5/T5.3).** | none | Svelte shell | Follow drives camera through the adapter's `setCamera`/`focusBounds`; never owns camera state itself. |
| Diagnostics host | Renderer health + frame/cache stats drawer. | `components/RendererDiagnosticsDrawer.tsx` (consumes `RendererHealth`/`RendererStats` from the bridge) | Svelte component | Pure read-out of `FrameStats`/health the adapter emits. |
| Active text-overlay host | Mounts the DOM `<textarea>` over the GPU card during editing; IME/clipboard via browser. | `RendererCanvasHost` `overlayRoot` div + engine `beginTextEdit`/`commitTextEdit`/`{type:"overlay"}` event | Svelte overlay host node | Shell *mounts the DOM node at coordinates the adapter computes*; the adapter/core decides target + value commit. (Strategy doc "Active editing" rule.) |

Platform-swap guarantee: every row's "Owns" column is product/UI state, not renderable scene state. A macOS shell re-implements these in SwiftUI against the Metal adapter (T1.3) and the same server/op contracts; nothing in this table forces a fork of the scene model.

### 2. Web shell target contract: Svelte shell ↔ canvas, the bridge already exists

The breakdown locks the web shell as **Svelte** with React/React-DOM removed (no dual/compat shell). The crucial finding for this task: the React↔canvas boundary is **already narrow and imperative**, so the Svelte migration wraps the same adapter rather than rewriting the engine. Two real symbols define the seam today:

**Shell → adapter (imperative handle).** `RendererCanvasHostHandle` in `src/client/components/RendererCanvasHost.tsx`:

```ts
// EXISTING — the entire shell→canvas command surface
type RendererCanvasHostHandle = {
  fitScene: () => void;
  focusBounds: (bounds: WorldRect, options?: FocusBoundsOptions) => void;
  wheelAtScreen: (screen: { x: number; y: number }, deltaY: number) => void;
  setCamera: (camera: CameraState) => void;
  applyPatch: (patch: RenderScenePatch) => string[];
  getSnapshot: () => SceneSnapshot | null;
};
```

**Adapter → shell (event callbacks).** `EngineEvent` in `src/client/renderer/engine.ts`:

```ts
// EXISTING — the entire canvas→shell event stream
type EngineEvent =
  | { type: "stats"; stats: FrameStats }
  | { type: "selection"; hit: HitResult | null }
  | { type: "patch"; patch: ScenePatch; errors: string[] }   // ScenePatch = RenderScenePatch
  | { type: "overlay"; request: DomOverlayRequest | null }
  | { type: "gesture"; active: boolean }
  | { type: "status"; message: string };
```

The Svelte bridge contract is **this exact pair, framework-neutralized** (drop React's `forwardRef`/`useImperativeHandle`/`useEffect`; keep the methods and events verbatim). Sketch of the Svelte-owned host:

```ts
// Target: a framework-neutral host the Svelte shell instantiates.
// Same commands as RendererCanvasHostHandle, same events as EngineEvent.
interface ShapeCanvasHost {
  mount(input: HTMLCanvasElement, webgpu: HTMLCanvasElement, overlayRoot: HTMLElement): Promise<void>;
  loadScene(snapshot: SceneSnapshot): void;       // shell maps Scene→snapshot via shapeSceneToFilteredRenderSnapshot
  applyPatch(patch: RenderScenePatch): string[];  // batched
  setCamera(c: CameraState): void;
  focusBounds(b: WorldRect, o?: FocusBoundsOptions): void;
  fitScene(): void; wheelAtScreen(s: ScreenPoint, dy: number): void;
  getSnapshot(): SceneSnapshot | null;
  onEvent(cb: (e: EngineEvent) => void): void;    // stats|selection|patch|overlay|gesture|status
  destroy(): void;
}
```

This is the strategy doc's `ShapeCanvas` JS API made concrete from real code. The bridge is **already batched** (engine `sendInputBatch` / `applyPatchBatch`; strategy doc "patch batch / input batch / frame당 호출 수 제한") — the Svelte shell must keep batching, not call per-event.

**What leaves React (and dies):** `react`, `react-dom`, `@vitejs/plugin-react` deps; `src/client/main.tsx` (`createRoot`/`StrictMode`); JSX in `App.tsx` and `components/*`; React hooks used purely for shell state (`useState`/`useEffect`/`useRef`/`useImperativeHandle`). The detailed removal plan is owned by T6.2; T1.4 only fixes the target and the bridge shape.

**What becomes Svelte (UI composition + event routing only):** every component in §1's table — shell chrome, inspector, panels, drawers, the new MCP dock / spectator controls / template picker, the diagnostics host, and the overlay-host node. Svelte holds product/app state (current scene, selection, active tag filter, busy/status, export preview, MCP/companion state) and routes user gestures into the host's imperative methods and the `lib/api.ts` calls.

**What must stay in Rust/core (never lifted into Svelte component state):** everything in §3.

### 3. The Rust/core line — responsibilities Svelte must NOT absorb

Locked Decision: canvas performance-sensitive work lives in Rust/core by default. The Svelte shell may *command* and *read* these, but must never become their source of truth.

| Responsibility | Owner | Why not Svelte |
| --- | --- | --- |
| Camera math / viewport transform | Rust core (`model.rs#CameraState`, applied in core) | Per-frame math; React already mirrors camera only as a derived value from `FrameStats` (`cameraFromStats`). Svelte mirrors the same way — core stays authoritative. |
| Hit testing | Rust core (`stats.rs#CoreHitResult`, engine `hitTest`) | Geometry under load; emitted to shell as `{type:"selection"; hit}`. |
| Selection / hull geometry | Rust core | Selection *identity* is document state (in `Scene.selection`); selection *geometry* is core. |
| LOD thresholding | Rust core (`SceneStyleToken.states.compact` seed; full policy T3.1) | Must stay stable under zoom; visual-only degradation. |
| Culling / spatial index / render caches | Rust core / webgpu.rs | The whole reason for the engine. |
| Text layout / shaping | Rust core (`text.rs`, fontdue+rustybuzz) | Single shared text engine; one shaper, not per-primitive. |
| Render primitive generation + frame stats | Rust core (`webgpu.rs`, `stats.rs#WebGpuFrameStats`) | GPU-side. Shell only reads `FrameStats`. |
| Input batching / patch batching | engine/adapter (`sendInputBatch`, `applyPatchBatch`) | JS/WASM boundary cost control; strategy doc principle. |

The DOM text overlay is the one deliberate shared seam: the **shell mounts the DOM node**, but the **adapter computes the target+coordinates** (`DomOverlayRequest` via `beginTextEdit`, value committed back through `commitTextEdit` → `applyPatch`). This keeps IME/clipboard/native-input in the browser without putting layout math in Svelte.

### 5. Boundary invariants (binding for downstream tasks)

1. **Shell never draws a frame.** The shell holds no object geometry, visible-object set, hit region, LOD decision, text layout, or render cache as a source of truth — it reads them as `EngineEvent`/`FrameStats` and commands via the handle.
2. **Canvas never calls product I/O.** The adapter/core never call HTTP, never know MCP/export/proposal semantics. Persistence stays server + `lib/api.ts`; business semantics stay TS app (matches `excludedBusinessFields()` and T0.1).
3. **One bridge, two directions.** All shell→canvas traffic goes through the `RendererCanvasHostHandle`-shaped methods; all canvas→shell traffic through `EngineEvent`. No back-channel through component reactivity.
4. **Per-platform shell, shared core.** Swapping React→Svelte, or adding a macOS shell, changes only §1/§4 rows; the core scene model, op vocabulary, and adapter contracts are untouched.

## Open questions / risks

- **Camera write-back ownership.** Follow/spectator (P5) and `setCamera` both write camera to core, while core also emits camera back via `FrameStats`. The single-writer rule (core authoritative, shell mirrors) must be kept when follow mode is added so manual input and follow don't fight; flagged for T5.3, not decided here.
- **Bridge typing during migration.** Extracting `ShapeCanvasHost` from `RendererCanvasHost` cleanly (without React) is a T6.2 mechanics concern; this task only fixes the method/event surface, which is already React-agnostic in shape.
- **MCP/companion document-vs-ephemeral split.** The dock/spectator state is ephemeral, but the *write provenance* it visualizes (who wrote what) is document state via the op model (T2.5). The shell must read both without persisting presence/animation — boundary stated here, mechanics owned by T2.5/P5.
- **Svelte store granularity vs batching.** Naive Svelte reactivity could re-derive canvas inputs per keystroke; the shell must route through the batched handle, not reactive statements. Contract/boundary tests for this belong to T6.3.
