# T5.4 Operation Trace And Write Preview

> Phase P5 (MCP Companion Activity Tracker), Wave E. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P5 intro, T5.4); upstream `docs/design/ai-companion-canvas/tasks/T2.5.md` (the `OperationEnvelope`, the append-only `events` table as the operation log, the minimal `sceneProposalSchema` slot + `accept-proposal`/`reject-proposal` ops, the document/ephemeral split, the "trace overlay is derived from the events log, never document state" rule), `T5.2.md` (the `CanvasTarget` resolver, `lastTarget`, the `actor_marker` overlay placed via `selection_world_rect` + `CoreOverlayRequest`, the tracking middleware at the `jsonResponse` choke point), and `T5.1.md` (the ephemeral `McpClientIdentity` registry, dock states, `color`/`iconRef`, the `/api/mcp/clients` read path, the `muted` toggle that suppresses motion **and trace**).
> Real symbols grounded in: `src/server/storage.ts` (`events(id, type, payload_json, created_at)` table DDL at :433 — exists, currently zero `INSERT`; `withWritableDb`, `bumpSceneVersion`, `selection_json` metadata key), `src/shared/renderPatch.ts` (`RenderScenePatch` union, `applyRenderPatchToShapeScene`, `commitAppPatch`, `addShapeSceneComment`), `src/server/mcp.ts` (the 3 read tools `query_scene`/`list_groups`/`get_group` that bypass the write funnel + the write tools, `jsonResponse`), `src/shared/schema.ts` (`sceneSelectionSchema`, `sceneCommentSchema`, `artifactSchema`, `exportTypeSchema`), `src/renderer/core/src/stats.rs` (`CoreOverlayRequest{ target, value, world_rect, screen_rect, style }`, `CoreOverlayTarget{ kind, id, field }`, `CoreOverlayStyle.state` — the per-overlay style-state hook the "compact"/ghost variant rides), `src/client/components/RendererDiagnosticsDrawer.tsx` (the existing right-side ephemeral inspector drawer pattern the activity trail panel mirrors).

## Outcome

Make every agent operation answerable from the canvas — *what did this client just read, write, comment, export, or propose, and did anything fail* — by deriving a bounded **trace** from the already-built T2.5 `events` log (writes) plus a small ephemeral **read-event ring** (the read tools that never reach the log), surfaced as transient on-canvas pulses + a per-client inspectable activity trail, and by rendering a non-committing **ghost write preview** for risky writes on top of T2.5's already-defined `sceneProposalSchema` staged-operation slot — all without persisting any trace as document state and without adding a permanent on-canvas decoration layer.

## Deliverable

The breakdown's T5.4 has two Deliverable bullets: (§2) the **trace model** for reading, writing, commenting, exporting, proposal creation, proposal acceptance/rejection, and errors; and (§3) the **ghost diff / write-preview** behavior for risky writes. §1 fixes where trace data comes from (it is *derived*, not a new store); §4 defines the bounded-visibility / inspectable-history rendering that keeps the Stop-or-ask gate clear; §5 fixes core-vs-shell placement. Nothing beyond the bullets is added.

### 1. Where trace data comes from — derived, never a new persisted store

T5.4 introduces **no new document state and no second write log.** Every trace event resolves from one of two sources that already exist after T2.5/T5.2:

| Trace source | Already exists? | What it gives T5.4 |
| --- | --- | --- |
| **Write/comment/export/proposal events** | **Yes — T2.5.** The append-only `events(id, type, payload_json, created_at)` table (`storage.ts:433`) now holds one `OperationEnvelope` per committed op. | `actorType`/`actorId`/`clientId` (which agent), `type` = verb (what), `targetIds` (where), `sourceToolCall.{tool,callId}` (which MCP call), `timestamp`, `baseRevision`. This is the audit unit; the trace is a **read query** over it. |
| **Read events** (`query_scene`, `list_groups`, `get_group`) | **No envelope** — these three never reach `commitAppPatch`/the write funnel (`mcp.ts:66,75,102`), so T2.5 correctly never logs them. | A small **ephemeral in-memory ring** of `ReadTraceEvent` per client (§2.2), keyed off T5.2's `CanvasTarget` already resolved by the tracking middleware. Reads are not document mutations, so they are **never** written to `events` — they live and die with the session, matching T2.5's "reads are not logged ops" boundary. |

So the trace is the **union of (a) a filtered `events` query and (b) the per-client read ring**, projected per client. Locked Decision compliance: "temporary trace effects … derived from the `events` log, not stored as document state" (T2.5 §4) — T5.4 is exactly that derivation, plus the read ring that T2.5 deliberately left to P5.

```ts
// NEW — ephemeral app-layer types (proposed home: src/server/mcpClients.ts, next to McpClientIdentity + CanvasTarget).
// NOT persisted; reset is harmless. Reads = in-memory ring; writes = projected from the events table.
type TraceKind =
  | "read"             // query_scene / list_groups / get_group
  | "write"            // any committed RenderScenePatch verb (create/move/edit-text/delete/group/...)
  | "comment"          // add-comment op (T2.5 promoted)
  | "export"           // export op → artifact (T2.5 promoted)
  | "proposal-created" // staged, uncommitted envelope written to sceneProposalSchema (status:"pending")
  | "proposal-accepted"// accept-proposal op committed the staged envelope
  | "proposal-rejected"// reject-proposal op discarded the staged envelope
  | "error";           // tool handler threw before/while producing an op

type TraceEvent = {
  clientId: string;                 // T5.1 McpClientIdentity.clientId / T2.5 OperationEnvelope.clientId
  kind: TraceKind;
  target: CanvasTarget;             // T5.2's resolved target (group | node | edge | selection | viewport | artifact | canvas)
  verb: string;                     // events.type for writes; tool name for reads; "" for canvas-level
  operationId: string | null;      // events.id for logged ops; null for reads (not logged)
  callId: string | null;           // OperationEnvelope.sourceToolCall.callId — links trace back to the MCP call
  at: number;                       // epoch ms (events.created_at for writes; arrival time for reads)
  summary: string;                 // short, human "edited title of node X" / "read group Y" (§2.3)
  errorMessage: string | null;     // populated only for kind:"error"
};
```

`TraceEvent` is a **projection**, not a store: the `write`/`comment`/`export`/`proposal-*` variants are reconstructed from `events` rows on demand; only `read` and `error` (pre-commit failure) variants need the in-memory ring because they have no `events` row.

### 2. Trace model (every breakdown-named trace category)

Each category maps to a concrete source, a `CanvasTarget` (from T5.2), an on-canvas cue, and an activity-trail line. The on-canvas cue is a **transient pulse on the existing `actor_marker` overlay** (T5.2's `CoreOverlayRequest`), differentiated by style state — never a new persistent canvas object.

| Trace category | Source (real symbol) | `CanvasTarget` (T5.2) | On-canvas cue (transient) | Activity-trail line |
| --- | --- | --- | --- | --- |
| **reading** | read ring; `query_scene`/`list_groups`/`get_group` (`mcp.ts:66/75/102`) | `viewport` (scene-fit or tag-hull) / `group` (`get_group`) | low-amplitude **read sweep/pulse** over the rect; marker does **not** acquire a write ring | "read group _Auth_" / "scanned 12 groups" |
| **writing** | `events` row, `type ∈ {create-*, move-*, edit-card-text, set-card-z-index, delete-*, group-objects,…}` | single id → `group\|node\|edge`; multi → `selection` (union) | **write flash** on the target, accent = `McpClientIdentity.color` (T5.1) | "moved node _Cache_" / "created edge" / "edited title" |
| **commenting** | `events` row, `type:"add-comment"` (T2.5 promoted from `addShapeSceneComment`) | comment `target` (1:1), canvas-level → `canvas` | write flash + **comment glyph** cue on the target | "commented on group _Auth_" |
| **exporting** | `events` row, `type:"export"` → `artifactSchema` row (`addArtifact`, `mcp.ts:231`) | `artifact` (preview anchor on `groupId`) | read-then-produce: read sweep over scope, then a **produce pulse** on the artifact preview | "exported _Auth_ → design_doc_md" |
| **proposal creation** | `sceneProposalSchema` row `status:"pending"` (T2.5 §3); the staged `OperationEnvelope` is *not* committed | `target` of the staged inner op | **ghost preview** rendered (§3) + a pending badge on the target; no write flash (nothing committed) | "proposed: rename node _Cache_ → _LRU_ (pending)" |
| **proposal acceptance** | `events` row, `type:"accept-proposal"` (the staged envelope is now committed → its own `write` event also lands) | target of the now-committed op | ghost clears → **write flash** (it is now a real write) | "accepted proposal → renamed node" |
| **proposal rejection** | `events` row, `type:"reject-proposal"` (staged envelope discarded) | target of the discarded op | ghost **dissolves**, no geometry change | "rejected proposal (no change)" |
| **errors** | read ring `error` entry; tool handler threw (e.g. `Group not found`, `mcp.ts:104`) before/while producing an op | last resolved `CanvasTarget` or `canvas` | **error pulse** (warning tint) on the last target; marker does not jump to a new place | "error: Group not found: _g-9_" |

Notes that keep this faithful to the codebase:

- **Reads and errors are the only categories needing the in-memory ring.** Everything else is reconstructed from `events`, so the trace can't drift out of sync with the operation log (single source of truth for committed history).
- **Proposal creation is a real T2.5 document-state row but produces no committed write.** Its trace cue is the ghost (§3), and its activity-trail line is explicitly tagged `(pending)` so it reads as "staged, not done" — this is the one category where the on-canvas cue out-lives a single pulse, because a pending proposal is a real (rejectable) state, not a transient effect.
- **`export` resolves to an artifact preview, not a node** — consistent with T5.2 §2 and the breakdown's "artifact preview" marker destination; the trail line names the produced `exportType` (`design_doc_md`, `mermaid`, …, `schema.ts:36`).

#### 2.1 Write-trace query (the `events` projection)

```text
-- trace for one client = filtered read of the existing T2.5 log, no schema change:
SELECT id, type, payload_json, created_at FROM events
  WHERE json_extract(payload_json, '$.clientId') = :clientId
  ORDER BY created_at DESC LIMIT :n;     -- n bounded (§4); recent-first
```

`payload_json` is the full `OperationEnvelope`, so `targetIds`, `actorType`, `sourceToolCall`, and `baseRevision` are all available without a join. `idx`-free is fine at P5 scale; if the log grows, a `(clientId, created_at)` index is a pure-additive follow-up (flagged §Open).

#### 2.2 Read-event ring (the only new ephemeral structure)

```ts
// per-client bounded ring; oldest evicted. Lives in the McpClientIdentity registry (T5.1), in-memory.
type ReadTraceEvent = { tool: string; target: CanvasTarget; at: number };
// capacity small (e.g. last N reads per client); reset with the session — never persisted, no events row.
```

The ring is written by the **same T5.2 tracking middleware** at the `jsonResponse` choke point: when the resolved op is a read tool, push a `ReadTraceEvent`; when it is a write, the `events` row is already the record, so the ring is **not** used. This keeps one middleware, two sinks (durable `events` for document ops, ephemeral ring for reads).

#### 2.3 `summary` derivation

`summary` is a short shell-rendered string built from `verb` + `target` + (for `edit-card-text`) the `field` (`title|summary|detail`, `renderPatch.ts:12`). It is *display-only*, recomputed from the envelope/ring; it is never persisted, so it can change wording without a migration.

### 3. Ghost diff / write-preview behavior for risky writes

The "preview before apply" path is **not invented here** — it reuses T2.5's staged-operation model end to end. A risky write is expressed as a **proposal**: the MCP write is staged into `sceneProposalSchema` (`status:"pending"`) with its full `OperationEnvelope` instead of being committed, and the agent (or a future policy) decides; the human accepts/rejects via the already-defined `accept-proposal`/`reject-proposal` ops (T2.5 §3). T5.4 owns only the **preview rendering** of that staged op — T2.5 explicitly deferred "the diff/ghost-write/preview UX" to T5.4.

**What "risky" means (the gate that routes a write to staged vs immediate):**

| Risk class | Examples (real verbs) | Routing |
| --- | --- | --- |
| **Destructive / wide** | `delete-group` (cascades `descendantGroupIds`, `renderPatch.ts:41`), `delete-card` (drops incident edges), multi-target `patch_scene` touching many ids | stage as proposal → ghost preview, await accept |
| **Non-risky / additive** | `move-card`, `edit-card-text`, `create-card`, `set-card-z-index`, `set_selection` (ephemeral) | commit immediately, normal write flash (§2) |
| **Agent-flagged** | any op an MCP client explicitly stages (a future `propose:true`-style affordance routes through the same proposal slot) | stage regardless of class |

The risk classifier is a small server-side predicate over the op `kind` + `targetIds` cardinality; it is the *only* new policy T5.4 adds, and it produces a T2.5 proposal — no new staging mechanism.

**Ghost rendering (the diff overlay):**

- The staged `OperationEnvelope.patch` is applied to a **throwaway copy** of the scene via the *existing* pure `applyRenderPatchToShapeScene` (`renderPatch.ts:31`) — which already returns a new `Scene` without mutating the input — yielding a **preview snapshot**. The diff between current and preview snapshot is rendered as a **ghost overlay**, not committed: nothing reaches `commitAppPatch`/`saveScenePatch`, so `sceneVersion` does not move and no `events` row lands until accept.
- The ghost rides the **same ephemeral overlay path** the `actor_marker` and text-edit overlay already use: `CoreOverlayRequest` (`stats.rs:105`), differentiated by `CoreOverlayStyle.state` (`stats.rs:99`) — the per-overlay `state` field is exactly the seam for a `"ghost"` / `"preview"` style variant (semi-transparent fill, dashed outline, `McpClientIdentity.color` accent), alongside the existing `"compact"` LOD state. A **delete** preview ghosts the target with a strike/dim; a **create/move** preview ghosts the *future* geometry; an **edit-text** preview ghosts the new text. Geometry for all three comes from the preview snapshot through the same core `selection_world_rect` → `world_rect_to_screen_rect` path T5.2 established — no new core method.
- Accept → `accept-proposal` commits the staged envelope (a real write event lands, ghost clears, write flash fires); reject → `reject-proposal` discards it (ghost dissolves, no geometry change). Both are themselves logged ops (T2.5), so the *decision* is also traceable in §2.

**Why this keeps the canvas clean:** a ghost exists only while a proposal is `pending`; accept/reject removes it. It is bounded by the number of pending proposals (a real, inspectable document-state count via `Scene.proposals`), not by edit volume, so it cannot accumulate into permanent clutter.

### 4. Bounded visibility + inspectable history (the Stop-or-ask answer)

The breakdown's Stop-or-ask is "trace events become permanent visual clutter instead of inspectable history." The design separates the two surfaces so the **canvas stays clean** while **history stays complete**:

| Surface | Lifetime | Backed by | Clutter control |
| --- | --- | --- | --- |
| **On-canvas pulse** (read sweep / write flash / comment glyph / produce pulse / error pulse) | **transient** — a short animation tied 1:1 to one op, then gone | derived; no canvas object created | self-terminating per op; off the GPU document layer (ephemeral overlay); honors `prefers-reduced-motion`; suppressed entirely when the client is `muted` (T5.1) |
| **`actor_marker` resting position** | persists only as *current* location | T5.2 `lastTarget` | one marker per live client; moves, never accumulates |
| **Ghost preview** | only while a proposal is `pending` | `Scene.proposals` row | bounded by pending-proposal count; cleared on accept/reject |
| **Activity trail panel** | inspectable, scrollback | `events` query (§2.1) + read ring (§2.2) | a **drawer**, not on the canvas — recent-first, bounded `LIMIT`, per-client filter; mirrors the existing right-side `RendererDiagnosticsDrawer` ephemeral-inspector pattern (`RendererDiagnosticsDrawer.tsx`) |

So: **no trace event is a permanent canvas mark.** Writes leave a durable record in the *operation log* (`events`) and the *activity trail drawer*, never a sticky on-canvas badge. Reads leave only a transient pulse + a ring entry that ages out. The "what did this agent just do?" question is answered two ways — a momentary on-canvas cue *as it happens*, and a scrollable per-client trail *after the fact* — without either becoming visual debris. This is the explicit design choice that keeps the gate clear (§Stop-or-ask).

Trail panel shape (a shell drawer, ephemeral, reads server state — does **not** ride the `EngineEvent` stream):

- Per-client filter (chip click in the T5.1 dock → trail filtered to that `clientId`).
- Each line: `[icon/color]` (T5.1) · `kind` · `summary` · relative time · click → `focusBounds(target)` (T5.2/T5.3 follow path) to jump to where it happened.
- Bounded scrollback; `muted` clients excluded from the live pulse but still queryable in the trail (mute suppresses *motion*, not *history* — matches T5.1's "muted still tracks internally").

### 5. Core-vs-shell placement

| Concern | Home | Why |
| --- | --- | --- |
| `events` query + `OperationEnvelope` projection → `TraceEvent` | **server** (`src/server/mcpClients.ts` + `storage.ts` read helper over the existing table) | pure metadata read; no GPU work |
| read ring + error-event capture | **server** (T5.2 middleware at `jsonResponse`) | same choke point T5.1/T5.2 already use |
| risk classifier (op kind + `targetIds` cardinality → stage vs commit) | **server / shared contract** | op semantics, not rendering |
| building the ghost **preview snapshot** (apply staged patch to a throwaway scene) | **shared** (`applyRenderPatchToShapeScene`, already pure) | reuse; no new logic |
| ghost/pulse **geometry** (target rect, screen placement) and overlay emission | **Rust/core** (`selection_world_rect`, `world_rect_to_screen_rect`, `CoreOverlayRequest` + `CoreOverlayStyle.state:"ghost"`) | selection/hull geometry + overlay/culling are Locked-Decision core responsibilities |
| on-canvas pulse animation + ghost diff styling | **core overlay + shell** | overlay request is core; transient animation/style is shell-driven off the document frame |
| activity-trail drawer, per-client filter, accept/reject affordance | **shell** (Svelte target; React is migration input) | UI orchestration; reads `/api/mcp/clients` + a trail read path, commands canvas via the existing handle |

This holds every Locked-Decision boundary: trace is *derived* from the log (no new document state), ghost reuses the staged-proposal slot + the pure apply function + the existing overlay path (no new canvas-core method, no `Scene`/snapshot schema change), and all geometry stays in Rust/core.

## Stop-or-ask

| Stop-or-ask condition | Status | Why |
| --- | --- | --- |
| Trace events become permanent visual clutter instead of inspectable history. | **CLEAR (not triggered).** | The design structurally splits the two and never lets a trace event become a sticky canvas mark. **No on-canvas surface is permanent:** every pulse (§2) is transient and self-terminating per op, rides the ephemeral overlay (not a `Scene` object), honors `prefers-reduced-motion`, and is suppressed for `muted` clients (T5.1); the `actor_marker` *moves* rather than accumulating; the ghost (§3) exists only while a proposal is `pending` and is bounded by the pending-proposal count, cleared on accept/reject. **History lives off-canvas and is fully inspectable:** committed ops are the durable T2.5 `events` log, surfaced as a bounded, recent-first, per-client **activity-trail drawer** (§4) modeled on the existing `RendererDiagnosticsDrawer` inspector — not as on-canvas badges. So "inspectable history" is the drawer + the operation log, and "visual clutter" is avoided because the canvas only ever shows *transient* cues, the *current* marker, and *pending* ghosts — each of which is bounded and clears itself. The gate's failure mode (permanent canvas decoration) is excluded by construction. |

## Open questions / risks

- **Read-ring vs `events`-log dual sources.** Reads are deliberately not logged (T2.5), so a session restart loses read history while write history survives. This is the correct boundary (reads are not document mutations), but the activity trail is therefore *complete for writes, session-scoped for reads* — flagged so the asymmetry is a deliberate choice, not a gap. If a future requirement wants durable read provenance, it needs a new ephemeral-but-persisted store, which would be a fresh decision, not a T5.4 widening.
- **`events`-by-client query cost.** §2.1 filters via `json_extract(payload_json,'$.clientId')` with no index. Fine at P5 scale; if long-lived workspaces grow the log, add a `(clientId, created_at)` index (pure-additive) — this is the same unbounded-`events`-growth risk T2.5 already flagged (no retention/compaction policy), surfacing again here for the trace read path.
- **Risk classifier policy is a small new judgement call.** §3 routes `delete-*` and wide multi-target `patch_scene` to staged proposals; the exact threshold (e.g. how many `targetIds` make a write "wide") is a tunable the build should confirm with real agent traffic. Conservative default: stage only destructive (`delete-*`) and agent-flagged ops; treat multi-target moves/edits as immediate unless flagged — avoids over-gating routine agent edits behind accept prompts.
- **Ghost overlay vs marker/text-edit overlay sharing.** §3 and T5.2 both ride the single `CoreOverlayRequest` slot; a pending ghost + an active `actor_marker` on the *same* object simultaneously would contend for one overlay (the same single-overlay limitation T5.2 §Open already noted). Acceptable for the single-user local model; if simultaneous ghost+marker on one object is needed, the core overlay slot must hold more than one request — a deliberate scope boundary, not an oversight.
- **`CoreOverlayStyle.state:"ghost"` is a core touch.** Adding a `"ghost"`/`"preview"` value to the existing `state` field (alongside `"compact"`) is additive and within the established overlay-style contract, but it is a Rust/core edit; flagged so T5.4 and the core overlay owner agree on the one shared style-state vocabulary rather than each inventing a parallel preview path.
