# T4.5 Presentation Template

> Phase P4 (Template System On Primitives), Wave H. Design-only pass: no production code is written, moved, or scaffolded.
> Source refs: `docs/ai-companion-canvas-task-breakdown.md` (Objective, Locked Decisions, Explicit Non-Goals, P4 intro, T4.5); upstream `docs/design/ai-companion-canvas/tasks/T4.1.md` (the binding `TemplateContract` — metadata/recipe/layout/exports/tags/promptHints, the `lowerTemplateToOps` funnel, the `styleKey`-from-template rule, the image-substrate caveat), `T0.1.md` §6 + `T2.1.md` §6 (the **already-pinned presentation recipe**: `frame` per slide → title/body `text`, `image_artifact` previews, `edge` connectors, speaker-note `shape`/`comment_marker`, export-outline preset), `T2.3.md` (frame title / box-less `text` editing), `T2.4.md` (tags + frame membership), `T2.5.md` (`OperationEnvelope`, the logged-op funnel), and `D1` conditions C1 (image substrate) / C3 (`styleKey` decoupled from `nodeType`).
> Real symbols grounded in: `src/shared/template.ts` (T4.1 contract — not yet implemented), `src/shared/schema.ts` (`sceneGroupSchema`, `sceneNodeSchema`, `sceneEdgeSchema`, `exportTypeSchema`, `artifactSchema`/`SceneArtifact`, `GroupSeedOutput`), `src/shared/renderScene.ts` (`SceneSnapshot`, `RenderGroup`/`RenderCard`/`RenderEdge`, `defaultStyles`, `SceneStyleToken`, `WorldRect`), `src/shared/renderPatch.ts` (`RenderScenePatch`: `create-group`/`create-card`/`create-edge`/`edit-card-text`/`select`, `applyRenderPatchToShapeScene`→`commitAppPatch`), `src/server/local.ts` (`seedGroupScene`, `boundsForNodes`, `generateLocalExport`, `imagePrompt`, `taskPlanSections`), `src/server/mcp.ts` (`export_group`, `exportGroupContent`, `create_group`), `src/shared/graph.ts` (`exportTypeLabels`, `graphTextDigest`, `sceneGraphForGroup`).
> Relationship to upstream: **T4.5 authors one `TemplateContract` instance** (the presentation template) against the T4.1 contract — it owns *no* new primitive, op, schema field, renderer object, or export *type*. The presentation recipe is already pinned by T0.1 §6 / T2.1 §6; this task makes it a concrete, declared `TemplateContract` whose recipe lowers to existing `create-group`/`create-card`/`create-edge` ops, and specifies the one genuinely new *reader* it needs: a slide-ordered **outline export preset** that reads the produced primitives (no new `exportType`).

## Outcome

Define the **presentation `TemplateContract`** — slide `frame`s, title/body `text`, `image_artifact`/speaker-note cards, optional connector `edge`s, and an export-outline preset — as a declared recipe over the existing primitives that lowers entirely to `RenderScenePatch` create ops through the T4.1 `lowerTemplateToOps`→`applyRenderPatchToShapeScene`→`commitAppPatch` funnel, so a slide deck is ordinary `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` objects edited with the same select/move/resize/text tools as any shape or note, with **no presentation renderer, no slide object type, no presentation editing mode**.

## Deliverable

The breakdown's T4.5 Deliverable is a single bullet with six parts: a **template plan for (1) slide frames, (2) title/body text, (3) image/artifact preview, (4) connectors, (5) speaker-note cards, and (6) export outline.** §1 fixes the recipe spine; §2–§7 are the six parts as concrete `TemplateContract` data (real T4.1 symbols, real recipe elements); §8 gives the export-outline preset (the only genuinely new reader); §9 the application/placement; §10 the additive delta and core-vs-shell placement; §11 the scope guard. Nothing beyond the six parts is added.

### 1. The presentation template is a `TemplateContract`, not a new surface

T4.1 fixed that a template is `TemplateContract { metadata, recipe, layout, exports, tags, promptHints? }` lowered to ops at apply time. T4.5 fills that struct for `id:"presentation"`. The recipe spine is exactly the row already pinned in T0.1 §6 / T2.1 §6:

> Presentation outline | `frame` per slide → title/body `text`, `image_artifact` previews, `edge` connectors, speaker-note `shape`/`comment_marker`; export-outline preset.

So every Deliverable part maps 1:1 onto an existing primitive and an existing `RecipeFrame`/`RecipeShape`/`RecipeEdge` from T4.1 §2 — no presentation-private element is introduced. A "deck" is a top-level `frame` containing N child slide `frame`s (nested grouping is already supported: `SceneGroup.parentGroupId`, `schema.ts:101`).

| Deliverable part | Primitive (T2.1) | T4.1 recipe element | Lowers to op |
| --- | --- | --- | --- |
| slide frames | `frame` | `RecipeFrame` (one per slide, `parentLocalId` = deck) | `create-group` |
| title / body text | `text` (box-less `shape`) | `RecipeShape` (`styleKey:"slide-title"` / `"slide-body"`) | `create-card` |
| image / artifact preview | `image_artifact` | `RecipeShape` with `meta.artifactId` (T2.1 §1 placement) | `create-card` |
| connectors | `edge` | `RecipeEdge` (slide-to-slide / element-to-element) | `create-edge` |
| speaker-note cards | `shape` (or `comment_marker`) | `RecipeShape` (`styleKey:"speaker-note"`) / suggested `comment_marker` | `create-card` (note as `shape`) |
| export outline | export preset (reader) | `TemplateExports.allowed`/`default` + §8 outline reader | `export_group` / `generateLocalExport` |

### 2. Slide frames (deck → slides)

A deck is a deck-level `RecipeFrame`; each slide is a child `RecipeFrame` with `parentLocalId` = the deck. This reuses the nested-frame support (`parentGroupId`) and the T2.4 §10 `create-group` `parentGroupId` passthrough that T4.1 §2 already depends on. **Slide order is encoded in `meta.slideIndex`** (a plain `meta` value, T2.1 §4) and mirrored into `RenderGroup.zIndex` so the outline preset (§8) and any "next slide" affordance read a stable order without a new field.

```ts
// presentation TemplateContract.recipe.frames (sketch; T4.1 RecipeFrame[])
{ localId: "deck",   title: "Presentation", meta: { templateKind: "presentation", semanticType: "deck" } },
{ localId: "slide-1", parentLocalId: "deck", title: "Title slide",
  meta: { templateKind: "presentation", semanticType: "slide", slideIndex: 0 } },
{ localId: "slide-2", parentLocalId: "deck", title: "Slide 2",
  meta: { templateKind: "presentation", semanticType: "slide", slideIndex: 1 } },
// …N slides
```

Slide frame geometry is a fixed 16:9-ish `WorldRect` per slide (e.g. `1280×720` world units), laid out by the §9 layout pass (row or column of slides). `bounds` are **not authored** — they are derived by `boundsForNodes(members)` (`local.ts:201`) exactly as `seedGroupScene`/`createGroup` already derive frame bounds; the recipe authors only member positions, and the frame hugs them. A slide is an ordinary frame: it is selected, moved, resized, renamed (frame-title editing, T2.3 §2), reordered, duplicated, and deleted by the same ops as any frame.

### 3. Title / body text

Title and body are `text` primitives — box-less `shape`s (T2.1 §1/§4: a `text` is a degenerate `shape` whose `styleKey` omits surface/stroke). Each slide carries one title `text` and one or more body `text`s as `RecipeShape`s whose `frameLocalId` is the slide:

```ts
// recipe.shapes (T4.1 RecipeShape[])
{ localId: "s1-title", frameLocalId: "slide-1", title: "Title", styleKey: "slide-title",
  meta: { templateKind: "presentation", semanticType: "slide-title" } },
{ localId: "s1-body",  frameLocalId: "slide-1", summary: "First bullet\nSecond bullet",
  styleKey: "slide-body", meta: { templateKind: "presentation", semanticType: "slide-body" } },
```

- The `title` lands in `SceneNode.title`, body text in `summary`/`detail` — the **same** fields cards use, edited by the existing card-text overlay path (`edit-card-text`, generalized in T2.3) with **no new text engine** (single `text.rs` shaper; T2.3 §3 text-quality gates apply automatically). The Verify line ("same editing tools used for shapes and notes") is satisfied structurally because title/body **are** shape/text cards.
- **`styleKey` comes from the template, not a `nodeType`** (D1 C3, T4.1 §2). `slide-title`/`slide-body`/`speaker-note` are new `SceneStyleToken.id`s the presentation template registers; `SceneStyleToken.id`/`RenderCard.styleKey` already accept any free string, so this needs **no schema change**. Until those tokens ship in `defaultStyles` (`renderScene.ts:206`), the cards render with the graceful `"default"` token fallback — never a broken card.

### 4. Image / artifact preview

An image preview is an `image_artifact` placement, modeled per T2.1 §1 as a `RecipeShape` whose `meta` references an existing `SceneArtifact` id (`artifactSchema`, `schema.ts:142`):

```ts
{ localId: "s2-image", frameLocalId: "slide-2", styleKey: "slide-image",
  meta: { templateKind: "presentation", semanticType: "slide-image", artifactId: "<SceneArtifact.id>" } },
```

**Image-substrate dependency (D1 C1 / T4.1 §2 caveat).** Real image *pixels* depend on the image/texture-quad primitive D1 promotes, which does not yet exist in `webgpu.rs`. Until it lands, a `slide-image` recipe element applies as a documented **captioned-box placeholder** (an ordinary `shape` card carrying the `artifactId` ref + a caption `title`), and renders pixels once the substrate ships — **no contract change needed then** (the ref is already carried). This is the same caveat T4.1 §2 records; T4.5 inherits it verbatim and adds nothing.

### 5. Connectors

Slide-to-slide flow arrows and intra-slide pointers are `edge`s — `RecipeEdge`s whose endpoints are slide frames' anchor cards or element cards:

```ts
{ localId: "flow-1-2", frameLocalId: "deck", sourceLocalId: "s1-title", targetLocalId: "s2-title",
  label: "then", styleKey: "slide-flow", meta: { semanticType: "slide-flow" } },
```

This reuses `create-edge` unchanged. `commitAppPatch`/`validateRenderPatchForShapeScene` already require both endpoints to exist (`renderPatch.ts:197`), which is why §9 orders `create-card` before `create-edge`. `styleKey` is template-chosen (`slide-flow`), not derived from `edgeType` (D1 C3; T4.1 §2 replaces the `edgeToRenderEdge` `blocks/trades_off_with→risk` coupling per-template). Connectors are optional: a flat deck with no arrows is a valid presentation, so `recipe.edges` may be empty.

### 6. Speaker-note cards

A speaker note is a `shape` card (`styleKey:"speaker-note"`) sitting outside or beside the slide frame, or a `comment_marker` anchored to the slide. Recommend a **`shape` card** as the default (it carries multi-line body text via `summary`/`detail`, is movable/editable like any note, and exports cleanly in the outline §8); a `comment_marker` is the alternative for a lighter pin (anchored via `SceneSelection` to the slide `group`, T2.1 §1). Both are existing primitives:

```ts
{ localId: "s1-notes", frameLocalId: "slide-1", title: "Speaker notes",
  summary: "What to say for slide 1…", styleKey: "speaker-note",
  meta: { templateKind: "presentation", semanticType: "speaker-note" } },
```

Modeling notes as a primitive card (not a hidden slide field) is the Locked-Decision-correct choice: notes are *visible, editable canvas objects*, not a private per-slide property. The outline export (§8) reads `meta.semanticType:"speaker-note"` to place them under each slide's notes section.

### 7. Suggested tags + prompt hints (the remaining `TemplateContract` parts)

- **`tags.suggested`** (T4.1 §5): seed a small label set through the single `Tag` registry — e.g. `{name:"draft-slide"}`, `{name:"needs-image"}`, `{name:"final"}` — created via `create-tag` only if absent, attached via the recipe's `tagLocalIds`. No presentation-private taxonomy (honors T2.4's Stop-or-ask).
- **`promptHints`** (T4.1 §6, optional, non-canonical): advisory text for an MCP client authoring a deck, e.g.
  ```ts
  promptHints: {
    systemHint: "This is a slide deck. Each child frame is a slide ordered by meta.slideIndex; " +
                "title/body are text cards, speaker-note cards hold narration, image cards reference artifacts.",
    fieldHints: { "slide-title": "One short headline.", "slide-body": "2–5 short bullets.",
                  "speaker-note": "Narration, not shown on the slide." },
    suggestedOperations: ["create", "edit text", "connect", "tag"]
  }
  ```
  These never persist onto objects and never gate rendering; the template is fully usable with `promptHints` absent.

### 8. Export outline (the one genuinely new reader — a preset, not a type)

The Deliverable's "export outline" part. **No new `exportType` is added** — the presentation template advertises *existing* `exportType`s via `TemplateExports`, and "outline" is a **reader over the produced primitives**, ordered by `meta.slideIndex`. Ground truth:

- `generateLocalExport` (`local.ts:164`) is keyed off `exportType`; `image_prompt` is a real preset (`imagePrompt()`, `local.ts:385`); `design_doc_md` currently **falls through to the MADR default branch** (`local.ts:194`, `graph.ts:46` labels it "MADR Markdown") and `ai_plan_md` runs `taskPlanSections`. None of these reads slides in order today.
- The export drawer / `export_group` MCP tool (`mcp.ts:178`, `exportGroupContent`) call `generateLocalExport` over `sceneGraphForGroup(scene, groupId)` (`graph.ts:121`).

Refining T4.1 §4's presentation row (`allowed: image_prompt, design_doc_md`):

```ts
// presentation TemplateContract.exports (T4.1 TemplateExports)
exports: { allowed: ["design_doc_md", "image_prompt"], default: "design_doc_md" }
```

| `exportType` (existing) | What it produces for a deck | Reads via |
| --- | --- | --- |
| `design_doc_md` | the **slide outline** — `# deck title`, then per slide (ordered by `meta.slideIndex`): `## {slide title}`, body bullets, and a `> Speaker notes:` block from speaker-note cards | new outline reader (below) |
| `image_prompt` | an image-generation prompt per slide image card (or a deck cover prompt), reusing `imagePrompt()` style prose | existing `imagePrompt` preset over the deck's `image_artifact` refs |

**The outline reader** is the only new code this template implies, and it is additive and primitive-reading — not a new export object or a structured slide model. It reads the deck's child slide `frame`s sorted by `meta.slideIndex`, and for each emits the slide title (`frame.title` or the `slide-title` card), body bullets (`slide-body` cards' `summary`/`detail`), and a speaker-notes block (`speaker-note` cards). Two placement options:

- **(A, recommended)** route `design_doc_md` for a presentation-tagged group through a new `presentationOutline(scene, groupId)` branch in `generateLocalExport`, selected when the group's `meta.templateKind === "presentation"`. `design_doc_md` keeps its MADR fallback for non-presentation groups, so the change is additive and back-compat (mirrors T4.1 §9 discipline). This is a *reader over primitives* — it touches `local.ts` only, adds no `exportType`, no `artifactSchema` change.
- (B) add a dedicated `presentation_outline` value to `exportTypeSchema`. Rejected for T4.5: it enlarges the canonical enum and the MCP wire surface for what is a reader specialization; (A) keeps the contract additive. Flag for revisit only if product wants outline distinct from `design_doc_md` in the picker.

The outline preset reads the **same primitive text** (`SceneNode.title`/`summary`/`detail`, `SceneGroup.title`) the slides already hold — no separate slide data store — satisfying "Templates create editable primitive groups, not opaque widgets" (P4 Verify) on the export side too. (Note: `sceneGraphForGroup`/`makeMermaid` are decision-graph readers; the outline reader reads `SceneNode`/`SceneGroup` directly by `meta.semanticType`/`slideIndex`, not the `DecisionGraph` projection — it is a sibling preset reader, not a graph consumer.)

### 9. Application + placement (the "results in normal objects" proof, inherited from T4.1 §7)

Applying the presentation template is the T4.1 §7 lowering, with the presentation recipe:

1. Allocate a deck `group-${uuid}` id; rewrite every recipe `localId` → scene-unique id (the `scopedId` pattern, `local.ts:249`).
2. Resolve `tags.suggested` → `create-tag` for new registry entries.
3. Build the op list in dependency order: `create-group` (deck, then child slides — parents before children) → `create-card` (title/body/image/note cards) → `create-edge` (connectors; endpoints now exist) → `set-object-tags` for suggested labels. `meta.templateKind:"presentation"`, `meta.semanticType`, `meta.slideIndex`, and `styleKey` ride each create payload.
4. **Layout / placement.** Per slide: title at the top, body below, notes beside — relative positions in the recipe (like `defaultSeedNodePositions`, `local.ts:16`), with `defaultShapeSize` from `RecipeLayout` (T4.1 §3). Slides tile in a row/column (deck-relative). Each slide `frame`'s `bounds` = `boundsForNodes(members)`; the whole deck translates into free space via `nextGroupOffset(db, bounds)` (`storage.ts`) so it does not overlap existing groups — exactly today's `createGroup` behavior. **No auto-layout engine** (Explicit Non-Goal): positions are fixed recipe offsets, frame bounds derived.
5. Run the op list through `applyRenderPatchToShapeScene`→`commitAppPatch` inside one T2.5 `batch` + `OperationEnvelope` (`actorType:"human"` from the picker, `"mcp"` from an agent), so the whole deck application is one logged operation whose `targetIds` are the created ids.

After step 5 the scene contains only `SceneGroup`/`SceneNode`/`SceneEdge`/`Tag` rows, byte-identical to hand-drawn ones, distinguishable solely by their ordinary `meta` values. The deck is fully editable, breakable, connectable, and exportable by the **same** ops as any object — which is the P4 Verify guarantee.

### 10. Additive delta + core-vs-shell placement

| Concern | Home |
| --- | --- |
| presentation `TemplateContract` instance (recipe/layout/exports/tags/promptHints) | **shared contract** — declared data registered against T4.1's `TemplateContract`; new file or a `templates/presentation.ts` next to `src/shared/template.ts` |
| `slide-title`/`slide-body`/`speaker-note`/`slide-image`/`slide-flow` `SceneStyleToken`s | **shared render contract** — appended to `defaultStyles` (`renderScene.ts:206`); pure tokens, free-string `id`s, no schema change |
| running the lowered ops; geometry/hull/hit/selection of produced slides | **Rust/core** — already owns scene-mutation application + hit/hull (T2.4); templates only emit ops |
| presentation outline reader (`design_doc_md` presentation branch, option A) | **server** (`local.ts` `generateLocalExport`) + `export_group` (`mcp.ts`), reusing the existing export path |
| template picker entry, export-drawer `allowed` filtering, prompt-hint surfacing, "next slide" affordance | **shell** (Svelte target; React is migration input) |

Net additive delta (no wholesale replacement, no schema break, mirroring T4.1/T2.1 discipline):

- **One declared `TemplateContract`** (`id:"presentation"`) — data, no runtime, no persistence, no renderer.
- **Five `SceneStyleToken`s** appended to `defaultStyles` — additive tokens; `SceneStyleToken.id`/`styleKey` already free strings (no schema/op/enum change).
- **One additive export reader** — a `presentationOutline` branch in `generateLocalExport` for `design_doc_md` on presentation-tagged groups; no new `exportType`, no `artifactSchema` change, MADR fallback preserved for other groups.
- **Zero** new primitive kind, op kind, `schema.ts` field, table, `ALTER TABLE`, renderer object, or editing mode. `meta.templateKind`/`semanticType`/`slideIndex`/`artifactId` ride the already-additive `meta` bag (T2.1 §4).

### 11. Scope guard — minimum presentation composition, not a PowerPoint clone

The Stop-or-ask is "the feature drifts into a full PowerPoint clone." Held in this design:

- **No presentation runtime / play mode / transitions / animations / master-slide system / theme engine / templated layouts engine.** A deck is static frames; "next slide" is at most an ephemeral camera focus (`FocusBounds`, ephemeral, no document op), not a playback mode.
- **No slide object type, no per-slide private schema.** Slides are `frame`s; title/body/notes/images are `text`/`shape`/`image_artifact` cards. All editing is the shared T2.2/T2.3 tools.
- **No auto-layout / reflow engine** (Explicit Non-Goal): fixed recipe offsets + `boundsForNodes`; the user moves things by hand.
- **No rich-text / WYSIWYG slide editor**: body text is the same multi-line `text.rs`-shaped runs as any card (T2.3), not a document editor (defers to the breakdown's deferred "full presentation editor").
- The outline export is a primitive reader, not a slide-rendering/PPTX exporter. Real image *pixels* wait on the D1 image substrate; until then, captioned-box placeholders (§4).

## Open questions / risks

- **Outline export placement (option A vs B, §8).** Recommending (A): a `presentationOutline` branch inside `generateLocalExport` for `design_doc_md` on presentation-tagged groups, keeping the canonical `exportType` enum unchanged. If product wants the outline as a distinct picker entry / MCP `type`, a dedicated `presentation_outline` `exportType` (B) is the additive alternative — a deliberate enum/wire-surface decision flagged here, not a silent default.
- **Image substrate dependency (D1 C1, §4).** Slide image cards depend on the image/texture-quad primitive that does not yet exist in `webgpu.rs`; until it lands they apply as captioned-box placeholders carrying the `artifactId` ref. The contract is shaped to render pixels once the substrate ships with no contract change. Inherited from T4.1 §2; noted so the dependency is owned, not assumed.
- **Slide-order field choice (`meta.slideIndex` vs `zIndex`).** §2 encodes order in `meta.slideIndex` and mirrors it into `RenderGroup.zIndex`. If reordering slides should be a first-class op rather than an `edit`/`set-z-index` on the frame, that is a T2.x op decision, not a T4.5 concern — flagged so reorder UX is a deliberate later call. Instances are plain frames, so any later choice does not migrate existing decks.
- **Presentation `styleKey` tokens not yet in `defaultStyles`.** `slide-title`/`slide-body`/`speaker-note`/`slide-image`/`slide-flow` are template-chosen `styleKey`s; until appended to `defaultStyles` (`renderScene.ts:206`) cards fall back to the `"default"` token. This is graceful (no broken render) but means slide cards look generic until the tokens ship — a one-time additive token PR, owned alongside this template, not a blocker.
- **Per-template `meta` validation (D1 C4, T4.1 Open question).** The presentation template may carry an optional Zod schema validating its `meta` namespace (`semanticType ∈ {deck, slide, slide-title, slide-body, slide-image, speaker-note, slide-flow}`, `slideIndex:int`) at authoring/apply time only — never gating the renderer/core. Recommended; the concrete schema is authored with the template instance, consistent with T4.1's recommendation.
