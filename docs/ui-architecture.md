# shape.ai UI architecture — Rust ui-core + extension layers

Status: LOCKED design (2026-06-14), driving an autonomous multi-phase build.
Owner decision: all UI moves off the Svelte shell into Rust; the shell becomes
pure deployment mapping. Two extension families ride on top.

This doc is grounded in a survey of the current code (renderer-core draw-data API,
the web-shell UI inventory, IME/input routing, platform-contract/host-ports). It
sets the architecture; each build phase produces its own detailed sub-design.

## 1. Vision (from the owner)

- The web shell does ONLY the four shell jobs (`platforms/CLAUDE.md`) and, after
  this work, really only **deployment mapping**: surface handle, OS-event
  forwarding, host-port impls (incl. the shared IME library), wasm load + bridge.
  No product UI in Svelte.
- A Rust **ui-core** sits on renderer-core's core draw-data types. Declarative
  widget input → fixed rendering + simple styling, plus interactive inputs
  (text input, button, slider, …) as components. Rendered THROUGH renderer-core
  (GPU), exactly like the canvas — not DOM.
- A Rust **ui** extension layer composes ui-core widgets; **built-in UIs**
  (toolbar, edit-mode/inspector, modals, context menu, presence, status/toast)
  live here.
- A **data-representation extension** family (todo-kanban, code-diagram, ADR, …).
  Unlike ui-core it has NO platform-owned core: each extension is a self-contained
  plugin bringing its own domain model and exposing two platform seams —
  ① an MCP access surface (AI authoring), ② an export-to-core-scene-types function
  so it renders on the one core canvas. Realizes the AI↔human co-authoring product
  framing. (As built, the contract dropped a per-extension UI-compose seam: an
  extension authors only its domain model + scene export, and the human edits the
  resulting objects through the built-in `ui` chrome on the core canvas — no
  extension-owned UI surface. See decision 7.)
- IME is factored into a reusable library shared by the canvas text-edit AND the
  ui-core text-input widget (the canvas already has text input).

## 2. Layering (target)

```
crates/scene-core      canonical model + the one op-apply + catalogs (commands/gestures/inspector)
crates/client-runtime  collaboration semantics
crates/renderer-core   PURE CPU draw-data types (RenderObjectScene/RenderObject) + tessellation + MSDF text + diff
crates/renderer-wgpu   GPU uploader/passes (the render seam consumer)
        │
crates/ui-core   (NEW, pure)   retained widget tree → RenderObjectScene (screen-space px) + layout + hit-test + focus
        │  depends: renderer-core (draw-data), shared affine/geometry
crates/ui        (NEW)         extension layer: composes ui-core widgets; built-in UIs (toolbar/inspector/modals/…)
        │  depends: ui-core + scene-core (catalogs, inspector_view, *_op constructors)
extensions/*     (NEW)         data-representation extensions (kanban first): model + mcp + export→scene (no ui-compose seam; see decision 7)
        │
platforms/web    thin shell: surface, OS-event→neutral input, host ports (+ shared IME lib), wasm bridge. NO product UI.
```

## 3. Key decisions (with rationale)

1. **ui-core emits at the `RenderObjectScene` tier**, not raw `SceneGeometry`.
   It builds `RenderObject`s (SVG-subset `geometry_d` in 8u/px quantized coords,
   `transform: [[f64;3];3]`, inline `RFill`/`RStroke`/`RText`, theme `RPaint::Token`)
   and feeds the SAME `build_frame_plan_with_text` → renderer-wgpu uploader the
   canvas uses. This inherits CPU tessellation, AA, MSDF text, theme-token flip,
   and the transform/color-only partial-update fast path (`geometry_revision`
   excludes transform & color) for free. ui-core is a **peer producer** of
   `RenderObjectScene`, above renderer-core; it does NOT need scene-core's
   `ObjectScene`/op-apply. (renderer-core survey confirmed RenderObjectScene is a
   plain public struct a UI layer can build by hand.)

2. **Retained / declarative widget tree** (not immediate-mode). Matches the owner's
   "선언적으로 데이터를 입력해서 고정적으로 표현" and the perf contract: the tree
   diffs to a `RenderObjectScene` each frame, then leans on `diff_plans`/`PlanPatch`
   so widget move/recolor is a partial buffer write, not a rebuild. Widget geometry
   (rect, rounded-rect, etc.) is generated by ui-core into `geometry_d` paths
   (corner radius = path nodes, since renderer-core has no radius style field).

3. **UI renders as a SECOND screen-space scene composited on top of the canvas.**
   Close renderer gap (the wgpu uploader is single-scene today): add a second
   `ObjectRenderer`-equivalent for the UI `RenderObjectScene`, drawn after the
   world scene with an IDENTITY camera (camera=(0,0,zoom=1), viewport in px) so UI
   is screen-space and does not pan/zoom. Minimal, additive; no change to the world
   path.

4. **Two-tier input dispatcher.** UI hit-test (ui-core, screen-space) runs FIRST;
   a consuming widget swallows the event, else it falls through to the canvas
   pointer path. The canvas hot path keeps its synchronous frozen-mirror gesture
   routing (`controller/gestureBindings.ts`, build-verified against the core
   catalog) — NO wasm await per pointer event. One focus arbiter replaces the
   scattered `isTypingTarget` checks: a focused text widget (canvas OR ui-core)
   owns typing; otherwise the catalog dispatcher runs. UI commands register into
   the SAME core command catalog (single binding source).

5. **IME = shell host-port library, driven by a core overlay-request.** Cores stay
   text-input-free (`platform-contract` says the OS text system owns IME). The
   ui-core text-input WIDGET (box visual, caret, edit state) is Rust and emits a
   `CoreOverlayRequest`-style "edit here, this style/value" request; the shell's
   reusable IME library mounts the OS editing surface (web: `contenteditable`/
   `<textarea>`; native: NSTextView/UITextView), owns the composition guard
   (`isComposing`), the blur-before-preventDefault hazard, and caret seeding, and
   returns ONE committed string. The canvas text-edit and the ui-core text-input
   both route through this one library. This finally wires the already-designed-
   but-unwired `webAdapterContract.beginTextEdit` / `CoreOverlayRequest` seam.

6. **Built-in UI actions route to scene-core ops.** The `ui` crate depends on
   scene-core to read the command/gesture/inspector catalogs + `inspector_view`
   and to construct ops (`inspector_edit_op`, etc.). A widget actuation produces a
   core op the shell authors — the shell never builds an op. Same "one vocabulary,
   two authors" the inspector catalog already serves (human panel + AI MCP).

7. **Data-rep extension 2-seam.** (a) MCP register — as built, the existing single
   `/mcp` transport (`server::SceneMcp`): an `ExtensionRegistry` appends each
   extension's `ext_<name>_<tool>` namespaced tools to `tools/list`, and a call
   dispatches to the extension, which authors through the SAME
   `ActorHandle::apply_op` funnel as the core write tools (no second transport, no
   second op-apply); (b) export → core scene types via scene-core authoring (domain
   model → `ObjectScene`/`RenderObject`s on the canvas). The originally-planned
   per-extension UI-compose seam was DROPPED: the as-built `Extension` trait
   (`extensions/extension-contract`) has only `mcp_tools`/`read`/`author` (seam a)
   + `export`/`empty_model` (seam b) and depends on scene-core only — never
   ui/ui-core. The human edits an extension's exported objects through the built-in
   `ui` chrome on the core canvas (selection, inspector, drag), so an
   extension-owned editing surface earned no caller; both reference extensions
   (todo-kanban, structure-diagram) ship with no UI dependency. Each extension is a Rust module/crate (in-tree first; a runtime
   WASM-component plugin system is a later option). No platform "kanban core" —
   the platform owns only ui-core, the MCP infra, and the scene types. The domain
   model is the source of truth and rides the per-extension ROOT object's
   `meta[extModel]` blob, so it flows through op-apply/sync/storage with no sidecar
   state; on each author the registry re-exports with a stable id allocator and
   reconciles to the MINIMAL op set (transform/style/text/meta property ops, no
   `EditGeometry` — geometry keys are stable), preserving the zero-rebake bar.

8. **ui-core stays a pure core**: no time/rng/threads/IO; pointer-width-agnostic;
   workspace lints; falsifiable tests. As built, no injected time port exists:
   the shipped UI is a static retained tree re-fed per frame (no caret-blink,
   easing, or animation), so a time port would be an abstraction past any present
   caller. If animation lands later it takes an INJECTED time port (renderer-core
   has none today — add one then), values computed per frame and fed in, exactly
   like the `measure`/`glyph_uv` injection seams — not before.

## 4. The render seam, concretely

`ui-core::render(tree, viewport_px, theme) -> RenderObjectScene` (screen-space).
Shell/bridge: `renderer-wgpu` gains a UI scene slot; `drawFrame` renders world
scene then UI scene (identity camera). Widget transform/style changes ride
`PlanDiff::Patches` (no re-tessellation). Hit-test: `ui-core::hit(tree, screen_pt)
-> Option<WidgetId>` consulted before canvas input.

## 5. Phase plan (each phase = one ultracode workflow; verified between)

- **P1 Foundation & render integration** — scaffold `crates/ui-core`; minimal
  retained widget tree (container/rect/text/button) → screen-space RenderObjectScene;
  add the UI second-scene render path in renderer-wgpu + wasm bridge; prove a
  Rust-defined widget renders ON TOP of the live canvas and is clickable.
  Falsifiable tests + a live on-canvas proof.
- **P2 Widget toolkit, layout, input, IME** — full primitive set (stack/flex
  layout, label, button, text-input widget, slider, toggle, segment, swatch);
  styling/theme tokens; ui-core hit-test + focus; the two-tier dispatcher; the
  shared IME library (shell) wired to the text-input via the overlay-request seam.
- **P3 `ui` extension layer + built-in UIs** — reimplement toolbar, inspector
  panel, settings modal, context menu, text-edit overlay, presence cursors,
  status/toast in Rust, driven by scene-core catalogs/inspector_view.
- **P4 Shell thinning & migration** — route the app through the Rust UI; DELETE the
  Svelte components + UI CSS; reduce the shell to deployment mapping + host ports +
  IME library; update `thin-shell-endstate` guards to forbid product UI in TS.
- **P5 Data-rep extension framework + TWO reference extensions** — investigate the
  MCP surface; define the extension contract (model + mcp + export→scene; no
  ui-compose seam — see decision 7);
  build TWO end-to-end references that exercise complementary shapes:
  (1) **todo-kanban** — list/board layout (containers + cards, reuses the Flow
  layout solver); (2) **구조도 / structure diagram** — a node-and-edge graph
  (boxes + connectors), which exercises the connector/anchor association axis and
  proves a non-layout, relational domain maps onto the core scene. Two references
  de-risk the contract against both a layout-shaped and a graph-shaped domain.
- **P6 Program review & fix + final build + live verify.**

## 6. Open items resolved during build

- Exact renderer-wgpu second-scene wiring (P1 investigates `ObjectRenderer`/
  `drawObjects`/the wasm `ShapeWebGpuRenderer` surface).
- The injected time port shape (P1/P2): resolved by omission — no animated UI
  shipped, so no time port was added (see decision 8).
- The MCP surface location + per-extension registration (P5): the single `/mcp`
  transport, `ext_<name>_<tool>` namespacing via `server::ExtensionRegistry`,
  authoring through the one `ActorHandle::apply_op` funnel (see decision 7).
- Native shells (macOS/iOS) realize the IME library + surface against
  `platform-contract` with zero core change — out of scope now, but ui-core/ui
  being pure Rust keeps them portable by construction.
